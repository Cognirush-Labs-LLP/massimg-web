# T45 — SEO surface

**Status:** complete

## What was built

Every public route now carries its own `<title>`, meta description, canonical URL, Open Graph
and Twitter card metadata, and route-appropriate JSON-LD (`WebApplication` on the tool route,
`FAQPage` on the FAQ route) — set from one mechanism (`useRouteSeo()`, mounted once in
`SiteShell.vue`) rather than per page. A build-time script generates `dist/sitemap.xml`,
`dist/robots.txt` and `dist/llms.txt` from the real built output.

## Files touched

- `src/config/site.ts` — added `siteName` constant (reused in `og:site_name` and JSON-LD `name`).
- `src/app/router.ts` — `PageRoute` gained `title`, `description` (sourced from the i18n
  catalogue) and `isFaq` (same convention as `isApp`); all three are threaded into route `meta`.
- `src/i18n/en/messages.json` / `context.json` — ten new `site.seo.<page>.title`/`.description`
  keys, one pair per page.
- `src/app/seo/buildRouteSeo.ts` (+ `.spec.ts`) — pure function building the Unhead input object
  (title/meta/link/script) from a route's data. Typed against Unhead's own `Meta`/`Link`/`Script`
  types rather than hand-rolled shapes, which matters — see Surprises.
- `src/app/seo/useRouteSeo.ts` — thin composable: reads `route.meta`, calls `useHead()`.
- `src/app/content/extractFaqEntries.ts` (+ `.spec.ts`) — parses `content/en/faq.md`'s existing
  `**Question?**\nAnswer.` paragraphs into `{question, answer}` pairs via markdown-it's token
  stream, so `FAQPage` JSON-LD is derived from the real FAQ content rather than a hand-duplicated
  second copy.
- `src/app/site/SiteShell.vue` — calls `useRouteSeo()` once.
- `src/app/site/SiteShell.spec.ts`, `src/app/App.spec.ts` — both mount components that now call
  `useHead()` internally; both needed `createHead()` from `@unhead/vue/client` added to their
  test's plugin list, or `injectHead()` throws (see Surprises).
- `src/app/router.spec.ts` — extended with `isFaq` coverage and a unit-level check that every
  route's title/description is non-empty and that no two routes share either (R-S6).
- `scripts/generate-seo-files.mjs` (new) — post-`vite-ssg build` script; writes
  `dist/sitemap.xml`, `dist/robots.txt`, `dist/llms.txt`.
- `scripts/verify-ssg-html.mjs` — extended with distinct-title/canonical checks across all routes
  and sitemap.xml/robots.txt consistency checks.
- `package.json` / `pnpm-lock.yaml` — added `@unhead/vue` (`^2.1.17`, pinned to what `vite-ssg`
  already resolves) as an explicit dependency; `build` script now runs the generator after
  `vite-ssg build`.

## Decisions made

- **Title/description strings live in the i18n catalogue (`t()`), not `content/`.** They're
  short, keyed, parameterizable strings — closer to interface chrome (R-L1–R-L5) than to the
  continuous prose `content/<locale>/<page>.md` holds (R-S4). Alternative considered: a separate
  SEO-specific content file. Rejected — would be a second, redundant string mechanism for ten
  short strings.
- **`generate-seo-files.mjs` reads `dist/*.html` rather than importing `src/app/router.ts`/
  `src/config/site.ts`.** This project has no `tsx`/`ts-node`/`vite-node` to run a TS/ESM module
  with path aliases from a plain Node script. Reading the actual build output instead guarantees
  the sitemap can never list a route that wasn't really produced — arguably a stronger guarantee
  than importing the route config would give. The base URL constant and site name are mirrored
  (duplicated, deliberately, in a one-line comment) rather than imported, for the same reason.
- **`llms.txt` is generated, not static**, by extracting each route's already-baked `<title>`/
  description out of its own `dist/*.html` — reuses the real per-route metadata instead of a
  third, separately-authored copy.
- **FAQPage JSON-LD is parsed from `content/en/faq.md`'s existing bold-question/plain-answer
  paragraph pattern**, not hand-duplicated. Alternative considered: author a separate structured
  Q&A data file. Rejected — AGENTS.md is explicit that `content/en/faq.md` is the one source of
  truth for FAQ text; a second authored copy would drift the first time someone edits the FAQ
  without remembering the JSON-LD.
- **`WebApplication`, not `SoftwareApplication`**, for the tool route's JSON-LD `@type`. R-S7
  names either; `WebApplication` is schema.org's more specific subtype for a browser-based tool.
- **Twitter card type is `summary`, not `summary_large_image`.** No image asset is referenced in
  R-S6–R-S10 or Technical Design §12.5, and adding an `og:image`/`twitter:image` was not asked
  for — inventing one (and the crop/dimensions decision that comes with it) would be adding a
  requirement, not satisfying one.
- **`sitemap.xml` carries only `<loc>`**, no `<lastmod>`/`<priority>` — R-S8 doesn't ask for them.
- **No `hreflang` alternate tags yet.** `supportedLocales` has one entry today, so there is
  nothing to alternate between; the per-route `meta` already carries everything a future
  multi-locale pass needs to add them without restructuring.

## Surprises

- **`@unhead/vue` is pulled in transitively by `vite-ssg`** (`app.use(createHead())` inside
  `ViteSSG(...)`), so no `main.ts` change was needed — only the explicit dependency pin and the
  per-route `useHead()` calls. Assumption F1 had already flagged this as T45's job.
- **`useHead()` throws without an active head context**: `injectHead()`'s exact message is
  `"useHead() was called without provide context, ensure you call it through the setup()
  function."` Any Vitest component test that mounts `SiteShell.vue` or `App.vue` (which wraps it)
  now needs `createHead()` from `@unhead/vue/client` in its `global.plugins` list, the same way
  it already needs `createPinia()`. Both existing specs that do this (`SiteShell.spec.ts`,
  `App.spec.ts`) were updated; a future component test that mounts either will need the same.
- **Unhead's own tag input types (`Meta`/`Link`/`Script` from `@unhead/vue`) must be used
  directly**, not a hand-rolled interface shape. A first draft typed `script` as a custom
  `{ type: string; innerHTML: string }[]` interface; `vue-tsc` rejected passing it to `useHead()`
  because `ResolvableScript` requires a `` data-${string} `` index signature that a named
  interface without one can't satisfy, even though no object literal actually had such a
  property. Switching the return type to Unhead's own `Meta[]`/`Link[]`/`Script[]` fixed it.
  `Script.innerHTML` is typed `InnerContentVal | undefined`, so test code reading it back needs a
  cast (see `buildRouteSeo.spec.ts`'s `scriptJson()` helper).
- **markdown-it emits a leading empty `text` token** before the first real inline token in a
  paragraph (observed via `md.parse(...)` directly) — a paragraph starting with `**bold**` has
  `children[0].type === 'text'` with empty content, not `strong_open` at index 0.
  `extractFaqEntries.ts` skips past any such empty leading text token before checking for
  `strong_open`; without that skip every entry in the real FAQ silently failed to match.
- **The FAQ extraction heuristic needed no fallback or partial-match handling** in practice:
  every one of the 45 bold-question paragraphs in `content/en/faq.md` matched cleanly
  (`grep -cE '^\*\*.+\?\*\*$'` on the source and the extracted entry count agree exactly), and the
  closing bullet list ("What's still being finished") and category intro paragraphs were
  correctly skipped as non-matches rather than misparsed.

## What the next task should know

- `useRouteSeo()` is the one place every route's SEO surface is set — a future task adding a
  sixth route only needs a `title`/`description` entry in `router.ts`'s `pages` array; no other
  file needs touching unless that route also wants its own JSON-LD type.
- T48 (Language completeness) will want to give `site.seo.*` keys real per-locale translations
  the same way every other `t()`-driven string gets one — no special-casing needed, they're
  ordinary catalogue keys.
- T52 (Build and deploy) should set `VITE_SITE_BASE_URL` for the production build; until it does,
  `generate-seo-files.mjs` and every canonical/OG/JSON-LD URL fall back to
  `https://site-base-url-not-set.invalid`, exactly as `src/config/site.ts` already documented.
- If a future task adds a non-route HTML file to `dist/` (e.g. a custom 404 page),
  `generate-seo-files.mjs`'s "every `dist/*.html` is a real route" assumption needs revisiting —
  flagged in that file's own header comment.
- `content/en/faq.md` was re-read per AGENTS.md's standing rule; this task adds no user-visible
  behaviour and changes no answer, so no edit was needed.

checked — nothing added here is hidden from a visual reader.
