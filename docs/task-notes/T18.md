# T18 — File and folder selection

**Status:** complete

## What was built

`platform/picker.ts` (plain file selection, by picker and by drop) and `platform/folder.ts` (folder
selection, by picker and by drop, with recursive traversal) now feed real `File`s into the app for
the first time. Folder input applies Functional Design §5.3's rules: hidden and system files skipped
silently (R-I27), the selected root's own relative-path convention (R-I25/R-I26), and provisional
depth and file-count caps enforced before any file is returned (R-I30). A Playwright browser test
proves both entry points produce identical file lists for the same nested tree on Chromium, Firefox
and desktop WebKit, and B5 is updated with the measured result.

## Files touched

- `src/platform/picker.ts` — `SelectedFile`, `pickFiles()`, `readDroppedFiles()`.
- `src/platform/folder.ts` — `FolderSelection`, `pickFolder()`, `readDroppedFolder()`, and the private
  traversal/filtering machinery (`isHiddenOrSystem`, `isPathHiddenOrSystem`, `walk`,

- `tests/e2e/folder.spec.ts` — browser test for both `folder.ts` functions: picker happy path, drop
  happy path, picker-vs-drop parity on the same tree, and both cap-breach paths for both functions.
- `docs/assumptions.md` — B5 updated from `OPEN 75%` to `TESTED 90%` with the measured evidence.
- `docs/task-notes/T18.md` — this handover note.

## Decisions made

- **Output shape is `SelectedFile { file: File; relativePath: string | null }`, not `ImageRecord`.**
  `ImageRecord` needs an `ImageId`, and nothing in `src/domain/types.ts` mints one — no constructor
  exists anywhere in the repo. T18 has no requirement or reason to invent one, so its output stays one
  level more primitive; `ImageRecord` construction is left to whichever task first builds it (T32/T33
  territory). `relativePath: string | null` mirrors `ImageRecord.relativePath`'s own convention
  exactly (`null` for a flat selection), so a later task can adopt this shape directly.
- **Provisional caps, local constants in `folder.ts`, not a new `src/config/` module.**
  `MAX_TRAVERSAL_DEPTH = 32` and `MAX_TRAVERSAL_FILES = 2000` — R-I30 requires *a* cap to exist now;
  Technical Design §8.3 and Functional Design §5.7 both explicitly assign the real, *measured* values
  to T50, from "one runtime configuration module" that doesn't exist yet and isn't in Technical Design
  §2's module list. Inventing that module now would be presenting a guess as settled architecture.
  Keeping the constants local and clearly commented as provisional is the smaller commitment; T50 can
  relocate them without any caller-visible change, since `FolderSelection`'s `cap` field is already
  read from the constant, not hardcoded at each call site.
- **Hidden/system filtering is case-insensitive for `Thumbs.db`/`desktop.ini`.** R-I27 names them with
  specific casing, but both are Windows-originated filenames on a case-insensitive filesystem;
  matching case-insensitively is the more defensible reading and costs nothing.
- **A dot-prefixed directory skips its entire subtree**, not just files directly inside it — checked
  once per directory entry before descending (`walk`'s `depth > 0 && isHiddenOrSystem(entry.name)`
  guard applies to directories exactly like files), rather than filtering every resulting file path
  after a full descent. Cheaper, and matches the intuitive reading of "skipped silently."
- **The selected/dropped root's own name is exempt from hidden/system filtering**, only its
  descendants are checked. The user explicitly chose that folder (or explicitly dragged that item);
  R-I27 is about surprises found *while traversing*, not about refusing a deliberately-chosen root
  named e.g. `.photos`. Applied identically in both `pickFolder()` (skip `relativePath`'s first
  segment) and `readDroppedFolder()` (`depth === 0` for every top-level dropped item, not just a
  single root — a drop can contain several top-level files/folders at once, each treated as its own
  root for this purpose).
- **Depth is `pathSegments.length - 1`** — a file directly inside the selected root is depth 1. Applied
  identically whether derived from `webkitRelativePath` (picker) or accumulated during recursive
  descent (drop), which is what makes the two paths' cap behaviour comparable.
- **On a cap breach, no files are returned at all** (`FolderSelection`'s `ok: false` variant carries no
  `files` field), matching R-I30's "before any file is added" literally. `readDroppedFolder()`'s
  traversal short-circuits via a thrown `TraversalBreach`, stopping further reads rather than reading
  the whole tree first; `pickFolder()` can't short-circuit the browser's own traversal (it already
  handed back the complete flat list before our code runs) so it checks the caps against the full
  filtered list instead — same outcome, different timing, disclosed here rather than presented as
  identical mechanisms.
- **No symlink detection is implemented (R-I32).** Checked directly against the installed
  `lib.dom.d.ts`: `FileSystemEntry` exposes `filesystem`, `fullPath`, `isDirectory`, `isFile`, `name`,
  `getParent` — no symlink flag anywhere in the API, on any engine. There is no cross-browser signal
  this code could act on. The depth cap is the only practical backstop against a symlink cycle. Not
  silently glossed over — see Surprises.
- **The drop path is tested by calling `readDroppedFolder()`/`readDroppedFiles()` directly with a
  hand-built payload, never by simulating a real OS-level drag.** See Surprises — this isn't a
  Playwright limitation specifically, it's a real web-platform constraint, so no test in this repo
  could do better without a fundamentally different (and non-existent) automation capability.
- **`pickFiles()`/`pickFolder()` each create their own transient `<input>` element**, append it to
  `document.body`, and remove it after `change` fires, rather than expecting a UI-owned persistent
  input element. This keeps `platform/` free of any Vue/UI dependency (matching Technical Design §2's
  description of `platform/` as UI-independent wrappers) and is exactly what makes them testable via
  Playwright's `page.on('filechooser', ...)`, which intercepts the native dialog regardless of what
  triggered `.click()`.

## Surprises

- **Genuine directory drag-and-drop cannot be automated in any browser, not just Playwright.**
  `DataTransferItem.webkitGetAsEntry()` returns a real `FileSystemEntry` only when the browser itself
  populated the item from an actual OS-level drag; items built via `DataTransfer.items.add(file)` or
  `DataTransferItem.getAsFile()` return `null` from `webkitGetAsEntry()` — a long-standing, documented
  Chromium behaviour, and the same is true elsewhere since no engine exposes a scriptable path from
  synthetic data to a real filesystem entry. `new DataTransfer()` additionally cannot be constructed
  in WebKit page scripts at all. None of this was mentioned anywhere in the design docs — it was found
  during this task's own research. The browser test proves the *traversal and filtering logic* (the
  part actually worth proving) by calling `readDroppedFolder()`/`readDroppedFiles()` directly with a
  structurally faithful payload instead, and cross-checks its output against the real picker path on
  an identical tree. What it cannot prove, on any engine, is that a real OS-level folder drag reaches
  our drop handler with a `DataTransfer` shaped the way we assume — that step is DOM event wiring with
  no traversal logic in it, owned by whichever later task (T31+/T33) wires a real `drop` listener to
  `dataTransfer.items`, and is a thin, low-risk seam by comparison.
- **Desktop WebKit's folder-picker behaviour matched Chromium and Firefox exactly** — same
  `webkitRelativePath` values, same surfacing of hidden dotfiles and hidden directories to script
  (nothing filters them before JavaScript sees them), same cap-breach behaviour. B5's 75%-confidence
  worry ("iOS Safari's behaviour with folders is doubtful") did not manifest on desktop WebKit. This is
  still not proof about real iOS Safari — see B5's updated "Why not higher" and T50.
- Otherwise none. `readEntries()`'s call-until-empty requirement, `setInputFiles()`'s single-directory
  support for `webkitdirectory` inputs, and `page.evaluate`'s JSON-serialization of `File` objects (see
  below) all behaved exactly as researched during planning, once accounted for.

## What the next task should know

- Import `SelectedFile`, `pickFiles`, `readDroppedFiles` from `@/platform/picker`; `FolderSelection`,
  `pickFolder`, `readDroppedFolder` from `@/platform/folder`.
- **`page.evaluate`'s return value is JSON-serialized — a `File` (or anything holding one) does not
  survive the trip back to Node.** It serializes to `{}` (its properties are prototype getters, not
  own properties), so `f.file.name` reads back as `undefined` with no error. Any future Playwright test
  touching `File`/`Blob` must map results down to a plain, serializable shape *inside* `page.evaluate`
  before returning — both new spec files here do this; it's not yet written down anywhere else in this
  repo's conventions.
- **A future task wiring the real drop UI must construct the `dataTransfer.items` → `readDroppedFiles`/
  `readDroppedFolder` call itself** — these two functions only process a `DataTransfer` handed to them;
  nothing here attaches a `drop` listener to any element, since `platform/` has no DOM structure of its
  own to attach one to. Per-item dispatch (file vs. directory, via `item.webkitGetAsEntry()?.isDirectory`)
  is that future task's job too — neither `picker.ts` nor `folder.ts` inspects a mixed drop and routes
  pieces to each other.
- `MAX_TRAVERSAL_DEPTH`/`MAX_TRAVERSAL_FILES` in `folder.ts` are provisional placeholders, not measured
  values. T50 owns the real numbers and the shared configuration module; when that lands, these two
  constants should move there rather than staying local.
- R-I29 ("a folder with no supported images is reported plainly") is **not** implemented here — it
  needs `domain/classify.ts` to know which files are supported images, and `folder.ts` only knows paths,
  not image bytes. Same split T16 already established for R-F8 (detection vs. rejection are different
  modules): folder traversal produces a file list; whichever task wires selection to classification
  decides what an all-unsupported folder means.
- If a future task needs to simulate a real OS-level file/folder drag in a browser test, don't — it has
  been confirmed unautomatable this session (see Surprises). Use the direct-function-call-with-a-mock-
  payload pattern in `tests/e2e/folder.spec.ts` instead.
