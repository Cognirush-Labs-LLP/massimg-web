# T01 — OPFS streaming and download memory behaviour

**Status:** complete

## What was built

A throwaway Playwright harness at `verification/t01-opfs-memory/` that writes a large file into
OPFS in 32 MB chunks (1 GB, then 3 GB), triggers a download of the finished file via
`URL.createObjectURL` + a synthetic anchor click, and records peak OS process memory (RSS, summed
across the browser's full process tree) during the write and during the download. It ran end to
end on Chromium, Firefox and desktop WebKit, twice, with consistent results.

**Headline finding: B4 holds on all three engines tested.** Peak memory stayed in the low hundreds
of MB (WebKit) to just over a gigabyte (Firefox, which has an unusually high flat baseline) and did
**not** grow proportionally when the file size tripled from 1 GB to 3 GB — the signature of a
streaming write/download rather than in-memory materialisation. See the table in
`docs/assumptions.md` under B4, and the raw numbers in `verification/t01-opfs-memory/results.json`.

## Measured results

Two full passes across Chromium, Firefox and WebKit, both 1 GB and 3 GB, both phases. Peak = peak
RSS summed across the browser's entire OS process tree during that phase; idle baseline = peak RSS
sampled for 1s immediately before the phase, with the harness page already loaded.

| Engine | Size | Idle baseline | Write peak | Download peak | Write time | Download time |
| --- | --- | --- | --- | --- | --- | --- |
| Chromium | 1 GB | ~256 MB | ~352 MB | ~330–333 MB | ~1.1–1.3 s | ~0.7–0.8 s |
| Chromium | 3 GB | ~296–326 MB | ~367–398 MB | ~371–399 MB | ~3.0–3.5 s | ~2.8–3.1 s |
| Firefox | 1 GB | ~1002–1004 MB | ~1071–1072 MB | ~1045–1046 MB | ~0.4 s | ~1.0–1.1 s |
| Firefox | 3 GB | ~1042–1044 MB | ~1077–1078 MB | ~1050–1078 MB | ~1.1–1.2 s | ~3.3 s |
| WebKit | 1 GB | ~109–115 MB | ~109 MB | ~109–115 MB | ~0.4–0.5 s | ~0.7 s |
| WebKit | 3 GB | ~109–115 MB | ~109 MB | ~97–109 MB | ~1.3 s | ~2.8–3.5 s |

For every run, the written OPFS file's `file.size` and the downloaded file's on-disk byte count
both matched the target exactly (1,073,741,824 and 3,221,225,472 bytes) — the low memory readings
are not an artefact of a truncated write or a cancelled/incomplete download.

Interpretation: a full in-memory materialisation of the file would show peak-minus-baseline
tracking file size directly, i.e. roughly 3 GB more at the 3 GB size than at the 1 GB size. Instead,
peak-minus-baseline stayed within a few hundred MB (Chromium), tens of MB (Firefox), or effectively
zero (WebKit) across that same 3x size change. **B4's fallback was not needed for any engine
tested.**

## Decisions made

The design docs don't specify *how* to automate "watch tab memory in the browser task manager," so
several mechanics here were my call:

- **Memory proxy: summed RSS across the browser's full OS process tree, sampled every 200ms.**
  Browsers are multi-process (renderer/GPU/network/utility processes vary by engine), and there's no
  single in-page number that's both accurate and engine-agnostic — `performance.memory` is
  Chrome-only, and the OS task manager is a manual/human action that doesn't automate. Summing RSS
  across the whole tree via `ps` is coarse (it includes GPU/network/etc. processes, not just the
  "tab"), but it's the same measurement on all three engines, it's automatable, and disk-materialised-in-RAM
  behaviour would show up as a clear proportional bump regardless of which process holds the bytes.
  Rejected alternatives: `performance.memory` (Chrome-only, doesn't answer the question for
  Firefox/WebKit); a Node memory-profiling library like `pidusage` (adds a dependency for something
  `ps` already does in three lines); CDP `Performance.getMetrics` (Chromium-only, same problem).

- **`launchPersistentContext` instead of `launch()`/`launchServer()`+`connect()`.** This substitution
  was forced by a real finding, not a preference — see Surprises: WebKit's default/ephemeral context
  has no working OPFS at all. Once using `launchPersistentContext`, there's no `Browser.process()`
  (that only exists on `BrowserServer`, returned by `launchServer()`), so the driver finds the root
  PID by matching the unique `userDataDir` temp path against `ps` command lines among the Node
  process's direct children (`memory-sampler.mjs` and `run.mjs`'s `findRootPid`). Verified this finds
  the correct top-of-tree process for all three engines (including WebKit's `pw_run.sh` wrapper,
  whose one child is the real WebKit process).

- **32 MB chunk size**, from the middle of the task's suggested 16–64 MB range. Not tuned further —
  chunk size wasn't the variable under test.

- **Headless mode**, for reproducibility and speed. Ran the WebKit debug check in both headed and
  headless to confirm the OPFS-availability finding wasn't headless-specific (it wasn't — both fail
  the same way in an ephemeral context).

- **Two full passes** (1 GB and 3 GB, all three engines, both phases) rather than one, given B4 is
  explicitly "the largest unknown in the project" — cheap to re-run and worth the reproducibility
  check. Results were consistent within a few percent between passes. Did not attempt a large N for
  statistical rigour; this is a directional/pass-fail measurement, not a precision benchmark.

- **`createObjectURL` + anchor click** for the download trigger, matching B4's claim text exactly
  (some alternatives, like `showSaveFilePicker`, are Chromium-only and are the *fallback*, not the
  thing being tested).

- **Cleanup between phases**: the OPFS file is removed (`opfsCleanup`) after each size, and the
  downloaded temp file is deleted immediately after its size is confirmed, so disk usage doesn't
  accumulate across the run (each engine otherwise would leave up to ~8 GB behind).

- **COOP/COEP response headers** on the static server, though nothing in this harness uses
  `SharedArrayBuffer` or threads. Added defensively/for parity with what a real deployment will need
  (Technical Design §9.5 / B6) in case a later reuse of this server adds worker/thread code; harmless
  here.

## Surprises

- **WebKit's default (ephemeral) browser context has no working OPFS at all.** A plain
  `browser.newContext()` (via `launch()` or `launchServer()`+`connect()`) makes
  `navigator.storage.getDirectory()` throw `UnknownError: The operation failed for an unknown
  transient reason (e.g. out of memory)` — not a quota error, a hard failure, both headed and
  headless. Chromium and Firefox both work fine in the same ephemeral-context setup. Only a real,
  disk-backed profile (`launchPersistentContext`) has working OPFS in WebKit. This isn't in
  Technical Design §9.2 or the B1–B4 entries and is worth flagging: it strongly resembles B3
  ("OPFS unavailable in private browsing") — Playwright's default WebKit context behaves, for OPFS
  purposes, like a private/incognito session. Anything that tests OPFS behaviour under WebKit via
  Playwright needs `launchPersistentContext`, not the more common `launch()` + `newContext()`
  pattern.

- **`launchServer()`+`connect()` (needed to get `Browser.process()` for the PID) breaks
  `download.path()`**, with the explicit error "Path is not available when connecting remotely. Use
  saveAs() to save a local copy." This, plus the WebKit finding above, is why the driver ended up on
  `launchPersistentContext` with PID discovery via `ps` instead.

- **Firefox's idle baseline RSS is surprisingly high** (~1 GB, vs. Chromium's ~260–330 MB and
  WebKit's ~110 MB) for a blank automation profile with one trivial page loaded. This looks like a
  fixed cost of Playwright's bundled Firefox build (labelled "Nightly" in its own binary path) under
  automation — content process + GPU process + RDD (media) process + socket process + plugin-container
  helpers — rather than anything to do with this task's file sizes, since it does not scale with file
  size at all (a few tens of MB difference between 1 GB and 3 GB). Worth knowing if a later task uses
  this same measurement approach and is surprised by Firefox's baseline.

- **All three engines supported main-thread `createWritable()`** in this environment (Chromium build
  153/Playwright chromium-1243, Firefox 155/Playwright firefox-1543, WebKit "26.6"/Playwright
  webkit-2359). The worker + `createSyncAccessHandle` fallback path (`opfs-worker.js`) was built
  because WebKit has historically been stricter about main-thread writable streams, but it was never
  actually exercised in this run — every write reported `path: "createWritable"`. Note this is a
  snapshot of *this* WebKit build; don't assume it generalises to older Safari versions without
  re-checking.

## What the next task should know

- **`launchPersistentContext`, not `launch()`, for any OPFS work under Playwright/WebKit.** This is
  probably the single most reusable fact from this task for T04+ (and for the permanent Playwright
  suite from T05 onward): the common pattern of `browser.newContext()` silently breaks OPFS on
  WebKit.
- **`memory-sampler.mjs`'s approach (sum RSS across a PID's full process tree via `ps`, sampled on an
  interval) is reusable** for any future task needing browser memory measurement under Playwright —
  most immediately relevant to T03 (WASM memory reclamation), which will also want a memory proxy,
  though T03's Technical Design also names `WebAssembly.Memory.prototype.buffer.byteLength` as an
  in-page, WASM-specific signal to use alongside/instead of this OS-level one.
  The PID-discovery trick (`findRootPid` in `run.mjs`, matching a unique `userDataDir` path against
  `ps` output) is only needed if using `launchPersistentContext`; `launchServer()`'s
  `BrowserServer.process()` is simpler when persistent-context isn't required.
- **iOS Safari is completely unverified by this task** — out of scope per T01's own scope (Playwright
  only covers Chromium/Firefox/desktop WebKit engines), deferred to T50 on real hardware. Given B2
  (iOS's OPFS quota is only ~20% of disk, vs ~60% on Chromium) and iOS Safari's known aggressive
  memory-pressure tab termination (C4, 25% confidence), iOS is the platform most likely to be where
  B4 actually fails or needs the fallback. T50 should treat this as the priority open question, not
  a formality.
- **Disk headroom**: this harness needs several GB of scratch space per full run (writes + one
  download in flight at a time, per engine); it cleans up after itself (OPFS file removed after each
  size, downloaded temp file deleted after its size is confirmed, `userDataDir` temp directories
  removed on close). If a future run is interrupted mid-phase, check
  `$TMPDIR` for leftover `t01-udd-*` directories.
- Re-run with `pnpm test` (equivalently `node run.mjs`) from `verification/t01-opfs-memory/`; browsers
  must already be installed (`pnpm exec playwright install chromium firefox webkit`, or
  `pnpm run install-browsers`). `T01_QUICK=1 pnpm test` runs a fast 64 MB/192 MB smoke pass instead
  of the full 1 GB/3 GB run, useful for validating the pipeline itself without waiting on the large
  sizes.
