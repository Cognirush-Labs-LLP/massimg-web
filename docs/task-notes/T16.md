# T16 — Input classification

**Status:** complete

## What was built

`domain/classify.ts` now sorts raw file bytes into the three buckets from Functional Design §5.1:
supported image (with its `Format` and `isAnimated` fact), image we cannot handle (with a reason),
or not an image. Detection reads magic bytes only — never a filename or extension — and correctly
distinguishes an APNG from a single-frame PNG via the `acTL` chunk (R-I4), which matters because
ImageMagick's PNG reader silently returns one frame otherwise (Technical Design §10.2, D6).

## Files touched

- `src/domain/classify.ts` — `Classification`, `UnhandledReason` types, `classify()`, and private
  per-format byte/box-walking detectors (PNG chunk walk, GIF block walk, WebP RIFF/VP8X flags,
  ISO-BMFF `ftyp` brand extraction, TIFF-family and camera-raw signatures).
- `src/domain/classify.spec.ts` — fixture builders for each binary format plus table-driven
  coverage, including a `Record<Format, () => Uint8Array>` completeness map.
- `docs/task-notes/T16.md` — this handover note.

## Decisions made

- **`classify()` does not itself reject animated AVIF.** `format.ts`'s `resolveFormat` already
  implements R-F8's rejection unconditionally (`inputFormat === 'avif' && isAnimated` → rejected,
  regardless of the chosen format setting), and T11's handover note treats "excluded at selection
  time" as future wiring, not something it owns. So `classify()` reports animated AVIF as an ordinary
  `{ class: 'supported', format: 'avif', isAnimated: true }`, exactly like any other animated format,
  detected from real `ftyp`/`avis` bytes. The actual R-F8 rejection is the *combination* of
  `classify()` + `resolveFormat()`, to be wired up by whichever task handles file/folder selection
  (T18). Rejected alternative: having `classify()` also return a rejected branch for animated AVIF —
  that would give two modules two different opinions about when AVIF is excluded, and one of them
  would eventually drift. **Do not "fix" `classify.ts` to reject animated AVIF itself.**
- **No `fileName` parameter.** R-I23's own example — "a JPEG named `.png` is processed as a JPEG" —
  means the name must have zero influence on the result. A parameter that's accepted but ignored
  invites a future edit to "helpfully" consult it. `classify(bytes)` makes the guarantee structural.
- **No `frameCount` in the return type.** `ImageRecord.frameCount` stays `null` until a decode-stage
  task populates it; `isAnimated` is the only animation fact this module owes anyone — it feeds the
  Gallery `ANIMATED` badge and `resolveFormat`'s second parameter directly.
- **`UnhandledReason` is a flat 4-member union** (`'psd' | 'ico' | 'svg' | 'camera-raw'`), not split
  per raw vendor. Functional Design §1.2 lists RAW input as a non-goal, and no document proposes
  distinct user-facing copy per vendor; `report.ts`'s `reason: string` is built by a later task from
  whatever token this returns.
- **HEIC and HEIF are distinguished by their ISO-BMFF brand family**, even though nothing downstream
  currently treats them differently (`naming.ts`'s `CANONICAL_EXTENSIONS` is keyed on
  `EncodableFormat`, which excludes both). This is a correct, low-cost implementation of the two
  `Format` enum members T09 already committed to, not new behaviour — rejected the alternative of
  collapsing both to `'heic'`, which would silently ignore a type the codebase already models.
- **NEF/ARW/DNG fall through to `{ class: 'supported', format: 'tiff' }`, not a `camera-raw`
  rejection.** These formats are themselves plain TIFF or TIFF-with-vendor-tags at the container
  level, with no cheap signature that reliably distinguishes them from real TIFF. CR2 (TIFF + `CR`
  marker at byte offset 8), CR3 (`ftyp` brand `crx `), and RW2 (`II` + version `0x55` instead of
  TIFF's `0x2A`) do have cheap, reliable signatures and are classified as `camera-raw`. A real
  NEF/ARW/DNG that ImageMagick can't actually decode becomes a `decode-failed` `FailureReason` at
  T23's decode stage — listed in the report, not silent, which is the documented non-silent fallback
  (P1/P2). This is a bounded scope decision, not a gap: FD §1.2 excludes RAW input as a non-goal, and
  the Done-when list only requires PSD and docx as bucket-2/3 proof points. ORF (Olympus) was left
  out entirely — its exact magic bytes couldn't be confirmed against a primary source during this
  task, and an unverified guess would be worse than the TIFF fallback it would otherwise get.
- **SVG detection is a text heuristic**: scan the first 4 KB (skipping a UTF-8 BOM) for the literal
  ASCII bytes `<svg`. Known, disclosed limitation: a non-SVG text file with an inline `<svg` tag in
  its first 4 KB would false-positive into bucket 2 instead of bucket 3. Accepted because it errs
  toward visibility (a wrongly-listed rejection) rather than silence, matching P1.
- **PNG chunk CRCs are never read or validated** — only chunk type presence matters for the
  `acTL`-before-`IDAT` rule, so test fixtures use a dummy 4-zero-byte CRC field.
- **Every detector declines and falls through rather than guessing** when a buffer is too short for
  its signature, and a signature that matches but runs out of data before an animation marker (a
  truncated PNG before `IDAT`/`acTL`, a cut-off GIF, a short WebP) returns the confirmed format with
  `isAnimated: false` — never a crash, never a guess toward "animated."

## Surprises

None. `acTL`-before-`IDAT` behaved exactly as D6 and Technical Design §10.2 describe once
implemented.

## What the next task should know

- Import `classify`, `Classification`, and `UnhandledReason` from `@/domain/classify`.
- **`classify()` needs the complete file bytes, not a truncated prefix, for correct GIF animation
  detection.** A GIF's second `0x2C` image descriptor can legitimately appear arbitrarily far into
  the file, after the first frame's pixel data — unlike PNG's `acTL`, WebP's `VP8X` flags byte, and
  AVIF's `ftyp` brands, which are all guaranteed near the start of a spec-compliant file. A future
  selection-wiring task must not "optimize" by reading only the first N KB before calling `classify`.
- To implement R-F8's actual selection-time rejection, call `classify()` then, for a `supported`
  result, `resolveFormat(result.format, result.isAnimated, ...)` from `@/domain/format` and act on its
  `rejected` branch — do not add rejection logic to `classify.ts` itself (see Decisions made).
- `class: 'unhandled'` is R-I2's "image we cannot handle" bucket (rejected and listed in the report,
  file name plus reason). `class: 'not-image'` is the silent, never-listed bucket, matching
  `report.ts`'s `nonImages` field, which T15 already documented as ignored.
- D6 (Assumptions Register, 90% confidence, `TESTED`) is unchanged by this task. Its stated caveat —
  "confirmed on generated APNGs, not on files from varied encoders" — is not resolved here: this
  task's synthetic fixtures validate the chunk-walk *algorithm* against the APNG spec, not real-world
  encoder conformance. Do not read T16 as evidence that raises D6's confidence.

## Requirements covered

R-I2, R-I4, R-I23. R-F8 is covered on the detection side only — `classify()` correctly reports
`{ format: 'avif', isAnimated: true }` from real bytes; the selection-time rejection itself is
explicitly left to a later task per the Decisions made above.
