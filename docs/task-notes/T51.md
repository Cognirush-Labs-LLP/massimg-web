# T51 — End-to-end suite

**Status:** complete with caveats. Every journey and route the task names is covered and passes on Chromium, Firefox and WebKit, on macOS and on Linux. The caveats: the journeys exposed a real storage race in the application (below), which is not fixed here and makes them fail intermittently until it is; and one Firefox journey is intermittently red for a reason not yet understood.

## What was built

Ten new browser specs that drive the whole product the way a person does (file chooser, buttons, the browser's own Back button, a real download read back from disk), plus a public-routes spec that runs against a production build. Together they cover every journey in the task: single image, mixed batch, folder tree, animated batch, a run with failures, cancellation, leaving without delivery, Share (available, accepted, dismissed, failed, refused), the ten-versus-eleven boundary, and FAQ, Privacy, Terms, Credits, Desktop, `sitemap.xml` and `robots.txt`.

- `tests/e2e/journeys/{single-image,mixed-batch,folder-tree,animated-batch,run-with-failures,cancellation,leave-without-delivery,share-ui,share-boundary}.spec.ts`: the journeys, 21 tests.
- `tests/e2e-site/routes.spec.ts`: 16 tests over the six pages, `sitemap.xml` and `robots.txt`.

- `package.json` (`test:e2e:site`), `.github/workflows/ci.yml` (`e2e-site` job, three engines), `CONTRIBUTING.md` and `AGENTS.md` (the new command and directories).

## Decisions made

1. **Journeys run on the dev server, routes on a production build.** `sitemap.xml`, `robots.txt` and `llms.txt` are written into `dist/` by `scripts/generate-seo-files.mjs`, so they do not exist anywhere else. Alternative rejected: moving everything to a build-and-preview config, which would have made every journey pay for a build.
2. **Share is stubbed, on every engine.** Chromium and Firefox cannot share files, and Playwright's WebKit can only on macOS (`webkit-platform.ts`). The stub replaces `navigator.canShare/share` before the page loads, so the app's own capability detection sees it. What the real browsers do is still covered by `share.spec.ts`.
3. **Animation is checked structurally** (GIF image descriptors, WebP `ANMF`, APNG `fcTL`), not by rendering, because WebKit on Linux draws animated images blank. This is why no test here needs `skipWebKitOutsideMac`.
4. **The sitemap is compared with the pages, not with a list.** Its entries must equal the `dist/*.html` set, and each must be the URL that page declares as its own canonical. A test fails if the build produces a page this file does not name.
5. **The site config blocks service workers and answers the Cloudflare beacon locally.** The production build calls `cloudflareinsights.com`; a test of our own pages must not depend on it, and Playwright cannot route requests the service worker makes. The beacon itself stays covered by `useAnalyticsBeacon.spec.ts` and `tests/e2e-pwa`.
6. **Existing specs were left alone**, including the two that each carry their own copy of the PNG builder. Alternative rejected: de-duplicating them into `support.ts`, which is churn in passing tests.
7. **`waitForRunFinished` fails with a message if the run halted.** A halt otherwise shows up as a count mismatch several assertions later (see Surprises).
8. **No `hreflang` assertion.** Only one locale exists, and no page emits `hreflang`. The task text does not name it either.

## Surprises

- **A real race in the application: a multi-image run can halt with "Storage stopped working partway through this batch".** Found on Linux Chromium: 6 of 40 runs of a plain ten-image batch halted, and 5 of 126 journey runs. The cause, from the error the halt handler swallows (`catch {}` in `useProcessingRun.ts`): `NoModificationAllowedError` from `createWritable`. In `run-archive.ts`, the first success writes the single-file download candidate (`writeOutputCopy(0)`) but its write is not awaited by the second success, which deletes that same file (`deleteOutputCopy(0)`) once ZIP delivery is certain. If the delete lands between the first write's `getFileHandle` and `createWritable`, the write fails, the whole run is discarded and the user sees the storage message. It needs two images finishing almost together, so small images and several workers make it likely. A fix that makes the second success wait for the first write (a stored promise, about four lines) took the same ten-image run from 6 in 40 failing to 0 in 80, and all journeys passed 63 of 63 on each engine. **I did not apply it to this repository**: the plan was to report a bug found by a journey, not fix it inside T51. It also explains the earlier macOS "1 succeeded of ten" run. Until it is fixed, the journeys will fail intermittently, most often on a loaded machine.
- **`Download and leave` on Firefox sometimes delivers nothing.** In `leave-without-delivery.spec.ts` the browser never reports a download, although the app believes it succeeded, shows Gallery and shows no error. Rates: about 1 in 40 on one worker, 8 in 40 with four workers in parallel. The plain Download button was 0 in 40 under the same load, and Chromium and WebKit were clean. I tested the obvious cause, that leaving deletes the run's storage while Firefox is still reading it, by delaying the teardown by 1.5 s and then 6 s; it still failed (fewer times at 1.5 s, still some at 6 s), so that is not the whole story. **Not established whether this is the application or Playwright's Firefox driver.** The assertion is deliberately kept strict rather than loosened; the wait is bounded at 15 s so the failure is quick and clear.
- **A run once ended with "1 succeeded" of ten** (Firefox, `share-boundary`, macOS). That was almost certainly the storage race above, which halts a run partway. The 12 MP cancellation test now uses 8 images instead of 12 regardless, and `waitForRunFinished` now says when a run halted and why.
- **Everything passed on the first run** for the journeys, which is why each was checked by mutation (below) rather than trusted.

## What the next task should know

- **Mutation checks, done by hand and reverted:** removing the Share file-count limit fails the two eleven-image tests; removing the leave dialog fails the three leave tests; adding a `title` to the Share payload fails the accepted-share test; removing the hidden-file filter fails the folder test; leaving Cancel on Processing fails the cancellation test; hiding the failures list fails the failure test; dropping a page from the sitemap generator fails the sitemap test.
- **Platform and what ran:** all on macOS (Darwin 25.6, Apple silicon). `pnpm check` passes (one existing `v-html` warning). Journeys: 21 tests, three engines, three repeats, 188 of 189 green; the one red was the Firefox case above. Routes: 16 tests, three engines, three repeats, all green. Full suite: **1126 passed, 18 failed, 23 skipped in 7.9 minutes** at default parallelism.
- **Time added (one worker, as CI runs it):** journeys about 20 s on Chromium, 38 s on Firefox, 31 s on WebKit; routes under 15 s per engine plus the build. I read this as acceptable; the figure to watch is CI's own, which I could not take.
- **Not run:** GitHub's own CI. Linux was run by hand as above; Done-when's "passes in CI" is open until the workflow runs.
- **The 18 failures I first reported are not stale tests.** They were `codecs.spec.ts:93`, `gallery-grid.spec.ts:209/250/267` and `preview.spec.ts:364/577` on all three engines in one full macOS run. I said they also failed alone; that was true once and is not reproducible: later the same six pass alone and together, with a cold Vite cache, and the three specs in full pass 84 of 84 on all three engines. On a clean Linux machine (Node 22, no leftover state) none of them fails on any engine. They all read counters from a module imported inside the page and got 0, which points at a local environment state on that machine at that moment, not at the tests. Nothing was removed. I did not find what that state was.
- **One Linux-only failure not in that set:** `decode.spec.ts:566` ("the fallback decode does not block the main thread") fails on WebKit on Linux every time, alone or in parallel (longest main-thread gap 313 to 423 ms against a 250 ms bound); it passes on macOS WebKit. It is a timing bound the Linux WebKit build does not meet, not something T51 touched. It needs a decision: scope it with `skipWebKitOutsideMac`, or loosen the bound.
- **Linux (Ubuntu 26.04, Node 22, `CI=1`, three workers, no retries)**: Chromium 379 passed, 9 skipped, 1 failed; Firefox 382 passed, 6 skipped, 1 failed; WebKit 368 passed, 20 skipped, 1 failed. The failures: a journey halted by the storage race (Chromium), the Firefox `Download and leave` case (it passed 3 of 3 later on Linux, so it is no more explained than before), and `decode.spec.ts:566` (WebKit). The routes passed on Chromium and Firefox; on WebKit-on-Linux they logged a module-script error during client-side navigation that does not occur on macOS WebKit and does not stop the page rendering, so that one message is now tolerated there only (see `isLinuxWebKitChunkNoise`). The runner differs from GitHub's: Ubuntu 26.04 against 24.04, and three workers against one.
- **T51-A's third bullet is still stale** (T49 noted it: Privacy and Terms are final text, not placeholders). Not edited here.
- **The sitemap currently lists `https://site-base-url-not-set.invalid`**, the placeholder T51-A replaces. The routes test compares each entry with the page's own canonical URL rather than a configured value, so it keeps passing whatever `VITE_SITE_BASE_URL` is; it will not catch the placeholder. T51-A's grep is the guard for that.
