# T17 — Capability detection

**Status:** complete

## What was built

`platform/capability.ts` now feature-detects (never user-agent sniffs) the three capabilities named
by Technical Design §10.1/§10.3/§12: OPFS availability, folder-picker availability, and
`crossOriginIsolated`. OPFS detection is a functional probe — it actually opens the origin-private
root, writes and removes a real file — rather than a presence check, because a presence check would
be wrong on WebKit: T01 found `navigator.storage.getDirectory()` can exist and still throw. A
Playwright browser test exercises all three signals on Chromium, Firefox and WebKit, including two
real private-browsing launches (Firefox private mode, WebKit's ephemeral default context) that prove
the negative case, not just the positive one.

## Files touched

- `src/platform/capability.ts` — `Capabilities`, `detectCapabilities()` (uncached), `getCapabilities()`
  (memoized module-singleton), and the three private detectors (`probeOpfs`, `detectFolderPicker`,
  `detectCrossOriginIsolated`).
- `src/platform/.gitkeep` — removed; the directory now holds real content.
- `tests/e2e/capability.spec.ts` — the browser test: standard-fixture detection on all three engines,
  a WebKit `launchPersistentContext` case proving OPFS *is* available with a real profile, a Firefox
  `firefoxUserPrefs` private-mode case proving OPFS is *not*, and a visibly-skipped Chromium case
  documenting why no private-window test exists there.
- `docs/task-notes/T17.md` — this handover note.

## Decisions made

- **OPFS probe writes and removes a real file, not just a directory handle.** `getDirectory()`
  succeeding doesn't by itself prove the origin can persist data; the extra `getFileHandle({create:
  true})` → `createWritable()` → write → `close()` → `removeEntry()` round-trip is defensive against
  an engine that hands back a handle but rejects writes under some private-mode variant B3 doesn't
  name. Cleanup is wrapped in its own `finally` with the removal error swallowed — a cleanup failure
  must never turn a working browser into a thrown exception or a false negative.
- **Fixed, dot-prefixed probe filename** (`.icompress-capability-probe`), not a per-call unique name.
  There's no concurrent-caller story yet; a fixed name is simpler, and even if cleanup were ever
  skipped, a dot-prefixed file is exactly the kind of thing T18's hidden/system-file rule already
  ignores.
- **Two-function split: `detectCapabilities()` (uncached) vs. `getCapabilities()` (memoized).** The
  OPFS probe has a real async cost and a side effect (a write), so a future app-wide caller should
  ask once per session (`getCapabilities()`), while tests need every call to re-probe independently
  (`detectCapabilities()`, used throughout the browser test). No consumer exists yet — T18/T19/T31+
  wire this in later — so the split exists to be correct for that future caller, not because anything
  today needs it.
- **Folder-picker scope is the `<input webkitdirectory>` property only**, not the separate
  drop-based `DataTransferItem.webkitGetAsEntry` path. R-I31 talks about hiding "the control," i.e.
  the picker button; drop has no visible control to gate. Left as a possible T18 addition if it turns
  out to need its own flag, not backfilled here.
- **No ambient `.d.ts` needed.** Verified directly against the installed TypeScript 5.9.3
  `lib.dom.d.ts`: `StorageManager.getDirectory`, `FileSystemDirectoryHandle.getFileHandle`/
  `.removeEntry`, `FileSystemFileHandle.createWritable`, `HTMLInputElement.webkitdirectory`, and the
  global `crossOriginIsolated` are all already typed under the current `tsconfig.app.json` lib
  (`["ES2022", "DOM", "DOM.Iterable"]`).
- **The browser test calls the module via a parameterized dynamic `import()` inside
  `page.evaluate`, against the Vite dev server** (`import(/* @vite-ignore */ path)` with `path` as a
  function parameter, not a string literal), rather than statically importing it or adding a UI
  harness page. `tests/e2e/**` is type-checked by `tsconfig.node.json` (`lib: ["ES2022"]`, no DOM,
  not project-referenced to `tsconfig.app.json`), so a static import would fail `vue-tsc -b`
  (composite-project membership error), and the test file can't reference `document`/`navigator`
  itself either. Passing the path as a parameter rather than a literal is also required: `tsc --strict`
  only attempts (and fails) static resolution of `import()` when given an analyzable string literal.
  `Capabilities` is duplicated locally as a 3-field interface with a comment explaining why, rather
  than adding a tsconfig project-reference edge for a shape this small and stable.
- **`{}` empty-destructuring on three test callbacks, with a targeted `eslint-disable-next-line
  no-empty-pattern`.** Confirmed by running the suite: Playwright's runtime rejects a plain named
  first parameter ("First argument must use the object destructuring pattern") when a test needs
  `testInfo` but no fixtures — the literal `{}` is mandatory, not a style choice, so the lint rule is
  suppressed rather than worked around.

## Surprises

None. The Firefox real-private-mode launch (`firefoxUserPrefs: {'browser.privatebrowsing.autostart':
true}`) came back `opfs: false` exactly as B3 predicts — a genuine confirmation of B3 on a real
private-browsing launch (not just T01's WebKit ephemeral-context proxy), though B3 was already at
90% DOC confidence and this doesn't change its status. WebKit's standard Playwright fixture behaved
exactly as T01 described (no working OPFS); the `launchPersistentContext` workaround from T01 was
reused as-is and worked first try.

## What the next task should know

- Import `Capabilities`, `detectCapabilities` and `getCapabilities` from `@/platform/capability`.
- `getCapabilities()` is the one to use from app code once there's a consumer (T18 for
  `folderPicker`, T19 for `opfs`, T31+ for wiring into the UI/R-I31). It's a module-singleton cache —
  calling it twice in one page session returns the same resolved promise without re-running the OPFS
  probe. If a caller ever genuinely needs to re-probe mid-session, call `detectCapabilities()`
  directly instead of trying to invalidate the cache.
- **Any future Playwright test that needs *working* OPFS on WebKit must use
  `webkit.launchPersistentContext(userDataDir, {})`, not the standard `{ page }` fixture.** The
  standard fixture's default ephemeral context has no working OPFS at all (T01's finding, reconfirmed
  here) — this is now the second task to hit this, so treat it as a settled fact about
  Playwright+WebKit in this repo, not a one-off. `tests/e2e/capability.spec.ts` has a working,
  copy-pasteable example of the launch/cleanup pattern (scratch `userDataDir` via `mkdtemp`, `rm` in
  `finally`).
- `crossOriginIsolated` reads `false` in every environment tested here, correctly — no COOP/COEP
  headers exist until T48. Re-verify this test's expectation once T48 deploys those headers, or the
  assertion will need updating (not because detection is wrong, but because the environment will
  have changed).
- Chromium has no private-mode assertion and, per the "where the runner supports it" wording in
  T17's own done-when clause, isn't expected to. If a future Playwright version adds a supported way
  to launch real Chrome Incognito, that test currently just documents why it's skipped — it isn't a
  placeholder that needs filling in as a matter of course.
