# T28 — GIF path

**Status:** complete. One recommendation is left open for the user, and it is a requirement
correction rather than a gap in the work: **R-I13 says GIF cannot carry an ICC profile, and in this
build it can.** See "What the user still has to decide".

## Headline findings for later tasks

- **`gifsicle-wasm-browser` cannot run inside a Worker without help, and it fails by *hanging*.**
  Its argument type-check begins `A instanceof Element`, `Element` does not exist in a Worker, and
  the resulting `ReferenceError` is thrown inside `new Promise(async (resolve, reject) => …)` —
  where a throw in the async executor rejects the executor, not the promise. So `run()` never
  settles, the job never completes and never fails, and the worker sits there. Measured on Chromium,
  Firefox **and** WebKit alike. `ensureGifsicle` now defines a stub `Element` class where the name is
  absent. **The lesson is about testing, not about gifsicle:** every other test drove the stage from
  the page, where `Element` exists, and all 120 of them passed while the shipped pipeline hung. A new
  codec is not proven until a job has gone through `pipeline/worker.ts`.
- **gifsicle fails about one run in five on WebKit, for reasons that have nothing to do with the
  file.** Its wrapper resolves a run when the WASM module calls its `output` callback and rejects —
  with `undefined` — when the module's own promise settles first; nothing orders those two. Measured
  on `anim-16f-400.webp` at slider 95, 250 attempts per engine: **Chromium 0, Firefox 0, WebKit 44
  (17.6%)**, and 18 of 80 (22.5%) in a second run. Nine other subjects failed zero times anywhere.
  The path now asks up to four times and, if it still has nothing, keeps ImageMagick's own GIF
  rather than failing the image. **After the fix, 80 runs per engine: no job failed anywhere**;
  WebKit retried 14 times and fell all the way back once. Without this, roughly one Safari GIF job in
  five would have failed outright — and every test in `gif.spec.ts` passed while that was true,
  because a 22.5% rate on *one* input is invisible unless you run it two hundred times.
- **A7 `DOC 95%` → `TESTED 100%`.** R-Q8's "substantially smaller" holds — 69% to 83% on animations
  whose frames share content — but it holds *for one reason only*, and the reason bounds it. `-O2`
  replaces what a frame shares with its predecessor with transparency, so the saving tracks
  inter-frame redundancy and nothing else. On content where every pixel changes every frame it is
  0.0%, and on a **still photograph gifsicle's output is larger than its input**. The stage keeps
  whichever candidate is smaller; that is not defensive programming, it is a case that occurs.
- **ImageMagick's GIF writer speaks *total plays*, and converts correctly.** `animationIterations`
  = 4 writes a NETSCAPE2.0 block holding 3; = 0 writes 0; and **= 1 writes no block at all**, which
  is exactly right for a GIF that plays once. So `Animation.loops` is assigned to it unchanged, and
  `gifTotalPlays` is used only to read the result back. This is the reverse of the *reader*, which
  T29 found untrustworthy for the same field.
- **A GIF can carry an ICC profile in this build.** ImageMagick writes one into an `ICCRGBG1012`
  application extension, gifsicle preserves it through `-O2 --lossy`, and it comes back byte-
  identical — measured here on an animated file, and by D3 in T23 on a still one. R-I13's premise
  ("when the output format cannot carry a profile (GIF)") is therefore false, and following it would
  mean converting pixels nobody asked to have converted (R-I15).
- **§7.3's gifsicle rationale was wrong in its reasoning, right in its conclusion.** `-O3` is not
  "every option for no gain": it is byte-identical to `-O2` on eight of ten subjects and **smaller
  on two**, by 2.8% and 3.7% — the larger of those for 1.9x the time, and it costs time on the eight
  where it returns nothing. Both the row and the reasoning are now measured.
- **A still photograph as a GIF is about 10 MB** (4000x6000, palette, no lossy pass) and takes about
  1.2 s per gifsicle pass. T30 and T46 both need to know that.

## Decisions made

- **The `--lossy` band is 20 to 200, and the scale between them multiplies rather than adds.**
  §7.4 said only "derived from quality", so the derivation is this task's, and every part of it is
  measured — see `gifLossyLevel` and §7.4. The short version: below 20 the option makes files
  *bigger*; size falls logarithmically with the level, so a linear map would leave most of the
  slider inert; and the top is gifsicle's own maximum because slider 10 means "smallest", as it does
  for JPEG. **This is the part of T28 a reviewer should challenge first.** It rests on ten subjects,
  two of them real photographs, and the mean channel error at every level is in `results.json` so
  the argument can be had from data.
- **Keep the smaller of ImageMagick's file and gifsicle's.** gifsicle enlarged the still photograph
  by 1,090 bytes, so this is a measured case rather than a hypothetical one.
- **Retry gifsicle, then fall back to ImageMagick's GIF rather than failing the image.** The failure
  rate above forced the first half; the second half is a judgement. Failing would make a transient
  library race cost the user a whole image, and we are holding a valid GIF at that moment. It does
  mean a rare job silently ships a much larger file — about one in eighty on WebKit — so
  `gif.spec.ts` asserts that the scene fixture's output *is* gifsicle's, which is what would fail
  loudly if the optimiser ever broke permanently rather than transiently. No caveat is recorded,
  because adding one is a requirement change and R-X46's list is the user's.
- **Do not compare against a third candidate** (gifsicle with no lossy pass). Measured cost: 1.9% on
  one subject of ten, at slider 95 only. Measured price of fixing it: a whole extra gifsicle run on
  every lossy job, up to 1.2 s on a large still.
- **A non-zero delay never rounds to zero.** GIF stores centiseconds, so a 1 ms frame has to become
  either 0 or 1 cs. 0 does not mean "no delay" in GIF — it means the file declines to specify one,
  and viewers substitute something like 100 ms — so a naive `Math.round` would play that frame a
  hundred times too slowly rather than ten. A delay that is *already* zero stays zero, so a GIF read
  and written back is unchanged.
- **Delays are handed to ImageMagick in centiseconds, not milliseconds.** Both produced a file of
  the same length holding the same delays, because the writer converts either way. The difference is who rounds: at
  1000 ticks it is ImageMagick, silently, by a rule nothing has tested; at 100 it is
  `gifDelayCentiseconds`, which is tested, and which the encoder then checks the written file
  against. T29's rule, applied to the one field where this path had a choice.
- **No `--loopcount` and no `-d` on the gifsicle command line.** Both values are already in the file
  ImageMagick wrote and gifsicle preserves both; a second opinion would be a second place to be
  wrong.
- **GIF joins `ColourFormat`.** `colourPlan(colour, 'gif')` gives an `icc` frame its profile and an
  untagged one nothing, exactly as every other format. A non-sRGB CICP source going to GIF is
  refused as `unimplemented`, which is the same deferred follow-up JPEG, WebP and PNG already have.

## Surprises

- **The hang described above.** Worth restating as a class: a library that swallows its own errors
  into a never-settled promise cannot be diagnosed from the outside at all. What found it was
  attaching a `pageerror` listener, which took thirty seconds; what would have hidden it for a long
  time is that every stage-level test passed.
- **ImageMagick's GIF writer is very bad at animation, and that is the whole of R-Q8's case.** It
  wrote 93,634 bytes where the ffmpeg-produced source was 15,782 and gifsicle's output was 15,533.
  A GIF "converted" without gifsicle would routinely be **six times larger** than the file the user
  started with.
- **Every animated fixture in the repository was the worst possible case for this task.** All of
  them are flat colour per frame, which is precisely the content `-O2` and `--lossy` can do nothing
  with. Measured on those alone, gifsicle looks worth 9.7% and `--lossy` looks like it does nothing
  at all — a conclusion that would have been wrong by a factor of eight. `anim-scene.gif` exists
  because of this, and the generated subjects in the harness exist because even a committed GIF
  fixture has already been optimised by whoever wrote it.
- **GIF to GIF is visually lossless through this path.** The only pixels that differ after a full
  round trip are the RGB values *underneath* fully transparent pixels; alpha is exact everywhere and
  every visible pixel is exact. Nothing in the pipeline promised this and it is pleasant that it is
  true.
- **gifsicle writes `GIF87a` for a file that needs no 1989 extensions**, which a still GIF does not.
  Both signatures are valid; a test that hardcodes `GIF89a` will fail on the still path.

## What the user still has to decide

**R-I13 is wrong for this build, and it is a requirement, so the correction is not mine to make.**

> R-I13 When the output format cannot carry a profile (GIF), the image is converted to sRGB using
> the embedded profile before encoding, so the colours remain correct.

GIF carries one. The path therefore treats GIF like every other format — preserve the profile, never
convert the pixels (R-I12, R-I15) — and `ColourFormat` in `encode-plan.ts` records why in the code.
The suggested correction is to move GIF from R-I13 into R-I12's list and delete R-I13, or to keep
R-I13 as a contingency for a format that genuinely cannot carry a profile.

Two things worth weighing before deciding:

- **Most viewers ignore a GIF's ICC profile.** Preserving it is right by R-I15 (the pixels are not
  altered) but it will not make a Display P3 animation *look* right in a browser. Converting would,
  at the cost of altering pixels — and this build has no sRGB profile to convert *to*: `magick-wasm`
  exposes no built-in one, so honouring R-I13 literally would mean shipping or authoring an ICC
  profile first.
- **The profile is not free.** The Display P3 profile is 6,668 bytes, which was 33x the size of the
  201-byte GIF it was attached to in one measurement. On a small tagged GIF the colour information
  can outweigh the image.

## What the next task should know

**T30, size targeting**, inherits a usable axis and one trap:

- `--lossy` gives a smooth, monotone size curve on detailed content — 328,211 B at 20 through
  197,629 at 100 to 165,540 at 200 on one subject — so a binary search over the level will converge.
- **But on flat content the axis is completely inert**: every level from 1 to 200 returns the
  identical 1,043 bytes on `anim-6f.gif`, 362 on `anim-disposal.gif` and 22,105 on
  `anim-16f-400.webp`. This is the same shape of problem §7.4 records for PNG's `minimum`, and a
  search that does not detect an unresponsive axis will spend all eight iterations learning nothing.
- Each iteration is one gifsicle run: 20–40 ms on a small animation, **1.2 s** on a 4000x6000 still.
  Eight iterations on a large still is ten seconds of wall time for one image — and on WebKit some of
  those runs will fail and be retried, so budget about 1.25x that.
- Dimension is the other axis and it is not gifsicle's: the frames are resized before the GIF is
  written.

**T46, limits**: a still photograph as a GIF is ~10 MB at 24 megapixels, and gifsicle's Worker
memory for a file that size is unmeasured.

## What could not be proven

- **The lossy band's ends rest on ten subjects**, of which two are real photographs and four are
  generated here. Both ends are judgement calls informed by measurement, not measurements in
  themselves.
- **No perceptual metric.** The error figures in `results.json` are mean and worst absolute channel
  error against the source, which is not SSIM and is not an eye. "Slider 10 should reach 200" is a
  claim about what a slider means, argued from a size curve.
- **Why gifsicle's race is so much worse on WebKit** than on the other two. The mechanism is
  visible in the wrapper's source and the rates are measured, but what makes WebKit lose the race
  four times out of five more often is not established. Nor is whether the rate depends on the
  input's size, its frame count, or only on timing: one subject of ten failed, which is suggestive
  and not conclusive.
- **Whether four attempts is the right number.** Independence predicts a 0.4% fallback rate; the
  measurement gave 1.25%, so the attempts are somewhat correlated and the arithmetic overstates what
  a fifth attempt would buy. Not measured at any other cap.
- **The `Element` stub's blast radius is reasoned, not measured.** It defines a global in the worker
  scope where the name is absent. Nothing else loaded there feature-detects `Element` — checked by
  reading, not by test — but a future codec that decides it is in a document because
  `typeof Element !== 'undefined'` would be misled.
- **gifsicle's own memory** per run. It builds a Worker, instantiates its WASM, and terminates on
  completion, so nothing accumulates between jobs; the peak during one run is unknown.
- **Only `--lossy` and `-O` are exercised.** A7 lists `--resize`, `--crop` and `--rotate` as
  available; this pipeline does all three in RGBA before the GIF exists, so they are recorded as
  present and left unused.
