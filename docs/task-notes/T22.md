## Headline numbers for later tasks

- **C8 closed `OPEN 60%` → `TESTED 80%`.** One worker loading every §5.2 module it might need stays
  within **116–152 MB** of idle baseline on desktop across Chromium, Firefox and WebKit — nowhere near
  a level that forces the heterogeneous-pool contingency. **Not measured: up to three pipeline workers
  (§5.1's desktop cap) loading codecs concurrently**, which could plausibly run 2–3× that figure.
  Whoever tunes worker-pool memory behaviour (T50, or a dedicated follow-up) should measure that case

- **ImageMagick's re-initialisation cost, for T21's watchdog (`config/limits.ts`'s `jobTimeoutMs`,

  **Firefox ~230 ms**, all measured via a real `initializeImageMagick()` call in

  — §5.3 says the watchdog threshold is set from measured re-init cost, but a sensible timeout also
  needs to know how long a real job might legitimately run (AVIF at default speed measured 29 s in
  D1's numbers), which is outside this measurement. Not setting `jobTimeoutMs` myself; leaving the
  number here for whoever does.
- **A real bug in `verification/t20-thumbnails/memory-sampler.mjs`'s technique, found and fixed here

  macOS and invisible to a pure ppid-tree walk from the launched browser's PID.** Before the fix,
  WebKit's measured peak was indistinguishable from idle (+0–1 MB) for every scenario in this harness.

  to the walk, against 104 MB actually counted. **C5's own entry (`docs/assumptions.md`) is now
  caveated in place**: every WebKit RSS figure it reports — the `0` in its "0–737 MB above an idle
  baseline" line and the "unchanged at 109" figure in "Cancellation works" — came from this same
  un-fixed sampler and is flagged there as unreliable pending re-measurement. C5's 85% confidence is
  **not** lowered: its cancellation conclusion rests on "zero further completions afterwards," a
  completion count independent of RSS, which holds on all three engines including WebKit. Not
  re-measured — C5 is not this task's assumption to re-open. See Surprises and
  `docs/assumptions.md`'s C5 entry.
- **Package choices for §7.1's remaining unnamed slots**: `gifsicle-wasm-browser` (gifsicle),
  `@jsquash/oxipng` (oxipng), `imagequant` (the libimagequant quantizer — **GPL v3**, matching §7.2's

## What was built

`pipeline/codecs/loader.ts` and `pipeline/codecs/routing.ts` — lazy, memoised loaders for all six
§5.2 modules, plus the pure per-format routing rule between them. `pipeline/execute.ts` now calls

should, on all three engines with no skips. `verification/t22-codecs/` measured real production bundle
sizes and live peak memory for eager vs. lazy vs. jpeg-only loading, closing **C8**.

## Decisions made

- **Package choices, verified against §7.1/§7.2 rather than picked from memory.** For each: checked
  `npm view` for the real published version, license and size against the design doc's table, and for
  the one genuine judgement call — the "quantizer" (technical-design.md names only "libimagequant," not
  an npm package) — chose `imagequant` (0.1.2, license literally `GPL v3`) over the newer
  `libimagequant-wasm` (0.3.0). **Rejected `libimagequant-wasm`**: its `MIT` licence field covers only
  its own binding layer, while the libimagequant code it bundles and statically links stays
  GPL-3.0-or-later regardless of what wraps it — the field understates the actual obligation.
  `imagequant` declares `GPL v3` and ships libimagequant's real `COPYING` file, which is the honest
  label for what is actually shipped, and that `COPYING` is byte-identical to
  `3rd_party_licenses/libimagequant/COPYING` (T06's). §7.2's GPLv3/AGPLv3 compatibility analysis is
  correct on its own terms either way — GPLv3 §13 expressly permits combining with an AGPLv3 work —
  the point in favour of `imagequant` is accurate labelling of the bundled licence, not preserving a
  paragraph that would need to change regardless of which package is chosen (the doc is living,
  AGENTS.md).
- **Build-risk checked before adopting, not assumed.** `imagequant`'s JS glue does a bare
  `import * as wasm from './foo_bg.wasm'` (wasm-bindgen's "bundler" target), a known historical
  bundler pain point. Verified empirically with a scratch Vite production build before committing to
  it: Vite 8.3 (this project's version) handles it natively, emitting a real `fetch`/
  `instantiateStreaming` chunk, not an inlined blob. Scratch files removed after the check; nothing
  was left under `src/`.
- **All six licence directories T06 already created (`imagemagick`, `gifsicle`, `oxipng`,
  `libimagequant`, `upng-js`, `apng-optimizer`) hold real upstream licence text for the underlying
  component — but two of the six npm *wrapper* packages T22 actually installs carry their own,
  separate notice that T06's component-level directories did not anticipate, and my first pass here
  wrongly reported the check as clean without checking for that.** `check-licenses.mjs`'s manifest is
  component-level by §7.2's design (a hardcoded list of the statically-linked components named in its
  attribution table, not a `node_modules` walk) and passes regardless, since it only checks presence of
  the files it already expects — it cannot flag a wrapper notice it was never told to look for. Two
  wrapper packages ship real notices of their own, separate from the underlying component's licence
  T06 already captured: `@jsquash/oxipng` 2.3.0 declares **Apache-2.0** with its own LICENSE (separate
  from `3rd_party_licenses/oxipng/LICENSE`, which is oxipng-the-Rust-tool's own MIT text), and
  `gifsicle-wasm-browser` 1.5.19 carries an MIT notice (2021 renzhezhilu) separate from
  `3rd_party_licenses/gifsicle/`'s GPLv2 Gifsicle-the-C-tool text. Both are AGPL-compatible either way
  and there was never a compliance blocker, but Apache-2.0 §4 and MIT both require notice retention,
  and T22 is the task that turned these two from planned to actually bundled — so I added
  `3rd_party_licenses/oxipng/LICENSE-jsquash-wrapper` and
  `3rd_party_licenses/gifsicle/LICENSE-gifsicle-wasm-browser`, copied verbatim from the installed
  packages, rather than only noting the gap. `check-licenses.mjs` still passes (it does not need to
  know about these extra files to keep doing so).
- **`codecsForSettings` (the pure routing rule) lives in its own module, `routing.ts`, separate from
  `loader.ts` (the actual loading, which touches all six packages).** Discovered why while writing
  `routing.spec.ts`: Vitest statically resolves every import a test's module graph touches, including
  the dynamic `import()` specifiers inside `loader.ts`, and `imagequant`'s bare `.wasm` import — which
  resolves correctly under Vite's real *client* build/dev-server target (see the build-risk check
  above) — fails to resolve under Vitest's Node-targeted transform. This is the same shape as
  `platform/thumbnail-render.ts` vs `platform/thumbnail-worker.ts`: pure logic kept unit-testable by
  keeping it out of the module that does the browser-only side effect.
- **§5.2's "oxipng, quantizer | First job resolves to PNG output" row is read as *still* PNG only —
  `routing.ts`'s branch is exclusive, animated PNG gets UPNG/apng-optimizer and never oxipng/quantizer.**
  §5.2's own wording doesn't say "still," but §4.2's stage-dispatch table does the deciding: PNG still
  is `decode, orient, edit, resize, quantize, optimise, compare against lossless`, while PNG animated is
  `decode-frames, edit-frames, resize-frames, assemble-apng, optimise-apng` — no quantize/optimise step
  at all for the animated path. §4.2 is named as this task's authority for stage shape, so the narrower
  reading governs. **T27 (whichever task builds PNG-still and animated-PNG encoding) should treat this
  as settled, not re-derive it** — an animated PNG job that also loaded oxipng/quantizer would be
  loading a module its own stage list never calls.
- **`ensureCodecsForJob` is wired into `execute.ts`, not left for T23-T29 to add.** T21's note
  explicitly names `execute.ts` as what T22 starts modifying ("T22 (codec loading) owns `execute.ts`'s
  body along with T23–T29"), and the Done-when clause itself requires a real job dispatched through the
  real pool to trigger the right codec load — which needs *something* inside `execute.ts` to call the
  loader, since the worker is where §5.2's per-job loads actually happen. The call happens *before* the
  `unimplemented` throw and doesn't change what the throw reports — `pool.spec.ts`'s two assertions
  that expect `unimplemented`/`error` (flagged by T21 as "expected to fail until [full stage dispatch
  lands]") are untouched and still pass, because I am not building stage dispatch, only the codec load
  that has to happen before it.
- **`ensureCodecsForJob` always includes ImageMagick, for every format.** §5.2's table lists
  ImageMagick's *load trigger* as "first image added, or idle after first paint" — a main-thread event
  — not "first job," but that only describes when the *preload* is scheduled, not a guarantee that
  every worker will already have it by the time a job arrives. §5.2's own next sentence — "a worker
  that needs a module it has not loaded loads it and then proceeds" — is the fallback this
  implements: nearly every stage in §4.2's table uses ImageMagick for decode/orient/edit/resize, so a
  cold worker's first job always needs it regardless of output format. Verified directly: a JPEG job
  dispatched to a fresh worker with zero prior page activity still triggers an ImageMagick load
  (`tests/e2e/codecs.spec.ts`, "a JPEG job still loads ImageMagick... even before the idle preload
  fires").
- **`notifyImageAdded()` is exported and left unwired.** There is no Gallery yet (T30+) to call it
  from — the same seam shape T20 left for `fallbackDecoder`. `scheduleImageMagickPreload()`, by
  contrast, *is* wired into `main.ts` for real: it needs no UI to exist, it is exactly §12.1's
  documented "idle after first paint" behaviour, and leaving it unwired would have made the "first
  paint is not blocked, and the load does eventually happen" Done-when clause provable only against a
  synthetic harness rather than the real app.
- **T20's `fallbackDecoder` seam in `platform/thumbnails.ts` is *not* wired here.** T20's note asks
  "T22/T23" to wire it, and named it a seam specifically because "wiring a 14.8 MB WASM decision into a
  platform module ... would pre-empt" whichever task owns the lazy-load strategy (T22) *and* whichever
  task owns real decode logic (T23, "Decode, orientation and colour"). T22 now supplies the loading
  half (`ensureImageMagick()`), but `fallbackDecoder`'s actual body needs a real ImageMagick-backed
  *decode* function returning pixels in the shape `thumbnails.ts` expects — that is decode logic, T23's
  subject, not loading. Wiring it here would be inventing a decode implementation the design doc
  assigns elsewhere. **T23 should treat this as open, not assume T22 closed it.**
- **The memory harness measures three scenarios (eager / lazy-sequential / jpeg-only), not the two
  C8's Method line names (all-three-eager / lazy).** The "lazy" scenario as literally specified — one
  session touching every format in sequence — converges with "eager" in peak memory almost trivially
  (both end up with everything loaded), which does not answer the actual question of what laziness
  saves a typical user. Added "jpeg-only" (the common case) to give C8 a number worth reporting rather
  than a null result. Recorded as a deliberate expansion of the Method's letter to serve its spirit,
  not a substitute for it — the two named scenarios are both still measured and reported.
- **`verification/t22-codecs/` is a fully standalone pnpm project (own copies of all six codec
  packages)** rather than reaching into the root project's `node_modules` or `src/` — matches T20's
  convention, and was also the pragmatic fix for a real build error: a probe file outside any project
  with a `node_modules` ancestor cannot resolve bare package specifiers at all (`vite build` fails
  outright), which is why the harness's probe/scratch files live inside the project rather than the OS
  temp directory.

## Surprises

- **A real, previously-unnoticed bug in T20's `memory-sampler.mjs` technique.** WebKit's WebContent,
  GPU and Networking processes — the ones that actually run page JS and hold the WASM heap — are
  reparented to PID 1 on macOS rather than staying children of the launched browser process. A pure
  ppid-tree walk from the found root PID therefore never sees them. Confirmed directly with
  `ps -A -o pid=,ppid=,command=` during a live launch: `com.apple.WebKit.WebContent.xpc` carried
  100+ MB RSS with `ppid=1`, while only the `Playwright`/`pw_run.sh` wrapper processes carried the real
  parent chain the sampler was walking. Before the fix, every WebKit scenario in this harness measured
  a peak indistinguishable from idle (+0–1 MB) — which would have read as "WebKit uses no memory for
  this," precisely wrong. Fixed here (this project's own `memory-sampler.mjs` only) by unioning the
  ppid-tree walk with every orphaned (`ppid=1`) process sharing the same
  `ms-playwright/<engine>-<build>/` install directory as the root — safe for Chromium/Firefox too,
  since their children are already reachable via ppid and this only ever adds processes (deduped by
  PID), never double-counts. **Not fixed in `verification/t20-thumbnails/memory-sampler.mjs` itself —
  out of this task's scope — but C5's own entry in `docs/assumptions.md` is caveated in place**: its
  WebKit RSS figures are flagged as produced by the un-fixed sampler and unreliable pending
  re-measurement, while its 85% confidence stands unchanged on the completion-count evidence that
  doesn't depend on RSS at all.
- **Comparing "eager" against "lazy" in the same browser profile silently invalidated the first
  measurement pass.** Running both scenarios in one `launchPersistentContext` meant Vite dev server's
  cacheable responses (ETag/304) let "lazy" — which ran second — pay almost nothing (1 MB peak, 3 MB
  transferred vs. eager's 18 MB), because "eager" had already warmed the HTTP cache. Fixed by giving
  every scenario its own fresh profile. A pattern worth remembering generally: comparing "before" and
  "after" cache states needs either a fresh profile per state or an explicit cache-defeat, not just
  running them in sequence.
- **`gifsicle-wasm-browser` and `upng-js` emit no separate `.wasm` asset in a production build** —
  gifsicle bundles its own worker source (WASM included) as a JS string; UPNG is pure JS. Both show up
  as ordinary JS chunk weight rather than a `.wasm` file, which is why the bundle table in C8 has no
  separate gifsicle/UPNG row (`otherChunkBytes` in `build-sizes.mjs`'s output covers them).
- **`gifsicle-wasm-browser` has no exposed init step separate from `.run()`.** "Loaded," for this
  module, means its dynamic `import()` has resolved — the code-split chunk fetched — not that its WASM
  is instantiated; that only happens when the real GIF encode stage (T26) calls `.run()` with actual
  GIF bytes. Documented in `loader.ts`'s doc comment so T26 doesn't assume `ensureGifsicle()` already
  paid that cost.
- **`initializeImageMagick()` accepts a `URL` directly and fetches it itself** — no manual `fetch()` +
  `ArrayBuffer` step was needed, unlike `verification/t20-thumbnails/magick.mjs`'s Node-side
  `readFile()` call (Node has no equivalent convenience).
- Otherwise, no engine divergence: all three engines passed every `codecs.spec.ts` assertion
  identically, no WebKit-specific branching needed for anything in `loader.ts` itself (the WebKit
  surprise above is in the *measurement harness*, not the shipped code).
