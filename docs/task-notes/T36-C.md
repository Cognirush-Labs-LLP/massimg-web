# T36-C — Durable local sources and the Preview entry tab

**Status:** complete with caveats

## What was built

Accepted images now have independent temporary IndexedDB source copies, created from the first
successful classification read. Preview, Edit, compression, thumbnails, and dimension probes read
those copies lazily; removing an image, clearing the batch, or cleaning an abandoned session releases
them. Entering Preview from Gallery starts on Compressed, while stepping within Preview preserves
the selected tab.

## Decisions made

- The user explicitly chose to retain the photo picker with temporary local source copies over
  switching to the Files picker. A failed storage operation rejects that selection with an
  explanation rather than admitting a picker reference already shown to be unreliable.
- Reuse the classification read, rather than trying another read after import. Wrapping or slicing
  the picker File does not create independent bytes. Copies commit before acceptance.
- Use IndexedDB, with Blob storage by default and a byte-array fallback for WebKit's ephemeral
  storage. Keep only copy IDs for the batch and materialize sources for active consumers; do not
  retain every source in JavaScript memory.
- Hold a random session's Web Lock until document destruction. Startup deletes only sessions whose
  lease can be acquired immediately; this protects another live tab, including one using bfcache.
  Page exit also attempts cleanup, but cannot guarantee asynchronous writes finish before teardown.
- Retain `setSourceFile` for caller-owned File fixtures/API callers. Production picker, folder, and
  drop ingestion use the preserved-copy path.

## Surprises

- On Samsung SM-E346B / Android 16 / Chrome 156.0.8078.47, the original picker File could be read
  successfully twice, then fail about eleven seconds after selection with `NotReadableError` and
  `net::ERR_UPLOAD_FILE_CHANGED`. The underlying photo's checksum still matched an earlier
  independent read. This refutes C9 and invalidates reliance on picker File durability, but does not
  establish the internal Android/Chrome cause or imply the photo is damaged. The permission wording
  in the exception is generic and does not prove permission revocation.
- The same photo selected through Files survived fifteen reads and three full compression/Gallery
  cycles. Compressed versus Original on entry was not the cause of the source failure. The default
  tab nevertheless violated R-P2 and is fixed independently.
- WebKit ephemeral IndexedDB rejected Blob/File values with `UnknownError: Error preparing Blob/File
  data to be stored in object store`; byte arrays and strings succeeded in an isolated probe. The
  fallback preserves lazy loading rather than keeping a batch-sized memory cache.
- Reusing a Vite server across many edits produced duplicate source module instances between the
  browser-test fixture imports and the interface, making fixture-seeded sources appear missing.
  Restarting Vite resolved those failures without changing assertions; T33-A records the same trap.

### Storage lifetime

Copies are temporary browser data, not a history or recovery feature. Browser eviction or user
clearing site data can still remove them. A crash can leave rows until the next startup cleanup.
Do not substitute run-output cleanup for source cleanup: returning from Processing must retain the
sources so the next run can read them. Queue payloads must stay lazy to avoid loading all sources
back into application memory.
