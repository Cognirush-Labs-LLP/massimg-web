# T19 — Origin-private storage

**Status:** complete

## What was built

`platform/opfs.ts`: a single-slot store for "the current run's archive" — `writeArchive`,
`readArchive`, `deleteArchive`, `estimateQuota`, `checkQuota` — backed by real OPFS when available
and an in-memory `Blob` otherwise, with the choice of backend made once per operation by reusing
`platform/capability.ts`'s cached `getCapabilities()` (T17). A Playwright test writes, reads back and
deletes a 320 MB archive via real OPFS on Chromium, Firefox and WebKit (the last via a persistent
context, since WebKit's default Playwright context has no working OPFS at all — T01), and separately
proves the in-memory fallback round-trips correctly on two independently-known no-OPFS contexts
(Firefox private browsing, WebKit's default ephemeral context).

## Files touched

  `estimateQuota()`, `checkQuota()`.
- `tests/e2e/opfs.spec.ts` — real-OPFS round trip (all three engines), quota preflight (all three

## Decisions made

- **Single-slot store, not a generic named-entry key/value store.** OPFS has exactly one real
  consumer in this app — the ZIP archive assembled during a run (R-X38/R-X39, Technical Design
  §9.1–9.2) — and nothing else in the design corpus touches OPFS. Building a generic multi-entry API
  would be presenting unrequested generality as architecture. `ENTRY_NAME` is a private constant,
  never exposed; callers only see the four operations.
- **Backend selection reuses `capability.ts`'s `getCapabilities()`, not a fresh probe.** `probeOpfs()`
  already does a real functional check (create, write a byte, close, delete); re-probing here would
  duplicate work and risk disagreeing with the cached result a caller might already have consulted for
  UI purposes. `writeArchive`/`readArchive`/`deleteArchive` each call `getCapabilities()` themselves
  (cheap after the first call — it's cached) rather than requiring callers to pass the flag in, so the
  module's own API surface stays four plain async functions.
- **`writeArchive` streams via `source.pipeTo(writable)` on the real path, no manual chunk loop.**
  `FileSystemWritableFileStream extends WritableStream`, so `pipeTo` is sufficient and is the whole
  mechanism keeping memory at "one chunk at a time" (R-X38) rather than materialising the archive —
  no reimplementation of what `pipeTo`'s backpressure already does.
- **`deleteArchive()` always swallows not-found**, on both backends. R-X42 calls delete from three
  different lifecycle points (after download, on leaving Processing, on application start), and at
  least two of those will often find nothing there. Idempotent delete is the correct primitive for all
  three call sites, not a special case any one of them needs to guard against separately.
- **`readArchive()` throws on the fallback path if nothing was written yet**, matching what the real
  path does naturally (`getFileHandle` without `create` throws `NotFoundError` on a missing entry).
  Read-before-write is a caller bug, not a condition this module should design a quiet fallback around.
- **`checkQuota()` in fallback mode always returns `ok: true, available: Infinity`, never calls
  `navigator.storage.estimate()`.** There is no OPFS quota to preflight against once OPFS isn't the
  active backend — the real constraint R-X41 names instead ("reduced batch cap") is a **T50-owned
  measured number**, not something this module should invent by misreading a `StorageManager` estimate
  that may not even reflect OPFS's own constraint in a private context. Gating on the same
  `capabilities.opfs` flag used elsewhere in this module keeps the two code paths internally
  consistent.
- **No auto-cleanup on module import.** `deleteArchive()` is a plain exported function; wiring it to
  "on application start" is left to whichever task boots the app (same precedent T18 set for leaving
  drop-UI wiring to a later task) — `opfs.ts` has no concept of "app start," only of "delete the
  entry."
- **`FileSystemDirectoryHandle` has no async-iteration methods in this repo's installed
  `lib.dom.d.ts`** (checked directly, same verification method T17/T18 used for other DOM APIs):
  `getDirectoryHandle`, `getFileHandle`, `removeEntry`, `resolve` only, no `entries()`/`values()`/
  `[Symbol.asyncIterator]`. This is why the single-slot design above isn't just a convenience — a
  general enumerable OPFS store would have needed either an ambient type augmentation or an `any`-cast
  to enumerate the directory, neither of which is worth taking on for an API nothing needs.
- **`Uint8Array` values read off a `ReadableStreamDefaultReader<Uint8Array>` are re-wrapped via
  `new Uint8Array(value)` before being pushed into the fallback's `BlobPart[]`.** TypeScript 5.9's
  DOM types widen a reader's yielded chunks to `Uint8Array<ArrayBufferLike>` (which includes
  `SharedArrayBuffer`-backed views), which `BlobPart` rejects since it requires
  `ArrayBufferView<ArrayBuffer>` specifically. Re-wrapping is a real copy (this is the in-memory
  fallback path only, not the streamed real-OPFS path, so the extra copy is a non-issue) and resolves
  the type error without an unsound cast.

## Surprises

- None beyond what T01/T17 already found and this task reused directly (WebKit's ephemeral context
  having no OPFS; `launchPersistentContext` being the fix). No new divergence between engines showed
  up in the write/read/delete round trip or the quota preflight — `navigator.storage.estimate()`
  returned a sane positive `quota` on all three engines' real-OPFS contexts without any special
  handling needed.
- The TypeScript 5.9 `Uint8Array<ArrayBufferLike>` vs. `BlobPart` friction (see Decisions made) wasn't
  anticipated from the plan — found only once `pnpm check` actually ran. Worth knowing for any future
  code that pushes stream-read chunks into a `Blob`/`BlobPart[]` array under this repo's TS version.

## What the next task should know

- Import `writeArchive`, `readArchive`, `deleteArchive`, `estimateQuota`, `checkQuota`, and the
  `QuotaCheck` type from `@/platform/opfs`.
- **T40 (Archive assembly) is the real consumer**: pipe `client-zip`'s `ReadableStream` straight into
  `writeArchive()`. Call `checkQuota(predictedLength)` before starting the run (R-X40) using
  `client-zip`'s `predictLength` (byte-exact per E2, Technical Design §9.1) as `requiredBytes`; a
  `false` result carries both `required` and `available` ready to report to the user, matching R-X40's
  "naming both figures."
- **T42 (Download and leaving) owns wiring `deleteArchive()` to its three R-X42 call sites** (after
  download, on leaving the Processing view) and whichever task boots the app owns the "on application
  start" leg — none of that wiring exists yet, `opfs.ts` only provides the primitive.
- `readArchive()`'s result is a `Blob` (a `File` on the real backend, a plain `Blob` on the fallback) —
  callers that need a `File` specifically (e.g. for a filename) should not assume one; T42's download
  step should construct its own filename rather than relying on `Blob.name`.
- Same JSON-serialization caveat as T18: a `Blob`'s own bytes don't survive `page.evaluate`'s return
  trip to Node, but values read out of it (`.size`, `.slice(...).arrayBuffer()`) do — any future test
  touching this module's `Blob` results should read what it needs from the `Blob` *inside* the page
  before returning, same pattern used throughout `opfs.spec.ts`.

## Requirements covered

R-X38, R-X40, R-X41, R-X42. R-X39 ("compression begins on the primary action, not on Download") is a
UI-orchestration requirement with nothing to build in `platform/opfs.ts` itself — `writeArchive()`
starting to accept data the moment it's called already makes that ordering possible; enforcing *when*
it's called is T40/T42's job.
