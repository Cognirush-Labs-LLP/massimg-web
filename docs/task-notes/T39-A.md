# T39-A — Multi-file Web Share verification

**Status:** complete with caveats

## What was built

A manual device-testing harness, `verification/t39a-web-share/` (zero dependencies, no bundler,
following the `verification/` convention): a Node static/`POST /results` server fixed to port 8787
(fixed so Android's `adb reverse tcp:8787 tcp:8787` names the same port on both ends), a client page
that builds OPFS-backed or in-memory `File[]` sets from real fixture bytes streamed live from
`PHOTO_FIXTURES_DIR` (never copied into the repo) or from precisely-sized synthetic blobs, probes
capabilities, calls exact `canShare`/`share()`, and auto-records every outcome. It was run by the
user across real hardware/browsers — real evidence for assumption **E4**, which is now `TESTED` at
85% (was `OPEN` 60%) — see `docs/assumptions.md` E4 and `docs/technical-design.md` §14.

## Decisions made

1. **iOS Safari deliberately out of scope for this pass**, resolved with the user before testing.
   No iPhone was available; the only iOS hardware on hand (an iPad mini, iOS 12.5.8) predates OPFS
   and multi-file Web Share entirely, so it can only prove graceful absence, not E4's real question.
   T50 already requires a physical iPhone, including an older low-memory model, for C4, and already
   re-runs "T39-A's ten-file and maximum-byte Share cases" there — this task leans on that rather
   than inventing a parallel iOS plan. The harness itself needs no changes for that follow-up.
2. **Fixture bytes are streamed live from `PHOTO_FIXTURES_DIR` on each request, never copied into
   the repo.** Simpler than the copy-then-gitignore pattern other harnesses use, and the AGENTS.md
   fixture rule ("copy out of it if a task needs to place a fixture somewhere in-repo") only requires
   a copy when one is actually placed in-repo — streaming avoids needing one at all.
3. **The byte-size ramp uses synthetic zero-filled blobs, tagged with a real MIME/extension, rather
   than more real photographs.** `canShare`/`share()` only look at `File.type` and size, not pixel
   validity (same reasoning T01 used for its OPFS payload) — confirmed in practice, since the
   measured Chrome ceiling was purely a function of total bytes.
4. **Recommending `maximumShareBytes` ≈ 40 MB** — a safety margin under the measured 50 MB-safe /
   60 MB-failing Chrome boundary (the most restrictive engine tested, and also the engine on the
   lowest-memory mobile hardware actually tested, Android). This is a recommendation for whoever
   wires the real constant (T50 owns `maximumShareBytes` as a config value per `docs/tasks.md`), not
   a code change here.
5. **Ten files is not the constraint; total bytes is.** The task's own fallback wording ("lower the
   file or total-byte cap") anticipated either; measurement pointed entirely at bytes — 10 real
   mixed-format files at ~9.8 MB total shared successfully everywhere tested, so no Functional
   Design limit needed lowering before T40.
6. **Firefox (desktop) included even though not explicitly required** ("every available shipping
   desktop implementation" was read to include it) — cheap, and the result (no file-sharing support
   at all) is a clean, useful negative.

## Surprises

**A harness bug produced a wave of false-negative `NotAllowedError`s before the real findings
emerged.** The first draft sampled memory with `await sampleMemory()` *before* calling
`navigator.share()`. On Chrome, `performance.measureUserAgentSpecificMemory()` is slow enough
(triggers a real memory sweep) that it reliably burned through the click's transient-activation
window before `share()` ever ran, surfacing as `NotAllowedError: Must be handling a user gesture` —
indistinguishable from a real gesture problem. Safari has neither that API nor `performance.memory`,
so its sample returns instantly and never showed the bug — which is exactly why early Safari runs
were clean while Chrome/Android runs were flaky. Fixed by calling `share()` as the first synchronous
statement in the click handler and moving all memory sampling to after it settles. Worth remembering
for any future harness built the same way: nothing async may run ahead of a gesture-gated API call.

**`canShare({ files }) === true` does not predict `share()` will succeed, on Chrome, past a real
byte-size ceiling.** `canShare` kept saying `true` well above the point `share()` itself started
throwing `NotAllowedError: Permission denied` — a hard, repeatable boundary between 50 MB (always
fine) and 60 MB (always fails) on macOS Chrome. Safari showed no such ceiling up to the largest value
tested, 1 GB. This is the central, genuinely new fact this task produced — it directly sets the
recommended `maximumShareBytes` and confirms Technical Design §9.1 was already right to gate on the
byte total before calling `canShare`, rather than trusting `canShare` as the size gate.

**Chrome's transient-activation window tolerates at least 3 seconds.** The harness's
"delayed-click" test was built specifically to force a deterministic non-cancellation failure by
breaking activation — it was expected to reliably fail. Instead it resolved on every Chrome
(macOS/Android/Windows) and Safari run. The real `NotAllowedError`/`InvalidStateError` failures that
did occur came from the byte-size ceiling and from a second `share()` call overlapping a still-
pending first one, respectively — both genuine platform behaviour, not the forced case. The
"delayed-click" test still exists in the harness and is harmless to keep, but it isn't a reliable way
to exercise the failure path on current Chrome.

**Safari's private-browsing in-memory ceiling is far below its OPFS-backed ceiling on the same
browser.** OPFS-backed Safari shared up to 1 GB cleanly; in private mode, just *constructing* a 50 MB
in-memory `File` failed outright with `"The operation failed for an unknown transient reason (e.g.
out of memory)"`, before `share()` was ever reached. The gap between the two paths is much larger
than Technical Design §9.2's "reduced cap" language implies — private mode isn't a smaller version
of the same ceiling, it's a different regime.

**Chrome incognito exposes OPFS; Safari private browsing does not.** Expected given B3 is phrased
generally ("OPFS unavailable in private browsing") but the two engines diverge here — worth knowing
if a future task reads B3 as uniform across browsers.

## What the next task should know

- **T40**: build the Share OPFS sink per Technical Design §9.1 as planned — nothing here contradicts
  the ten-file / one-encode-teed-to-two-sinks design. Just don't rely on `canShare` to catch an
  oversized payload; apply `maximumShareBytes` first (the design already says this — now confirmed
  necessary in practice, not just in theory).
- **T50**: owns the real `maximumShareBytes` constant. Start from ≈40 MB (see Decisions #4) and
  confirm/adjust on real Android/iPhone hardware, where available memory is lower than the desktop
  machines this task measured on. Also owns the deferred real-iOS run — the harness in
  `verification/t39a-web-share/` needs no changes for that, just a real iPhone and (if useful)
  `iproxy` for USB forwarding (see that folder's README).
  `iproxy`/`adb reverse`-style forwarding is one-directional per platform: `adb reverse` exposes the
  *host's* port to the device; `iproxy` exposes a port the *device* is listening on to the host —
  opposite directions. There is no iOS equivalent of `adb reverse`; reaching a dev machine's server
  from Safari on a real device needs a tunnel (e.g. `cloudflared tunnel --url http://localhost:8787`)
  instead. Recorded here so T50 doesn't waste time rediscovering it the way this task did.
- Two open sub-questions, each cheap to close with a more careful re-run rather than more
  infrastructure: whether Chrome incognito's repeated share-cancellation is genuine user action or
  the browser narrowing targets, and whether Safari private mode can share the ordinary small
  bounded case (1–2 real files) despite failing to build a 50 MB synthetic one.
- Raw data for all of the above: `verification/t39a-web-share/results.json`.
