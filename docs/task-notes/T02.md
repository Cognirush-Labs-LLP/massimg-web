# T02 — AVIF encode speed on real photographs

**Status:** complete

## What was built

A throwaway Node harness (`verification/t02-avif-speed/`) that encodes twenty real
photographs to AVIF at `heic:speed` 6, 7, 8 and 9, quality 70, using
`@imagemagick/magick-wasm` 0.0.43. It records output size and wall-clock encode time for
all 80 encodes, and a perceptual-quality score (SSIM) for each encode against its source.

## Decisions made

- **Perceptual metric: ImageMagick's own SSIM compare** (`ErrorMetric.StructuralSimilarity`
  via `MagickImage.compare()`), not a separate `ssim.js` dependency (installed initially,
  then removed once this was confirmed to work). It decodes the AVIF result internally and
  returns a distortion value where 0 = identical; reported here as `1 − distortion` so
  higher means more similar, matching the usual SSIM convention. Chosen because
  `magick-wasm` was already loaded for encoding and its built-in metric is exactly SSIM, not
  an approximation of it — no reason to add a second dependency.
- **Photo selection is algorithmic, not a hardcoded filename list.** `run.mjs` reads
  `PHOTO_FIXTURES_DIR/MIC_Demo/input_image` (a folder of roughly 145 real,
  photographer-contributed JPEGs on the fixtures drive), sorts by file size as a proxy for
  resolution/detail, and stride-samples 19 of them, then adds one nature/wildlife photo from
  the parent folder for additional subject variety (the input_image folder is dominated by
  portrait and product/gear photography; the twentieth photo broadens the content mix).
  Content actually spans: portraits from several different shoots and cameras, a
  camera-gear product shot taken at night (with visible stars), a drone photo, and a wildlife
  photo, at resolutions from 2848 to 7200 px on the long edge. Rejected: hardcoding the
  twenty filenames directly — simpler to read, but several of those files are named with
  photographers' Instagram handles, and the selection only needs to be reproducible against
  the same directory, not eyeballed, so there's no reason to commit third-party names into
  git history for it.
- **magick-wasm x86/x64 pairing.** Undocumented in the package README: it ships both an x86
  and an x64 WASM build, and each must be paired with its matching initializer
  (`initializeImageMagick` ↔ `dist/x86/magick.wasm`, `initializeImageMagickx64` ↔
  `dist/x64/magick.wasm`). Passing the wrong bytes to either fails in Node 22.16 with
  `CompileError: WebAssembly.instantiate(): invalid table elements limits flags`, which does
  not point at the actual mismatch. Used the x86 pairing (adequate here; no image in the set
  approached a size where 32-bit addressing would matter). This is also consistent with **B7**
  in the Assumptions Register ("the x64 build requires memory64"), which this task ran into
  independently before finding that entry.
- **Twenty photographs from one library**, as the task specifies, not more. Quality fixed at
  70 throughout, per the task and matching D7's original test condition.

## Surprises

- **Encoded size does not fall monotonically as speed decreases (effort increases) on real
  photographs**, which is the reverse of the usual "more effort, smaller file" expectation.
  Mean size was smallest at speed 6 (1124.4 KB) and 5.6% larger at speed 9 (1191.6 KB); 18 of
  20 photos were larger at speed 9 than at speed 6 (range −0.87% to +15.1% on one small,
  detail-light photo where the percentage swing is exaggerated by a small denominator).
  Plausible explanation: `heic:speed` trades off rate-distortion search thoroughness in a way
  that isn't strictly monotonic in size at a fixed *quality* parameter (as opposed to a fixed
  bitrate/two-pass target). This doesn't change the recommendation — the spread is still
  small (comparable to the "under 8%" already seen on synthetic noise) and is dwarfed by the
  time difference — but it's worth knowing before assuming higher speed always means a larger
  file.
- **Quality differences between speeds are even smaller on real photographs than the
  original D7 entry worried about.** D7's "why not 100" reasoned that synthetic noise might
  flatten a real quality difference between speed settings that would show up on photographs.
  It didn't show up: the largest SSIM range seen for any single photo across all four speeds
  was 0.00124 (0.12 percentage points), smaller than the photo-to-photo variation in the set
  itself (SSIM ranged 0.9804–0.9954 depending on image content, independent of speed).

## What the next task should know

- The magick-wasm x86/x64 initializer pairing above will bite any future verification
  harness that loads `@imagemagick/magick-wasm` in Node — see
  `verification/t02-avif-speed/run.mjs` for the working init pattern (`initializeImageMagick`
  + `dist/x86/magick.wasm`).
- `ErrorMetric.StructuralSimilarity` via `MagickImage.compare()` is a ready perceptual-quality
  metric for future format/quality verification (e.g. re-measuring D2, or D8's PNG quantizer
  comparison) without adding another WASM/JS dependency.
- Raw per-encode data (80 rows: photo, speed, size, time, SSIM) and one encoded `.avif`
  sample per photo/speed are in `verification/t02-avif-speed/.scratch/` — gitignored, not
  committed. Regenerate with `pnpm install && pnpm test` from that directory (needs
  `PHOTO_FIXTURES_DIR` set in the repo-root `.env`).

## Results (headline numbers)

20 real photographs (2848–7200 px long edge, 1.7–8.2 MB as source JPEGs), `heic:speed` 6/7/8/9,
quality 70. Mean over 20 photos per speed:

| `heic:speed` | Mean size | Mean time | Mean SSIM | Min SSIM | Max time |
| --- | --- | --- | --- | --- | --- |
| 6 | 1124.4 KB | 18,170 ms | 0.98607 | 0.98064 | 43,697 ms |
| 7 | 1184.3 KB | 9,236 ms | 0.98608 | 0.98073 | 20,328 ms |
| 8 | 1172.9 KB | 3,871 ms | 0.98570 | 0.98039 | 8,810 ms |
| 9 | 1191.6 KB | 1,793 ms | 0.98586 | 0.98058 | 2,971 ms |

**Recommendation: `heic:speed` 9.** It is 9.94x faster than speed 6 on average (range
4.68x–16.01x) and 2.10x faster than speed 8 (range 1.14x–3.48x per photo), for a mean SSIM
statistically indistinguishable from every other speed tested and under 1% mean size
difference from speed 8. No photo in the set showed a speed-8-or-slower setting buying a
meaningful (>0.15% SSIM, or a materially smaller file) improvement over speed 9. `docs/assumptions.md`
D7 raised to 99% confidence and marked closed; `docs/technical-design.md` §7.3 now names
`heic:speed` 9 rather than "8 or 9."
