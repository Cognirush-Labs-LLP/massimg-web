# T48 — Language completeness

**Status:** complete

## What was built

A real locale-switching core (`src/i18n/locale.ts`), a test-only `pseudo` locale generated from
English (`src/i18n/pseudo/messages.ts`), a `<html dir>` sync composable wired into `App.vue`, and
two new tests: a Vitest check that the downloadable report is byte-identical regardless of
interface locale, and a Playwright suite that renders Gallery, Preview, Edit, Processing, and the
mobile drawer under the pseudo locale and asserts the side panel/drawer actually swap edges. The
shared `context.json` moved from `src/i18n/en/context.json` to `src/i18n/context.json`. One real
literal-string gap (`Header.vue`'s wordmark) was fixed.

## Files touched

- `src/i18n/locale.ts` — new. `LocaleCode = 'en' | 'pseudo'`, a module-scope reactive
  `currentLocale` ref, and `setLocale`/`getLocale`/`isRtl`.
- `src/i18n/pseudo/messages.ts` — new. Generates the pseudo locale from `en/messages.json` at
  module load by wrapping every string in Unicode bidi override marks (`‮…‬`).
- `src/i18n/t.ts` — resolves messages via `LOCALE_MESSAGES[currentLocale.value]` instead of a

- `src/i18n/en/context.json` → `src/i18n/context.json` — moved (`git mv`).
- `src/i18n/i18n-consistency.spec.ts` — import path updated to `./context.json`; comment updated
  to explain why `pseudo/` has no context entries (it's generated, not translated).
- `src/i18n/useLocaleDirection.ts` — new composable; inside `onMounted` (vite-ssg's client-only
  guard, same one `ToolPage.vue` already uses), a `watchEffect` sets `document.documentElement.dir`
  from `isRtl()`.
- `src/app/App.vue` — calls `useLocaleDirection()` alongside the existing `useAnalyticsBeacon()`.
- `src/app/shell/Header.vue` — literal `"Mass Image Compressor"` text node → `t('site.nav.home')`.
- `src/i18n/locale.spec.ts` — new. Locale switching, pseudo-wrapping, interpolation still working
  under pseudo, `isRtl` per locale.
- `src/domain/report.spec.ts` — new `describe` block: `buildReport(fixtureRun)` serialized under
  `en` and under `pseudo` produces identical YAML.
- `tests/e2e/i18n-rtl.spec.ts` — new. Six tests: default locale is `ltr`; side panel mirrors in
  Gallery/Preview/Edit; mobile drawer mirrors; Processing renders under `rtl` with no horizontal
  overflow. Passing on Chromium, Firefox and WebKit.

## Decisions made

- **Locale state is a module-scope reactive singleton, not a store or a per-call parameter.** `t()`
  is called bare (`t('key')`) from ~50 call sites with no locale threaded through, so the
  thumbnail-service style of per-call dependency injection doesn't fit. A plain exported `ref` is
  the same shape vue-i18n/react-intl use themselves, and because `t()` reads `currentLocale.value`
  during a component's render, Vue's own reactivity tracks it with no extra wiring.
- **The pseudo locale is generated from English at module load, not hand-authored or checked in as
  static JSON.** Wrapping every string in RLO/PDF bidi override marks forces right-to-left
  rendering of the literal Latin text without a real RTL-script translation — the same technique
  as Microsoft's "qps-plocm" mirrored pseudo locale, named `pseudo` here instead of that code for
  readability. Deriving it by construction means its key set can never drift from `en/messages.json`
  as later tasks add keys, so no second consistency check was added for it, and it needs no
  `context.json` entries (R-L2's context file is for human translators; this locale has none).
- **`pseudo` is not added to `src/config/site.ts`'s `supportedLocales`.** That list drives real
  routing/hreflang/sitemap generation (T31/T43/T45); a pseudo-locale must never become a routed,
  indexed locale. It is reachable only by calling `setLocale('pseudo')` directly, which only the
  new tests do.
- **The RTL test asserts mirroring, not direction alone.** stylelint's `liberty/use-logical-spec`
  (T07) already fails the build on a physical property *name* at lint time; a runtime test that
  only checked `document.documentElement.dir === 'rtl'` would prove nothing about whether logical
  properties are actually wired up. Comparing the side panel's/drawer's bounding-box position
  before and after switching locale, and asserting it moved to the opposite edge, is the thing that
  can only pass if R-L4's `inline-start`/`inline-end`/`inset-inline-end` properties are doing real
  work.
- **The RTL e2e spec seeds two images, not one.** Seeding exactly one triggers R-M1
  (`useUiStore.onBatchCountChanged`, fired by `useBatchStore.addImages` regardless of caller) and
  auto-opens Preview before the test can observe actual Gallery mode. This cost one debugging round
  trip during implementation — worth flagging since it will bite any future e2e test that wants a
  populated-but-still-Gallery fixture.
- **Confirmed non-gaps, left untouched** (all pre-existing, documented conventions from earlier
  tasks, not reopened by this one): `domain/report.ts`'s hardcoded English (R-L3 — the report is
  never translated); `SidePanelQuality.vue`'s `KB`/`MB` unit labels; `SidePanelFormat.vue`'s and
  `ToolPage.vue`'s format acronyms (`JPEG`/`PNG`/`WebP`/`AVIF`/`GIF`); `site.ts`'s `siteName` used
  only in `<meta>`/JSON-LD, never rendered in-app.
- Rejected: naming the pseudo locale directory `qps-plocm` (Microsoft's own convention for a
  mirrored pseudo locale). `pseudo` was chosen instead for readability by engineers unfamiliar with
  that jargon; the doc comments in `locale.ts`/`pseudo/messages.ts` name the real technique so the
  connection isn't lost.

## Surprises

- `src/stores/ui.ts`'s R-M1 handling (`onBatchCountChanged`) fires from `useBatchStore.addImages`
  itself, not from the real selection path (`ui/gallery/ingest.ts`) — so it also fires for a test
  that seeds the store directly, which is not obvious from the task text and cost a debugging round
  trip (see Decisions made).
- Otherwise none: the codebase was already extremely close to R-L1–R-L5 compliance going in (one
  literal string found across the entire `src/` tree), and Technical Design §11's description of
  the target `context.json` location already matched what this task produced, so no doc edit was
  needed there.

## What the next task should know

- `setLocale('pseudo')` and `getLocale()`/`isRtl()` are real, exported, reactive — a future task
  building an actual locale switcher UI or a real second human-translated locale (`es/`, per
  Technical Design §11's example tree) can call `setLocale` directly rather than re-deriving this
  plumbing. Adding a real locale means: a new `src/i18n/<code>/messages.json`, an entry in
  `LOCALE_MESSAGES` in `t.ts`, a `LocaleCode` union member, and — unlike `pseudo` — an entry in
  `src/config/site.ts`'s `supportedLocales` (which is what would actually make it routed/indexed).
- `i18n-consistency.spec.ts` is still hardcoded to one real locale (`en`) against the shared
  `context.json`, deliberately (see its own header comment). When a real second locale arrives,
  generalize it to loop over every `src/i18n/<code>/` directory except `pseudo/`.
- The RTL e2e spec's `mirroredBoxes` helper (bounding-box-before/after-locale-switch) is a pattern
  worth reusing for any future component whose own layout depends on `inline-start`/`inline-end`,
  rather than re-deriving the technique.
