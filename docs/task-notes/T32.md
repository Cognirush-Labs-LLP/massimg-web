# T32 — Stores

**Status:** complete

## What was built

The four Pinia stores from Technical Design §3: `useBatchStore`, `useSettingsStore`,
`useRunStore`, `useUiStore`. All hold metadata only, in Pinia's setup-store syntax. The
Functional Design §3.1 mode-transition table is encoded as store logic — explicit actions on
`useUiStore` for the transitions a UI component triggers directly, plus two automatic methods
(`onBatchCountChanged`, `retargetAfterRemoval`) that `useBatchStore` calls from `addImages`/
`removeImage` for the count-boundary transitions (R-M1/R-M2). `useStageMode.ts`, T31's
module-scope placeholder, is deleted; `ToolPage.vue`, `Header.vue` and `PrimaryActionButton.vue`
now read real store state instead of the hardcoded/local values T31 left in place.

## Decisions made

- **Selection-time rejection entries are not added to `useBatchStore`.** `docs/ui-design.md`
  §4 says the store "also holds selection-time rejection entries (§14)," but no `RejectionEntry`
  type exists anywhere in the codebase yet. T39 owns Functional Design §10/§14 and is the task
  that should define that shape against the real eighteen-row table — guessing it here would be
  inventing a requirement. **T39 needs to add a field to `useBatchStore`, not build a new
  store.**
- **`useSettingsStore`'s default quality slider value is 70.** Nothing in functional-design.md
  or ui-design.md states a default numeric position — only the three shortcut chips (`LOW 40`,
  `MED 70`, `HIGH 90`) exist, with none marked as the initial value. 70 (the `MED` chip) was
  chosen as the least-surprising default. This isn't user-visible yet (T35 hasn't built the
  panel), but T35 should treat this as an assumption to confirm, not a settled spec fact.
- **`drawerOpener` (the DOM element focus-return target) stays local to `ToolPage.vue`**, not
  moved into `useUiStore`. It isn't in ui-design §4's store field list, and a live `HTMLElement`
  reference inside Pinia state has the same non-serializable, DOM-coupled character the
  binary-data rule guards against in spirit, even though it isn't one of the four named types.
- **The force-close-drawer-on-entering-Processing behaviour moved into
  `useUiStore.enterProcessing()`** rather than staying a component-level `watch` in
  `ToolPage.vue`. Keeps transition-adjacent logic in the store, consistent with where the
  count-boundary logic lives, and every future entry point into Processing (not just the one
  `ToolPage.vue` currently has no real path to yet) gets it automatically.
- **`useBatchStore` calls `useUiStore()` directly from its own actions**, rather than a
  `$subscribe` or a separate always-mounted watcher composable. Idiomatic Pinia, keeps the
  transition synchronous (tests assert immediately after calling an action, no microtask
  flushing needed), and creates exactly one, one-directional dependency (`batch.ts → ui.ts`,
  never the reverse — `retargetAfterRemoval` takes the post-removal array as a parameter rather
  than calling back into `useBatchStore()`).
- **`onBatchCountChanged` does nothing while `stageMode` is `'edit'` or `'processing'`.** Not
  reachable through real interaction yet (nothing can add images while those modes are mounted,
  since Gallery/Preview are the only entry points to adding images), but it's a defensible guard
  against a future path doing so unexpectedly, and it's what "unless Edit or Processing is
  already active" in the store's own doc comment describes.
- **`useRunStore.recordResult`'s outcome parameter is a small ad hoc union**
  (`{ kind: 'succeeded', ... } | { kind: 'failed', reason }`), not shaped against the real worker
  result message from `src/pipeline/protocol.ts`. T38 (Processing view) is the task that
  actually wires this store to worker messages and may need to adjust this signature once that
  integration exists — this task only needed a plausible shape to prove the store's own state
  transitions.
- **No new lint rule was added** for the binary-data-never-enters-a-store rule, despite
  Technical Design §1.1 saying "this is enforced by a lint rule and by a unit test." No such
  lint rule exists anywhere in `eslint.config.js`/`eslint-rules/` before this task, and writing
  one (a rule that would need to understand Pinia store definitions specifically, not just flag
  any `File`/`Blob` reference) is a larger, separate piece of work than this task's Done-when
  requires (only the unit test is named there). The structural unit test
  (`binary-store.spec.ts`) is the enforcement this task provides; a lint rule is future work if
  wanted.

## Surprises

`useUiStore.onBatchCountChanged` needed the current `images` array as a second parameter, not
just the count, to be able to set `currentImageId` to the one remaining image's id when the
count reaches exactly one (R-M1) — a plain count is enough to decide *that* a transition should
happen but not *which* image to target. Adjusted its signature from the plan's original
`onBatchCountChanged(count)` sketch to `onBatchCountChanged(count, images)` accordingly; noted
here since it's a small deviation from what was planned before implementation started.

## What the next task should know

- **T33/T34 (Gallery grid/list):** `useBatchStore.addImages`/`removeImage` already drive R-M1/
  R-M2's mode transitions — Gallery's "add files" and "remove tile" actions can call these
  directly without re-deriving any transition logic themselves. `useUiStore.setGalleryView` is
  ready for the grid/list toggle.
- **T35 (Side panel settings):** `useSettingsStore`'s three fields are ready to bind controls
  to. Confirm or change the default quality value of 70 (see Decisions made) once the actual
  slider exists — nothing currently depends on this default being any particular number.
- **T36 (Preview mode):** `useSettingsStore` is reactive and is the "trigger" R-P3 describes,
  but this task built no debounce/token/cancellation mechanism — that's T36's own job, watching
  the settings store's fields.
- **T37 (Edit mode):** `useUiStore.openEdit(id)` / `closeEdit()` are the two actions to call for
  entering and leaving Edit; `closeEdit()` covers Apply, Cancel and Remove edit alike (all three
  return to Preview of the same image per the transition table) — Edit mode itself decides what,
  if anything, to persist onto `ImageRecord.edit` before calling it.
- **T38 (Processing view):** `useUiStore.enterProcessing()`/`cancelProcessing()`/
  `finishProcessing()` are ready; `useRunStore.startRun`/`recordResult`/`finishRun` exist but
  `recordResult`'s parameter shape is a placeholder pending the real worker-protocol integration
  (see Decisions made) — expect to adjust it, not necessarily to keep it as-is.
- **T39 (Errors and rejections):** add a rejection-entries field to `useBatchStore`, not a new
  store (see Decisions made).
- **T42 (Download and leaving):** `useRunStore.finished`/`downloaded` exist specifically so
  R-X18's three-way confirmation guard has something to read; the confirmation dialog itself is
  not built here.

## Requirements covered

R-M1, R-M2, R-M4 (satisfied structurally by T31's exclusive component mounting, unaffected by
this task), R-G2 (removing one image never touches another's fields, proven in
`batch.spec.ts`), R-G5 (insertion order), R-P2 (Preview's default comparison tab), R-A3 (primary
action disabled when the batch is empty — now store-driven rather than hardcoded). R-M3, R-M5,
R-X18 are enabled (state exists for later tasks to build against) but not themselves completed
here — R-M3's "Add more images" action and R-X18's confirmation dialog are T36's and T42's UI
work respectively.
