# T47 — Accessibility

**Status:** complete

## What was built

A full source audit (not just the design docs) found most of R-K1–R-K11 already built correctly
by T31/T36/T37/T38/T42. This task closed the three real gaps that audit found — a keyboard path
for Preview's zoom/pan inspector, live-region announcements for Processing's delivered/error
states, and one redundant `aria-label` — and stood up the automated accessibility audit (axe-core)
the Done-when clause names, run once per stage mode. It also fixed a WCAG AA text-contrast failure
that audit surfaced in a design token used across the whole interface.

## Decisions made

- **Preview zoom/pan keyboard step sizes (40px pan, 1.2× per zoom keypress) are feel-tuned
  placeholders**, no design document gives values — same category as `MAX_VIEWPORT_SCALE`'s own
  placeholder status (T36.md). `Shift+0` (the literal `)` character) was chosen over plain `0` for
  reset specifically to avoid colliding with typing a digit into a number field, per direction
  given for this task.
- **The new keydown handler is bound on the frame element itself, not `window`**, so it can never
  collide with `Preview.vue`'s existing window-level R-K2 arrow-key batch-stepping: every key this
  handler recognises calls `preventDefault()`, and the window listener checks
  `event.defaultPrevented` before acting on anything that bubbles up to it. No change was needed on
  the `Preview.vue` side.
- **`RejectionList.vue` (selection-time rejected-files panel) was left without a live-region
  announcement.** R-K5's text names exactly five events ("encode started, encode finished, image
  failed, run progress, run complete"); a selection-time rejection is none of them, and — unlike
  Processing's delivered/error states, which T42's own note named as this task's to close — no
  earlier task flagged this as an open gap. Left alone rather than silently expanding R-K5's scope.
- **The axe scans are appended to each stage's existing populated-stage e2e test** rather than
  built as one dedicated new spec file per stage, since Gallery/Preview/Edit already had a cheap,
  real, populated instance in an existing file. Processing had no existing e2e coverage at all
  (`tests/e2e/share.spec.ts` only exercises `src/platform/share.ts` directly against synthetic
  `File`s and never renders the stage), so it got the one genuinely new file.
- **The automated audit scans each stage's own root (`[data-testid="…-root"]`), not the whole
  page**, so pre-existing site chrome (T43's header/footer, T45's SEO surfaces) stays out of scope
  for this task's four stage-mode audits.
- **The contrast fix for `--color-text-muted-quiet` (`#6e6e6e` → `#7e7e7e`) was sized against the
  lightest real surface colour it is actually painted on (`--color-surface-tile`, `#121212`), not
  only the pure-black app background axe happened to report** — a value that only cleared 4.5:1 on
  pure black could still fail once rendered over a tile/panel surface.
- **`--color-tint` (`#cf0000`) was deliberately left unchanged, after trying the lightened
  alternative and finding it visually unacceptable.** It fails WCAG AA 4.5:1 as *text* colour at a
  few places below the large-text threshold (12–15px, not bold enough or not large enough to
  qualify for the 3:1 large-text minimum it already clears at 3.65:1) — `.change.reduction` in
  `PreviewComparisonPill.vue`, and `.total`/`.halted`/`.delivery-error`/`.delivered` in
  `Processing.vue`. The minimum red that clears 4.5:1 as pure-hue text on black also has to stay
  dark enough that white button text on a tint background keeps its own 4.5:1 (every white-on-tint
  button in this interface sits below the WCAG large-text threshold too), which pins the fix to a
  narrow band around `#ec0000` — markedly brighter than the original across every tint-coloured
  surface in the app, not just the handful of places that actually needed it. Tried first, rejected
  after seeing it rendered: too disruptive a visual change for what it fixed. Left as a known,
  documented exception instead — `tests/e2e/preview.spec.ts` and `tests/e2e/accessibility.spec.ts`
  exclude exactly those elements from their axe scans (see each file's `expectNoViolations` doc
  comment) rather than silently passing or silently expanding scope. `RejectionList.vue`'s
  `.dismiss` button has the same tint-as-text issue but is not currently exercised by any e2e test,
  so it is not excluded anywhere — flagging here in case a future test renders it.

## Surprises

- `tests/e2e/gallery-ingest.spec.ts`'s two pre-existing tests (`'0 SELECTED'`/`'2 SELECTED'` text
  assertions) fail against the current app on main, unverified to this task — confirmed via
  `git stash` against the unmodified file before touching anything. The UI now reads "SELECTED
  IMAGES" as a heading and `Compress ({count})` on the primary button; neither produces literal
  `"{count} SELECTED"` text anywhere. Pre-existing test rot, unrelated to T47; this task's own new
  test in that file uses `gallery-grid` visibility instead and passes. Left the two broken tests
  as found — fixing unrelated stale locators was out of this task's scope.
- Three `tests/e2e/preview.spec.ts` tests (`'the stepper wraps…'`, `'stepping releases…'`, `'a
  settings change forces…'`) also fail on current main, independently of this task — same
  `git stash` check. Not investigated further; flagging so the next task doesn't assume a clean
  baseline.
- The automated audit this task was asked to add immediately found two real, pre-existing WCAG AA
  contrast failures (the two tokens above) — the mechanism working as intended, not a false
  positive, and worth remembering next time a design token's hex value is adjusted in isolation
  from how it is actually used.

## What the next task should know

- `tests/e2e/accessibility.spec.ts` is the only e2e coverage Processing has at all. Anything that
  changes `Processing.vue`'s structure should check this file, not assume another suite covers it.
- The four stage-mode axe scans are a real regression gate for new contrast/name/role issues
  introduced from here on — a failure there is not automatically another instance of the one
  documented tint exception; check the violating selector against `PROCESSING_TINT_TEXT`/
  `'.change.reduction'` before assuming it's already known.
- `docs/functional-design.md` §14.1 now documents both the `--color-text-muted-quiet` change and
  the reasoning for leaving `--color-tint` as-is; read that before proposing either token's value
  change again.
