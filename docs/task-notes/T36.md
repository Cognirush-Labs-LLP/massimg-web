# T36 — Preview mode

**Status:** complete

## What was built

Preview is now real: entering it runs a genuine worker-pool encode of the current image (R-P1),
shows the measured compressed size and a size-comparison pill once it completes (R-P2, R-P5),
hides those figures while an encode is in flight (R-P4), and shows an inline error with a retry
when one fails (§10). A transform line below the pill describes the output (name, dimensions,
format, and any alpha-flatten/animation-substitution note) driven live off the settings store, not
off the encode result, so it updates on every slider move rather than only once an encode lands. A
toolbar (Back to images, Add more images, a wrapping `n / total` stepper, Edit/Edit changes) is
registered into `ToolPage.vue`'s per-mode toolbar slot.

Beyond the written requirements, Preview also has a zoom/pan inspector: wheel/pinch to zoom about
the pointer, drag to pan, with no slider and no toolbar chrome (direct manipulation only, per
product decision — see Decisions made). The viewport is stored once, in one canonical coordinate
space (fractions of the rotated, uncropped source — the same frame a stored crop `rect` already
uses), and projected into whichever tab is showing, so flipping between Original and Compressed
keeps the same patch of the image centred even though the two tabs can be different rasters once
Edit mode (T37) exists.

## Decisions made

- **Viewport state is center + scale, not a `NormalisedRect`.** A rect implies an aspect ratio a
  viewport doesn't have, and a distinct type preserves `domain/edit.ts`'s existing
  "coordinate spaces must not be assignable to each other" discipline (`FrameRect` vs.
  `NormalisedRect`). Rejected: reusing `NormalisedRect` directly, which would make an inspector
  viewport structurally interchangeable with a stored crop rectangle.
- **The zoom/pan inspector is new scope beyond R-P1–R-P8**, confirmed directly with the user in
  three parts: (1) gesture-only interaction (wheel/pinch/drag, no slider, no toolbar control); (2)
  the viewport persists across a settings-driven re-encode of the *same* image but resets on
  stepping to a *different* one; (3) crop-aware projection is built correctly now, using the real
  `EditRecord`/`domain/edit.ts` geometry, even though it has no real UI to exercise it until T37.
  Rejected: transcoding an unrenderable original to a browser-safe format just to display it (see
  next point) and a slider-driven zoom control (rejected by the user in favour of direct
  manipulation).
- **A browser-unrenderable Original (HEIC on Chromium/Firefox, TIFF, JPEG XL) is reported, not
  transcoded.** The `<img>`'s own `error` event flips `originalUnrenderable`, and the frame shows a
  message naming the file and mentioning the desktop application, rather than silently re-encoding
  the source into something the browser can show and calling that "Original" — which would show the
  user a lossy stand-in under a label that promises the untouched file. This is also the documented
  product pattern: Functional Design §1.3 names "formats the browser cannot decode" as one of three
  cases where a message should point to the desktop product, and R-I21 sets the exact phrasing
  convention (`"...the desktop application has no such limit."`) that
  `preview.frame.originalUnavailable` now follows.
- **Preview gets its own `WorkerPool` instance (`preview-pool.ts`), never shared.** `pipeline/pool.ts`'s
  `supersede()` keys on `imageId` alone and is blind to `intent` (T21's own handover note flags
  this): a `preview` job and a `run` job for the same image could silently supersede each other with
  no failure recorded. Two separate pool instances cannot do that to each other regardless of
  timing — stronger than relying on `STAGE_COMPONENTS` unmounting Preview whenever Processing is
  mounted, which is true today but a property of the current component tree, not of the pool.
  **T38 must create its own pool and must not call `getPreviewPool()`.**
- **The pool itself is never destroyed** on leaving Preview or stepping; only the rendered data
  (object URLs, `Blob`s) is released. Destroying it would throw away loaded codecs (ImageMagick alone
  is 14.8 MB to re-initialise), and R-X29 names that cost as the expensive escape hatch, not the
  normal path for something as ordinary as leaving a stage mode.
- **"Release the outgoing working set before encoding the incoming one" (R-P7/R-B5) is read as
  releasing what Preview renders/retains on the main thread, not as force-interrupting whatever the
  outgoing job is still doing in the worker.** An abandoned in-flight job is cheap (bounded to one
  image, discarded on arrival per R-X28); forcing a true interrupt would pay R-X29's codec-reinit
  cost on every ordinary step for no visible benefit. A generation counter in `usePreviewEncode`
  guards against a stale result reaching the screen regardless.
- **`MAX_VIEWPORT_SCALE = 8`** is a feel-tuned placeholder — no design document gives a ceiling.
- **`mimeForFormat`/`describeSizeComparison`** were added to `domain/format.ts`/`domain/sizes.ts`
  rather than kept local to `src/ui/preview/`, since both are small, closed-set mappings in the same
  spirit as `supportsAlpha`/`formatReportSize` already there, not UI concerns.

## Surprises

- **A real bug, not just a design risk: Vue reactive Proxies reaching `postMessage`.** `image`
  (read off the batch store's reactive array) and `resolveSettings`'s pass-through branches (an
  unresolved dimension rule, a `'size'`-kind quality target, a crop's stored background) can hand
  back live reactive Proxies rather than plain data. A `Job` built from them fails structured clone
  the instant `pool.run()` posts it to the worker — a runtime `DataCloneError`, not a TypeScript
  error, so `npm run check`/`npm test` (jsdom, no real structured-clone enforcement) never caught it.
  Fixed in `usePreviewEncode.ts`'s `runEncode()` with `toRaw()` at the one choke point before
  `resolveSettings` is called: since Vue's nested reactivity is applied lazily when read *through* a
  reactive parent rather than persisted on the target, a single `toRaw()` per entry point (the image,
  and each of `settings.quality`/`settings.dimension`) is sufficient — no need to walk the object
  graph by hand. Confirmed fixed by running the real Playwright suite against real workers on all
  three engines; this class of bug does not show up in jsdom-based unit tests at all.
- **Two Playwright test-authoring gotchas, both now fixed in `preview.spec.ts` and worth knowing for
  future e2e work in this repo:** (1) `tests/e2e/**` compiles under `tsconfig.node.json`, which has no
  `DOM` in `lib` — a bare `document`/`WheelEvent` reference inside a `page.evaluate` callback fails
  `vue-tsc`, even though the callback only ever runs in the browser. The established, already-used
  fix is `declare const X: ...`/`declare function X(...)` ambient declarations (see
  `thumbnails.spec.ts`'s `OffscreenCanvas`) or `Locator.evaluate((el) => ...)`, never a bare global.
  (2) A geometry assertion read via `document.querySelector` inside `page.evaluate` is better
  expressed as `page.getByTestId(...).boundingBox()` — avoids the lib issue entirely and is more
  idiomatic Playwright.
- **A revoked-object-URL test (R-B5) deliberately provokes a browser resource-load failure**
  (`fetch()` against a revoked `blob:` URL), which both Chromium and WebKit log to the console with
  engine-specific wording. That log line is the test's own proof that the URL was revoked, not a
  product defect, so it's excluded from the test's "nothing else went wrong" check by matching on
  the shared `"Failed to load resource"` prefix rather than asserting an empty error list outright.
- **A `ResizeObserver`-driven one-tick lag is real, and briefly visible in geometry if you look at
  exactly the wrong instant.** Between `setViewportSize` and the host's `ResizeObserver` callback
  firing, the frame's rendered box is already CSS-clamped to its new flex container while the
  absolutely-positioned image inside is still sized from the previous measurement — the same kind of
  lag `GalleryGrid.vue`'s identical pattern has. Not a product defect (imperceptible during a real
  drag-resize, self-correcting within one frame); the R-P6 viewport-size test now polls the whole
  invariant (ratio *and* containment) rather than racing a single snapshot immediately after resize.
- **Three pre-existing, unrelated test failures** (`app.spec.ts`'s mobile tab-cycling test,
  `gallery-grid.spec.ts`'s two 400/500-image R-G10 tests) reproduce identically with every T36
  change reverted (verified via `git stash` against the exact same commit), so they are not a T36
  regression — likely a timeout/performance characteristic of this machine under the large synthetic
  batches those tests seed. Not investigated further; out of this task's scope.

## What the next task should know

- **T38 (Processing) must create its own `WorkerPool` and must never call `getPreviewPool()`** — see
  Decisions made. If this is ever "simplified" to share Preview's pool, T21's supersession hazard
  becomes live and a run's job can be silently killed by an unrelated preview encode with no failure
  recorded anywhere.
- **The crop-aware viewport projection (`projectViewportToCompressed`,
  `viewportEditGeometry`'s crop branch) is implemented and unit-tested against constructed
  `EditRecord` fixtures, but has no real UI path to exercise it until T37 ships Edit mode.** A
  regression here would not be caught by any existing end-to-end journey; T37 should add one once a
  real crop exists.
- **`viewportEditGeometry` explicitly refuses to project a rotation that comes after a crop op, or a
  second crop op**, reporting `unprojectable` rather than guessing — neither shape is reachable from
  the interface today (`editOpsFor` in `domain/edit.ts` only ever produces rotation-then-at-most-one-crop),
  but if a future edit pipeline ever produces one, the inspector disables its gestures rather than
  silently mis-projecting. Worth keeping in mind if T37's edit-ops ordering assumptions ever change.
- **The gesture-only (no keyboard) zoom/pan interaction is a deliberate, user-confirmed exception**
  to this app's otherwise-universal keyboard-operability expectation (R-K1 applies elsewhere), not an
  oversight. It wasn't re-litigated here; flagging it in case a later accessibility pass expects
  every interactive surface to have a keyboard path. (Closed by T47 — see docs/task-notes/T47.md.)
- **Arrow-key stepping (R-K2) is the first `keydown` shortcut in this codebase.** It's bound on
  `window` in `Preview.vue` and scoped off whenever focus is inside an `input`, `select`, `textarea`,
  or `[contenteditable]` (so the quality slider's own arrow-key handling isn't stolen). Any future
  global shortcut should follow the same scoping rather than inventing a second convention.
- **`MAX_VIEWPORT_SCALE` (8×) has no product sign-off** — a placeholder if this ever needs to be a
  deliberate, documented limit.

## Requirements covered

R-P1 to R-P8, R-M3 (Add more images; R-M1/R-M2's own mode-transition logic was already built in
`stores/ui.ts` by T32 and is unchanged here), R-I16 (encoded bytes go straight into an `<img>`,
never a canvas), R-B1/R-B4/R-B5 (preview working-set release and ordering), R-X26/R-X28/R-X29
(consumed via the pool, not reimplemented), R-D1/R-D4 and R-C16/R-C17 (consumed by the transform
line and toolbar, not re-derived), R-K2 (arrow-key stepping), R-K5 (phase changes announced via a
live region), R-K8 (size-increase shown with both a glyph and non-tint colour, not colour alone),
R-E1 (every Preview failure names the file and says what to do).

Not covered, by design, at the time this task was written: the zoom/pan inspector's own
keyboard-equivalent path (R-K1 in the general case) — closed by T47, see docs/task-notes/T47.md.
