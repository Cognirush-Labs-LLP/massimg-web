# T39 — Errors and rejections

**Status:** complete with caveats

## What was built

A selection-time rejection mechanism that did not exist anywhere before this task: a
`RejectionReason`/`RejectionEntry` type (`src/domain/rejection.ts`), a `rejections` field and
`setRejections`/`dismissRejections` actions on `useBatchStore`, and wiring in `src/ui/gallery/
ingest.ts` that turns every previously-silent-drop point (an `unhandled` classification, a HEIC
file with no decoder capability, an oversized file, a batch-count overflow, a folder/drop cap
breach, a folder yielding zero supported images) into a named entry instead of discarding it. A new
`RejectionList.vue` renders this as one dismissible panel. Animated AVIF (R-F8) is now rejected at
selection time via `classify()` itself rather than coerced into a run-time failure later. The
ordinary picker gained `accept="image/*"`. Processing gained a genuine out-of-memory run-halt
(previously treated as an ordinary per-image failure, per T38's own handover note) and a distinct
"nothing to download" message for an all-failed-or-skipped completion.

## Decisions made

1. **Byte-size cap only; pixel-cap and animated frame/pixel-budget rows deferred to T50.**
   Classification is magic-bytes only and dimensions resolve asynchronously (T33-A, deliberately
   non-blocking); a true pixel/frame check at selection time would mean decoding every file
   synchronously, undoing that design. Resolved with the user before implementation.
2. **Rejection list replaces on each new selection action, not accumulated.** Matches R-E2's
   "shown once per selection action" literally. Resolved with the user.
3. **HEIC-no-decoder: built the capability flag and rejection wiring anyway, documented as
   untested.** R-I7 (cited by this §10 row) doesn't exist in `functional-design.md`, and §5.2
   confirms HEIC decode works in this build on all three engines. `Capabilities.heicDecode` is
   hardcoded `true`; the rejection path is unit-tested only by injecting `heicDecode: false`
   directly — see `docs/backlog.md` BL-009. Resolved with the user, who asked for this exact
   treatment (build it, document as untested in the backlog) rather than skipping it.
4. **Scope split for the rest of the §10 table.** Five rows — ZIP assembly failure, download
   blocked by browser, storage quota insufficient, storage write failure mid-run, origin-private
   storage unavailable — are explicitly **not** built here. Their mechanisms don't exist yet:
   `Processing.vue`'s own pre-existing comment says Download's click handler "is T42's... once T40
   (archive assembly) and T41 (report) exist," and `recordResult` only ever stores an output byte
   *count*, never actual bytes. Building these now would mean inventing the T40/T42 mechanisms
   early. The task list's own ordering rule ("a task's dependencies are always earlier in the
   list") supports this reading over "every row, now." Whoever builds T40/T42 should add that row's
   §10 test alongside the mechanism, not assume it's covered.
5. **Batch-count-exceeded accepts up to the cap and summarizes the remainder in one entry**, rather
   than rejecting the whole selection or naming every overflow file individually. Consistent with
   R-E2 (one entry, not one alert per file) and with "rejecting some files never blocks the rest."
6. **Folder-empty only fires when the folder *also* produced zero individual `unhandled`
   rejections.** Originally planned to always append it when `addedCount === 0`, but testing showed
   this produced a redundant second message on top of an already-specific one (e.g., a folder
   containing exactly one PSD would get both "bad.psd: ... isn't supported" and "this folder didn't
   contain any images"). Gating on `rejections.length === 0` too avoids that while still covering
   the real R-I29 case (a folder of only silently-skipped non-images, or a literally empty folder).
7. **`RejectionList` mounts in `ToolPage.vue`, not inside `Gallery.vue`.** Found during manual/e2e
   verification, not planned — see Surprises.
8. **Out-of-memory halt keeps the counter/donut/failed/skipped lists visible** for diagnostic value,
   but unconditionally hides Download and replaces the normal completion message with the halted
   one. "Partial results discarded" is read as "nothing is downloadable," not "erase the visible
   counts" — there's nothing to actually discard yet anyway, since output bytes aren't retained
   anywhere until T40 exists (`recordResult` only ever stored a byte count). Easy to change if a
   later task's real archive-retention logic needs something stricter.

## Surprises

**`RejectionList` could not live inside `Gallery.vue`.** First implementation mounted it at the top
of Gallery's own template. The three-engine e2e suite caught this immediately: R-M1 ("a batch of
exactly one image auto-opens Preview") unmounts Gallery the instant a single-image selection lands,
which silently deleted the rejection panel along with it whenever a selection mixed one accepted
image with a rejected one. Moved it to `ToolPage.vue` (the shell that persists across every stage
mode, same place `ConfirmDialog` lives), gated on the same `showPanel` condition as the side panel.
`tests/e2e/gallery-rejections.spec.ts` has a dedicated test for exactly this case.

**A pre-existing, unrelated e2e test file is already broken on `main`.**
`tests/e2e/gallery-ingest.spec.ts` asserts `getByText('N SELECTED')`, text that does not exist
anywhere in the current UI (`gallery.title` is the static string "SELECTED IMAGES"; the actual count
line is `gallery.meta`, "{count} images · {size}"). Confirmed via `git stash` that both of that
file's tests fail identically on the commit this task started from — not something this task
touched or caused. Left as-is since fixing unrelated pre-existing breakage is out of this task's
scope, but flagging it here so it isn't mistaken for new breakage.

**`processing.failure.memory`'s copy already matched the §10 wording almost exactly** ("Try a
smaller image — the desktop application has no such limit"), despite being written for the old
per-image-failure treatment of out-of-memory. The new `processing.halted.memory` key deliberately
does not reuse it (batch framing — "fewer or smaller images" — vs. the old singular framing), since
after this task `out-of-memory` no longer reaches the per-image Failed list from a real run at all.

## What the next task should know

- `domain/format.ts`'s `FormatResolution`'s `{ kind: 'rejected'; reason: 'animated-avif-input' }`
  branch (and its defensive handling in `useProcessingRun.ts`, `transform-line.ts`,
  `usePreviewEncode.ts`) is now provably unreachable from real data, since `classify()` rejects
  animated AVIF before it can ever become an `ImageRecord`. Left in place as defensive code rather
  than removed — not this task's call to make, but a cleanup candidate.
- T40/T41/T42: the rejection entries need to feed the report's Skipped section eventually
  (`docs/ui-design.md` §14 says so explicitly) — not wired here, since `domain/report.ts`'s real
  data wiring is T41's job.
- T50: owns real values for `maximumFileBytes` and `maximumBatchFiles` (currently 100 MB and 500,
  both provisional, same pattern as `folder.ts`'s own `MAX_TRAVERSAL_*` consts), and owns deciding
  how (or whether) a true pixel-cap / animated frame-budget check can coexist with T33-A's
  async dimension probe.
- T40/T42: when archive assembly and Download exist for real, add the five explicitly-deferred
  §10 rows' tests at that point (see Decisions, #4) — they were not forgotten.
- The HEIC-decoder-unavailable path (`Capabilities.heicDecode`) has no live trigger in any current
  browser; see `docs/backlog.md` BL-009.
