# T35 — Side panel settings

**Status:** complete

## What was built

Real Quality, Dimension and Format controls filling the three side-panel sections T31 scaffolded
as empty placeholders, all writing straight to `useSettingsStore`, plus the primary action's
facts-only meta line (R-A2, R-F4) beneath the Compress button. Every control was exercised
end-to-end in a real browser (Chromium, via a throwaway Playwright script, not committed) as well
as through Vue Test Utils component tests.

## Decisions made

1. **`PrimaryActionButton` stays store-free** (T31's explicit design note). `metaLine` is computed
   in `ToolPage.vue` from `describePrimaryActionOutput` + `t()` and passed down as an
   already-translated string, the same pattern `count`/`disabled` already used.
2. **Wiring the button's `@click` to `useUiStore().enterProcessing()` is out of scope.**
   T33-A's own handover note says this explicitly: "since `PrimaryActionButton` has no real click
   handler yet — T38 hasn't built Processing's real entry point." Confirmed by re-reading that
   note before starting; not revisited here.
3. **Format acronyms (JPEG/PNG/WebP/AVIF/GIF) are not routed through `t()`**, in the dropdown or
   in the meta line — same convention `domain/sizes.ts` already established for `KB`/`MB`. Only
   "Don't change" / "Original formats" are actual sentences and get translated. If a future
   locale needs a different acronym convention (unlikely — these are standardised), this is the
   one place to revisit.
4. **R-F4's "Original formats" wording is read as unconditional on batch size.** The requirement
   text doesn't say "for a batch," and a single image under "Don't change" still doesn't get a
   concrete format named in the meta line, even though one is resolvable via `resolveFormat`
   (unlike the dropdown's own behaviour, which always shows the real per-image transform
   elsewhere in the design once Preview/T36 exists). If this reading is wrong, it's a one-line fix
   in `describePrimaryActionOutput`'s single-image branch.
5. **No design document states a default Size-target value or a default per-row Dimension pixel
   value.** Chose 500 KB (Size) and 1920/1080/1080 (Fit/Width/Height), the same numbers the sample
   mockup's own demo state used — a source for reasonable defaults, not for behaviour, given the
   doc's precedence rule (functional-design > ui-design > sample).
6. **Toggling Quality↔Size does not remember the other mode's last value; toggling between
   Dimension rows does.** Switching back to Quality always resets to 70 (the store's own initial
   default). Switching back to a previously visited Dimension row keeps what was last typed there.
   No spec requirement either way; the asymmetry is because the Dimension rows already need
   per-row local state for the field to work correctly at all (bytes can't round-trip through a
   KB/MB toggle without a remembered display value, but a dimension row's remembered pixel value
   was "free" once that per-row map existed), while Quality's two targets don't share that
   structural need.
7. **`sizeTargetDisabledReason` is checked against the batch's raw format setting, not a resolved
   per-image format**, and is `false` (never disabled) whenever the setting is `'dont-change'` —
   there's no single format to check in that case. Since it returns `null` for every format today,
   this path is untested against a real disabled state; whoever eventually sets a real reason
   should add that case then.
8. **Accessibility**: native `<input type="radio">` for the Dimension rows (mutual exclusivity and
   keyboard support for free, wrapped in a labelled `role="radiogroup"`), native `<select>` for
   Format, and the same `role="group"` + `aria-pressed` segmented-toggle pattern
   `GalleryToolbar.vue` already established for Quality/Size and KB/MB — no new interaction
   pattern invented.

## Surprises

None. Every existing piece this task depended on (`useSettingsStore`'s shape, `resolveEditedSize`,
`resolveResizedSize`, `resolveFormat`, the `GalleryToolbar.vue` segmented-toggle precedent) worked
exactly as its own task's handover note described.

One thing worth flagging, not a surprise so much as a limitation: the R-D2/R-D3 crop-override
notes cannot be triggered through real UI yet, since crop authoring is T37's. They're proven by
`SidePanelDimension.spec.ts`'s store fixtures (`useBatchStore().addImages([...])` with a hand-built
`EditRecord` carrying a crop op), not by an end-to-end browser flow. Worth a manual/e2e check once
T37 exists.

## What the next task should know

- **T36 (Preview mode):** `useSettingsStore` is now genuinely live — every control in this task
  writes it immediately, so Preview's debounce/token mechanism will see real, frequent changes
  from day one, not just the T32-era defaults. `describePrimaryActionOutput`'s single-image
  dimension math (`resolveEditedSize` + `resolveResizedSize`) is very close to what Preview's own
  transform line will need to show the same figure — worth checking before writing a second
  version of it.
- **T37 (Edit mode):** once crop authoring exists, add a real Playwright check that R-D2/R-D3's
  notes and the Dimension accordion's disabled state actually appear/engage from a genuine crop,
  not just the component-test fixtures this task used.
- **T38 (Processing):** `PrimaryActionButton` still has no click handler — that action is still
  this task's for the taking, unchanged from T33-A's note.
- **T50 (Limits):** `sizeTargetDisabledReason` is the one place to add a real disabled reason if
  measurement ever finds one; the mechanism (disabled Size button, no message key wired yet since
  nothing has ever needed one) is already there.
