# T25 — Resize

**Status:** complete.

## What was built

This task has two halves.

- **`domain/dimension.ts`** turns a size and a `ResolvedDimension` into an exact output size.
  - *Fit within long edge* only ever shrinks.
  - *Fixed width* and *fixed height* keep the aspect ratio (R-N1) and enlarge too (R-N2).
- **`pipeline/stages/resize.ts`** resamples a `Frame` to that size through ImageMagick. When the size doesn't change, it returns the same frame untouched.

The arithmetic is unit-tested in Vitest. The stage is proven in Playwright on Chromium, Firefox and WebKit. Those tests cover:
- downscale, upscale and the no-op;
- a cropped image ignoring the rule, through the real `decodeFrame` → `resolveSettings` → `applyEdit` → `applyResize` chain;
- a rotated, uncropped image following the rule on its rotated size;
- transparency, color and orientation carried through;
- the pinned filter, compared byte for byte against direct ImageMagick calls;
- no color bleed from fully transparent pixels.

## Decisions made

- **The arithmetic is in the domain and the resample is in the stage.** The Preview output-size readout (T36) and R-X24/R-X45 ("was a dimension change asked for") need the same numbers without decoding. The stage imports `codecs/loader.ts`, which Vitest can't load (T22), so the size logic had to live elsewhere to be unit-testable.
- **ImageMagick, not TypeScript, does the resample.** Unlike T24's byte moves, a good resampling filter is real work, and §7.1 assigns resize to ImageMagick.
- **Rounding.** The constrained edge (the long edge, or the fixed axis) is set to the requested value *exactly*. Only the other edge is computed, as `max(1, round(edge × N / from))`. Setting the constrained edge through a float scale could produce 1919 for a 1920 request. ImageMagick receives both edges with `ignoreAspectRatio`, so it never rounds a second time. The stage also asserts that the size it got back is the size it asked for.
- **An exact limit is a no-op.** An image whose long edge equals the fit value, or whose width already equals the fixed width, returns unchanged.
- **Invalid values throw `RangeError`.** This covers values that aren't whole numbers, and anything below 1, NaN or infinite. `ResolvedDimension` doesn't rule them out, and a 0×0 frame would fail far from its cause. This is a backstop, not a validation rule. Neither the Functional Design nor T35's entry says how the Dimension field treats 0, blank or non-numeric input; that is user-visible and still an open question for T35. Note that `worker.ts` maps `RangeError` to `out-of-memory`. That label is wrong for this case, but the input can't come from a validated panel.
- **The filter is pinned: Lanczos to shrink, Mitchell to enlarge.** This is ImageMagick's own documented default pair. It is set explicitly because ImageMagick's automatic choice uses Mitchell for any image with an alpha channel, and a raw RGBA read always has one. The default would therefore have given every downscale the softer filter. Shrinking versus enlarging is decided by pixel area; both axes move the same way because aspect is preserved. The browser test compares the stage's output byte for byte with direct ImageMagick calls: it equals Lanczos and not Mitchell when shrinking, the reverse when enlarging, and it differs from the automatic choice when shrinking.
- **The resample works on encoded values, not in linear light.** There is no color conversion of any kind (R-I15). ImageMagick weights by alpha during the resize, so fully transparent pixels don't bleed their RGB into the edge on a `preserve` path. The browser test proves it: opaque red beside fully transparent pixels whose stored RGB is pure green. Every seam pixel with alpha 16 or more has green ≤ 8, where an unweighted average would give roughly (1 − alpha) of 255.
- **An identity resize returns the same frame object and never loads ImageMagick.** Every cropped image takes this path, because `resolveSettings` has already made the rule `original` (R-D1).
- **Consumes its input,** like `edit.ts`. The pixel buffer of a new frame is owned, which is asserted as in `decode.ts`.
- **There is no output pixel cap.** The Functional Design leaves the pixel caps to the Technical Design, which doesn't set one for outputs. **Flagged, not invented.** The consequences, measured in Chromium during review:
  - A 1×2000 strip at fixed width 3000 asks for 3000×6,000,000. ImageMagick completes the resize, and only then does the output allocation throw `RangeError` ("Invalid typed array length"), which `worker.ts` reports as `out-of-memory`.
  - A 100×2000 image at fixed width 3000 **succeeds**, producing a 3000×60,000 frame of about 720 MB.

  So the out-of-memory path only catches absurd cases, and a plausible fixed width on a tall image can create a huge frame in the middle of a batch. This bears on R-I19 and the memory assumptions C2/C3, and whoever sets the caps should consider output size as well as input size.
- **Not wired into `executeJob`,** for the same reason as T23 and T24.

## Surprises

- **A stray Vite server on port 5173 broke every e2e run.** Another project's dev server was listening there. `playwright.config.ts` has `reuseExistingServer: true` locally, so Playwright silently used it, and every module import returned that project's `index.html` ("Failed to fetch dynamically imported module"). The already-green `edit.spec.ts` failed the same way. The tests passed using a throwaway config outside the repo that points Playwright at port 5199 (not committed, repo untouched). It's worth knowing if a whole e2e file fails at its first `import()`.
- None in the stage itself: every case passed on all three engines on the first run.
- **The hand-picked rounding cases all round down**, so on their own they would not catch `floor` in place of `round`. The grid property test does: in review, `floor` failed 517 checks and `ceil` 588. The grid test is the real guard on the rounding rule; don't remove it as redundant.
- **Review found that the first version of the browser tests couldn't detect a wrong filter or color bleed.** They compared with a tolerance of 30 at quadrant centers, which nearest-neighbor would also pass. The filter and bleed tests were added in response.

## What the next task should know

- **T26 (encode):** call `await applyResize(editResult.frame, job.settings.dimension)` after `applyEdit`, and drop the edited frame when a new one comes back. Resize runs after flattening, so a JPEG path resizes opaque pixels only.
- **R-X24/R-X45 (the original-substitution rule):** `needsResize(sourceSizeAfterEdit, settings.dimension)` reports whether a rule changes the image's size. R-X24 says "no dimension rule … applies". That could mean "no rule is set" or "no rule changes the image". For a fit-within rule the image already satisfies, the two readings give different answers. This note doesn't decide it; treat it as open.
- **T36 (Preview readout):** `resolveResizedSize(resolveEditedSize(source, ops), settings.dimension)` is the output size, and it matches the pipeline exactly.
- **T35 (Dimension field):** only positive whole-number pixel values are valid. Anything else throws.
- **Animated `resize-frames`** isn't built. `resolveResizedSize` applies per frame unchanged; the filter choice and frame loop are that task's.
- **Not measured:** time and memory of a 48 MP → 1920 resize. C2 and C3 (WASM heap during large operations) are where that belongs; the stage allocates the source copy into the ImageMagick heap, plus the resized image, plus the output buffer.
