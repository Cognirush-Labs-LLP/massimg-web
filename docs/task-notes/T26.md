# T26 — Still encoding

**Status:** complete with caveats.
- **AVIF has no usable lossless mode in this build (D9), so 96–100 is highest-quality 4:4:4 instead** — the slider value, capped at 99. A documented deviation from R-Q5, decided by the user. Functional Design §7.1's AVIF row still promises lossless and should be revisited.
- A CICP-signalled image going to JPEG or WebP fails as `unimplemented`, by the user's scoping decision.

## What was built

- **`pipeline/stages/encode.ts` encodes a still `Frame` to JPEG, WebP or AVIF.**
  - Effort is pinned (§7.3).
  - Lossless is used above 95 for WebP (R-Q5); AVIF cannot, see D9.
  - R-Q6's WebP comparison runs behind a unique-colour gate.
  - The ICC profile or CICP is carried through, and no metadata reaches the output.
- **Every decision is a pure function in `encode-plan.ts`, unit-tested in Vitest:** modes, defines, colour plan, gate, tie-break.
- **`executeJob` now runs the full still chain** (decode → edit → resize → encode) for JPEG, WebP and AVIF, so the shipped worker returns real bytes for the first time.
- **`verification/t26-encode/`** reproduces D2 in three browsers and calibrates the gate against 311 real images.

## Decisions made

- **Scope, decided by the user before implementation:**
  - T26 writes ICC and CICP-to-AVIF and wires `executeJob`.
  - CICP to JPEG/WebP (R-I35's "resolved into the pixels", with the `colour-converted` caveat) is left for a follow-up and fails as `unimplemented`.
- **Two CICP forms go to JPEG/WebP as untagged, not refused:**
  - **all-unspecified (2/2/2):** it carries no information.
  - **BT.709 primaries + sRGB transfer (1/13/any):** it says exactly what R-I14 already assumes of an untagged output.
  - The matrix is ignored for RGB outputs: it describes the source's YUV storage, which decode has undone. Anything else (P3, BT.2020, PQ, HLG, the BT.709 transfer, partly unspecified) is refused rather than written as sRGB.
- **WebP lossless leaves the quality unset.** libwebp then uses its default effort (75) with method 4.
  - Measured: an explicit quality alongside `webp:lossless` is *not* lossless in this build. With quality 75 the maximum error was 2 on opaque pixels and 175 on translucent ones.
  - `webp:exact` is not set. The colour of fully transparent pixels may change; they are invisible.
- **AVIF above 95 is the slider value with `heic:chroma 444`, not lossless, and the value is capped at 99.** The user chose this after the measurement; D9 records the evidence. 100 is AOM's lossless switch and its output is wrong in every browser, so the cap exists only to keep the encoder out of that mode — 96 still encodes at 96, and only 100 moves. Below 96, chroma stays at ImageMagick's default.
- **AVIF CICP output keeps the source's primaries and transfer and writes matrix 6**, plus `heic:preserve-cicp`. This build converts RGB to YUV with BT.601 whatever it labels the file, so writing the source's matrix tells decoders to invert a conversion that never happened — 10 units of error for a BT.709 label, 12 for BT.2020, against 3 for BT.601. The primaries and transfer are what describe the colour, and they are carried unchanged.
- **JPEG quality is the slider value, including 96–100** (§7.4). Chroma subsampling is left at ImageMagick's default.
- **The gate counts distinct RGBA values and stops at 65,536.** How the threshold was chosen, from the calibration data, is in D2. The gate runs on the frame after resize, so small images always try both encodes, and those attempts are cheap.
- **A tie keeps lossless**: same size, no loss.
- **An opaque frame has its alpha channel switched off before encoding.** AVIF otherwise writes an alpha plane even when every pixel is 255 (803 → 623 bytes on a small test). WebP already dropped it.
- **Every attempt reads the frame fresh**, so a quality set for the lossy attempt cannot leak into the lossless one, which depends on it being unset. The spike showed `removeDefine` works; the fresh read is still simpler and costs one copy.
- **`write`'s callback data is a view onto the codec heap** (measured), so it is copied and asserted owned, because the worker transfers it.
- **An unsupported colour is refused in `executeJob`, right after decode.** The colour is known as soon as the frame exists, so a job that cannot be encoded does not pay for an edit and a resize. `encodeFrame` checks again, since it is callable on its own.
- **Stage errors:** a decode that throws anything other than `RangeError` becomes `DecodeError` → `decode-failed`. Previously a corrupt source would have been reported as `encode-failed`.
- **`executeJob` keeps `ensureCodecsForJob` first**, ahead of the unimplemented checks: `codecs.spec.ts` observes that load for PNG and GIF jobs.
- **Caveats:** a run returns the edit stage's caveats (currently only `transparency-flattened`); a preview returns `[]`, per `protocol.ts`.
- **The verification harness has no dependencies of its own**, unlike t23. It serves `src/` through the repository's own `vite.config.ts`, so what it measures is the shipped module graph.

## Surprises

- **An explicit quality breaks WebP lossless**, as above. Every "lossless" WebP written with a quality set would have been silently lossy.
- **Lossless AVIF is broken in browsers, and my first round of tests could not see it (D9).**
  - ImageMagick read its own lossless output back within one unit, so the stage looked correct.
  - Decoded by the engines themselves: 5 units out on Chromium, 16 on Firefox, and **black on WebKit**.
  - The cause is the `full_range_flag` of 0 that comes with the identity-matrix `nclx` box, which no define can change. The ±1 I first recorded was that limited-range rescale, not codec loss.
  - **Found by review, not by me.** Every test in the first version decoded with the library that wrote the file. There is now one that decodes through the browser, which is what Preview (R-I16) and the downloaded file use.
- **The writer's matrix label and its actual conversion disagree.** Two independent decoders shifted the colour of a BT.709-labelled file. R-I35 exists to prevent exactly that shift, and the first version caused it while its test — which checked only that the CICP numbers read back — passed.
- **The D2 ratios do not reproduce; the direction does.** The original content is unknown, and content decides the ratio: the stand-in photograph loses lossless by 53x, real photographs by 12.3x–29.7x, the flat graphic wins by 12x. See the D2 entry.
- **The same canvas "screenshot" gives different colour counts per engine** (1,558 on Firefox, 1,633 on Chromium), and lossless wins by 2.8x and 1.2x respectively — the comparison, not a classifier, is what gets this right.
- **My WebKit screenshot row was a harness artifact, caught in review.** WebKit's `getImageData` returns alpha 254 on thousands of pixels of a fully opaque canvas drawing, so that frame was not opaque, carried a noisy alpha plane, and lost. D2 now excludes the row and says why. Nothing in the pipeline builds frames from a canvas, but anything that does would meet this.
- **Real photographs can have few colours.** 8 of 60 sampled JPEGs fell under 65,536 at 1600 px (minimum 15,808), so they pay about 1 s for a losing lossless attempt.
- **My first "lossy wins despite the gate" fixture was wrong.** Random pixels from a 256-colour palette compressed to 6 KB lossless against 72 KB lossy. The real case is a small photograph, which the e2e now uses.
- **Port 5173** is still occupied by another project's Vite server. The e2e runs used the port-5199 scratch config from T25 again.

## What the next task should know

- **`encodeFrame(frame, format, quality)`:**
  - `format` is `'jpeg' | 'webp' | 'avif'`, and `quality` must be `{ kind: 'quality' }`; `executeJob` rules out `size`.
  - `EncodeResult.attempts` and `uniqueColors` expose the gate's decision. They are not in `JobResult`.
- **T27 (PNG):**
  - R-Q14 mirrors R-Q6. `pickSmaller` and `countUniqueColors` are format-agnostic and can be reused.
  - `encoderAttempt`/`colourPlan` only know the three still formats.
  - Remove the PNG branch in `executeJob` when the path lands.
- **T28/T29:** the same for GIF and animated output. `unimplemented` stays in `JobFailure` until every branch is gone.
- **T30 (size targeting):** calls the encoder repeatedly. `encodeOnce` isn't exported; export a lossy-only entry point rather than going through `encodeFrame`, which would run the WebP comparison on every iteration. AVIF at speed 9 costs a few hundred ms per 1600×1200 encode here.
- **R-X24/R-X45 (original substitution) still has no owner task.** An AVIF larger than its input is returned as encoded (R-Q7). T25's open question on what "no dimension rule applies" means is still open.
- **The `metadata-removed` caveat has no producer.** R-I17 holds structurally: the output is built from raw pixels, and the e2e confirms no EXIF/XMP reaches it. Detecting that the *source* had EXIF/XMP/GPS, which the caveat needs, is unowned.
- **CICP → JPEG/WebP** needs a follow-up task: a source profile for the CICP primaries and transfer, a conversion to sRGB, and the `colour-converted` caveat.
- **`Cicp.fullRange` is still not written** (T23): `heic:cicp` has no field for it.
- **`RangeError` is still mapped to `out-of-memory`.** `encoderAttempt` throws `RangeError` for a quality outside 1–100, the same mislabel T25 flagged for dimensions; a validated panel can't produce one.
- **`decodeSource` turns any non-`RangeError` decode failure into `decode-failed`**, including ImageMagick's own resource-limit errors, which are `MagickError` rather than `RangeError`. Those are reported as a corrupt file. Narrowing it needs a reliable way to tell the two apart, which this task did not find.
- **`ResolvedSettings.quality.lossless` is still `true` for AVIF above 95**, because `domain/job.ts` implements R-Q5 and was not changed. The stage ignores it for AVIF. If anything user-facing reads that flag to say "lossless", it will be wrong for AVIF until D9 is resolved.
- **Spelling:** `colourPlan` and `UnsupportedColourError` use the UK spelling that `FrameColour` established in T23, while `countUniqueColors` and `LOSSLESS_GATE_MAX_COLORS` follow AGENTS.md's US English. The mix is deliberate — matching the neighbouring type names — but worth settling repository-wide at some point.
- **Only a browser-decode test can catch a mislabelled file.** Worth carrying into T27–T29: an ImageMagick round trip proves the bytes are self-consistent, nothing more.
- **Not measured:**
  - peak memory of encoding a large frame; the stage holds the frame, one heap copy per attempt and the encoded bytes;
  - AVIF encode time at 48 MP;
  - phones.
- **Re-running the harness:** from `verification/t26-encode/`, run `pnpm test`, or `T26_QUICK=1 pnpm test` for Chromium only with no calibration.
  - It needs the repository's root install.
  - The real-photo rows and calibration read `PHOTO_FIXTURES_DIR` and are skipped with a reason when it is unset.
  - It records dimensions, counts, sizes and times only, never names or paths.

## Requirements covered

- **R-Q5:** above 95 selects WebP's lossless mode, and it is exact. JPEG stays at quality as given, as the requirement says. **AVIF does not comply** and cannot in this build (D9); it encodes at quality 99 with 4:4:4 instead, by the user's decision.
- **R-Q6:** WebP below 96 attempts both encodes and keeps the smaller, behind a content gate. The e2e tests prove both directions and the skip, byte-identical to independent encodes.
- **R-Q7:** an AVIF larger than its input is returned as encoded; nothing suppresses it. The requirement is written about lossless AVIF, which this build cannot produce (D9), so what is proven is the general case rather than the one R-Q7 names.
- **§7.3:** AVIF `heic:speed` 9 on every attempt, proven byte-identical to speed 9 and different from the default and speed 6. WebP method 4, different from method 6. One gap: a *missing* WebP `method` define would still pass the byte comparison, because 4 is libwebp's own default; the unit test pins the define itself.
- **§7.4:** the quality mapping carried out per format.
- **§7.6:** D2 reproduced in three browsers; the gate is calibrated on real images and skips photographs.
- **By the user's scoping:**
  - R-I12 (ICC verbatim to JPEG, WebP and AVIF);
  - R-I14 (untagged adds nothing);
  - R-I35 for AVIF output only.
- **Structurally, and asserted:** R-I10 and R-I17's stripping half.
