# T36-B — Pixel-density-matched tab switching and forced regenerate switch

**Status:** complete

## What was built

The Preview inspector's Original/Compressed tab switch now preserves on-screen *pixel density*
rather than apparent box size. Previously, `scale` passed through the tab projection unchanged, so a
resized or cropped Compressed output was shown at the same apparent size as Original regardless of
how many real pixels either raster had — useful for "does this look about the same", useless for
judging compression quality pixel-for-pixel, which is what was asked for. Canonical scale is now
pinned to the Original tab's own convention (Original always has exact 1:1 pixel correspondence with
canonical space — no crop, no resize, and rotation only reshuffles axes), and only the
Compressed-side projections convert it, via a new `nativePixelsPerCanonicalPixel` ratio. The
conversion works from the very first, unzoomed view, using each tab's best *available* size —
decoded natural pixels once an `<img>` has loaded, the predicted size from settings before that —
not just once both rasters happen to have rendered.

Separately, any same-image settings- or edit-driven regenerate (quality, format, dimension rule,
rotation, crop — anything that causes a new Compressed output) now forces the Compressed tab to the
front at its own actual size, centred. This replaces the previous unconditional "viewport survives a
settings-driven re-encode" behavior for this one case: the product decision is that the user must see
the new Compressed result, not stay parked on whatever they were looking at (possibly on Original)
before it changed. Stepping to a different image is unaffected — R-P7's "stepper preserves the
selected tab" still holds, because the new trigger (`regenerateToken`) is bumped only on the
same-image branch of `usePreviewEncode`'s existing watcher, never on an image change or the initial
mount.

A density match may legitimately require more zoom than a tab's normal ceiling
(`effectiveMaxScale`) allows — e.g. zoomed deep into Original detail, then switched to a much
lower-resolution Compressed. Per product decision, this is now allowed to exceed the ceiling rather
than be clamped away on arrival; `PreviewFrame.vue`'s `zoomCeiling` raises itself to cover whatever
scale is actually in effect, rather than any clamping logic in `domain/viewport.ts` changing.

## Decisions made

- **Canonical scale is pinned to the Original tab's convention**, not left tab-agnostic. This was the
  one real design fork: once scale transforms per tab, "canonical scale" needs one fixed meaning, and
  anchoring it to Original (which always has ratio 1 to canonical, by definition — no crop, no
  resize) means `projectViewportToOriginal`/`unprojectViewportFromOriginal` need no change at all,
  halving the surface area of the change versus converting both directions symmetrically through a
  third neutral space.
- **A cross-tab density match is allowed to exceed the normal zoom ceiling** rather than being
  clamped. Implemented entirely at the `PreviewFrame.vue` layer (`zoomCeiling` rises to cover the
  current `viewport.local.value.scale`) rather than touching `clampViewportScale`/
  `resolveViewportFrameRect`/`zoomViewportAt`/`panViewport`, all of which stay scale-provenance-blind
  as before.
- **The forced regenerate-switch recentres (0.5, 0.5) rather than preserving the old pan point.**
  After a dimension- or crop-affecting change, the point the user was looking at may no longer
  correspond to anything meaningful in the new output, and `projectViewportToCompressed`'s own
  clamp-to-nearest-edge behavior for an out-of-crop point would otherwise land somewhere
  arbitrary-feeling rather than a deliberate centre.
- **The forced jump uses a placeholder-aware actual-size scale (`bestCompressedActualSizeScale`),
  not the stricter `actualSizeScale` the manual "Actual size" button uses.** Every regenerate starts
  from "Creating preview" — the new raster is by construction not decoded yet at the moment the jump
  fires — so requiring a real decoded size there would mean the jump almost always degraded to plain
  "Fit" instead of true actual size. The manual button keeps its stricter contract, since it should
  never claim a scale it cannot yet prove.
- **`regenerateToken` is a counter, not a boolean.** Two regenerates in a row with nothing else to
  diff against must each still be individually observable by a `watch`; a boolean toggling true/false
  could coincide and be missed.
- **Task numbering continues the `T36`/`T36-A`/`T37`/`T37-A` sub-letter lineage as `T36-B`** rather
  than consuming the plan's next untouched top-level number (`T43`, an unrelated Phase 7 step), since
  this is a direct continuation of T36's viewport work and depends on T37's crop/rotation geometry.
- **"Rest" is anchored lazily (`pristine`/`anchorIfPristine`), not synchronously inside `reset()`.**
  The frame's host is measured by a `ResizeObserver` callback that fires *after* mount, so `tabSizes`
  is usually still null the instant `reset()` runs; a plain `watch(options.tabSizes, ...)` (with
  `immediate: true`, for the rarer case sizes are already known) commits the tab-aware anchor exactly
  once per reset, the moment both tabs' sizes actually become available. `canonical.value ===
  DEFAULT_VIEWPORT` cannot be used as the "still untouched" signal — Vue wraps an object ref's value
  in a reactive proxy, so that reference-equality check is never true even right after the assignment
  — hence the separate plain-closure `pristine` boolean.
- **The zoom floor (`zoomFloor` / `minScale`) is symmetric to the existing zoom ceiling
  (`zoomCeiling`/`maxScale`), threaded through the same five domain functions and the same
  `PreviewFrame.vue` call sites.** Every one of those functions already took an optional `maxScale`
  for exactly this "a cross-tab value may legitimately exceed the normal range" reason; `minScale`
  needed the identical treatment at the other end rather than a one-off special case, and defaults to
  `MIN_VIEWPORT_SCALE` everywhere so no existing call site (or its tests) needed to change.

## Surprises

- An existing component-spec fixture (`PreviewFrame.spec.ts`'s old "carries the scale set by Actual
  size on one tab over to the other" test) happened to produce numerically identical results under
  both the old (apparent-size) and new (pixel-density) formulas, purely because its two natural
  sizes shared the host's own aspect ratio exactly — which makes `restBoxSize` coincide for both
  tabs regardless of how different their natural pixel counts are. The rewritten fixture deliberately
  uses a Compressed natural smaller than the host (so its restBox is its own true size) against a far
  larger Original, specifically so old and new behavior diverge and the test actually exercises the
  new logic.
- The real e2e regenerate test initially failed in a way that looked like a bug (image width snapped
  to 400px, the same as the pre-zoom rest state) but was exactly correct: that fixture image's natural
  size is already smaller than the test's frame host, so "actual size" and "fit" coincide for it. The
  test was rewritten to assert the self-consistent property (the "Actual size" button is disabled
  because the view is already there) rather than a hard-coded pixel width.
- Three unrelated e2e tests that click `preview-step-next` (`R-P7` stepper wrap, `R-B5` stepping
  release ordering, and the tail of this task's own rewritten regenerate test) fail identically on
  unmodified `main` in this environment — confirmed by stashing this task's changes and re-running.
  This is a pre-existing environment issue with the long-running reused dev server this session used,
  not a regression from this task.
