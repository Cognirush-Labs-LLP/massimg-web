# T24 — Edit stages

**Status:** complete with caveats — one open question on the transparency caveat's exact condition (see Decisions made), which changes one line if answered the other way.

## What was built

`pipeline/stages/edit.ts`: `applyEdit(frame, edit, alpha)` walks `EditRecord.ops` in array order over the upright RGBA `Frame` from T23, fills crop spill, and flattens surviving transparency when the resolved output format has no alpha. It emits the `transparency-flattened` caveat when it does. It is pure TypeScript with no codec, so it is unit-tested in Vitest: the §6 worked example is checked to the pixel against an independent oracle, including the 8000×6000 spill row, with all four quarter turns composed on top. A Playwright file proves R-I11 on a real EXIF-rotated decode and rotation agreement with the thumbnail renderer, and measures D5.

## Decisions made

- **Pure TypeScript, not ImageMagick.** Quarter turns, offset copies and a solid fill are byte moves. Doing them in TS makes the output agree with `resolveCropOutput` exactly, with no ImageMagick gravity, virtual-pixel or rounding behaviour in between. It also avoids a copy into and out of the WASM heap and keeps the module out of `codecs/loader.ts`, so it is unit-testable (the T22/T23 Vitest constraint doesn't apply). Rejected: `rotate()`/`extent()` in ImageMagick, which would have needed a browser test for every pixel assertion and would still have had to be reconciled against `domain/edit.ts`.
- **Flattening happens in this stage, after the ops, for every image**, including `edit === null` (white, per R-C17, already resolved by `domain/job.ts`). Doing it after the ops, with spill filled opaque under `flatten`, means the caveat reports exactly "source transparency that reached the output". A transparent stored crop background can't raise it falsely, and neither can a transparent region the crop discarded. Rejected: flattening before the ops, which would disclose flattening of pixels that never reached the output.
  **Open question for the user — this is a user-visible reading of R-X46.** R-X46 words the condition as "Source had transparent pixels, output format has no alpha", and calls the caveat set "not open to judgement at implementation time". This stage records it only when transparency *survives the edit*. The two differ only when a crop discards every transparent pixel: under the literal reading the report would say "flattened" when nothing was flattened. The implemented reading follows R-C17 ("where transparency will be flattened") and P1 (disclose what happened). It is pinned by `edit.spec.ts`'s "discloses nothing when the crop discarded every transparent pixel". If the literal reading is wanted, scan before the ops instead and flip that test. **T36 must use the same condition for the Preview transform line**, or Preview and report will disagree for such a crop. A line driven by `ImageRecord.hasTransparency`, which describes the source, would say "flattened" where this report does not.
- **Spill fill under `flatten` is `{ ...op.background, a: 1 }` per crop op.** For the single crop the UI produces, this equals `resolveSettings`'s flatten background. For a hypothetical multi-crop list, each crop uses its own colour.
- **Blend formula:** straight alpha, in the frame's encoded (non-linear) values, `round((c·a + bg·(255−a)) / 255)`, as ImageMagick `-flatten` and browsers composite. The background is written as given in the frame's own colour space and never converted (R-I15). So a picked colour on a Display P3-tagged frame is read as P3 by a colour-managed viewer. White and black are unaffected.
- **`Rgba` byte mapping:** r, g, b are rounded and clamped to 0–255; alpha 0–1 maps to `round(a × 255)`, so `0.5` → 128.
- **`applyEdit` consumes its input frame.** Flattening writes in place into whichever buffer is current, which is the caller's when no op replaced it. §8.1 makes decoded pixels the binding memory cost, and a defensive copy of a 50 MP frame is 200 MB. A frame whose pixels are *not* an owned buffer is copied first, so a view onto someone else's memory is never written to or passed on as owned.
- **Identity ops return the same frame object** (rotate 0; a crop with no spill, same size, zero offset). No allocation for "Apply" on an untouched image.
- **An unknown op kind throws `EditError`**, matching `thumbnail-render.ts`. `worker.ts` currently maps it to `encode-failed`; there is no closer `FailureReason`. An allocation failure for a huge spill output throws `RangeError`, which `worker.ts` already maps to `out-of-memory`, correctly.
- **Not wired into `executeJob`**, and `pool.spec.ts`'s `unimplemented` assertions are untouched, for the same reason T23 gave: no stage produces bytes yet.

## Surprises

- **Review found a real bug the oracle cases did not reach: a crop that misses the image to the right.** At low zoom, R-C12 keeps the rectangle inside the *frame*, not over the image, so the UI can place a crop wholly beside the image. With the source past the output's right edge, the copy span went negative. `subarray` then read the negative end as a from-the-end index and copied image pixels into what should be fill, or the offset overran the output and threw `RangeError`, which `worker.ts` would report as out-of-memory. Left, above and below were already fine, by the asymmetry of the arithmetic. It is fixed with an empty-intersection early return, plus five oracle cases (each side, and a diagonal one) and the reviewer's zoom-0.25 UI-built case. Three of those fail without the fix. The oracle itself was right; no case pushed `offsetX` past the output width.
- The oracle was checked by deliberate mutation: flipping the rotation direction failed 16 tests, and shifting the crop copy by one column failed 14. Both were reverted.
- **The 8000×6000 cases run in Node far faster than expected**: the whole test file, 16 table cases included (64 M pixels × 4 turns of per-pixel oracle checks), runs in about 4 s. No timeout was close.
- D5 turned out clearly cheap (see below). It was `OPEN` at 70%.

## What the next task should know

- Import `applyEdit`, `EditError` from `@/pipeline/stages/edit`. Call it as `applyEdit(decodedFrame, job.edit, job.settings.alpha)` and use the returned `frame` and `caveats`. **Don't reuse the frame you passed in.**
- **T25 (resize):** the frame you receive already has the edit and alpha handling applied. Resize after it, and skip the dimension rule when a crop exists (`settings.dimension` is already `original` then, via `resolveSettings`). Flattening happens *before* resize, so resize never sees translucent edges on a JPEG path.
- **T26 (encode):** `transparency-flattened` comes from this stage, not from the encoder. Pass this stage's caveats through to `JobResult.caveats` (empty for preview intent, per `protocol.ts`). Under `preserve`, the frame may carry translucent spill (`a < 255`) that the encoder must keep.
- **`ImageRecord.hasTransparency` (R-C13's default Transparent swatch)** is not set by this task. The pixel scan here only runs for `flatten`. The Edit-mode UI (T37) or the batch store still needs its own lazy detection. D5 says a full scan of a decoded frame is cheap, and the decode is the real cost.
- **R-C17's Preview transform line** (T36) can key off the `transparency-flattened` caveat on a preview job, but preview intent returns no caveats today (`protocol.ts`). T36 will need to decide how the transform line learns about it. It is not answered here.
- **Memory, for whoever wires the chain (T26):** drop the reference to the decoded frame before encoding. The stage allocates a new buffer per rotate and crop, and the caller holding the input is what keeps both alive. A half turn could reverse in place under the consumption contract, saving a full frame. That wasn't done because the unit tests deliberately share one 48 MB source across cases; worth doing if memory measurements (C3/C4) call for it.
- **`resolveCropOutput`'s `spill` bands are not literal strip widths** when the crop misses the image. `spill.left` can exceed the output width (e.g. 6000 on a 5000-wide output). `hasSpill` is still right; T37 should not draw those values as widths without clamping. This is pre-existing in `domain/edit.ts`, not changed here.
- The thumbnail renderer and this stage agree on rotation direction (browser-tested). The unit test pins a literal clockwise case, so a change to either shows up.
