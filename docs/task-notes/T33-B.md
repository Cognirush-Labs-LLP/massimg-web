# T33-B — Gallery, grid view

**Status:** complete

## What was built

The virtualized Gallery grid body that replaces the T31/T33-A placeholder in `Gallery.vue`'s
populated state, plus the populated-state header (title/meta/affordance line) above it, and the
first real consumer of T20's `platform/thumbnails.ts` — nothing before this task instantiated that
service anywhere in the app. Tiles show a bounded thumbnail, filename, `W×H · size`, badges
(`EDITED`/`ANIMATED`/`FAILED`) and a remove control; only visible-and-near-visible tiles are ever
requested, regardless of batch size.

## Files touched

- `src/ui/gallery/gridWindow.ts` (+ spec) — new. Pure, DOM-free windowing math:
  `computeGridLayout(containerWidth, itemCount)` (columns/tile width/row height/row count) and
  `computeGridWindow(layout, scrollTop, viewportHeight, itemCount)` (which item-index range to
  render vs. request, plus spacer heights). Table-driven Vitest coverage, same spirit as
  `domain/edit.ts`'s arithmetic.
- `src/ui/gallery/thumbnail-service.ts` (+ spec) — new. A lazy, module-scope singleton wrapping
  `createThumbnailService()`. Exists specifically so the encoded-thumbnail cache survives
  `GalleryGrid.vue` unmounting and remounting (every tile click, every Clear) rather than being
  thrown away and rebuilt each time — see Decisions made.
- `src/ui/gallery/GalleryTile.vue` (+ spec) — new. One tile: thumbnail or neutral placeholder,
  badges in fixed order, filename (ellipsis), `W×H · size` (UI size formatter, `_×_`/`Error` for
  an unresolved/failed dimension probe), and a remove button. Two sibling `<button>`s
  (`open-button`, `remove-button`), not a button nested in a button, so the remove control can sit
  on top without illegal HTML nesting.
- `src/ui/gallery/GalleryGrid.vue` (+ spec) — new. Renders only the current window's tiles inside
  a CSS grid (`repeat(columns, 1fr)`) bracketed by two spacer elements that hold scroll geometry
  steady. Listens for scroll/resize on the nearest `.stage-body` ancestor (no nested scroller).
  Recomputes the rendered window every scroll frame (cheap arithmetic); debounces the call to
  `thumbnailService.setVisible()` by 120ms of scroll inactivity. Calls `getThumbnailService().stop()`
  in `onUnmounted`.
- `src/ui/gallery/Gallery.vue` — edited. Populated branch now renders the header (title, mono meta
  line, affordance line — `docs/ui-design.md` §6's "Populated header row (Gallery, both view
  modes)") followed by `<GalleryGrid />`, replacing the `data-testid="gallery-placeholder"` `<p>`.
- `src/ui/gallery/ingest.ts` — edited. `clearGallery()` now also calls
  `getThumbnailService().clear()` (batch gone, release every Blob/URL). `removeIngestedImage(id)`
  now also calls `getThumbnailService().invalidate(id)` (release only that image's entry).
- `src/ui/gallery/Gallery.spec.ts` — updated: the placeholder assertion is now a
  `gallery-grid`/header assertion.
- `tests/e2e/gallery-ingest.spec.ts` — updated: its one `gallery-placeholder` assertion now checks
  for `gallery-grid`.
- `src/i18n/en/{messages,context}.json` — new keys: `gallery.meta`, `gallery.affordance`,
  `gallery.badge.{edited,animated,failed}`, `gallery.tile.{dimensionPending,dimensionError,meta,remove}`.
- `tests/e2e/gallery-grid.spec.ts` — new. Playwright, all three engines. Covers every Done-when
  clause: 500-image DOM-tile bound at multiple scroll positions, budget/placeholder behaviour with
  400 images against the 100 default, generation stopping on leaving Gallery, and removing one tile
  leaving the others' cache entries untouched.

## Decisions made

- **The `ThumbnailService` instance lives in a new module-scope singleton
  (`thumbnail-service.ts`), not inside `GalleryGrid.vue`'s own `onMounted`/`onUnmounted`.**
  Technical Design §1.1 states the one deliberate exception to "leaving a mode releases its data":
  the thumbnail cache may survive mode changes so returning to Gallery doesn't reread source files.
  `GalleryGrid.vue` unmounts on every tile click (→ Preview) and remounts on return; if the service
  lived in the component, that guarantee would be silently broken and every return trip would
  reread and re-encode every thumbnail. The singleton mirrors `ingest.ts`'s existing
  `probeService` pattern for the identical reason. Confirmed by manual test: `readsStarted` is
  identical before and after a Gallery → Preview → Gallery round trip, and the tile still renders
  its thumbnail immediately on return.
- **"Leaving Gallery" needs no explicit `stageMode` watcher**, unlike the dimension probe.
  `ToolPage.vue`'s `<component :is="stageComponent">` already unmounts `Gallery.vue` (and
  therefore `GalleryGrid.vue`) the instant `stageMode` changes away from `'gallery'`, which fires
  `onUnmounted` → `getThumbnailService().stop()` for free. The dimension probe needs its own watch
  because it runs independently of any mounted component; the thumbnail service's generation is
  intentionally tied to the grid component's lifecycle, so the existing unmount hook is sufficient.
- **Virtualization is hand-rolled, not a library.** No virtualization dependency exists in the
  project, and the grid's layout is simple enough (uniform tile aspect, a fixed meta-block height)
  that a small pure windowing module (`gridWindow.ts`) plus two spacer elements covers it without a
  new dependency. Column count is computed from measured container width rather than left to CSS
  `auto-fill`, because true windowing needs to know the column count up front to convert a
  scroll-row range into an item-index range.
- **The populated-state header (title/meta/affordance line) is built here, in `Gallery.vue`, not
  inside `GalleryGrid.vue`.** `docs/ui-design.md` §6 ("Gallery — grid view") is explicitly scoped
  to exactly T33-B's requirement set (R-G1–R-G6, R-G10, R-G12) and includes this header under
  "Populated header row (Gallery, both view modes)" — it isn't optional or someone else's task, and
  the "both view modes" wording is why it sits in `Gallery.vue` (shared by grid and list) rather
  than inside the grid-specific component, so T34's list body can reuse it unchanged.
- **`ResizeObserver` observes the `.stage-body` scroll host, not `GalleryGrid`'s own root
  element.** Tried observing the grid's own root first; it works functionally but throws
  `ResizeObserver loop completed with undelivered notifications` on WebKit, because the observed
  element's own block-size changes as a direct result of the callback (a width change reflows the
  row count, which changes total spacer height). Observing the ancestor whose size is set by the
  surrounding shell layout — and is not affected by anything this component renders — removes the
  self-referential loop entirely. Verified clean (zero page/console errors) on all three engines
  after the change.
- **Request buffer and render buffer are both one row.** Not specified numerically anywhere in the
  design docs beyond "visible and near-visible." One row of slack on each side is enough to avoid
  a visible pop-in during ordinary scroll speeds without meaningfully growing the thumbnail
  request window; not measured against real-device scroll velocities, so worth revisiting if a
  future task finds pop-in on a slow device.
- **Tile meta-block height (44px) is a fixed constant**, not measured from the real rendered DOM.
  Used for the windowing math's row-height estimate; a small mismatch between this constant and
  the real rendered height only affects spacer sizing (a few pixels of scroll-position drift), not
  correctness — self-corrects every scroll frame since the window is recomputed from real
  `scrollTop` each time, not accumulated.

## Surprises

- **A hand-rolled 1×1-pixel PNG fixture (reused from `gallery-ingest.spec.ts`, valid enough for
  `classify()`'s magic-byte check) silently failed thumbnail generation** —
  `createImageBitmap(blob, { resizeWidth: 1, resizeHeight: 1, ... })` never produced a usable
  result for it on Chromium, and `readsStarted` incremented while `retained` stayed `0` with no
  thrown error anywhere (the service's own design treats every decode failure as "show a
  placeholder," so this failed silently and looked identical to a wiring bug at first). Replaced
  with `OffscreenCanvas`-synthesized bytes at a real size (64×48), the same convention
  `tests/e2e/thumbnails.spec.ts` already uses, which decodes cleanly on all three engines. This is
  a fixture-construction gotcha, not a `GalleryGrid`/`thumbnails.ts` bug — worth remembering for
  any future test that needs a *decodable* image rather than just a *classifiable* one.
- **`ResizeObserver loop completed with undelivered notifications` on WebKit** — see Decisions
  made above. Not encountered on Chromium or Firefox; WebKit surfaces it as an uncaught page error
  where the others apparently either don't hit the loop condition or don't report it the same way.

## What the next task should know

- **T34 (Gallery, list view):** the populated-state header (title/meta/affordance line) already
  lives in `Gallery.vue`, shared by both view modes per `docs/ui-design.md` §6 — reuse it as-is
  rather than duplicating it inside a new list body. The grid/list toggle still belongs in
  `GalleryToolbar.vue`, unchanged by this task. `GalleryGrid.vue`'s `onUnmounted` already stops
  thumbnail generation, so switching to list mode only needs `Gallery.vue` to stop mounting
  `GalleryGrid` (e.g. `v-if="galleryView === 'grid'"`) — no new stop-wiring required, the existing
  unmount hook covers it. Do not call `getThumbnailService().clear()` on a switch to list mode; only
  `stop()` (via unmount) is correct there — `clear()` is reserved for an actual batch clear.
- **T36 (Preview) / T37 (Edit):** `removeIngestedImage`/`clearGallery` already keep the thumbnail
  cache in sync (invalidate/clear respectively) on the paths this task built. An edit changing an
  image's `EditRecord` is **not yet wired** to `getThumbnailService().invalidate(id)` anywhere —
  R-G4 ("thumbnails reflect stored rotation and crop") is satisfied for the *initial* render (the
  service's render pipeline replays `edit.ops` when generating a thumbnail), but if T37 mutates an
  existing image's `edit` in place after its thumbnail is already cached, that cached thumbnail
  will not refresh until T37 calls `getThumbnailService().invalidate(id)` itself after applying an
  edit. This task did not need to touch that path (no edit UI exists yet to trigger it), but T37
  should not assume it's handled.
- **T50 (Limits):** `maximumThumbnails`'s default (100) is still read from `runtimeLimits` exactly
  as T20 left it; nothing in this task hard-codes it. The grid's own render/request buffer sizes
  (`RENDER_BUFFER_ROWS`, `REQUEST_BUFFER_ROWS` in `gridWindow.ts`) are new constants this task
  introduced and are not currently part of the runtime limits module — they're presentation
  tuning, not a measured limit, so left as local constants; flag if a future measurement task wants
  them configurable too.

## Requirements covered

R-G1 (tile click opens Preview via `useUiStore().openPreview`), R-G2 (removing one tile leaves
others untouched — proven in `GalleryTile.spec.ts` and the Playwright suite), R-G3 (thumbnail
Blobs bounded and released on remove/clear — the source-file half was T33-A's, the thumbnail-Blob
half is this task's), R-G4 (thumbnails reflect stored rotation/crop — via the existing render
pipeline; see "What the next task should know" for the one edit-time gap), R-G5 (insertion order
preserved — grid renders `useBatchStore().images` directly, never re-sorted), R-G6 (Clear now also
releases every thumbnail Blob), R-G10 (lazy, budgeted, non-evicting, virtualized generation —
proven with 400/500-image Playwright fixtures), R-G12 (generation stops the instant Gallery is
left — proven via the real unmount path, not just the underlying service's own `stop()`). R-G7–R-G9
and R-G11 (view-mode toggle, automatic threshold, list mode, directory grouping) remain T34's, as
`docs/tasks.md` specifies.
