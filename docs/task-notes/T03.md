# T03 — WASM memory reclamation in a browser

**Status:** complete

## What was built

A throwaway Playwright harness at `verification/t03-wasm-memory/` that loads `@imagemagick/magick-wasm`
0.0.43 in a real Chromium tab (served over `http://127.0.0.1`, not `file://`) and processes a sequence of
synthetic images of increasing size — 0.48 MP up to 80 MP, including the required >40 MP case at 48 MP —
disposing between each, then repeats the 48 MP image 25 times in the same tab to distinguish "grew because
it needed to" from "leaking." After every image it records the WASM linear memory size
(`WebAssembly.Memory.prototype.buffer.byteLength`, read from inside the page) and a browser-engine-agnostic
"tab memory" proxy (summed RSS across the browser's whole OS process tree, sampled via `ps` from the Node
side). `docs/assumptions.md` C2 is updated in place with the results: confidence raised from 75% to 92%,
conclusion **no worker recycling is needed**.

## Decisions made

- **x64 build + `initializeImageMagickx64`, not the default `initializeImageMagick`/x86 pairing.** The
  package ships two paired variants: `initializeImageMagick` with `dist/x86/magick.wasm`, and
  `initializeImageMagickx64` with `dist/x64/magick.wasm`. Pairing the wrong initializer with the wrong
  binary (e.g. the generic `initializeImageMagick` with the x64 `.wasm`) produces a `LinkError: ... Import
  #122 "a" "ob": function import requires a callable` at instantiate time — a confusing error that looks
  like a broken build but is just the mismatched pairing. Used the x64 pairing since it's the more
  capacious variant and this task specifically wants to push large pixel counts. **Note for whoever owns
  B7** (`x64 build requires memory64`, currently 80% TESTED, method still open): this task instantiated the
  x64 build successfully in Chromium up to a 407.7 MB heap with no failure, which is direct evidence toward
  B7's "attempt instantiation of the x64 build in each target browser" method — but doesn't by itself
  confirm or refute the memory64 hypothesis, since 408 MB never approaches any wasm32-vs-memory64 ceiling
  difference (4 GB vs. much larger). Left B7 untouched per this task's scope (C2 only); flagging here so
  whoever closes B7 has this data point.
- **Capturing `WebAssembly.Memory` by monkey-patching `WebAssembly.instantiate`/`instantiateStreaming`.**
  The library's Emscripten glue doesn't expose the memory object through its public API, and the exported
  member isn't literally named `memory` in this build's export table (had to iterate `instance.exports`
  and pick the value that's `instanceof WebAssembly.Memory` — the plain `instance.exports.memory` lookup
  came back `undefined`). Patching both entry points (the code has a streaming-fetch path with a
  non-streaming fallback) and stashing whichever instance shows up was the reliable way to get at it
  without forking the library or reading its internals more invasively.
- **Synthetic images built directly in ImageMagick** (`ImageMagick.read(color, width, height, cb)`) rather
  than authoring or decoding real encoded files at these sizes. The task memo explicitly allows this since
  the point is decoded-pixel-buffer memory behaviour, which a solid-colour canvas exercises identically to
  decoding a same-size real photo (ImageMagick allocates its pixel cache the same way regardless of pixel
  values). Each image is then resized to half its dimensions and written to JPEG before disposal, so the
  lifecycle matches "decode → process → encode → dispose," the shape the real pipeline will use.
- **Process discovery via Playwright's `launchPersistentContext` + a "not `ps`" filter, not
  `browser.process()`.** The installed Playwright (1.63.0; the repo pins `^1.48.0` but nothing pins an
  upper bound yet since T05 hasn't run) has no `Browser.process()` accessor at all — that API is gone in
  this version. Also, `chromium.executablePath()` reports a path that doesn't match the actual binary
  Playwright launches under `headless: true` (it launches `chrome-headless-shell`, a different binary, not
  the path `executablePath()` names), so matching on that path doesn't work either. What does work: launch
  via `launchPersistentContext` (a plain `launch()` refuses `--user-data-dir` in `args` now — Playwright
  wants `launchPersistentContext(userDataDir, opts)` instead), wait ~500ms for child processes to fork, then
  take the one direct child of this Node process that isn't a `ps` invocation this script itself spawned.
  Everything under that root PID (renderer, GPU, network service — Chromium is multi-process even
  headless) is summed by walking `ppid` links from a single `ps -A -o pid=,ppid=,rss=` snapshot.
- **`--js-flags=--expose-gc --expose-gc` on launch**, and calling `window.gc()` after each disposal before
  the final heap-size read, to give the JS/wasm engine its best chance to actually reclaim before sampling,
  rather than measuring an artifact of lazy GC timing.
- **One engine (Chromium) only.** The assumption's method doesn't ask for cross-browser coverage the way B4
  does, and the task memo says one engine is the natural choice here.
- **25 repeats at 48 MP for the stress phase**, not more. Chosen because the first repeat already showed a
  flat heap (no growth at all versus the ramp phase's final 80 MP reading), and 25 consecutive flat readings
  with tab RSS also flat is a strong enough plateau to draw a conclusion from without spending significantly
  more wall-clock time on marginal additional evidence. If this were still ambiguous at 25, the next move
  would be more repeats and/or a bigger single image, not a different technique.

## Surprises

- **`WebAssembly.Memory`'s buffer cannot shrink** — there is no shrink instruction in the WebAssembly
  spec, only `memory.grow`. This means the assumption's literal pass condition ("the figure returns near
  its starting level") can never be satisfied by the WASM heap number once it has grown, regardless of how
  well disposal works. The updated C2 entry explains the reinterpretation: growth that happens only when a
  bigger image needs more headroom is expected and not a leak signal; the real signal is whether the heap
  *stops* growing under repeated processing of a constant-size image (it does — see Phase 2, flat at 407.7
  MB across all 25 repeats).
- The x86/x64 initializer-mismatch `LinkError` (see Decisions made) cost some time to diagnose — the error
  message gives no hint that it's a pairing problem, and it aborts the whole module (subsequent calls
  aren't possible; the Emscripten instance is left in an aborted state).
- Actual numbers were cleaner than expected: zero heap growth and near-zero (±0.2%) RSS drift across all 25
  stress repeats, with no crash even pushing a single image to 80 MP. Given C2's prior 75% (pinned to a
  Node proxy considered weak specifically because it might not reflect the browser), this is a notably
  stronger and more unambiguous result than "the Node number probably roughly holds in a browser too."

## What the next task should know

- The x64/x86 initializer pairing gotcha above is worth remembering for T04+ when the real app wires up
  magick-wasm for real: get the `initializeImageMagick*`/`.wasm` pairing right the first time, since the
  failure mode is a cryptic `LinkError`, not a helpful message.
- The harness's technique for reading the live WASM heap (patch `WebAssembly.instantiate` /
  `instantiateStreaming`, find the exported `WebAssembly.Memory` by `instanceof` rather than by export
  name) is reusable if a later task needs the same figure — e.g. C3/C4's per-image and per-platform limit
  work, or C8 (three WASM modules coexisting).
- The "tab memory via summed OS process-tree RSS, sampled with `ps`" technique in `run.mjs` (see
  `findBrowserRootPid`, `treeRssKB`, `withPeakRss`) is engine-agnostic and doesn't depend on any
  Chromium-only API (`performance.memory` was deliberately avoided) — reusable for Firefox/WebKit if a
  future task needs cross-engine memory figures (e.g. closing B7's browser-support column, or C3/C4).
- `verification/t03-wasm-memory/public/vendor/` is generated (gitignored) — anyone re-running this harness
  needs `pnpm install` then `pnpm test` (which runs `copy-assets.mjs` via `pretest`), not a manual copy.
- Left B7 (`x64 build requires memory64`) untouched even though this task incidentally instantiated the x64
  build successfully in a browser — that's a relevant data point for whoever closes B7, noted above under
  Decisions made, but out of this task's scope to edit.
