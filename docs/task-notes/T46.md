# T46 — Progressive Web App and usage visibility

**Status:** complete. **Later change:** the in-page beacon (`useAnalyticsBeacon.ts`, `src/config/analytics.ts`, `VITE_CF_BEACON_TOKEN`) and its unit test were removed; Cloudflare now injects the analytics script at the edge. `tests/e2e-pwa/pwa.spec.ts` now only checks that the shell loads offline from the service worker cache. See Technical Design §12.6 and assumption F2.

## What was built

A generated service worker (`vite-plugin-pwa`, `generateSW` strategy) makes the app
installable and usable offline after a first visit, reusing T43's existing hand-authored
`public/manifest.json` unchanged except for its `name`, which the user asked to be
"Mass Image Compressor Lite" rather than "Mass Image Compressor". A cookieless,
anonymous pageview beacon (Cloudflare Web Analytics) now fires on every production page
load, built against a placeholder token (`VITE_CF_BEACON_TOKEN`) tracked in T51-A for
later replacement. `docs/assumptions.md`'s F2 is resolved (90%, Chromium/Firefox
directly verified; see Surprises for why not WebKit).

## Decisions made

- **`generateSW`, not `injectManifest`** — this is a static-hosted app with no server
  (T52: Hostinger), which is exactly what `generateSW` is for, and T46's own task text
  already calls it "a generated service worker."
- **`workbox.globPatterns` explicitly excludes `.wasm`.** Workbox's own default
  (`**/*.{js,wasm,css,html}`) would put every codec `.wasm` file — including the 14.8MB
  ImageMagick build (confirmed by reading `dist/` directly) — in scope for precaching at
  install time, past the 2MB default ceiling. This plugin version (`vite-plugin-pwa@2.0.0`)
  turns that into a **hard build error**, not a warning (confirmed by reading its
  `showMaximumFileSizeToCacheInBytesWarning`/`throwMaximumFileSizeToCacheInBytes` option
  docs in `node_modules`). Scoped `globPatterns` to `js`/`css`/`html`/`manifest.json`/
  icon PNGs instead, and added a `CacheFirst` `runtimeCaching` rule for `.wasm` so each
  codec still gets cached the first time it's actually fetched — which, per T22, already
  happens shortly after first paint for ImageMagick and on first use of that format for
  the rest. Verified empirically (see Verification below), not just reasoned about.
- **Manifest stays hand-authored** (`manifest: false`) — T43 already built and linked a
  correct one; nothing about it needed the plugin to manage it.
- **`injectRegister: 'auto'`, no manual `virtual:pwa-register` import.** Verified by
  reading the built output that the injected registration script lands in every
  vite-ssg-prerendered route page (`index.html`, `faq.html`, `privacy.html` all checked
  directly), the same way `useRouteSeo.ts`'s per-route `useHead` calls already prove
  Vite's HTML-transform pipeline runs per route, not once. Avoids a hand-rolled
  `onMounted`/SSR-guard entirely — there's no `virtual:pwa-register` import in app code
  for `vite-ssg`'s Node prerender pass to trip over.
- **Beacon script declared via `useHead`, in `App.vue` (not per-route).** SSR-safe, so
  it's baked directly into every prerendered route's static HTML — confirmed by reading
  `dist/*.html` after a build. Mounted once at the root rather than inside
  `SiteShell.vue`'s per-route call, since it doesn't vary by route.
- **Beacon gated on `import.meta.env.PROD`.** Not in the original plan — added after the
  full e2e suite surfaced a real regression (see Surprises). Firing a real request at
  Cloudflare during `pnpm dev` or any test run was always going to be either pointless or
  actively disruptive; gating it to production builds only is the correct behaviour, not
  just a regression fix.
- **F2's test runs against a second, separate Playwright config, not the main one.**
  `playwright.config.ts` deliberately runs every spec against the plain `vite` dev server
  (T05's recorded decision, to avoid paying for a full build on every e2e run) —
  but a dev-server SW has no real precache manifest to test against, since
  `vite-plugin-pwa`'s generated SW is a production-build artifact. Rather than bend T05's
  policy for every spec or skip F2, `playwright.pwa.config.ts` + `tests/e2e-pwa/` pay for
  one `pnpm build` and run only this one spec against it.
- **`page.waitForFunction('navigator.serviceWorker.controller !== null')` as a string,
  not a typed arrow function.** `tsconfig.node.json` (which covers `tests/**/*.ts`) sets
  `lib: ["ES2022"]` with no `"DOM"` — `Navigator.serviceWorker` isn't among the ambient
  browser globals Playwright's own types otherwise provide for `evaluate`/
  `waitForFunction` callbacks (confirmed by a failing build before this change). A string
  expression sidesteps type-checking the browser-side code entirely, which is what
  Playwright's API supports this for.
- **T51-A gets the real env var name/file, not a vague description** — the whole point
  of that task is a literal, groppable checklist; a bullet that just said "the Cloudflare
  token" without naming `VITE_CF_BEACON_TOKEN`/`src/config/analytics.ts` would defeat it.

## Surprises

- **The beacon broke 30 existing e2e tests before the `PROD` gate was added.** Because
  `useHead` bakes the script into every build including the one the main e2e suite runs
  against (`pnpm dev`, port 5173), the beacon tried to fire a real cross-origin request
  on every test's page load. The dev server's origin isn't Cloudflare-CORS-allowed, so
  this surfaced as a CORS console error, which ~30 unrelated tests caught because they
  assert captured console output is empty. Caught by running the full
  `pnpm test:e2e --project=chromium` suite (not just this task's own new test) before
  calling the task done — exactly the T43-established lesson about chrome/app-wide
  changes needing a full-suite check, applied here to a non-visual change instead of a
  layout one. Fixed properly (gate on `import.meta.env.PROD`), then re-ran the full suite
  twice — once with my changes, once on a `git stash`-reverted `main` — and got the
  *identical* 8 failures both times (one of them is `app.spec.ts`'s already-documented
  pre-existing Tab-cycling flake from T43's own notes), confirming no new regression.
- **WebKit cannot run F2's test at all, with or without this app's service worker.**
  `context.setOffline(true)` followed by *any* navigation — reproduced with a two-line
  spec with no service worker, no beacon, nothing app-specific — throws `"WebKit
  encountered an internal error"` in Playwright 1.63's WebKit driver. Confirmed this is
  the Playwright/WebKit automation layer, not real Safari: the error-context snapshot
  taken at the moment of failure shows the app fully rendered underneath. `webkit` is
  dropped from `playwright.pwa.config.ts`'s projects and from the new CI job's matrix,
  with a comment pointing here. F2's confidence is 90%, not 100%, for exactly this
  reason — see `docs/assumptions.md`.
- Workbox's **default** `globPatterns` (`**/*.{js,wasm,css,html}`) would have silently
  tried to precache all four real codec `.wasm` files, not just ImageMagick's 14.8MB
  one — this wasn't obvious from either task text or Technical Design §12.6, only from
  reading `workbox-build`'s own type declarations directly, before the first
  `pnpm build` attempt (hypothetically) would have hard-failed on it.
- **`gifsicle-wasm-browser` has no separate `.wasm` file at all** — `node_modules`
  shows its entire package is one 336KB JS file (its WASM is inlined inside it,
  base64-style), confirmed by inspecting the package directly. It's already covered by
  ordinary precache (it's just a `.js` file matched by `globPatterns`) without needing
  the `CacheFirst` rule at all — only ImageMagick, oxipng, imagequant and
  apng-optimizer fetch a genuine separate `.wasm` URL.
- **The user asked, after this task's first pass, whether the *other* codecs'
  `.wasm` — not just ImageMagick's — were actually caught by the `CacheFirst` rule, and
  whether ETag revalidation mattered.** Worth recording that this wasn't covered by F2's
  test and had only been reasoned about from source, not directly verified, until asked.
  Verifying it directly (fetch each real `.wasm` asset against the live SW, inspect
  Cache Storage) surfaced a real timing trap worth remembering for any future test like
  it: Workbox's strategies hand the response back to the page as soon as it's
  available, then write to Cache Storage separately via the SW's own
  `event.waitUntil()` — for ImageMagick's 14.8MB file, checking the cache *immediately*
  after the fetch resolves is a **false negative**, not evidence the rule missed it; the
  write is still landing. `tests/e2e-pwa/codec-wasm-caching.spec.ts` polls instead of
  checking once, which is the general fix for this class of check. Confirmed clean on
  both engines once fixed: all four `.wasm` files land in `codec-wasm`, and a fully
  offline re-fetch of every one still succeeds — CacheFirst never revalidates against
  the origin's ETag, consistent with the content-hash-in-filename cache-busting this
  app (and T52) already relies on for every hashed asset.

## What the next task should know

- **T49 (Privacy, credits and source): what the beacon actually collects**, so R-V1/R-V3's
  real copy can be written directly instead of guessing. Cloudflare Web Analytics is a
  pageview-only beacon: it reports page loads/navigations, referrer, and Core Web
  Vitals-style timing, cookielessly and without any cross-site or per-user identifier. No
  custom events exist (and none were added — see the user's own earlier decision in this
  project's history to defer any richer "images compressed/size reduced" telemetry until
  a real backend exists). T46 did **not** edit R-V1's line itself — it doesn't exist yet,
  since T49 (which this task doesn't depend on) is what writes it.
- **T51-A needs the real Cloudflare token before release**, in `.env`'s
  `VITE_CF_BEACON_TOKEN` (read by `src/config/analytics.ts`). Until then, the beacon
  fires against a placeholder token in every production build — it will send requests
  that Cloudflare's backend will reject, which is harmless but means no real analytics
  data exists until T51-A runs.
- **`pnpm test:e2e:pwa` is a new, separate command** from `pnpm test:e2e` — it is not
  included in the default `pnpm check`/`pnpm test` flow and must be run explicitly (CI
  runs it as its own `e2e-pwa` job).
- **Any future task that changes `workbox.globPatterns`/`runtimeCaching` in
  `vite.config.ts`** should re-run `pnpm build` and grep `dist/sw.js`'s
  `precacheAndRoute([...])` call directly, the way this task did, rather than trusting
  the plugin's default — this app's 14.8MB+ of codec WASM makes the default precache
  scope actively dangerous, not just suboptimal.
