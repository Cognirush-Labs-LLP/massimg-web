# T42-A — Clear temporary data and start again

**Status:** complete with caveats

## What was built

Completed Processing now offers an optional cleanup row after Download started or Shared, with the
Dimension-style question-mark help dialog. The final user preference is a secondary outlined button
matching **Download again**, on its own row, rather than the originally planned plain text button.
Cleanup awaits output deletion and atomic source deletion before releasing the captured batch and
returning to empty Gallery; settings survive, and failures remain on completion with retry and
nonurgent manual-cleanup guidance.

Output storage now uses page-owned directories protected by the same lifetime Web Lock as source
copies. Startup removes abandoned owners without using age or inactivity heuristics, and preserves
live tabs and legacy unowned output storage.

## Decisions made

- Apply the user's final styling correction: reuse the existing secondary `.action` class from
  Download again. Permit the longer cleanup label to wrap on narrow screens. Keep its description,
  help affordance, and separate row; do not add a confirmation dialog.
- Use `icompress-output-sessions/<owner>/` instead of nesting beneath `icompress-run`. An older
  open build can still recursively delete its old root, so sharing that root would defeat isolation.
  The legacy directory is deliberately untouched; it may remain until the older build cleans it or
  the user clears site data. The action clears the current batch, not every app/site artifact.
- Keep output API signatures unchanged and source database rows unchanged. Introduce no dependency,
  new ownership protocol, expiry timer, or background janitor.
- Source deletion is last and atomic. If output removal fails or source deletion aborts, selected
  sources remain readable. A failed attempt disables Download again because outputs may be gone or
  partially deleted; Back to images remains available after the attempt settles.
- Capture image/copy IDs and retain component/run guards. Include unpublished sources and pending
  writes from a selection that was still importing when Processing started. A cleanup finishing after navigation can
  remove its intended old records, but cannot reset a newer run or clear newly selected records.
- A browser handoff is not proof that external reads finished. The wording explicitly asks users
  to finish saving/sharing first, and documentation does not promise immediate, complete, or secure
  deletion. Offline caches, settings, originals, and already-saved external copies are not targeted.

## Surprises

- The new storage-draining regression exposed a genuine archive race: closing the ZIP entry queue
  ended production but did not await the writer. A late flush could recreate the in-memory archive
  after cleanup or race an OPFS delete. Awaiting the writer before deletion fixes it. The new test
  failed before that correction and passes afterward; no separate unchanged-main run was needed to
  fix this within the task, and no existing assertion was weakened.
- WebKit can release a closed tab's lease asynchronously. The new ownership test polls cleanup
  until the lease is actually released rather than assuming `page.close()` releases it immediately.
  This is test synchronization, not an age-based production cleanup rule.
- Editing a live Vue component during a browser run triggered HMR and restarted a completed run,
  invalidating one new two-tab UI check. The final focused run used stable application code and
  passed. Initial new-test typing/evaluation issues were corrected without weakening assertions.
- The phone's localhost preview initially loaded an older service-worker-cached build. Its asset
  hash differed from the served build and it still used legacy output storage. That run is excluded
  from feature verification. A local-preview-only service-worker bypass loaded the verified build;
  the user reselected images there. The public deployment was never changed.
