# T41 — Report generation

**Status:** complete

## What was built

`image_compression_report.txt` is now written for real, from real run data, as the last entry in
the archive every multi-image run already assembles. T15's pure `domain/report.ts` model and
serializer needed no changes — only new, additive, hardcoded-English formatters (quality/format/
dimension settings, `FailureReason`, `RejectionReason`, a run timestamp). A new `stores/run.ts`
field records every success's exact bytes (not just caveated ones), a new `pipeline/run-report.ts`
joins the run/batch/settings stores into a `ReportSource`, and `run-archive.ts`'s `finish()` gained
one optional parameter to append the report as a trailing ZIP entry before the queue closes.

## Files touched

- `src/domain/report.ts` — added `formatFailureReason`, `formatRejectionReason`,
  `describeReportSettings` (quality/format/dimension → hardcoded English), and
  `formatReportTimestamp`. `ReportSource`/`buildReport`/`serializeReport` are unchanged.
- `src/domain/report.spec.ts` — new tests for the four additions above.
- `src/stores/run.ts` — added `successes: RunSuccessEntry[]` (imageId + exact input/output bytes
  for every success, not just caveated ones) and `runStartedAt: Date | null`, both reset in
  `startRun` and populated in `recordResult`.
- `src/pipeline/run-report.ts` (new) — `buildRunReportEntry()`, no parameters. Reads
  `runStore`/`batchStore`/`settingsStore` directly and returns `{ path, bytes }` ready for the
  archive sink.
- `src/pipeline/run-report.spec.ts` (new) — real-store integration tests: totals reconciling across
  successes/failures/skips/rejections, rejection ordering, exclusion of batch-/folder-wide
  rejections.
- `src/pipeline/run-archive.ts` — `RunArchiveSink.finish()` takes an optional
  `{ path, bytes }` and, when given and a ZIP queue exists, pushes it as the final entry before
  closing. A no-op when there's no queue (a 1-image run).
- `src/pipeline/run-archive.spec.ts` — two new cases: the report entry lands last; it's silently
  ignored for a single-image sink.
- `src/ui/processing/useProcessingRun.ts` — one call site: `sink.finish(multiImage ?
  buildRunReportEntry() : undefined)`, replacing the bare `sink.finish()`.
- `src/ui/processing/useProcessingRun.spec.ts` — two new integration tests that run the *real*
  (non-mocked) archive/OPFS-fallback path end to end: a multi-image run's real archive Blob
  contains the report's YAML text and its exact `Succeeded`/`Failed` counts; a 1-image run never
  writes an archive at all (R-X16).

No i18n, Vue component, or `platform/opfs.ts` changes — the report rides the existing ZIP queue and
R-L3 keeps it out of the translation system entirely.

## Decisions made

1. **`domain/sizes.ts`'s `BYTES_PER_UNIT = 1000`** (not 1024, despite R-X32/§9.3's literal
   wording) is correct as shipped — confirmed with the user. It predates this task (T15) and was a
   deliberate choice (OS file managers show decimal sizes); the doc wording is what's stale. Left
   both code and docs untouched; flagging here again in case a future task "fixes" this.
2. **Selection-time rejections (R-X9/R-I2) are read from `batchStore.rejections` as-is**, at
   report-build time — confirmed with the user. That store is dismissible and replaced wholesale
   per selection (T39's decision), so a dismissed or superseded rejection simply won't appear in
   the report. Not treated as a bug: building a durable, non-dismissible, accumulating log was
   considered and explicitly declined.
3. **Rejections merge into the existing `skippedImages` field**, not a new `ReportSource` field —
   `ReportSkippedImage.reason` was already `string | SizeTargetSkipReason`, so a pre-formatted
   rejection string fits directly. This means `buildReport`'s `Skipped` count and `Images processed`
   total automatically include rejections with zero changes to `buildReport` itself. Reading of
   R-X34: it groups "format we cannot handle" and "size ceiling unreachable" into one
   undifferentiated Skipped category; R-X9's "not represented in the counter" is read as the live
   Processing progress counter (R-X3/R-X4), not this end-of-run report.
4. **Batch-/folder-wide rejections are excluded from the report** (`batch-count-exceeded`,
   `folder-empty`, `folder-depth-exceeded`, `folder-file-count-exceeded`) — they have no single
   associated file (`RejectionEntry.name === null`) and don't fit the report's per-file row shape.
   Only `unhandled`, `heic-decoder-unavailable` and `file-too-large` (always file-named in
   practice) are included.
5. **A new `successes` array in `runStore`**, rather than refactoring `domain/report.ts`'s
   `ReportSource`/`buildReport` to accept pre-aggregated totals. `buildReport` sums
   `inputBytes`/`outputBytes` by reducing over every success (not just caveated ones), but the
   store previously only kept running aggregate sums plus a caveats-only array. Extending the store
   (mirroring its own existing `failures`/`skipped`/`caveats` pattern) kept T15's
   already-reviewed-and-tested model/serializer completely untouched, at the cost of one small
   parallel array.
6. **`buildRunReportEntry()` takes no parameters**, reading `settingsStore` directly rather than
   having its caller pass the frozen `BatchSettings` snapshot it already built. Safe because
   Processing mounts exclusively (AGENTS.md's stage-mode rule) — the side panel is unreachable
   while a run is in flight, so `settingsStore` cannot change between dispatch and report-build
   time.
7. **The report's own hardcoded-English wording was newly written**, not reused from any UI
   source — `processingText.ts`'s `describeFailureReason`/`describeSkipReason` and
   `rejectionText.ts`'s `describeRejection` all route through `t()` and are explicitly disqualified
   for the report (R-L3). The new strings mirror their tone where reasonable (e.g. the §9.3 sample's
   exact "File could not be decoded" / "Photoshop documents are not supported") but drop the
   file-name prefix and call-to-action, since the report already carries the file name as a
   separate field and has no "try this instead" register.
8. **The report byte count is not added to `preflightRunArchive`'s quota estimate.** The report is
   a few KB of text against an already-conservative per-image estimate; T40's own estimate basis
   (input `sizeBytes` as a stand-in for output) already has far more slack than the report could
   ever consume.

## What the next task should know

- **T42 (Download, share and leaving):** nothing about the report changes what T42 needs to do.
  `run-archive.ts`'s `finish()` signature changed but `useProcessingRun.ts` is the only caller, and
  that call site is already updated here. `run-download.ts`'s `downloadFinishedRun()` needed no
  changes — it reads back whatever `writeArchive` wrote, which now includes the report for any
  multi-image run.
- There is still no end-to-end browser test that clicks Download and inspects the resulting file,
  because the Download button isn't wired to `downloadFinishedRun()` yet (explicitly T42's job,
  per T40's own handover note). The verification here stops at: `useProcessingRun.spec.ts`'s two
  new tests exercise the real (non-mocked) archive-write/archive-read round trip directly, proving
  the real bytes contain the report; nothing yet proves the *button* does this, because it can't.
- `platform/opfs.ts`'s in-memory (non-OPFS) fallback holds `fallback.archive` as module-scoped
  state that outlives any single test — it is not reset by `setActivePinia`. Any future test in
  `useProcessingRun.spec.ts` that asserts on `readArchive()`'s absence/presence needs its own
  `deleteRunArtifacts()` reset (see the new `beforeEach` in that file's T41 describe block); every
  earlier test in that file already silently writes to this same module-level state without
  checking it, which previously didn't matter because nothing read it back.
