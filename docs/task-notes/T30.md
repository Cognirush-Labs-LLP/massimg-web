# T30 — Size targeting

**Status:** complete. One thing is left for the user, and it is a privacy judgement rather than a gap
in the work: **R-Q2's shortcut preserves the source metadata.** Non-PNG files pass through unchanged;
PNG and APNG files may be losslessly recompressed. See "What the user still has to decide".

## Later PNG amendment

The product decision left open below has since been made: every PNG output receives a lossless
oxipng attempt, including PNG → PNG and "Don't change" jobs whose source already fits a generous
size target. R-Q2 still short-circuits before decode, edit and resize, but the PNG/APNG source bytes
now go through `optimisePngBytesKeepingSmaller`; only non-PNG sources pass through byte for byte.
The smaller candidate is retained, so the amendment cannot make a file grow. An oxipng win carries
no `original-kept` caveat because the returned bytes are not the original; a tie or loss keeps the
original and the caveat. Metadata remains present on this raw-byte path, so the R-I17 tension
documented below is unchanged rather than resolved.

## Headline findings for later tasks

- **D1 `TESTED 95%` → `TESTED 99%`, and R-Q4's exclusion list is empty.** The question D1 was left open
  on is now a measured pair rather than an estimate: the same search, the same 1600×1200 frame, the
  same 150 KB target, **1,489 ms at §7.3's `heic:speed` 9 against 16,040 ms at the library default** —
  10.8× for the same eight iterations and one slider position of quality. At the shipped settings
  AVIF's search is the **second cheapest of the five** both per iteration (14–276 ms against WebP's
  24–1,568) and in the worst case measured (1,604 ms against WebP's 7,485). Nothing measured is
  prohibitive, so nothing is excluded.
- **The iteration count is a property of the axis, not of the content or the engine.** Over 375
  searches — five subjects × five targets × five formats × three engines — it takes exactly four
  values and never anything between 4 and 7: **1** (the lowest quality already misses, R-Q3), **2**
  (the highest already fits, or the axis is inert), **3** (a probe landed on a plateau — all 18 of
  these are PNG), **8** (there is a curve and the cap stops the bisection). The counts are identical
  on Chromium, Firefox and WebKit; only wall time differs, with Firefox 10–20% slower throughout.
- **§7.5's own recommendation for PNG does not survive measurement.** It said "a PNG size search wants
  `target` as its variable". With `minimum` pinned at R-Q11's floor of 70, `target` can only be swept
  from 70 to 100 at all — the library raises `VALUE_OUT_OF_RANGE` below the minimum — and over that
  range it is a size curve on two subjects of five, **inverted on a third** (a palette-like
  illustration is 132,536 B at target 70 and **57,066 B** at 100, so a lower target is 2.3× *larger*),
  inert on a fourth and absent on the fifth, where the quantizer aborts at every target. A binary
  search over it would hand a user asking for a smaller file a larger one. The slider stays the axis,
  and §7.5 now records what the alternative would have bought: on the two real photographs, 423,844 B
  and 239,559 B instead of 626,021 B and 800,098 B — real reach, and still nowhere near their target.
- **The search never needs to know that an axis is inert, because probing both ends finds out.**
  T28's warning — eight iterations spent learning nothing on flat GIF content — is answered by the
  probe order rather than by a detector: bottom, top, then the interior. An axis that does nothing
  returns the same bytes at the top as at the bottom, so the top fits whenever the bottom did and the
  search ends at two encodes. Measured on a flat 600×450 frame into WebP, where R-Q6's lossless
  candidate wins at every slider position and both ends return the identical 140-byte file: two
  encodes, and `size.spec.ts` asserts that on all three engines.
- **PNG is both the slowest per image and the one whose targets are most often unreachable**, and
  those are the same fact. A photographic frame has *no* axis — the quantizer cannot meet R-Q11's
  floor at any slider position, so both ends return the identical lossless file — and where
  quantization does succeed the axis has exactly two values. A PNG size target is cheap to attempt
  (1–3 encodes) and often impossible to meet, which is exactly what R-Q3 is for.
- **`Caveat`s compose.** A PNG whose quantized candidate is kept *and* whose target was missed carries
  `png-quantized` and `size-target-not-reached`, in that order. R-Q3's marking is added to what the
  encode already had to say, never substituted for it.

## Decisions made

- **The search walks the quality slider, not each codec's own parameter — and every probe is the
  whole encode stage.** T26's note recommended the opposite ("export a lossy-only entry point rather
  than going through `encodeFrame`, which would run the WebP comparison on every iteration"). It is
  declined, and the measurement is why: going through the shipped stage is what makes a size-targeted
  file *identical to the file the same slider position produces by hand* — asserted byte for byte in
  `size.spec.ts` — and R-Q6's lossless candidate is not overhead on the content it was written for.
  On a flat 600×450 frame every slider position returns the same 140-byte **lossless** WebP; a
  lossy-only search would have had a much larger file as its floor and would have reported targets
  unreachable that are comfortably reachable (D2 measured 12× on a flat graphic in T26's
  reproduction). The price is real and measured — see §7.5's table, where WebP's search is the
  slowest of the three smooth formats because the gate lets the lossless attempt run on every probe
  for palette-like content.
- **Both ends are probed before the interior.** The alternative — probe the bottom, then binary
  search upward — resolves the band exactly within the eight-iteration cap, which this order does not
  quite do (it lands one slider position low at worst; `size-plan.spec.ts` checks that exhaustively).
  It was rejected because it spends all eight iterations on an axis that does nothing, which is
  precisely what T28 warned this task about. Probing both ends answers "unreachable" in one encode,
  "the best quality already fits" in two, and detects an inert axis **without any code that detects
  one**: if the axis does nothing, the top fits because the bottom did.
- **A file size seen twice ends the search.** This is the other half of the PNG answer (§7.4): when a
  probe returns a size already measured, the axis is a plateau rather than a curve, and bisecting
  further only moves a boundary the user never sees. The risk — a curve flat between two probes that
  rises again inside the interval — is written into the code, and the measurement is in
  `results.json`. Of 375 searches, **18 ended on this rule and every one of them is a PNG**, each
  having probed 10, 100 and 55 and found that 55 returned the size 10 already had. Ties do occur on
  the other formats — 12 WebP searches, 21 GIF, 12 AVIF — but none of those ended a search early:
  WebP's and GIF's are the inert flat subject, where both *ends* tie and the search had already
  stopped at two probes, and AVIF's 12 are all between *adjacent* slider positions, where stopping
  costs nothing. **No JPEG, WebP or AVIF search was cut short by this rule.**
- **`sizeSearchBand` gives animated PNG a one-position band** rather than letting the search discover
  in two probes what R-Q15 already states. It saves one encode of the single most expensive animated
  encoder measured here, and it puts the reason in one place.
- **R-Q2's pass-through is guarded by R-X45's test**, and that test lives in `domain/job.ts` as
  `requestIsSatisfiedBySource` rather than in the pipeline, because R-X24 needs exactly the same one
  when it is built and two copies would be two places to get R-X45 wrong.
- **The band is the whole slider, 10 to 100, not the lossy band below R-Q5's point.** The lossless
  step at 96 (85 for PNG) is a jump in size, but never a jump *downward*: below it R-Q6 and R-Q14
  already keep the lossless candidate whenever it is smaller, so the axis stays non-decreasing across
  the step. Keeping the top of the band means a generous target on a screenshot can still land on a
  genuinely lossless file, which is what "at most 5 MB" should give that user.
- **An invalid target raises `SizeTargetError`, an ordinary `Error`, deliberately not a
  `RangeError`.** `pipeline/worker.ts` reads every `RangeError` as the machine running out of memory
  (T23), and a nonsensical target is an upstream bug, not an allocation failure. As an ordinary error
  it lands as `encode-failed`, which is at least true — no file was produced.
- **The codec load still runs before R-Q2's pass-through check.** §5.2 keys the load off the job's
  resolved settings and `codecs.spec.ts` observes it, so a passed-through image pays to initialise a
  codec it never calls. Making the load conditional on one branch of one stage is a worse trade than
  the idle initialisation.
- **R-Q4's exclusion list is empty, and there is no code for it.** An exported predicate that always
  returns true is dead code T35 would have to work around; §7.5 carries the decision and the table it
  was read off. If the user overrules it — PNG is the obvious candidate — that is when the predicate
  earns its place.

## Surprises

- **AVIF turned out to be one of the *cheapest* formats to size-target**, at 1.4 s against WebP's
  4.3 s on the same frame and target. D1 named AVIF as the candidate for exclusion and WebP as
  affordable; at §7.3's effort settings that ordering is reversed. WebP's cost is R-Q6's doing — the
  content gate lets the lossless attempt run on every probe for palette-like content, which is the
  price of the decision under "Decisions made" and is worth it for the reason recorded there.
- **A photographic PNG has no quality axis at all.** Both ends of the slider return the identical
  2,639,098-byte lossless file, because libimagequant cannot reach R-Q11's floor at any position.
  §7.4 predicted "one of two outcomes rather than a size curve"; on a photograph it is *one* outcome.
- **§7.5's PNG recommendation is refuted, and R-Q11's floor is what refutes it.** The floor caps the
  `target` axis at 31 of its 101 points before content has any say, because `set_quality(minimum,
  target)` raises `VALUE_OUT_OF_RANGE` for a target below the minimum. The axis §7.5 proposed
  searching cannot be searched below 70 while R-Q11 holds.
- **Firefox's content process died partway through the fourth subject of the first harness run**
  ("Execution context was destroyed"), having by then accumulated ImageMagick's, oxipng's,
  libimagequant's and gifsicle's heaps plus several full-resolution decodes in one document. One
  page per subject fixed it and the same run then completed on all three engines. It is a harness
  finding rather than a pipeline one — the app puts one job in a worker, not five subjects in a page
  — but it is the first time anything in this repository has killed a content process, and §8.2's
  worker recycling exists for the same reason.
- **The eight-iteration cap is worth exactly one slider position.** Checked exhaustively against a
  monotone axis for all 91 answers the band can have: the search lands on the best fitting position
  or one below it, never further. That is tighter than expected from six interior probes over 89
  positions.
- **GIF's axis has a genuine discontinuity at R-Q5's boundary**, and it points the safe way. Slider
  96 and above takes no lossy pass at all, so a search over palette-like content sees 55,202 B at
  slider 94 and 160,577 B at 97. Because the jump is *upward* with quality, monotonicity holds and
  the search handles it without knowing it is there.

## What the user still has to decide

**Historical decision at T30 completion:** R-Q2's pass-through returned the original file byte for byte, which meant it kept the metadata a
re-encode would have stripped.** R-I17 strips EXIF, IPTC and XMP "by default, including GPS
location"; a passed-through original carries all of it.

This is not a conflict T30 invented — **R-X24's substitution has exactly the same shape** ("the
original file is written to the output instead of the larger re-encode"), and both requirements say
plainly that the original file is what the user gets. What T30 changes is how often it happens: R-X24
fires only when a re-encode came out larger, while R-Q2 fires for every image already under the
target, which under a generous target is most of a batch of small images.

What is implemented is the literal reading: the original bytes, with an `original-kept` caveat on the
report. Three things are worth weighing before that is confirmed:

- **The report does not currently say metadata was *not* removed.** `metadata-removed` still has no
  producer at all (T26 recorded this), so a passed-through file's EXIF is invisible in the report as
  well as in the output. Whoever owns that caveat should decide whether the pass-through needs its
  own line.
- **Stripping without re-encoding is possible but is not free.** Removing EXIF from a JPEG or a PNG
  is container surgery of the kind `png-plan.ts` and `animation-plan.ts` already do; it is a new
  reader and writer per format, and it would make "passed through unchanged" no longer true.
- **The alternative — re-encoding anyway when the source carries metadata — contradicts R-Q2
  directly**, and would make the tool increase a file's size to meet a target in exactly the case the
  requirement exists to prevent.

My recommendation is to keep the literal reading and give the report a line for it, rather than to
change R-Q2. That is a requirement change either way, so it is not mine to make.

## What the next task should know

- **T35 (side panel): R-Q4's exclusion list is empty.** Every format offers the Size option; nothing
  is disabled and there is no predicate to call. The costs are in §7.5 if the panel ever wants to warn
  rather than disable — PNG is the slow one, and it is also the one whose targets are most often
  unreachable, because its axis has two values rather than a curve.
- **T36 (Preview): R-Q3 asks for the image to be marked in Preview, and a preview deliberately
  returns no caveats** (§4: "a preview returns the encoded bytes plus measured size; a run returns
  the same plus the caveat list"). No protocol change is needed — Preview knows the target the user
  typed and the measured size of what came back, so "the target was not reached" is a comparison it
  can make itself. Do that rather than widening `JobResult`.
- **T38 (Processing, Cancel): R-X20's "stops after the image in flight" got slower.** Cancellation is
  a between-jobs flag (§5.3) and a size search is one job, so the worst-case latency is now the
  worst-case *search*: 12.7 s for the worst PNG and 7.5 s for the worst WebP measured here, against
  roughly 4.9 s and 1.5 s for a single encode of the same images. Nothing is broken; the number is
  just larger than the quality path's, and it is reasoned from job times rather than measured as a
  cancel-to-stop latency.
- **`SizeSearchResult.probes` carries the per-image iteration count and every probe's size.**
  Nothing requires it to reach the UI, and `JobResult` deliberately does not carry it; it exists for
  tests and the harness.
- **Re-running the harness:** from `verification/t30-size/`, `pnpm test`, or `T30_QUICK=1 pnpm test`
  for Chromium only. It needs the repository's root install, generates its subjects in the page, and
  reads `PHOTO_FIXTURES_DIR` for the two real photographs — skipping them with a stated reason when
  it is unset.
- **Port 5173 is still contested.** Every Playwright run here used a scratch config on 5199 with
  `reuseExistingServer: false`; the harness runs its own Vite on 5188.

## What could not be proven

- **One machine, three engines.** Every time here is desktop macOS on Apple silicon, 8 cores. The
  iteration counts are content-dependent but machine-independent; the wall times are not.
- **Two real photographs**, fitted to 1600 px, plus three generated subjects. Enough to show that the
  iteration count does not depend on content the way the wall time does, not enough to characterise
  any format's curve.
- **The plateau rule's risk case has not been observed and cannot be ruled out.** A curve that is
  flat between two probes and rises again inside the interval would end the search early. No measured
  axis has that shape; content nobody has encoded here might.
- **The landing precision (best position, or one below) is proven against a monotone model**, not
  against every real axis. On a non-monotone one the search still returns a file that fits — that is
  read off the probes — but how close to the best it lands is not bounded.
- **Cancellation latency is reasoned, not measured.** The numbers above are job times, not observed
  cancel-to-stop times.
- **No perceptual metric.** "The best quality that fits" means "the highest slider position that
  fits". For JPEG, WebP and AVIF that is the encoder's own quality; for GIF and PNG it is only as
  meaningful as §7.4's mapping, which T27 and T28 argue for from size curves rather than from an eye.
- **Nothing above about 2 megapixels, and no animation beyond 16 frames, went through a search.**
  Every still subject is 1600×1200 or is a real photograph fitted to 1600 px, which is the shape D1
  used and the shape a fitted batch produces — but it is not the shape an unresized 24-megapixel
  photograph produces. T28 measured a single gifsicle pass at 1.2 s on a 4000×6000 still, so an
  eight-iteration GIF search on one is about ten seconds *by arithmetic*, and a PNG search on one is
  worse. Whoever owns T50's limits should measure a search at full resolution rather than trust that
  multiplication.

## Requirements covered

- **R-Q2** — an image already under the target skips decode and re-encode, and only when the job asks
  nothing else of it (R-X45's test). Non-PNG bytes pass through unchanged; PNG/APNG bytes receive a
  lossless oxipng attempt and keep the smaller candidate. The search never encodes above the top of
  the slider, so a file is never inflated to fill a target.
- **R-Q3** — an unreachable target keeps the smallest result the search achieved, records
  `size-target-not-reached` with both numbers, and never fails the image. The Preview and tile
  marking R-Q3 also asks for belongs to T34 and T36; the caveat they need is produced here.
- **R-Q4** — **decided from data: the exclusion list is empty.** §7.5 carries the table and the AVIF
  pair the requirement was waiting on.
- **R-Q10** — frame count is never reduced to reach a target; the animated search moves quality only,
  and `size.spec.ts` reads the frame count back out of the searched output with the T29 container
  readers.
- **R-Q5, R-Q6, R-Q11, R-Q12, R-Q14, R-Q15** — all continue to hold under a size target, by
  construction rather than by repetition: every probe is `qualityForSlider` followed by the same stage
  the quality path runs, and `size.spec.ts` asserts the searched bytes are identical to a direct
  encode at the slider position the search settled on.
- **R-X46** — the caveat is the fixed one, and it composes: a PNG that kept its quantized candidate
  *and* missed its target reports both, in that order.
- **R-I17 — not satisfied on R-Q2's shortcut**, deliberately and visibly. The raw PNG optimisation
  preserves source metadata just as the byte-for-byte non-PNG path does. See "What the user still
  has to decide".
