# T29 — Animated paths

**Status:** complete. No open questions — both were put to the user and settled before the commit,
and one of them added a requirement (R-Q15). Built in two passes against one plan: input side and
measurement first, output side and wiring second, each reviewed before the next began.

## Headline findings for later tasks

- **C7 `OPEN 45%` → `REFUTED 95%`.** Peak memory for an animated source is linear in frame count
  *and* in frame area, at **2.2x–2.7x marginal and up to 2.80x measured total** over the coalesced
  frame data, on all three engines, with R² at or above 0.994 on all six fits. 128 frames of 400x400
  cost 193–219 MB above a post-codec baseline for 78.1 MB of pixels. **Plan on 2.8x.**
- **R-B6's mitigation does not exist for this decoder, and that is measured.** Releasing each
  `MagickImage` as its pixels are lifted changes ImageMagick's heap growth by **zero bytes** —
  55,771,136 with the dispose and without, on all three engines — because `coalesce()` materialises
  every frame before the first pixel is extracted. **T33 should be sent straight to C7** for §5.7's
  animated frame budget; it is the binding limit for these inputs, not the pixel cap, and §5.1's
  worker cap multiplies it.
- **`D6` predicted the APNG behaviour and was right, at A5, long before this task.** "ImageMagick's
  PNG reader returned one frame from a six-frame APNG" is why R-I4 exists. T29 found the same is
  true of `readCollection` *and* of `ping` — there is no way to decode an APNG's frames through this
  build at all — so the animated path has **two decoders**: ImageMagick for GIF and WebP, UPNG for
  APNG. D6 is now 95% and says so.
- **Never use `animationIterations`, and never use ImageMagick's WebP delays.** The first reports a
  finite GIF loop count plus one and a WebP's unchanged; the second is quantized to centiseconds, so
  a WebP storing `[45, 33, 7, 101, 999, 1]` ms reads back as `[50, 30, 10, 100, 1000, 0]`. Every
  number the animated paths use is read from the container bytes by `animation-plan.ts`.
- **`Animation.loops` is total plays, 0 = infinite** — not the raw stored value. GIF's NETSCAPE2.0
  block counts repeats *after* the first play; WebP's `ANIM.loop_count` and APNG's `acTL.num_plays`
  count the total. A GIF storing 3 plays four times. `gifTotalPlays` is the single conversion point.
- **§7.3 gained an apng-optimizer row**: `deflateMethod` 1 (the library default) and `iter` **5**,
  not the default 15. Measured, not guessed.
- **R-Q11's floor is not enforceable on the animated PNG path.** apng-optimizer's `minQuality` is a
  request it neither meets nor reports on — there is no abort to catch. `pickSmaller` is what
  protects the user, and on photographic frames that is the difference between 42,411 bytes and
  236,609.

## The two questions the user settled

Both were raised by this task and decided by the user before it was committed.

**1. R-Q6 applies to animated WebP.** The question was whether "for WebP below quality 96, the app
also attempts a lossless encode and keeps whichever result is smaller" reaches an animation, given
that §7.6 describes the still case throughout — D2's single 1600×1200 frame, a gate `encode-plan.ts`
computes over one frame's pixels — and that the cost on an animation is one extra encode per frame
rather than one. **Decided: it applies.** The rule is written about WebP, not about still WebP, and a
GIF converted to animated WebP is exactly the flat, few-colour content R-Q6 wins on, so declining it
there would forfeit the case it was written for.

What §7.6 does not define is the gate, so `animationUniqueColors` in `animation-encode.ts` is a T29
choice: read the **first, middle and last** frames and take the **highest** distinct-colour count.
Three rather than one because an animation's first frame is not reliably representative — a title
card or a fade-in can be far flatter than the footage behind it, and gating on it alone would commit
to a lossless encode of every frame on the strength of the one frame that looked cheap. Three rather
than all because scanning every frame is the per-frame cost the gate exists to avoid. The maximum
decides, so the gate errs the way §7.6 asks: a skipped attempt that would have won costs bytes, an
attempted one that loses costs only time. **This sampling rule is the part a reviewer should
challenge first** — it is the only piece of R-Q6's animated behaviour that no document settles.

**2. Animated PNG is always lossless — now R-Q15.** R-Q11's floor is a guarantee on the still path
only because libimagequant *aborts* when it cannot reach it. apng-optimizer wraps the same library
and exposes no refusal, so a quantized animation would be quantized to an unknown quality at every
slider position with no way to detect that the floor had been missed. `pickSmaller` would stop the
user receiving a larger file but could not stop it banding, which is what R-Q11 exists to prevent.
**Decided: drop the quantized candidate entirely** — keeping R-Q11's intent by removing the only
path that could violate it, and halving the work, since `optAPNG` now runs once per animation.

Functional Design was amended accordingly: §7.1's quality table splits PNG into still and animated
rows, R-Q11 and R-Q14 are scoped to still PNG, and **R-Q15 is new**. The slider still governs
animated WebP, which is where an animated source goes when the user asks for a smaller file.

## Decisions made

- **`Animation.loops` is total plays, not the raw stored value.** GIF's block counts repeats after
  the first play and the other two count the total, so passing the number through unchanged turns a
  GIF seen four times into a WebP seen three — the drift R-Q9 forbids. Two independent
  implementations agree on the conversion: libwebp's `gif2webp` maps 3 → 4, 1 → 2, 0 → 0 and absent
  → 1, and ImageMagick's `animationIterations` reports the same numbers. `tests/e2e/animation.spec.ts`
  asserts ours equals ImageMagick's for all four states it can be asked about. **An earlier draft of
  this pass carried the raw value; it was wrong and was corrected in review.**
- **The container readers stay raw.** They are the byte oracle the tests assert against, so they
  report what is in the file and interpret nothing. `gifTotalPlays` is the single conversion point.
- **Every number comes from the container, including for GIF**, where ImageMagick happens to be
  exact. One source of truth is worth more than a second code path that agrees today.
- **Frames are coalesced.** R-Q9 asks for disposal *behaviour*; the three formats' disposal models
  differ, so a disposal *code* cannot cross a format change and mean the same thing, and resizing a
  stored sub-rectangle in isolation is wrong regardless. `Animation` deliberately has no disposal
  field — a field nobody may rely on is worse than no field.
- **`Frame` is reused per animation frame**, so `applyEdit` and `applyResize` work unchanged. §4.2's
  own reason: otherwise the two paths grow separate copies of the same arithmetic.
- **Caveats are deduplicated by kind.** Six frames flattened against one background is one thing
  that happened to the image, and §6.6's report says it once.
- **Editing is refused, not ignored** (R-C6, R-C16), and with an `AnimationStageError` that is
  deliberately *not* a `DecodeError`: the file is fine, and telling the user it is corrupt would be
  the wrong message.
- **A single-frame file is refused by `decodeAnimation`.** `domain/classify.ts` decides what is
  animated; a one-frame GIF belongs on the still path, and writing a WebP that announces an
  animation for it is a change nobody asked for.
- **Colour and orientation are read where the decoder can actually see them.** ImageMagick's WebP
  coder reports neither `ICCP` nor `EXIF` for an animated file, so both are lifted from the RIFF
  container; an APNG's come from `MagickImageCollection.ping`, which surfaces `eXIf` and the whole
  `iCCP` without decoding a pixel.
- **Orientation is applied, not merely recorded**, and it is a no-op unless a tag asks for a
  transform — so the common case pays nothing. Coalescing happens first, because coalesce composites
  in stored canvas geometry.
- **A delay an APNG cannot express exactly is refused, not clamped.** `apngDelayFraction` reduces
  `ms/1000` to lowest terms. Clamping would change how long a frame is on screen without saying so,
  and **R-X46's caveat set is closed** — there is no caveat for a shortened delay, so there is no
  honest way to do it quietly.

  **What the refusal can and cannot be reached by**, checked over the full legal range of each
  source format rather than reasoned about:

  - **A GIF can never reach it.** GIF delays are centiseconds, so `gcd(ms, 1000)` is at least 10 and
    the worst case — 65,535 cs, the largest the field holds — reduces to exactly `65535/100`, at the
    limit but inside it. All 65,536 legal values pass.
  - **A WebP can.** `ANMF` stores a 24-bit count of milliseconds, so a frame may ask for 65,537 ms,
    which is prime relative to 1000 and therefore inexpressible; 655,351 ms is another. Both refuse.
  - Whole-second delays are fine up to **65,535,000 ms, about 18.2 hours**.

  So the branch is reachable in principle from an animated WebP with an unusually long, oddly valued
  frame delay, and unreachable from a GIF. Refusing is still the right behaviour — the alternative is
  a silently shortened frame — but it is not dead code, and a future reader should not treat it as
  such.
- **`ResolvedSettings` gained `sourceFormat`** rather than `codecsForSettings` gaining an optional
  parameter. Two pipeline decisions key off the source rather than the output.
- **The fixtures are built by ffmpeg, img2webp and webpmux, never by ImageMagick or UPNG**, from
  hand-written PNG frames. T26 and T27 both established that a fixture produced by the library under
  test only proves the library agrees with itself.
- **`attachApngIccp` is not `rewritePngChunks`.** T27's note warned that its whitelist has no
  `acTL`, `fcTL` or `fdAT`, so an APNG through it comes out a still image. The animated one keeps
  everything except a short drop list — the opposite default, and the right one here.

## Surprises

- **ImageMagick cannot decode an APNG at all, through any of its three readers.** `readCollection`,
  `read` and `ping` each return one frame from a six-frame file and raise nothing. D6 predicted it
  for the still reader; nobody had checked the collection reader.
- **ImageMagick's WebP writer replaces any frame delay under 10 ms with 100 ms.** Swept exactly: 0,
  1, 5 and 9 all become 100; 10, 11, 15, 20, 25 and 30 are exact. libwebp itself has no such limit
  (`img2webp -d 1` writes a 1 ms duration), so the durations are put back into the `ANMF` chunks
  afterwards. **The whole fixture set was multiples of 10 ms, which is why nothing caught the
  matching read-side bug until review**; `anim-odd-delays.webp` exists now and would have.
- **The loop-count conversion was got wrong once, in this task, in the safe-looking direction.**
  "Pass the stored number through and interpret nothing" sounds like the conservative choice and is
  a silent off-by-one on every GIF that becomes a WebP.
- **apng-optimizer's quantizer can make a file 5.6x larger, silently.** On an 8-frame photographic
  APNG: lossless 42,411 bytes, `minQuality: 10` **236,609** with a 256-colour palette,
  `minQuality` 50/70/90/99/100 all **101,349** with no palette at all. Nothing throws and nothing
  reports that the request was not met — unlike libimagequant's own API, whose abort is what makes
  R-Q11's floor a guarantee on the still path.
- **apng-optimizer can also make a file bigger than UPNG's own output.** On the 16-frame 400×400
  flat animation UPNG wrote 8,915 bytes and every optimiser setting came back larger. A third
  candidate — UPNG's own bytes — would be nearly free and nobody owns it. Recorded against A10.
- **`deflateMethod: 2` took 49 seconds** on one 16-frame 400×400 animation, and T29 runs the
  optimiser twice per image.
- **WebKit's `ImageDecoder` loses alpha.** Given the committed animated WebP, WebKit's
  `createImageBitmap` reports alpha 0 at the transparent corner and its `ImageDecoder` →
  `VideoFrame` → `drawImage` path reports **255**, with the frame's own `format` still saying
  `RGBA`. Chromium agrees with itself at 0. The output file is correct — the pipeline's own decoder
  reads alpha 0 from the same 460 bytes on both engines — so this is a bug in the *instrument*. The
  alpha assertions use `createImageBitmap`, which works everywhere, and the finding is recorded
  rather than the engine being skipped.
- **ffmpeg's default GIF path dithers.** The first GIF fixtures came out as dithered noise
  (230,25,25 → 252,36,85) and the disposal fixture was unreadable. `palettegen` + `paletteuse` fixed
  it, and `reserve_transparent` + `alpha_threshold` are what map zero alpha onto GIF's transparent
  index; without them the hole came back solid.

## What the next task should know

- **T28 (GIF):** `decodeAnimation` already returns exactly what gifsicle needs, and `readGifAnimation`
  reads the loop count and delays back out of gifsicle's output independently. **Remember
  `gifTotalPlays` runs in reverse on the way out**: `Animation.loops` is total plays, and a GIF's
  NETSCAPE block wants `loops - 1` for a finite count and 0 for infinite. There is no
  `totalPlaysToGif` yet — add it beside `gifTotalPlays` rather than inlining the arithmetic.
  `execute.ts` refuses GIF **before** the animated branch, so removing that throw is all the wiring
  an animated GIF needs.
- **T30 (size targeting):** `quality.kind === 'size'` still throws, from both the still and the
  animated path. The animated axis is expensive — a search over an animation re-encodes every frame
  per iteration — and R-Q10 forbids dropping frames to hit a target.
- **T33 (§5.7's limits): go to C7 first.** It has both sweeps, the fitted slopes and the
  peak-over-arithmetic ratios, and the frame budget is the binding limit for animated input.
- **`encodeAnimatedWebp(animation, quality)`** and **`encodeApng(animation, quality)`** from
  `@/pipeline/stages/animation-encode`. The APNG result carries `branch`, `branches`, `sizes` and
  `caveats`; only `bytes` and `caveats` reach `JobResult`.
- **`ResolvedSettings.sourceFormat` is new** and `codecsForSettings` reads it.
- **Re-running the harness:** from `verification/t29-animated/`, `pnpm test`, or `T29_QUICK=1 pnpm test`

## What could not be proven

- **No phone**, so C4 is untouched. Every memory figure is desktop macOS, 8 cores, 16 GB.
- **No frame above 1200×1200 and no animation beyond 128 frames.** Both sweeps are linear with
  R² ≥ 0.994 across their range; extrapolating a little is fair, extrapolating far is not.
- **The C7 sources are flat-coloured.** Right for memory — decoded size is content-independent — but
  the *decode times* in `results.json` are not representative of real footage.
- **The dispose comparison runs a loop written in the harness**, not the shipped stage, because the
  stage has no switch for turning its own dispose off. It is the only measurement in C7 that is not
  the shipped module, and the entry says so.
- **§7.3's apng-optimizer row rests on two subjects**, one photographic and one flat, and they
  disagree about `deflateMethod` 0 against 1. The library default was kept on that basis rather than
  because the data chose it.
- **`ImageDecoder` is the per-frame instrument on all three engines, but WebKit's loses alpha**, so
  the per-frame *alpha* claim is proven on Chromium and Firefox and, for the first frame only,
  through `createImageBitmap` on all three.
- **The APNG `eXIf` orientation branch is untested.** `decodeAnimation` reads it through `ping` and
  would apply it, but no tool here writes an `eXIf` into an APNG and no fixture exercises it. The
  animated WebP case is proven, for orientation 6 only; the other seven values are unit-tested
  through `readWebpOrientation` and rest on D4 beyond that.
- **An APNG whose `fcTL` chunks follow `IDAT`** — a legal layout where the still image is not frame
  0 — is exercised by no fixture. Recorded against D6.
- **`setApngFrameDelays`'s refusal is unreachable from a GIF but reachable from a WebP** — see the
  bounds under "Decisions made". No fixture carries a 65,537 ms frame, so that branch is exercised
  only by a hand-built case.
- **Animated AVIF is not rejected at selection yet** (R-F8). `domain/classify.ts` reports AVIF
  without an animated flag and `resolveFormat` rejects `avif` + `isAnimated`, but nothing detects
  the animation in the first place. Still unowned, as T26 left it.

## Requirements covered

- **R-F5:** an animated source keeps its animation into WebP and PNG, proven for all three source
  formats × both output formats on three engines.
- **R-Q9:** frame delays and loop count preserved through every animated path, asserted through
  independent container readers on both sides of the pipeline. **Disposal behaviour** is preserved by
  coalescing rather than by carrying codes — the reading is in `Animation`'s doc comment and was
  settled with the user before implementation.
- **R-Q10:** frame count preserved exactly — never reduced and never increased — checked against the
  container's own declaration at decode and again at encode.
- **R-Q12, R-Q14:** **not applicable to animated PNG** — they govern the still path. See R-Q15.
- **R-Q15:** animated PNG is lossless at every slider value, asserted from 10 to 100, with the bytes
  identical either side of the still path's lossless point and no `png-quantized` caveat ever
  recorded. The tests exist to make a future quantized branch fail before it ships.
- **R-B6:** honoured as far as it can be — and **measured to be unachievable** for this decoder. The
  per-frame release is in place and changes nothing; C7 carries the numbers.
- **R-C6, R-C16:** editing is refused for an animated source, loudly.
- **R-I9:** EXIF orientation applied per frame, after coalescing, through D4's implementation.
- **R-I12, R-I14:** the profile is carried into both output formats byte-for-byte; an untagged
  animation gains nothing, and no `sRGB`, `cHRM` or `gAMA` contradicts a profile.
- **R-I17:** structural. Both writers build from raw pixels; the output's chunk inventory is
  asserted to carry no `eXIf`, `tEXt`, `zTXt`, `iTXt`, `tIME`, `EXIF` or `XMP`.
- **R-Q6:** **not applied to animated WebP.** See "The one open question".
- **C7:** refuted, with evidence, and the register updated in place.
