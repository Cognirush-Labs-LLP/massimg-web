# T33-A — Gallery infrastructure

**Status:** complete

## What was built

The layer that turns a picked/dropped `File` into a real `ImageRecord` in `useBatchStore`
(`src/ui/gallery/ingest.ts`), which nothing before this task built — T18 (picker/folder)
deliberately stopped at `SelectedFile`, and T32 confirmed it didn't add this either. Alongside it:
module-scope binary storage for each image's source `File` (`platform/source-files.ts`), a lazy,
worker-based, killable `W×H` probe that never blocks selection (`platform/dimension-probe.ts` +
its worker/render split), `useBatchStore.clearAll()`, and the empty state / toolbar UI shared by
both the future grid (T33-B) and list (T34) views. `docs/tasks.md`'s T33 entry is split into
T33-A (this task) and T33-B, and T34's dependency now points at T33-A.

This was originally scoped as part of T33 itself; the split was decided with the user mid-session
once the missing ingest layer surfaced during planning (see `docs/tasks.md`'s T33 entry for the
short version, and the git history of this file's commit message for context).

## Decisions made

- **`ImageRecord.width`/`height` are not changed in shape.** They start at `0` (the "not yet
  known" sentinel) and are patched via the already-existing `batchStore.updateImage(id, {width,
  height})` once the background probe resolves. A distinct **error** state is kept *outside*
  `ImageRecord` (`ingest.ts`'s reactive `dimensionErrors` Set) rather than adding a field to a T09
  contract that every earlier phase's fixtures/tests already depend on, for a condition (a cosmetic
  probe failure) unrelated to what `status`/`failure` already mean there (an actual encode
  failure). T33-B/T34's tile/row components read `0` as "show `_×_`" and membership in
  `dimensionErrors` as "show `error`" — this task builds no UI that reads either yet.
- **Dimension probing is a real decode (`createImageBitmap`), not a header parser**, decided with
  the user after an earlier, more complex plan (per-format binary header parsing, mirroring
  `domain/classify.ts`) was replaced by a much simpler design: lazy, low-priority, worker-based,
  killable the instant compression starts, no budget. See the module doc comment in
  `dimension-probe.ts` for the full reasoning, including why it differs from the thumbnail
  service's grid-only, budgeted lifecycle in three specific ways.
- **`stop()` re-queues an interrupted job instead of dropping it**, and pairs with `resume()`
  rather than being a one-way door like the thumbnail service's `stop()`. Discovered while
  designing the service: because R-G10's thumbnail budget has no equivalent here, silently losing
  a job on `stop()` would leave that image's dimensions permanently stuck at `_×_` after a
  cancelled run returned to Gallery. Proven by the Playwright "stop() terminates ... resume()
  retries" test.
- **`ingestDrop` always calls `readDroppedFolder`, never `readDroppedFiles`.** T18's handover note
  left "per-item file-vs-directory dispatch for a mixed drop" as work for "a future task."
  Re-reading `folder.ts`'s `walk()`, it already handles a top-level *file* entry exactly like a
  one-entry traversal — so routing every drop through it (not only ones known in advance to
  contain a folder) is a strict superset of `readDroppedFiles`'s capability and satisfies that
  leftover without writing the dispatch logic a second time.
- **Selection is processed sequentially, not with bounded concurrency**, flushed to the store in
  chunks of 25. `classify()`'s own doc comment requires the *complete* file for correct GIF
  detection, so reading each file's bytes is not skippable; sequential processing is what keeps
  R-G5's insertion/traversal order trivially correct (concurrent reads would finish out of order)
  at the cost of some throughput on a very large selection — not measured against a real large
  batch in this task; flag for T33-B if 500-file ingest time becomes user-visible.
- **The toolbar is a second, independently mounted component** (`GalleryToolbar.vue`), not part of
  `Gallery.vue`'s own template, because `<component :is="stageComponent">` in `ToolPage.vue` only
  fills `StageContainer`'s default slot, not its named `toolbar` slot T31 left empty for this. It
  shares no instance state with `Gallery.vue` — every action goes through `ingest.ts`'s plain
  exported functions acting on the global store and the module-scope services above. Teleport was
  considered and rejected: it risks the toolbar silently vanishing from vite-ssg's prerendered
  HTML (T31's F1 finding), which isn't worth the risk for what a plain second component solves for
  free.
- **The toolbar's visibility is gated in `ToolPage.vue`** (`stageMode === 'gallery' && imageCount >
  0`), not inside `GalleryToolbar.vue` itself returning nothing when empty. A `v-if="false"` root
  still leaves a comment node, which `StageContainer.vue`'s existing `.stage-toolbar:empty {
  display: none }` rule (from T31) would not match — gating one level up sidesteps that CSS
  footgun entirely rather than relying on it.
- **Drop is handled on `Gallery.vue`'s root, not only inside `GalleryEmptyState.vue`.** Functional
  Design §3.2 describes drag-and-drop under the empty state specifically; extending it to the
  populated state too was a deliberate, low-risk choice — the toolbar's Add images/Add folder
  already offer the identical underlying action there, drop is just one more way to trigger it.
- **The empty-state accepted-formats line is a static string**, not computed from a genuine
  per-browser feature probe. R-I1 asks for it to "reflect what the running browser and build can
  actually handle," but classification (`domain/classify.ts`) doesn't vary by browser — only
  decode capability does, and that's already covered end to end by the pipeline's ImageMagick
  fallback (T22/T23) regardless of what the empty state's copy says. Building a genuine dynamic
  per-browser format list for this one line was judged disproportionate; flagged as a small,
  known gap rather than silently claimed as fully satisfied.
- **Rejections remain fully out of scope**, exactly as T32's own handover note anticipated: a file
  `classify()` calls `unhandled`/`not-image`, and a folder/drop selection that breaches
  `MAX_TRAVERSAL_DEPTH`/`MAX_TRAVERSAL_FILES`, are silently dropped with no message shown anywhere.
  This is **not** an oversight — T39 owns adding a rejection-entries mechanism to `useBatchStore`.
- **No batch-size cap.** Functional Design §5.7 marks "Files per batch" as T50's job. Consistent
  with T18 leaving the folder-traversal cap provisional for the same reason.

## Surprises

- **A stale dev server on port 5173, left over from an earlier session, broke every Playwright test
  that dynamically imports a module via `page.evaluate`** — not just this task's new specs, but
  pre-existing ones too (`thumbnails.spec.ts`'s "budget is injected" test reproduced the identical
  `Failed to fetch dynamically imported module` failure against that same stale server). Not a
  regression from anything in this task; killing the stale process and letting Playwright's own
  `webServer` start a fresh one fixed every affected test immediately. Worth knowing if a future
  session sees this exact error on an otherwise-unrelated change: check for a leftover `vite`
  process on 5173 before assuming the code is wrong.
- Otherwise none — `createImageBitmap`, module workers and `Worker.terminate()` all behaved
  identically across Chromium, Firefox and WebKit for this service, with no branching needed
  (matching T20's own experience for the thumbnail service, though T20 found real engine
  differences elsewhere that this task's much simpler decode doesn't hit).

## What the next task should know

- **T33-B (Gallery, grid view):** `Gallery.vue`'s populated-state branch
  (`data-testid="gallery-placeholder"`) is exactly what to replace with the real virtualized grid.
  `ingest.ts` exports `removeIngestedImage(id)` already, built but unused — call it from each
  tile's remove button instead of re-deriving the invalidate-probe/release-file/remove-from-store
  sequence. Read `dimensionErrors` (a reactive `Set<ImageId>`) and each `ImageRecord`'s
  `width`/`height` (0 means still pending) to render `_×_`/`error`/real text. The thumbnail
  service (T20's `platform/thumbnails.ts`) is a **separate, additional** service T33-B still needs
  to instantiate and wire itself — this task did not touch it.
- **T34 (Gallery, list view):** `GalleryEmptyState.vue`/`GalleryToolbar.vue` are ready to reuse
  as-is; add the grid/list toggle into `GalleryToolbar.vue` rather than building a second toolbar.
  The dimension probe keeps running in list mode (it isn't grid-scoped, unlike thumbnails) —
  nothing extra to wire for that. Remember R-G9: list rows must still decode nothing else at all,
  which this task's dimension probe doesn't violate (it's a natural-size read only, no thumbnail
  rendering), but don't add anything else that decodes.
- **T36 (Preview) / T38 (Processing):** `platform/source-files.ts`'s `getSourceFile(id)` is the
  seam for the real source bytes to encode. `removeIngestedImage`/`clearGallery` already keep it
  in sync with the batch store; nothing else needs to release these files on the paths this task
  built.
- **T38 specifically:** `ingest.ts`'s dimension-probe `stop()`/`resume()` pairing is wired to
  `useUiStore().stageMode` transitioning to/from `'processing'` — but since `PrimaryActionButton`
  has no real click handler yet (T38 hasn't built Processing's real entry point), this integration
  is **not** end-to-end tested through real UI interaction, only the service's own `stop()`/
  `resume()` semantics (Playwright, module-level). Once T38 wires a real trigger into
  `enterProcessing()`, it's worth a quick manual/e2e check that dimension-probe work genuinely
  stops the instant that fires.
- **T39 (Errors and rejections):** every silent-drop point this task added (unclassifiable files,
  folder/drop cap breaches) is a candidate rejection entry — see "Decisions made" above for the
  exact list.
- `content/en/faq.md` was re-read against this change; nothing in it needed correcting (§10 still
  correctly lists the on-screen gallery as unfinished, which remains true — only infrastructure
  and shared chrome exist after this task, not the real grid/list content), and no new behaviour
  surfaced that isn't already covered by an existing answer, so no new question was proposed.
