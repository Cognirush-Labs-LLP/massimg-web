# T13 — Crop and rotation arithmetic

**Status:** complete

## What was built

`domain/edit.ts` now holds the whole of Technical Design §6 as pure arithmetic: fit and draw scales,
the two coordinate spaces and the conversions between them, crop constraint under a locked ratio and
a minimum size, output dimensions with source placement and per-edge spill, the typed-dimension
inverse, quarter-turn rotation, and a generic fold over `EditRecord.ops`. The §6 worked example is a
verbatim test fixture, and rotation composes on top of it.

## Files touched

- `src/domain/edit.ts` — the §6 arithmetic, the `resolveCropGeometry` resolver for the interface, and
  the frame-free `resolveCropOutput` / `resolveEditedSize` path for the pipeline.
- `src/domain/edit.spec.ts` — the §6 table as a fixture, plus spill, ratio, minimum, typed-dimension,
  rotation, fold and unresolvable coverage.
- `docs/task-notes/T13.md` — this handover note.

## Decisions made

- **Source fractions are the single source of truth for output size.** `outW = rw / drawScale` and
  `outW = rect.width × Ws` are algebraically identical but not equal in doubles, and they can differ
  by a whole pixel after rounding. Measured counterexample, now pinned as a test: source 1565×4771,
  frame 327×271, zoom 0.6356195350781404, `rw` 2.4731341939683626 gives 68.5 → 69 by the frame
  formula and 68.49999999999999 → 68 by the source formula. T24 must match "to the pixel" and T37
  "exactly", which two formulas equal only in exact arithmetic cannot deliver. `resolveCropOutput` is
  therefore the only place output size is computed, and the frame formula appears nowhere in the
  implementation — only in the spec, as a ±1 px sanity bound. Rejected: computing size in frame space
  and letting the pipeline re-derive it, which is what makes the two drift.
- **`NormalisedRect` fractions outside `[0, 1]` are legal and are how spill is represented.** The §6
  spill row normalises to exactly `{ x: -0.5, y: -0.5, width: 2, height: 2 }`. T09's note called the
  rect's numeric bounds "contracts for the functions that construct them"; T13 is that function, and
  the contract is widened here. Rejected: clamping to the unit square, which would silently destroy
  R-C9's legitimate larger-than-input output.
- **Minimum crop size is 16 output pixels** (`DEFAULT_CROP_LIMITS.minimumOutputPixels`). R-C12 says a
  minimum exists but names no number. Rejected: 1 (permits a degenerate 1×1 output and makes the ratio
  lock meaningless), 32 and 64 (start refusing legitimate icon-scale crops). `CropLimits` carries a
  second, independent `minimumFramePixels` floor, defaulting to 0 here, because 16 output pixels is
  0.8 frame pixels at `drawScale` 0.05 — invisible and ungrabbable. That usability floor depends on
  pointer target size and belongs to T37; suggested companion value 24.
- **Rotation resets the crop rectangle to the whole rotated image and resets zoom to 1.0.** R-C3 says
  the rectangle is "re-fitted" without saying what that means. Rejected: rotating the rect with the
  image content, which preserves the user's selection — the cost of the chosen rule is that a crop
  placed before rotating is discarded. Zoom must reset with it: at zoom > 1 the image overflows the
  frame, so "the whole rotated image" is unrepresentable while R-C12 forbids the rect leaving the
  frame. Resetting makes the post-rotation state a function of source, frame and ratio alone. The
  useful consequence is that rotation is exactly a fresh entry, so `rotateCropInput` delegates to
  `resolveCropInput`, which also serves R-C4 entry, R-C10 restore and R-C11 stepping.
- **A locked ratio keeps its label and the reset rectangle is re-fitted to it.** Rejected: transposing
  the ratio (4:5 → 5:4), which has no chip in the §3.4 row, so the lit chip and the rectangle would
  disagree — the exact failure R-C3 exists to prevent. Also rejected: dropping the lock to Free, which
  silently discards a user setting.
- **Rotation direction is clockwise; `quarterTurns` counts clockwise turns.** The design documents
  never state a direction. Rotate right is `+1`, rotate left is `+3`. **T24 must match this.**
- **Constraint precedence is frame, then ratio, then minimum.** R-C12 states frame containment
  absolutely, so it wins outright; the ratio survives next because a rectangle that disagrees with a
  lit chip is the R-C3 failure; the minimum is a preference and yields last. `constrainCropRect` is
  idempotent, which the spec asserts over inverted, zero-area, off-frame and `NaN` rectangles.
- **A free ratio clamps each axis to the frame independently; a locked ratio scales both uniformly.**
  Uniform scaling under a free ratio lets one axis's frame limit stop the other reaching its minimum —
  found while testing, not predicted.
- **Output dimensions round with `Math.max(1, Math.round(x))`.** `floor` turns `1999.9999999999998`
  into 1999 and `ceil` turns `8000.000000000001` into 8001; `round` is the only policy that absorbs
  last-ulp noise instead of amplifying it. Rounding happens exactly once, in `resolveCropOutput`.
- **Spill is decided on integer bands, not a float comparison against 1.** "Does any output pixel lack
  source data" is the honest question and is float-robust. The §6 "exactly covers" row yields all-zero
  bands.
- **`resolveCropGeometry` returns a discriminated union** with an `unresolvable` branch for
  `empty-frame`, `empty-source` and `invalid-zoom`, following `resolveFormat` and the rule that nothing
  in `src/domain/` throws. A Vue component reading its container before layout gets 0×0, and a
  `drawScale` of 0 would propagate `Infinity` into the output chips.
- **The typed-dimension inverse anchors on the rectangle's centre**, so typing a width preserves the
  framing rather than dragging the rectangle toward a corner.
- **`FrameRect` uses `left`/`top` where `NormalisedRect` uses `x`/`y`.** Neither is assignable to the
  other in either direction, so the compiler rejects a coordinate-space mix-up with no brand machinery
  and no constructor function, and `as const satisfies` literals still work in fixtures. Rejected: a
  `unique symbol` brand — required brands fight the house test style, optional ones give no protection,
  and branding only `FrameRect` leaves it assignable *to* `NormalisedRect`, the dangerous direction.

## Surprises

- The two §6 output formulas are not interchangeable in floating point. §6 presents `outW = rw /
  drawScale` as the definition and says "the table above is literally a test fixture", which is true of
  the table but not of the formula: it disagrees with the frame-free derivation the pipeline must use
  in roughly a third of random configurations, and by a whole pixel in constructible ones. The module
  is built around the source-fraction formula as a result. §6's text is not wrong for the interface;
  it is just not the formula that can be shared with T24.
- The §6 `drawScale` column is exactly representable. `800/4000` and `600/3000` produce the identical
  double, and `0.2 × 2`, `× 0.5` and `× 0.25` are exactly `0.4`, `0.1` and `0.05`, because all three
  are power-of-two scalings. The fixture's literals are therefore honest rather than approximations.
- A uniform shrink-and-grow constraint breaks the minimum size under a free ratio, as above.

## What the next task should know

- Import from `@/domain/edit`. T24 wants `resolveCropOutput`, `resolveEditedSize`, `hasCropOp` and
  `rotateSize` — none of which take a frame. **T24 must import `resolveCropOutput` rather than
  reimplement it**; that is what makes its "to the pixel" condition true by construction.
- **T24 must fill the whole output with the background first, then draw the source at
  `placement.offsetX/offsetY`.** The four spill bands are rounded independently and can be off by one
  against each other, so painting them by subtraction will leave seams.
- **`EditOp.zoom` is interface restore state only (R-C10).** The rectangle alone determines output
  size; `resolveEditedSize` never reads zoom, and the pipeline must not either.
- R-C3's "frame" and §6's `Wf, Hf` are different things. §6's frame is the fixed stage area and does
  not swap on rotation; R-C3 means the image's displayed box, which is `imageRect` here. The module
  holds `frame` immutable across rotation and recomputes `imageRect`. Getting this backwards is the
  most likely implementation error in T37.
- Do not "tidy" `FrameRect` and `NormalisedRect` into one shared rectangle type. The differing field
  names are the only thing keeping the two coordinate spaces apart.
- Ratio work is done in frame space because `drawScale` is isotropic, so a frame rectangle's aspect
  ratio equals its output's. In normalised space it would not, since each axis is divided by a
  different source dimension.
- `constrainCropRect` assumes a positive frame; `resolveCropGeometry` guards that, but a direct caller
  passing a zero frame will get non-finite results.
- Zoom-out is unbounded here: `z = 0.01` on a 4000×3000 source predicts 400000×300000. The bound
  belongs to T37's zoom slider minimum and the §8.3 limits module (T50). A `maximumOutputPixels` would
  slot into `CropLimits` without a signature change.
- `RATIO_IDS` is ordered as the §3.4 row presents it, and `aspectRatioFor` is the accessor; T37 should
  render from those rather than restating the list.

## Open question for the design documents

Four of the decisions above are user-visible behaviour that the design documents do not record.
**Functional Design R-C12 should carry the 16-output-pixel minimum, and R-C3 should carry the rotation
reset, the zoom reset and the ratio-label-persists rule.** They were put to the project owner and
answered before implementation, so this task is not blocked, but the documents are currently silent on
behaviour the code now commits to.
