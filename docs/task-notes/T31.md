# T31 — Shell, routing and static generation

**Status:** complete

## What was built

The placeholder root T04 built (`App.vue`'s "icompress scaffold OK", with T07's `TokensDemo`
and T08's `I18nDemo` mounted on it) is gone. In its place: a routed, statically generated site
(`vue-router` + `vite-ssg`, `src/config/site.ts`) with one real route — the compressor tool at
`/` — and the tool's own header/stage/side-panel shell (`src/app/ToolPage.vue` and
`src/app/shell/*`), responsive at 900px with a focus-trapped mobile drawer. Four stage-mode
placeholder components (`src/ui/{gallery,preview,edit,processing}/*.vue`) prove the exclusive
mounting mechanism `<component :is>` gives T32–T38 to build real content on top of. Assumption
F1 (vite-ssg produces genuinely static per-route HTML) is settled: `TESTED`, `95%`.

## Decisions made

- **`useStageMode`'s ref is a module-scope singleton, not per-instance state**, deliberately —
  it's what `useUiStore` (T32) replaces. Documented in the file itself. Chosen over local
  component state because the design docs (`docs/ui-design.md` §4) already describe stage mode
  as shared, store-owned state; a per-instance ref would misrepresent that and give T32 nothing
  real to "take over."
- **Router loops over `supportedLocales` now**, even though there's only one locale, rather than
  hardcoding a single `/` route. Technical Design §12.3 requires the same build step to produce
  locale-prefixed paths later with no second mechanism; writing the loop now is what makes that
  true without T44/T48 having to restructure `router.ts`.
- **T31 registers only the `/` route**, not stub entries for `/faq`/`/privacy`/`/terms`/`/desktop`.
  The task brief is explicit that those "arrive with their pages in T44" — adding empty stub
  routes now would be inventing scope T44 didn't ask for and might not want the shape of.
- **Focus trap is hand-rolled** (`useFocusTrap.ts`, ~90 lines), not a dependency. The behaviour
  R-K3 needs is small and fully specified; nothing in Technical Design §1's curated stack
  anticipates a focus-trap library, and this project's established pattern (no bundled webfonts,
  deliberately minimal dependency list) favours writing the ~40 lines of real logic over adding
  a package for it.
- **Primary action hides entirely during Processing, on both layouts** (`ToolPage.vue`'s
  `showPanel`). `docs/ui-design.md` §2 states the side panel — where the desktop anchor lives —
  "is not shown during Processing... replaced entirely by run status," and §13 gives Processing
  its own action set (Cancel, then Download/Back, T38's job). This was flagged as a possible
  open question during planning but is directly supported by that text, not an invented
  interpretation.
- **`PrimaryActionButton` hardcodes `disabled: true`, `count: 0`** rather than accepting a
  store-shaped prop. `useBatchStore` doesn't exist yet (T32 runs after T31); inventing its shape
  here isn't this task's job. A `TODO(T32)` comment marks the one line to change.
- **Stage-mode placeholders use their real, eventual filenames** (`src/ui/gallery/Gallery.vue`,
  not `GalleryStub.vue`) so T33–T38 fill them in place rather than renaming a throwaway.
- **No separate `Drawer.spec.ts`/`SidePanel.spec.ts`.** Their behaviour is covered at three
  levels that don't overlap: `useFocusTrap.spec.ts` (the trap mechanism in isolation),
  `ToolPage.spec.ts` (presence/absence of the static panel vs. the drawer, and the primary
  action, per breakpoint and stage mode), and the Playwright suite (real focus-API integration:
  Tab cycling, `:focus` after close). Adding component-level specs on top would duplicate one of
  these without adding coverage.
- **No slide/fade transition on the drawer or scrim.** `docs/ui-design.md` §15 asks for one, but
  T31's Done-when doesn't gate on it and a full motion/`prefers-reduced-motion` pass is T47's
  job. Left as a plain `v-if` rather than risk an incorrect `<Transition>` implementation for a
  cosmetic detail nothing here depends on.
- **F1 verification is a standalone Node script** (`scripts/verify-ssg-html.mjs`), not a
  Vitest/Playwright test, per the task's own "no script execution" wording — a `node:fs` read is
  the literal, unambiguous satisfaction of that; even a headless browser with JS disabled is
  still a browser engine.

## Surprises

- **`vue-router` is now at major version 5** (installed `5.3.1`), not the 4.x line this project's
  design docs and my own prior general knowledge assumed. It resolved with no peer-dependency
  warnings against `vue@^3.5.42` and `pinia@^4.0.3`, and its API used here (`createRouter`,
  `RouteRecordRaw`, `RouteRecordSingleView`, `<router-view>`) behaved as expected — but the type
  for a plain single-component route is `RouteRecordSingleView`, not something safely extracted
  as `RouteRecordRaw['component']` (that union-indexed type resolves to
  `RawRouteComponent | null | undefined` across all of `RouteRecordRaw`'s members, which doesn't
  satisfy `RouteRecordSingleView`'s stricter `component: RawRouteComponent`). Worth flagging for
  T44/T48: check `RouteRecordRaw`'s exact shape in the installed version before assuming 4.x-era
  patterns from memory or documentation.
- **`.vue` files aren't linted with a type-aware TS `project`** in this repo's `eslint.config.js`
  (only plain `.ts` files are, implicitly via typescript-eslint's default project service). This
  means base ESLint's `no-undef` can't resolve ambient DOM lib globals (`HTMLElement`,
  `MouseEvent`, ...) referenced in type position inside `<script setup>`, and false-positives on
  them. Never surfaced before T31 because no earlier `.vue` file used a DOM type by name.
  Resolved by disabling `no-undef` for `.vue` files specifically — `vue-tsc` already covers this
  correctly and is the authoritative check, running before `eslint` in `pnpm check`.
- **Importing `ToolPage.vue` unmocked in a Vitest spec fails at Vite transform time**, not
  runtime: `router.spec.ts` (which only wants to check route shape) transitively pulls in the
  real `@/pipeline/codecs/loader.ts`, whose `ensureQuantizer()` has a dynamic
  `import("imagequant")` — a package `vite.config.ts` deliberately excludes from pre-bundling
  (T27's wasm-bindgen double-instance workaround). Vite's import-analysis plugin tries to
  resolve that specifier at transform time regardless of whether the function is ever called,
  and fails under Vitest specifically (this exact import chain had never been exercised by a
  test before T31). Fixed by mocking `@/pipeline/codecs/loader` in every spec that transitively
  imports `ToolPage.vue`, same as `App.spec.ts`/`ToolPage.spec.ts` already needed to for the
  WASM-preload side effect itself. Not investigated further — root-causing the T27 exclusion's
  interaction with Vitest's transform pipeline isn't this task's job, but a later task touching
  `loader.ts` or `vite.config.ts`'s `optimizeDeps` should know this exists.
- **`useFocusTrap`'s `watch` needed `immediate: true`**, discovered by its own unit tests: a
  `watch(active, ...)` without `immediate` never fires if `active` is already `true` at the
  moment the composable runs (there's no "previous value" to compare against, so nothing counts
  as a change) — it only reacts to actual transitions afterward. Caught because three of five
  `useFocusTrap.spec.ts` cases mount with `active: true` from the start rather than toggling it
  on. Doesn't affect `Drawer.vue`'s real usage today (`ToolPage.vue` always mounts it with
  `drawerOpen: false` and the user opens it afterward, a real transition), but would have been a
  live bug the moment anything mounted a `Drawer` already open. Fixed, with the reasoning kept
  in the composable's own comment.
- **`vite-ssg@28.3.0` installed with no peer-dependency friction against `vite@^8.3.0`** — this
  was an open, flagged risk going into implementation (the task brief's own note that F1's
  fallback clause exists partly for this reason). No substitution was needed.
- vite-ssg's own internals log a `[VUE_ROUTER_R0025]` deprecation warning ("The `next()`
  callback in navigation guards is deprecated") to the console on every route render, under
  vue-router 5. This comes from vite-ssg's own router setup, not from any code this task wrote —
  no navigation guards exist anywhere in `src/`. Harmless (doesn't fail any test or build step)
  but worth knowing it's not this task's bug if it's still there when a later task touches
  routing.

## Requirements covered

R-R1 (space-driven breakpoint at 900px, not device-driven), R-R2 (stage toolbar row wraps,
never scrolls — structural only, no toolbar content exists yet to actually wrap), R-A1 (primary
action visible in both layouts, at all times except the one condition the design docs
themselves carve out — Processing), R-A3 (disabled when the batch is empty — hardcoded true,
since no batch mechanism exists yet), R-S1 (the tool is one route; its four stage modes are
never URLs), R-M4 (mode switch releases the outgoing mode's state via real unmount, proven by
`ToolPage.spec.ts`), R-K3 (drawer focus-trapped, Escape closes it, focus returns to the Options
button on every close path). R-R3/R-R4 (44px touch targets, larger crop-handle hit areas) are
addressed for the controls this task built (Options, Hide, primary action all ≥44px) but the
crop-handle half is Edit mode's own concern, T37. R-A2/R-A4, R-D1–R-D4, R-Q1–R-Q5,
R-F1–R-F8 are out of scope — those are T35's settings content, not this task's structural shell.
