# T04 — Project scaffold

**Status:** complete

## What was built

A working Vite + Vue 3 (`<script setup>`) + TypeScript (`strict`, `noUncheckedIndexedAccess`) + Pinia +
Vitest scaffold. `pnpm check` (vue-tsc + ESLint + Prettier) and `pnpm test` (Vitest) both pass on a clean
checkout, and the same commands work verbatim as `npm run check` / `npm test`. A minimal Vue app entry
(`src/app/main.ts`, `src/app/App.vue`) boots the app with Pinia installed, verified both by `vite build`
producing a working bundle and by `vite` dev-serving it. The `src/` tree is otherwise untouched from the
existing skeleton, which already matched Technical Design §2 exactly.

- `package.json` — added `dependencies` (`vue`, `pinia`), `devDependencies` (build/lint/test toolchain),
  and real `scripts`: `dev`, `build`, `preview`, `type-check`, `lint`, `format`, `format:check`, `check`,
  `test`. `check` and `test` keep the generic names the Done-when criteria and AGENTS.md ask for, and their
  command bodies call the underlying binaries directly (not `npm run <script>` internally) so they work
  unchanged under either `pnpm check`/`pnpm test` or `npm run check`/`npm test`.

- `tsconfig.node.json` — covers `vite.config.ts` and `vitest.config.ts` (Node types, not DOM). Same

## Decisions made

- **TypeScript pinned to `5.9.3`, not the `7.0.2` that `pnpm add typescript` resolved to latest.**
  `typescript-eslint@8.70.0` declares a peer range of `>=4.8.4 <6.1.0`; installing TS 7 produced an unmet
  peer warning (`pnpm peers check`). `vue-tsc@3.3.11` only requires `>=5.0.0`, so 5.9.3 (latest 5.x) is the
  newest version that satisfies both. Rejected: staying on TS 7 and ignoring the peer warning — untested
  combination, and the whole point of this task is a toolchain that gives real, trustworthy feedback, not
  one running against unverified type-checker versions.
- **Manual `tsconfig.*.json` rather than extending `@vue/tsconfig`.** The official Vue scaffolds pull in
  `@vue/tsconfig` as a base. Wrote the compiler options out directly instead, so every strictness setting
  (`strict`, `noUncheckedIndexedAccess`, `moduleResolution`, etc.) is visible in this repo rather than
  inherited from a package whose defaults could change on update. One more dependency avoided; the
  three-file split (root solution file + `tsconfig.app.json` + `tsconfig.node.json`) is still the standard
  shape so `vue-tsc -b` gets a real project-reference graph (DOM lib for app code, Node lib for config
  files, not mixed).
- **No `verbatimModuleSyntax` / `isolatedModules`-adjacent extra strictness beyond what was asked.** The
  task specifies `strict` + `noUncheckedIndexedAccess` explicitly; added `isolatedModules` since Vite's
  esbuild transform requires it for correctness (not a style choice), but didn't add
  `verbatimModuleSyntax` or other opinionated flags not named in the brief — keeps the scaffold to what
  was asked rather than inventing additional constraints later tasks would have to live with.
- **ESLint: `typescript-eslint` "recommended" (not "recommended-type-checked").** Type-checked linting
  needs `parserOptions.project` wired per-file (including for `.vue` `<script>` blocks), which adds real
  setup complexity and lint latency. `vue-tsc` already does full type checking as a separate, faster-to-run
  step in `check`; ESLint's job here is the non-type-aware rule set (unused vars, `no-explicit-any`-style
  correctness, Vue-specific rules) rather than duplicating type inference. Can be upgraded to
  type-checked linting later if a task specifically wants it; noting the alternative here per the task
  brief's request to record rejected options.
- **Root config files (`vite.config.ts`, `vitest.config.ts`) linted, not excluded** — added a small
  `files: ['*.config.ts']` block in `eslint.config.js` rather than ignoring them, so they get the same
  machine-checked feedback as everything else.
- **Prettier config kept minimal**: `semi: false`, `singleQuote: true`, `printWidth: 100`. Nothing that
  conflicts with `noUncheckedIndexedAccess` or TS strictness — Prettier only touches formatting, never
  type-level behaviour, so there was no actual tension to resolve here.
- **`.prettierignore` / ESLint `ignores` exclude `docs/`, `3rd_party_licenses/`, `verification/`,
  `tests/`.** `verification/*` are each their own `package.json` project (T01–T03 already have their own
  tooling, if any); `3rd_party_licenses/` holds upstream licence text that must not be rewritten;
  `docs/` is prose maintained outside this task's scope; `tests/` is currently just a `.gitkeep` awaiting
  T05. Also excluded `AGENTS.md`, `CLAUDE.md`, `NOTICE.txt`, `LICENSE` at root specifically — `prettier
  --check .` initially flagged `AGENTS.md` as unformatted; reformatting a pre-existing hand-maintained doc
  as a side effect of a scaffold task looked wrong, so it's ignored rather than rewritten.
- **The trivial Vitest module-resolution test mounts `App.vue` with `@vue/test-utils` rather than
  importing a plain value.** A bare `import x from '@/something'; expect(x).toBe(...)` would prove alias
  resolution but nothing about the SFC compile pipeline. Mounting the real root component through the
  alias exercises both at once, and doubles as the "Vite+Vue+Pinia boots" proof the task asked for (Pinia
  itself isn't exercised by this specific test, but `main.ts` wires it and both `vite build` and `vite`
  dev-serving were run manually to confirm the whole entry point boots — see Surprises/verification below).

## Surprises

- **Vite 8's "native" config loader warns on extensionless config imports.** `vitest.config.ts` originally
  did `import viteConfig from './vite.config'` (the form used by older Vue/Vitest scaffolding examples).
  Vite 8 printed a deprecation warning that this will stop working when the native (Rust-based, presumably)
  config loader becomes default. Fixed by importing `./vite.config.ts` with the explicit extension, which
  in turn needed `allowImportingTsExtensions: true` added to `tsconfig.node.json` (TS otherwise rejects a
  `.ts`-suffixed import path). Worth remembering for any future root-level `*.config.ts` that imports
  another one.
- **`vue-eslint-parser` had to be added as a direct devDependency.** `eslint-plugin-vue` depends on it, but
  under pnpm's default strict `node_modules` layout, `eslint.config.js`'s own `import 'vue-eslint-parser'`
  couldn't resolve it as a transitive dependency — pnpm doesn't hoist it into a place plain Node ESM
  resolution can see from the repo root. Added it directly; this is a pnpm-strictness detail, not a bug in
  either package.
- Otherwise nothing surprising: `pnpm add` resolved current, mutually-compatible versions for everything
  else on the first try (Vue 3.5.42, Pinia 4.0.3, Vite 8.3.0, Vitest 5.0.0, ESLint 10.10.0,
  `eslint-plugin-vue` 10.11.0, `typescript-eslint` 8.70.0, `vue-tsc` 3.3.11, Prettier 3.9.6), and both
  `vue-tsc -b` and `eslint .` were clean on the first full run once the two items above were fixed.

## What the next task should know

- `pnpm check` runs `vue-tsc -b --force && eslint . && prettier --check .`, in that order — cheapest/most
  informative failure first. `--force` on `vue-tsc -b` is there so a stale `.tsbuildinfo` never hides a
  real type error; the build info files live under `node_modules/.tmp/`, already excluded from version
  control via the existing `node_modules/` ignore.
- The `@` alias (`@/...` → `src/...`) is defined in exactly one place, `vite.config.ts`, and mirrored in
  `tsconfig.app.json`'s `paths` for editor/type-checker support; `vitest.config.ts` inherits it by merging
  `vite.config.ts` rather than redeclaring it. If a future task adds more aliases, add them to both of
  those two spots (`vite.config.ts` resolve.alias, `tsconfig.app.json` paths) and Vitest picks it up for
  free.
- ESLint is currently non-type-aware (`typescript-eslint` "recommended", not "recommended-type-checked" —
  see Decisions made). If a later task wants type-aware lint rules, that's an ESLint config change, not a
  scaffold gap — flag it as a deliberate upgrade rather than assuming it was missed.
- `src/app/App.vue` and `src/app/main.ts` are deliberately throwaway placeholders. T31 ("Shell and
  layout") is expected to replace `App.vue`'s content wholesale; `src/app/App.spec.ts` will likely need
  rewriting or removal at that point too, since it currently asserts the placeholder text.
- `verification/*` projects each carry their own `package.json`/`pnpm-lock.yaml` and are intentionally
  outside the root `check`/`test`/ESLint/Prettier scope — don't try to fold them into the root toolchain.
- Package manager note per AGENTS.md: this task used `pnpm` (matching the pinned `packageManager` field in
  `package.json`, `pnpm@11.13.0`) for every install; all script bodies avoid depending on which package
  manager invoked them.
