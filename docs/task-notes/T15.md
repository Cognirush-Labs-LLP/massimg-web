# T15 — Caveats and the report model

**Status:** complete

## What was built

`domain/report.ts` now builds the complete report model from run outcomes and serialises it as valid,
locale-independent YAML. It counts successes without listing ordinary ones, omits non-images, prefers
folder-relative paths for every detail entry, restricts exact bytes to summary totals, and renders the
closed nine-member R-X46 caveat set.

The required fixture covers failures, skipped unsupported images, non-images, an ordinary success and
four distinct caveats, and proves that the emitted YAML parses back to the identical report model.

## Decisions made

- **All nine R-X46 caveats are implemented.** T15 originally said eight while R-X46 and the existing
  core union list nine. The project owner explicitly resolved the conflict in favour of all nine,
  including Auxiliary images dropped, and approved correcting the task text.
- **The visible title is `# Mass Image Compressor`.** The original unkeyed title made the sample invalid
  YAML (`js-yaml` reported “end of the stream or a document separator is expected”). The project owner
  approved the comment form, which preserves Run, Summary, Settings, Failed, Skipped and Notes as the
  documented top-level model.
- The in-memory model uses the report's exact human-facing keys. Parsing the YAML therefore produces the
  same model directly, without a second mapping layer that could drift from serialization.
- All dynamic strings are emitted as JSON-style double-quoted scalars, which are valid YAML scalars.
  This preserves values such as `yes`, `null`, timestamps, colons and comment characters as strings
  across parsing rather than letting YAML infer another type.
- Each caveated success produces one Notes entry. When a success carries multiple caveats their fixed
  messages are joined in caveat order, so one success is still listed once rather than looking like
  multiple processed files.
- Summary byte totals are computed from successful outputs, the only results for which input/output
  savings reconcile. Failed and unsupported images are counted in their categories but do not create
  fictitious output savings. `Images processed` is the sum of succeeded, failed and skipped image
  categories, matching the §9.3 example; non-images are excluded.
- White and black transparency fills use their natural names; other fills use exact `rgb(r, g, b)`
  notation. Per-file byte-bearing caveats use the report size formatter, never raw exact byte fields.
- `js-yaml` 4.3.2 is MIT-licensed and used only by the unit test to independently parse output. The
  production serializer has no dependency, so `js-yaml` is not bundled or statically linked into the
  application and does not require a `3rd_party_licenses/` bundle attribution entry.

## What the next task should know

- Import `buildReport`, `serializeReport` and the report input/model types from `@/domain/report`.
- Give each file a `name` and its folder-root-relative `relativePath` when present; the builder chooses
  the relative path consistently for Failed, Skipped and Notes.
- Pass unsupported images through `skippedImages`. `nonImages` exists only so classification output can
  be passed without pre-filtering; it is deliberately ignored. Do not turn hidden/system files or other
  non-images into skipped report entries.
- Success caveats remain structured `Caveat[]` until `buildReport` renders them. Do not construct free-form
  note text in the pipeline or add ad hoc caveat kinds.
- `serializeReport` returns the report contents, not a filename or Blob. T41 owns writing it as
  `image_compression_report.txt` into the archive.
