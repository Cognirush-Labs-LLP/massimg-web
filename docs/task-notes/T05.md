## Decisions made

- **GitHub Actions**, per the task brief's own suggestion — de facto standard, nothing in the docs names
  an alternative CI provider, and no existing CI config exists to preserve.
- **`webServer` runs the Vite dev server (`vite --port 5173 --strictPort`), not a production preview
  build.** Rejected alternative: `vite build && vite preview`. Reasons: (1) `check` already runs
  `vue-tsc -b` as its own CI step, so building again inside the e2e job would duplicate type-checking
  work for no new signal; (2) a plain `vite build` (skipping the type-check half) would test a
  differently-configured artifact than what `check` verified, which seemed like a worse trade than just
  testing the dev server; (3) speed — the dev server starts in ~150-200ms locally vs. a multi-second
  build. This suite only needs to prove the app boots in a real browser right now; if a later task's
  browser tests need production-build fidelity (minification, real asset hashing, etc.), that's a
  `playwright.config.ts` change to make then, called out below under "What the next task should know."
- **Fixed port (5173) with `--strictPort`, not an ephemeral port.** Keeps the `webServer.url` and
  `use.baseURL` static and avoids a class of flakiness where Playwright's readiness probe races a
  dynamically-chosen port. `reuseExistingServer: !process.env.CI` means a dev server already running
  locally (e.g. from `pnpm dev` in another terminal) is reused rather than double-started; CI always
  starts fresh.
- **No changes to `App.vue`.** T04's placeholder already renders a static, assertable string
  (`icompress scaffold OK` inside a `<p>`) with no interactivity, so the placeholder test asserts that
  text directly via `page.getByText(...)` rather than adding a `data-testid`. Nothing needed touching.
- **Three parallel top-level CI jobs (`check`, `unit`, `e2e`), not sequential/dependent.** Rejected
  making `e2e` depend on `check`/`unit` succeeding first (via `needs:`) — that would be marginally
  cheaper on a broken PR (fail fast, skip the browser matrix) but slower on the common case (green PRs
  pay the full matrix wall-clock on top of, rather than alongside, the cheaper checks). Nothing in the
  docs specifies either way; parallel felt like the better default and is easy to change to `needs:` if
  CI cost becomes a concern.
- **`playwright install --with-deps <single-browser>` per matrix leg**, rather than installing all three
  engines once in a shared job and fanning out. Slightly more total download across three runners, but
  keeps each matrix leg fully independent (no artifact-passing needed) and lets `fail-fast: false` show
  all three engines' results even if one fails, which is closer to the Done-when condition ("passes on
  all three engines") than a single combined job would demonstrate.
- **Playwright reporter switches to `github` + `html` in CI, `list` locally** — the `github` reporter
  annotates failures inline on the PR diff (visible in the `actionlint`-checked workflow's default
  GitHub Actions environment detection via `process.env.CI`), `html` report is uploaded as a build
  artifact for post-hoc inspection; `list` locally is just quieter/faster to read in a terminal.
- **`tests/**/*.ts` and `playwright.config.ts` folded into `tsconfig.node.json`** rather than a new
  `tsconfig.playwright.json`. They're root-level tooling/tests, not part of the app bundle or the
  Node-config-only original scope of that file, but adding a fourth tsconfig for one file plus one
  directory seemed like more ceremony than the one-line `include` addition, and Playwright's types don't
  need anything `tsconfig.node.json` doesn't already provide (no DOM lib requirement).
- **Lint/format now cover `tests/`** (previously excluded by T04 in anticipation of this task). Decided
  against leaving `tests/` unlinted/unformatted now that it holds real, permanent content — "tests are
  part of the task, not a later task" (AGENTS.md) reads as applying to code quality tooling too, not
  just test coverage.

## What the next task should know

- `pnpm test:e2e` runs the full three-engine Playwright suite locally (spawns and tears down its own dev
  server via `webServer`); `pnpm exec playwright test --project=chromium` (etc.) runs a single engine.
  `pnpm exec playwright show-report` opens the last HTML report if one was generated.
- The e2e suite currently boots against the **dev server**, not a production build — see Decisions made.
  A future task adding real feature coverage (folder input, OPFS, download, worker cancellation —
  Technical Design §13's "Browser" row) should reassess whether dev-server fidelity is still good enough,
  particularly for anything sensitive to bundling/minification/worker chunking differences, and switch
  `webServer.command` to a build+preview pair if not.
- `tests/e2e/app.spec.ts` will need rewriting once `App.vue` stops being a placeholder (T31, "Shell and
  layout" — same caveat T04 already flagged for `src/app/App.spec.ts`). Don't treat this placeholder
  test as a template for real coverage; it deliberately asserts nothing about actual product behaviour.
  Real browser tests belong in `tests/e2e/` alongside it (or in subdirectories, if the suite grows large
  enough to want that).
- `playwright-report/` and `test-results/` are generated locally by any Playwright run; both were already
  in `.gitignore` (T04-era, anticipating this task) and are now also in `.prettierignore` and ESLint's
  `ignores`. Delete them freely; they're regenerated on the next run.
- CI's `e2e` job installs browsers fresh every run (`playwright install --with-deps`) rather than caching
  the Playwright browser binary cache across runs. That's the simpler, more reliable default (matches
  Playwright's own CI documentation); revisit only if install time becomes a measured bottleneck.
- Local verification commands and their exact output are recorded in this task's completion report to
  the orchestrating session; the short version: `pnpm check` — pass, `pnpm test` — 1 passed, `pnpm exec
  playwright test` — 3 passed (chromium, firefox, webkit), each run independently confirmed again with
  `CI=true` set to sanity-check the CI-mode config path (single worker, `forbidOnly`, github reporter)
  behaves the same.
