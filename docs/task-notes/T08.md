# T08 — i18n scaffold

**Status:** complete

## What was built

The two parallel locale files (`src/i18n/en/messages.json`, `src/i18n/en/context.json`) with three
real example keys, a small `t()` lookup/interpolation helper (`src/i18n/t.ts`), a Vitest-based CI
check that fails when `messages.json` and `context.json` disagree in either direction
(`src/i18n/i18n-consistency.spec.ts`), a custom ESLint rule that flags runtime concatenation of
`t(...)` results (`eslint-rules/no-translated-string-concat.js`, wired into `eslint.config.js` and
therefore into `pnpm check`), and a demo component (`src/app/I18nDemo.vue`, mounted from `App.vue`
behind a "T08 marker" block, same pattern as T07's `TokensDemo`) that renders a parameterised string,
with a Vitest component test asserting the interpolated DOM output.

## Decisions made

- **`context.json` schema**: a flat object keyed by the same message key, each value
  `{ "situation": string, "control": string, "maxLength": number | null }`. `situation` covers "the
  situation it appears in" (Technical Design §11 / R-L2), `control` covers "what the surrounding UI
  does", `maxLength` covers "any length constraint" (`null` when none is known/applicable — none of
  the three example keys had a design-doc-specified pixel/character budget, so `maxLength` values here
  are reasonable implementation guesses, not measured constraints, and are flagged as such in prose
  inside each entry where relevant). Rejected a richer schema (e.g. separate `partOfSpeech`,
  `pluralization` fields) as speculative — nothing in R-L2 or §11 asks for more than free-form prose per
  key, and a rigid schema invented now would likely need reshaping once real translator tooling
  (T48/later) is chosen.
- **Interpolation syntax: single curly braces, `{count}`**, not `{{count}}` or `%{count}`. Simplest
  legible option, visually distinct from a JS template-literal `${...}` slot, and happens to match
  vue-i18n's own named-interpolation syntax — not a dependency on vue-i18n today, but keeps a future
  migration to a real i18n runtime (T48) low-friction if that's the library eventually chosen.
- **`t()` throws on an unknown key or missing param**, rather than returning the raw key or a
  best-effort partial string. Chosen over silent fallback because Functional Design P1 ("silence is the
  failure, not the operation") reads as applying to development-time authoring bugs too — a missing
  translation key is exactly the kind of thing that should fail loudly rather than ship a broken string.
  `MessageKey`'s literal-union type already prevents most of this at compile time for static call
  sites; the runtime throw is the fallback for the (currently nonexistent, but plausible later) case of
  a dynamically-constructed key.
- **CI check implemented as a Vitest test (`pnpm test`), not a standalone script** (T06's
  `check-licenses.mjs` precedent, offered by the task brief as an alternative). `pnpm test` already runs
  as its own CI job (T05's `unit` job), the check is a fast, pure comparison of two already-parsed JSON
  objects, and a Vitest test gives a clear pass/fail per assertion with automatic wiring into `pnpm
  test` — no new script, no new `package.json` entry, no new CI step needed.
- **CI check enforces both directions**: `messages.json` key without `context.json` entry (what R-L2
  literally asks for) AND `context.json` entry without a matching `messages.json` key (the reverse, not
  explicitly required). Chose to enforce both because the reverse direction is free to check and catches
  a real failure mode — a stale context entry left behind after a key is renamed or removed, silently
  describing a string that no longer exists. Demonstrated to fail only on the forward direction in this
  task's proof, since that's what the task's own proof pattern names ("a deliberately orphaned key" — a
  `messages.json` key with no `context.json` entry); the reverse direction's assertion is exercised
  by every normal run of the suite (it currently passes because no orphaned `context.json` entry exists)
  and is the same code path, not a separately-proved mechanism.
- **CI check hardcoded to the `en` locale directory**, not scanning `src/i18n/` for locale directories
  at runtime. Considered a Node-`fs`-based directory scan (mirroring T06's `check-licenses.mjs`), but
  `src/i18n/*.spec.ts` files are type-checked under `tsconfig.app.json` (the browser-app project, "types":
  ["vite/client"] only, no Node lib) — `node:fs`/`node:path` imports fail `vue-tsc -b` there. Considered
  `import.meta.glob` instead, which does work under `tsconfig.app.json`, but its path-parsing adds
  complexity for a payoff (a second locale) that doesn't exist yet. Went with the same choice `t.ts`
  already made: hardcode `'en'`, document it, and revisit both files together when a second locale is
  real.
- **The no-concatenation check is a custom ESLint rule** (`local/no-translated-string-concat`,
  registered inline in `eslint.config.js`, no new npm dependency), not an existing plugin's rule or a
  Vitest test. No off-the-shelf ESLint rule targets "concatenation of a named function's call result"
  specifically (searched for one; `i18next`/`vue-i18n` ESLint plugin ecosystems have rules for missing
  keys / unused keys, not this). A custom rule can inspect the AST directly (`BinaryExpression`,
  `TemplateLiteral`) at lint time, which a Vitest test cannot do without re-parsing source files itself
  — ESLint already owns that parsing pipeline via `eslint.config.js`, matching T07's precedent of wiring
  a real static-analysis tool (`stylelint-use-logical-spec`) into `pnpm check` rather than hand-rolling
  the check as a test.
- **Rule scoped to `src/**/*.{ts,vue}`** (mirroring the `scripts/**/*.mjs` and `*.config.ts` file-scoped
  overrides already in `eslint.config.js`) — `t()` is only ever called from application source, not from
  build scripts or config files.

## How the no-concatenation check works (and its limits)

`eslint-rules/no-translated-string-concat.js` catches two patterns, name-matched on a function called
`t` (not type-checked — this is a plain ESLint rule, not a typed one, so it has no way to confirm the
`t` being called is actually `src/i18n/t.ts`'s `t`):

1. A `+` binary expression where any operand, walking a left-associative chain of `+`s, is a call to
   `t(...)` — e.g. `t('a') + t('b')`, `t('greeting') + name`, `t('a') + ' ' + t('b')`. Reported once per
   chain (at the outermost `+`), not once per nested `BinaryExpression` node.
2. A template literal with a `t(...)` call in one of its `${...}` interpolation slots — e.g.
   `` `${t('greeting')}, ${name}!` ``.

Proven during this task (see Verification below) by temporarily adding both forms to
`src/app/I18nDemo.vue`, confirming `pnpm exec eslint` fails with the rule's message on each, then
reverting and confirming `pnpm check` passes clean again.

**Documented, deliberate limits** (also commented at the top of the rule file):

- Does not catch concatenation through an intermediate variable
  (`const g = t('a'); const s = g + name`) — no data-flow analysis.
- Does not catch `String.prototype.concat`, `Array.prototype.join`, or any other concatenation API
  besides `+` and template literals.
- Flags a template literal with only **one** `t()` call and otherwise-static text too (e.g.
  `` `${t('a')}!` ``), even though that's arguably just interpolating a translated string into markup,
  not composing a sentence from multiple fragments. Distinguishing that case from "one `t()` plus
  another dynamic, possibly-translated fragment" would need type information this rule doesn't have;
  false positives here were accepted as the safer failure mode.
- Matches on the identifier name `t` only — a locally renamed import (`import { t as translate } from
  ...`) would not be caught. No project code does this today.
- Vue `<template>` mustache/directive expressions were **not verified** — `vue-eslint-parser` is
  believed to expose those as ordinary ESTree nodes to rules (this is how `eslint-plugin-vue`'s own
  rules work), so the rule likely also fires there, but this task's proof only exercised `<script
  setup>` code. A later task that hits a template-side violation should verify this rather than assume
  it, and update this note if it doesn't work as expected.

## Surprises

- `src/**/*.spec.ts` files are type-checked under `tsconfig.app.json` (the browser-app project), which
  has no Node types/lib — a first draft of the CI-check test used `node:fs` to scan `src/i18n/` for
  locale directories, and `vue-tsc -b` failed on it (`Cannot find module 'node:fs'`). Not a bug in the
  existing tsconfig setup — `tsconfig.app.json` deliberately scopes to browser-app code (T04's
  decision) and this file lives under `src/`, so it's subject to that scope. Fixed by dropping the
  Node-`fs` scan in favour of a direct JSON import, as described under Decisions made.
