# T37-A — Same-format output selection

**Status:** complete

## What was built

The pipeline now makes one source-versus-encoded selection after every format-specific encoder.
When the effective output format is unchanged and the source already satisfies the requested edit
and dimensions, an equal-size or larger encode is replaced by the source-side candidate. PNG/APNG
first losslessly optimises that source candidate and compares the resulting bytes with the encoded
candidate. A requested same-format transformation is still honoured; when it grows the file, the
run report records measured input/output sizes.

Preview consumes the same selected bytes and selection descriptor as a run. Its measured size,
percentage, displayed blob and result note therefore describe the output that Processing will
eventually receive rather than the discarded encoded candidate.

## Decisions made

- **Decoded upright dimensions are authoritative.** Before decode, only `Original size` can prove
  that the source satisfies the dimension request. After decode, `needsResize` decides whether any
  dimension mode is a no-op. This avoids trusting container dimensions before EXIF orientation is
  applied.
- **Equal-size ties keep the source.** “Not smaller” is deliberately `>=`, matching the clarified
  R-X24 language and avoiding a byte replacement with no size benefit.
- **Any explicit edit is ineligible even when its final dimensions happen to match.** A square
  rotation or same-sized crop is still a requested pixel transformation, so returning the source
  would violate R-X45.
- **PNG/APNG compares the best source-side candidate.** The raw source is first passed through the
  existing lossless PNG optimiser, and that candidate competes directly with the encoded result.
  `original-kept` is emitted only when the byte-for-byte source wins; optimiser output is described
  as `optimized-original` without pretending it is the original file.
- **Selection and reporting are separate.** `OutputJobResult.selection` is always present for both
  intents and drives Preview disclosure. Caveats remain run-only, preserving the existing protocol
  contract while ensuring Preview and Processing choose identical bytes.
- **Stage caveats follow the bytes they describe.** When source-derived bytes win, encoder/edit
  caveats are discarded; pre-resolved job caveats remain. When encoded bytes win, existing stage
  caveats are preserved and a measured `output-larger-than-input` caveat is added only for a real
  same-format transformation.

## Surprises

- A browser-generated low-quality JPEG was not a portable test fixture: Firefox and WebKit encoded
  it differently enough that a quality-70 re-encode sometimes became smaller. The Preview e2e test
  now generates the source with the repository's pinned ImageMagick codec, making the expected
  source-selection outcome deterministic on all three engines.
- The real `bapu.jpg` case supplied for manual verification confirms the originally reported
  symptom is closed: the source and selected Preview output are both 11,207 bytes, the reduction is
  `0%`, the selected blob is the byte-for-byte JPEG source, and Preview states that re-encoding was
  not smaller.
- Wiring R-X24 expanded the already documented BL-001 metadata tension beyond size-target
  pass-through. The FAQ now truthfully says original and losslessly optimised source selections may
  preserve source metadata; this task does not silently choose a new metadata-removal policy.

## What the next task should know

- T38 should persist/download the `OutputJobResult.bytes` it receives. It must not independently
  repeat source-versus-encoded selection; the worker result is already final.
- `selection` is an output/UI disclosure descriptor, not a report caveat. Processing/report code
  should continue reading `caveats`, where `original-kept` now always has a reason.
- Preview and run intentionally differ only in caveats. Tests pin byte and selection equality
  across intents.
