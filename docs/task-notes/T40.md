# T40 — Archive and share-output assembly

**Status:** complete

## What was built

A run-scoped OPFS artifact set (archive plus individual output copies) replacing the T19 single
archive slot; a streaming `client-zip` assembly module that tees each successful output into the
ZIP and, for eligible runs, an individual Share-ready copy, without a second encode or holding more
than one entry in memory; a two-threshold storage preflight that rejects a batch up front or falls
back to Download-only before any job runs; a new mid-run storage-failure halt alongside the
existing out-of-memory one; and the real `downloadFinishedRun()` implementation. Assumptions E1 and
E3 are both closed out with real measurements instead of being left open.

## Decisions made

1. **T39-A, named as a dependency, was not actually done when this task started** — only a
   verification-harness scaffold existed, no measurements, E4 still `OPEN`. Flagged to the user
   before proceeding; the user ran the harness for real (commit `464f8db`) and T40 proceeded
   against its real findings (`maximumShareBytes` ≈ 40 MB, file count not the constraint).
2. **`client-zip` (2.5.1, the latest release) has no compression capability at all, in any
   version** — confirmed from its own documentation and full version history. Technical Design
   §9.1's "stored rather than deflated, per entry" premise assumed a choice the library doesn't
   offer; every entry is always stored. Corrected §9.1 and refuted E3 (100% — this is a library
   capability fact, not a probabilistic measurement) rather than silently working around it.
3. **Naming uses each image's resolved-settings format** (known before dispatch), not
   `OutputJobResult.format` (known only after). These should always agree since `resolveSettings`
   already applies R-F6's substitution before the job is built; if a future case shows them
   diverging, that is a real bug to surface, not something to paper over by renaming post hoc.
4. **Quota preflight estimates each entry's size as its *input* `sizeBytes`**, a conservative
   upper bound, since actual output size isn't known before encoding and the design documents don't
   specify the estimate basis. A same-format output can legitimately be larger (R-X45) but that's
   the rare, already-warned case, not a basis for a hard reservation.
5. **Share-copy quota overhead is a flat 4096 bytes/file**, an unmeasured conservative filesystem
   allowance for Technical Design §9.2's "plus per-file overhead" — not a real measured figure.
   T46/T50 owns replacing it if one ever matters.
6. **`platform/share.ts` is split across T40 and T42** by necessity: T40 needs the preliminary
   batch probe to decide whether to tee at all; the exact completion-time `canShare`/`share()` live
   in the same file but are T42's to add. Confirmed consistent with Technical Design §9.1's own
   description of the split.
7. **The archive's own download filename** (`compressed-images.zip`) is an unspecified, generic
   choice — no design document names one.
8. **A mid-run sink failure (`writeOutputCopy`/`writeArchive` throwing) halts the whole run**,
   following the exact out-of-memory pattern: cancel the pool, clean up, halt with a distinct
   reason. This is Functional/UI Design's "Storage write failure mid-run" row, explicitly flagged
   as deferred by T39's own handover note. It is **distinct** from "ZIP assembly failure" (a
   different §10 row, scoped to *after* a run completes — surfaced next to Download — which stays
   T42's to build).
9. **Storage quota rejection is checked inside `useProcessingRun.start()`**, after the stage has
   already transitioned to Processing, rather than gating the primary-action click in Gallery/the
   side panel. Functionally equivalent to "before a run" (no job is ever dispatched), and keeps the
   change contained to Processing-owned files rather than touching Gallery/SidePanel/the ui store.
10. **One-image runs skip the preflight/sink machinery that assumes a possible multi-image
    archive** entirely (no `client-zip`, no quota check) — the existing per-file `maximumFileBytes`
    selection-time cap already bounds that single file.

## Surprises

**`client-zip` has no compression, in any released version** — see Decision 2 and the E3 rewrite.
The technical design's "per entry" store-vs-deflate language described a choice this library has
never offered; worth remembering that a library named early in a design doc can still turn out not
to match an assumption made about it later.

**WebKit's bundled Playwright build reports `Capabilities.fileShare: true` even in a fully headless,
no-real-OS-share-target context** — matching real desktop Safari's genuine support (T39-A) — while
Chromium's bundled build reports `false`, confirming in practice T39-A's own warning ("Playwright
engine presence is not evidence for a native share sheet") cuts both ways: it can under-report
(Chromium here) as easily as it could over-report. `tests/e2e/capability.spec.ts` and
`tests/e2e/share.spec.ts` assert the real measured value per engine rather than guessing.

**The WebKit `launchPersistentContext` OPFS tests are sensitive to concurrent execution.** Running
several at once (e.g. the whole `opfs.spec.ts`/`capability.spec.ts` file together, or the full
Playwright suite) intermittently produced `UnknownError: The operation failed for an unknown
transient reason (e.g. out of memory)` on otherwise-trivial writes, and one pre-existing T17 test
("detects OPFS as available on WebKit with a real persistent profile") failed once under `--workers=1`
too. Confirmed via `git stash` that the exact same pre-existing failures (that test, plus 7 unrelated
failures in `app.spec.ts`/`gallery-grid.spec.ts`/`gallery-ingest.spec.ts`/`preview.spec.ts`) reproduce
identically on unmodified `main` — this is pre-existing environment flakiness in this session (likely
real system memory pressure from a long, heavy day of testing, including this task's own 3.2 GB
memory harness), not a T40 regression. Every new test in this task passed reliably when retried in
isolation.

**`resolveOutputNames` (T12) was already built anticipating this exact task** — its own doc comment
says "Resolves ZIP-relative output paths in input order," and it had never been called from
anywhere. No surprise in behaviour, but worth flagging that cross-task anticipation like this is easy
to miss without reading the earlier task's domain code directly.

## What the next task should know

- **T41 (Report generation):** the archive's streaming generator (`run-archive.ts`) closes once
  every expected result has landed; it has no built-in extension point for a trailing report entry
  yet. The generator and `openRunArchiveSink`'s `finish()` are the places to add one — append the
  report bytes as one final `client-zip` entry before the queue closes, not after.
- **T42 (Download, share and leaving):** `platform/share.ts` currently has only the preliminary
  probe; add the exact completion-time `canShare`/`share()` to the same file, not a new one.
  `readOutputCopies()` already returns real `File[]` in index order, ready for the exact `canShare`
  call. `run-download.ts`'s `downloadFinishedRun()` is real now; wire the Download button to it
  directly rather than duplicating its single-vs-archive branching. "ZIP assembly failure" (§10,
  distinct from this task's mid-run storage halt) is still unimplemented — it belongs at the point
  T42 reads back the archive for delivery.
- **T46/T50 (Limits):** `maximumShareBytes` (40 MB) and the Share-copy-quota per-file overhead
  (4096 bytes, hardcoded in `run-archive.ts`) are both provisional. T50 re-measures
  `maximumShareBytes` on real iOS/low-memory Android hardware per T39-A's own handover.
- The in-memory (private-browsing) fallback's `checkQuota` still always returns `ok: true,
  available: Infinity` (T19's original gap, untouched here) — meaning a private-browsing run can
  never be rejected or fall back to Download-only by quota today. The reduced cap this needs is the
  same T46/T50-owned figure already deferred by T19.
- `useProcessingRun.ts`'s `start()` is internally async (`runInternal`) but keeps a synchronous
  public signature, matching how `Processing.vue` calls it fire-and-forget from `onMounted`. The
  `generation` guard is checked after each `await` inside `runInternal` itself now, not just inside
  `runOne`, since the preflight's own awaits need the same "was this run superseded" protection.
