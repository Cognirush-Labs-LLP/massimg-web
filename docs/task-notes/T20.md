# T20 — Thumbnails

**Status:** complete

## Headline numbers for later tasks

- **R-G8's automatic mode threshold: 100 files** — the same number as `maximumThumbnails`. **T34 reads
  this.** Above the read budget, grid mode cannot give every tile a thumbnail; the surplus renders as
  placeholders, which is exactly what list mode serves better. Tying it to the limit rather than to an
  independent constant means T46's measurement moves both together.
- **Encoded thumbnail format: WebP at quality 0.75, bounded to 384 px on the long edge** (both axes).
  Already the defaults in `platform/thumbnails.ts`; the rationale and the measured table are in C5.

## What was built

`platform/thumbnails.ts`, the batch-scoped thumbnail service Gallery grid mode will own: a factory
with an injected read budget, a non-reactive encoded-Blob cache, a queue that is replaced rather than
appended on each visible window, and a worker that `stop()` terminates. `platform/thumbnail-render.ts`
holds the generation itself — a `createImageBitmap` decode taken straight to thumbnail scale, the
stored rotation and crop replayed on an `OffscreenCanvas` at that scale, then an encode — and
`platform/thumbnail-worker.ts` is the terminable context it runs in. `config/limits.ts` is the first
piece of the runtime limits module, holding `maximumThumbnails`. A Playwright test proves the budget,
placeholder, no-reread, fast-scroll, injection, edit-fidelity and cancellation clauses on all three
engines, and `verification/t20-thumbnails/` measured generation time, retained bytes and peak memory
over 50 real photographs, closing **C5** at `TESTED 85%`.

## Decisions made

- **The ImageMagick fallback is a seam, not a wired dependency** (confirmed with the user before
  starting). `pipeline/codecs/` is empty and T22 owns `loader.ts` and its lazy-load strategy, with C8
  unmeasured; wiring a 14.8 MB WASM decision into a platform module here would pre-empt that. So
  `ThumbnailServiceOptions.fallbackDecoder` exists and is unwired, a native decode failure is reported
  as `unsupported` (distinct from `failed`), and such a tile stays a placeholder — which R-G10 already
  declares is not an error. The ImageMagick path was still *measured* in the harness, so C5 closed on
  real data. **Measurement changed the shape of this**: desktop WebKit decodes HEIC and TIFF natively,
  so the fallback is a Chromium/Firefox path, not a universal one.
- **`src/config/limits.ts` created here, minimally** (also confirmed with the user). T20 forbids
  hard-coding `maximumThumbnails` anywhere, and Technical Design §8.3 says limits come from one
  configuration module. T46 owns the measured values; this holds the one limit T20 needs at its
  shipped default of 100. T18's `MAX_TRAVERSAL_DEPTH`/`MAX_TRAVERSAL_FILES` were deliberately left in
  `folder.ts` — T46 relocates them alongside their measured values, as T18's note anticipated.
- **A factory, not a module singleton.** The cache and the budget are batch-scoped and Gallery-owned,
  and a factory is what makes the limit injectable without the service knowing where 100 came from.
  `stats().budget` reports whatever was injected, which is how the e2e proves the limit is not baked in.
- **`setVisible()` replaces the pending queue rather than appending.** This is the whole mechanism for
  R-G10's "scrolling quickly must not queue work for every tile it passes", and it belongs to the
  service rather than to T33's virtualization — otherwise the property could not be proven until a UI
  existed. The e2e drives three disjoint windows in succession and asserts at most five reads start
  for twelve tiles.
- **`stop()` keeps the cache; `clear()` releases it.** §10.4 says completed entries persist across
  Gallery/Preview/Edit mode changes so returning to Gallery rereads nothing, while R-G12 stops
  *generation* outside grid mode. Those are two different things and the API keeps them separate:
  T33/T34 call `stop()` on unmount and on entering list mode, whoever clears the batch calls `clear()`.
- **`invalidate()` does not bump the cancellation generation**; it marks the in-flight job dropped only
  when the job is the invalidated one. Bumping the generation would kill unrelated in-flight work every
  time a single image was removed.
- **Neither `invalidate()` nor a failure refunds the read budget.** R-G10 says an attempt is charged
  when reading starts and not refunded after failure or cancellation; the same reading applies to an
  entry released later, otherwise removing and re-adding an image would mint budget.
- **Decode goes straight to thumbnail scale, before the edit is applied.** `resolveEditedSize` gives
  the edited dimensions without decoding anything, which gives the scale, which is passed to
  `createImageBitmap` as `resizeWidth`/`resizeHeight`. Peak decoded cost is therefore `source × scale²`
  rather than a full-resolution bitmap, which is what R-B2/R-B3 and §8.1 ask for. The alternative —
  decode full, then crop and resize — would hold a 48 MB bitmap for a 12 MP source.
- **Both `resizeWidth` and `resizeHeight` are always passed, computed to preserve aspect.** They
  stretch to whatever they are given rather than fitting, so "bound both axes, not only width" is
  arithmetic this code has to do, not something the API does.
- **The crop is replayed through `resolveCropOutput` from `domain/edit.ts`**, not reimplemented. That
  function is documented as the only place a crop's output size is computed, so the thumbnail and the
  real pipeline cannot disagree about what a crop produces. `hasSpill` decides whether the stored
  background needs filling at all.
- **A final fit-draw when rounding through the op chain leaves the result off the bound**, so R-G3's
  bound is exact rather than approximate. Costs one extra draw at thumbnail scale.
- **No main-thread fallback if the worker cannot be constructed.** R-G12 requires that no thumbnail
  work continues in the background, and an un-abortable `createImageBitmap` on the main thread cannot
  honour that. So the service generates nothing and every tile is a placeholder. The e2e asserts
  `workerAlive` is true during generation on all three engines, so this degradation cannot engage
  unnoticed.
- **`Worker.terminate()` itself is taken as a platform guarantee.** The e2e proves the service's side
  of R-G12 — the worker reference released, no further completions, the raced completion discarded,
  the budget not advanced — and the harness proves the consequence, that CPU and memory growth stop.
  Neither re-proves that the browser honours `terminate()`.
- **`whenIdle()` exists** so tests and callers can await a drained queue instead of polling `stats()`.
- **Harness duplicates the render primitive in plain JS rather than importing the module.** The
  harness is a self-contained static page with no TypeScript transform (same shape as t01/t03), and
  C5 measures the platform primitive — `createImageBitmap` plus an `OffscreenCanvas` encode — not the
  service's queueing. ~40 lines, kept deliberately close to `thumbnail-render.ts`.
- **Fixtures are read from `PHOTO_FIXTURES_DIR` at run time and served by index**, never copied into
  the repo and never named in `results.json`. T02's precedent, and it keeps personally-tagged
  filenames out of committed files.

## Surprises

- **Desktop WebKit decodes HEIC and TIFF natively.** All 50 fixtures generated on WebKit; Chromium and
  Firefox both failed the same five (4 HEIC, 1 TIFF). Technical Design §10.4 describes the ImageMagick
  fallback as if it were engine-independent; it is a Chromium/Firefox path in practice. Recorded in C5.
- **WebKit's `convertToBlob` appears to ignore the quality argument for `image/webp`.** Mean encoded
  size at the 384 px bound: 130.3 KB on WebKit against 9.8 KB (Chromium) and 10.2 KB (Firefox), and
  4.8× WebKit's own JPEG at the same bound. Its JPEG output is also roughly twice Chromium's. Not
  enough to decide the format — 12.7 MB retained for a whole 100-thumbnail batch is negligible against
  a 48 MB single decode — but worth re-checking on a later WebKit.
- **The fixtures drive contains PngSuite and a TIFF with a malformed orientation tag**, both of which
  ImageMagick refuses. `fixtures.mjs` excludes the conformance suites by directory name and selects
  two spares per format so the set still reaches exactly 50 after an unreadable candidate is dropped.
- Otherwise none. `OffscreenCanvas`, module workers, `createImageBitmap`'s resize options and WebP
  encoding all worked on all three engines with no branching — notably including WebKit, which the
  other platform tasks have repeatedly had to special-case.

## What the next task should know

- Import `createThumbnailService`, `ThumbnailSource`, `ThumbnailService`, `ThumbnailStats`,
  `FallbackDecoder` from `@/platform/thumbnails`; `runtimeLimits` from `@/config/limits`.
- **T33 (Gallery grid) is the consumer.** Create one service per batch, call `setVisible()` with the
  visible-and-near-visible window on every scroll settle (it is cheap and idempotent — already-cached
  ids are dropped), render `urlFor(id)` or a neutral placeholder when it returns `null`, call `stop()`
  on unmount, `invalidate(id)` when an image is removed or its edit changes, and `clear()` on batch
  clear. `onReady` is the re-render signal. A `ThumbnailSource` needs the source `Blob` and the
  intrinsic `width`/`height`, both of which `ImageRecord` already carries.
- **T34 (list view) needs two things from here**: call `stop()` when entering list mode so R-G9's "no
  thumbnails at all" holds, and use **100** as R-G8's automatic threshold — read it from
  `runtimeLimits.maximumThumbnails` rather than writing the number again.
- **T22/T23 wire the ImageMagick fallback** by passing `fallbackDecoder` into the factory. It is called
  only for a `reason: 'unsupported'` result, the budget is already spent by then, and the service
  re-checks staleness after it resolves. Note the finding above: it is only needed on Chromium and
  Firefox.
- **T46 owns `config/limits.ts` from here.** It should absorb `folder.ts`'s two traversal constants and
  give `maximumThumbnails` a measured value; nothing in `thumbnails.ts` changes when it does.
- The service is deliberately UI-free: it attaches no listeners, knows nothing about scrolling or
  virtualization, and never touches a store. Binary data stays in a closure-scoped `Map`
  (Technical Design §1.1).
- Re-run the measurement with `pnpm test` from `verification/t20-thumbnails/` (`T20_QUICK=1` for a
  one-engine, one-configuration smoke pass). It needs the `.env` fixtures path and installed browsers.
- **T17's `capability.spec.ts:47` (WebKit OPFS via a persistent profile) flaked once** during a full
  suite run here, and passed on its own and on an immediate full re-run. It launches a real
  disk-backed WebKit profile, which is the most contention-sensitive thing in the suite, and the
  suite now has more WebKit work running alongside it. If it starts failing regularly, suspect
  parallelism rather than a regression in `capability.ts`.

## Requirements covered

R-G3, R-G4, R-G10, R-G12. **R-G9** is satisfied structurally — this module generates only what
`setVisible()` asks for and stops on `stop()` — but the decision to call `stop()` on entering list mode

threshold, which it does above; T34 implements the rule. The ImageMagick fallback named in Technical
