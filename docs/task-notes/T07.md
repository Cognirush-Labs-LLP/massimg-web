# T07 — Design tokens and base styles

**Status:** complete

## What was built

A CSS custom-property design-token layer (`src/styles/tokens.css`) covering every colour, font,
weight, letter-spacing and radius value from Functional Design §14.1/§14.2, plus self-hosted
`@fontsource` font faces for Archivo and JetBrains Mono (`src/styles/fonts.css`) and a small global
reset/base stylesheet (`src/styles/base.css`), all wired together via `src/styles/index.css` and
imported once from `src/app/main.ts`. A new `TokensDemo.vue` component renders every token (colour
swatches, type samples at each weight/role, radius samples) and is mounted from `App.vue` behind a
clearly marked, removable block. `stylelint` with the `stylelint-use-logical-spec` plugin is wired in
as `pnpm lint:css` and as a step in `pnpm check`, and fails the build on any physical-direction CSS
property (`left`, `right`, `margin-left`, `padding-right`, `top`, `bottom`, physical border-radius
corners, `float: left`, etc.) in both `.css` files and `<style>` blocks inside `.vue` files.

## Decisions made

- **CSS custom properties on `:root`, no SCSS/token-generator layer.** The task brief called this the
  obvious idiomatic choice and it is: Vite handles plain CSS natively, `var(--token)` works directly in
  both `<style>` blocks and inline `:style` bindings (used in the demo for data-driven swatches), and a
  design-token-generator layer (Style Dictionary or similar) would add a build step and an
  indirection layer for a token set this small (roughly 20 values). Not deviating from plain CSS custom
  properties.
- **Surface: three concrete tiers picked from the given `#060606`–`#121212` range**, evenly spaced in
  rising elevation order: `--color-surface-panel: #060606` (least elevated — side panel / large
  containers), `--color-surface-control: #0e0e0e` (buttons, inputs, segmented controls),
  `--color-surface-tile: #121212` (most elevated — image tiles/cards). The range's own endpoints anchor
  the low and high tiers; `#0e0e0e` is the arithmetic midpoint for the third. `docs/sample_design/`
  (reference only) uses a messier set of surface-adjacent greys (`#0b0b0b`, `#0f0f0f`, `#111`,
  `#121212`, `#141414`) for buttons/inputs/tracks/cards — consistent with "surface sits somewhere in
  this range," not with any specific three-way split, so it confirmed the range but didn't dictate the
  tiers. Rejected: matching the sample design's values exactly — the sample predates the design docs
  and is explicitly reference-only where it doesn't give exact numbers.
- **Muted text: two tiers taken from the two ends of the given `#6e6e6e`–`#a2a2a2` range, not an
  interpolated middle value.** §14.2 pins the loud end explicitly ("Functional micro-labels ... colour
  `#a2a2a2`"); the quiet end (`#6e6e6e`) is assigned to passive metadata, which §14.2 describes only as
  "deliberately quiet" — the darkest/lowest-contrast point in the given range is the direct reading of
  "quiet." No middle tier was invented since nothing in §14.1/§14.2 names a third muted-text use.
- **Radii: one concrete value per named category**, at a point inside each given range:
  `--radius-sm: 7px` (range 6–7px, chips/small fields), `--radius-md: 9px` (range 8–10px,
  controls/rows, arithmetic midpoint), `--radius-lg: 12px` (range 11–12px, primary button/stage frame).
  Picked the upper end for `sm` and `lg` and the midpoint for `md` to get a clean 7/9/12 progression;
  no requirement pins these further and the docs only give ranges.
- **`stylelint` + `stylelint-use-logical-spec`, not a hand-rolled
  `declaration-property-value-disallowed-list` rule.** The plugin (rule name `liberty/use-logical-spec`)
  is a real, actively-published package (successor to `csstools/stylelint-use-logical`) purpose-built
  for exactly this: it flags `left`/`right`/`top`/`bottom`, every physical `margin-*`/`padding-*`
  longhand, physical `border-*` sides and corner radii, `float: left`/`right`, and `text-align:
  left`/`right`, against their logical equivalents — a broader and more accurate net than reimplementing
  a disallowed-value list by hand would give for the same effort. Verified directly (see below) that it
  catches `margin-left`.
- **`stylelint-config-recommended`, not `stylelint-config-standard`.** `-recommended` only turns on
  correctness rules (no CSS present, no duplicate selectors, etc.); `-standard` layers on additionally
  the project's formatting/stylistic conventions. Since Prettier already formats every `.css` file and
  `.vue` `<style>` block (and stylelint's own stylistic rules were deprecated/removed as of v15/v16
  precisely because Prettier does that job better), `-recommended` avoids a second, potentially
  conflicting opinion on formatting for no correctness benefit.
- **`stylelint` pinned to `16.26.1`, not the currently-latest `17.15.0`.** `stylelint-use-logical-spec@5.0.1`
  declares a peer range of `stylelint: '>=11 <17'` — it does not yet support stylelint 17.
  `stylelint-config-recommended` was pinned to `15.0.0` to match (its own peer range is
  `^16.13.0`; the `18.0.0`/`17.0.0` latest versions require stylelint `^17`). `pnpm add` produced no
  unmet-peer warnings with this combination; `pnpm install` afterwards was clean too. Same reasoning
  T04 used pinning TypeScript to 5.x for `typescript-eslint` — install a combination that's actually
  verified compatible rather than the newest-by-default set with an unmet peer warning.
- **`postcss-html` added so `.vue` `<style>` blocks are linted, not just `.css` files.** Without it,
  `stylelint.config.mjs`'s `**/*.vue` override would have nothing to parse the file with; T07's own
  demo component (`TokensDemo.vue`) has a non-trivial `<style scoped>` block that needed exercising by
  the lint rule as much as the plain `.css` files do.
- **`lint:css` wired into `check` directly** (`vue-tsc -b --force && eslint . && stylelint ... &&
  prettier --check .`), not left as a same-named-but-separate sibling script. Rejected keeping it
  separate the way T06 did for `check:licenses`: that precedent was for an audit of a different kind of
  thing (licence-file completeness, a repo-hygiene concern orthogonal to code quality); CSS logical-
  property discipline is a code-quality gate exactly like vue-tsc/ESLint/Prettier, so it belongs in the
  same command a contributor already runs before considering a change done. Kept as its own
  `pnpm lint:css` script too, for running it in isolation (as the Done-when verification below does).
- **Demo mounted from `App.vue` behind a marker comment, not a separate Vite entry point.** Rejected a
  second HTML entry (`tokens-demo.html` + `rollupOptions.input`) — it would need its own `vite.config.ts`
  multi-page wiring, doesn't reduce risk to T04/T05's tests (they only assert against `App.vue`'s
  existing text either way), and adds a second thing for T31 to remember to clean up. Instead,
  `App.vue`'s existing placeholder markup (`<p>icompress scaffold OK</p>`) is left completely
  untouched — `<TokensDemo />` is added as a sibling, so T04's `App.spec.ts` and T05's
  `tests/e2e/app.spec.ts` needed **no changes** and both still pass verbatim. The whole addition (import
  + `<template>` usage) is wrapped in an explicit `T07 marker` comment in both the `<script setup>` and
  `<template>` blocks of `App.vue`, naming this handover note, so T31 (which replaces `App.vue`
  wholesale per its own task brief) finds it immediately.
- **`@fontsource` (self-hosted, per-weight CSS files), not a Google Fonts `<link>`.** The task brief's
  own reasoning applies directly: this is a local-processing-only app (Functional Design's privacy
  principles — no third-party network calls the user didn't initiate), so fonts ship from the same
  origin as the app bundle. `pnpm build` confirms this: the built `dist/assets/` contains real
  content-hashed `.woff2`/`.woff` files (Archivo 600/700/800, JetBrains Mono 400/700, one file per
  Unicode subset) and `index-*.css` totalling ~30 kB uncompressed / ~15.5 kB gzipped for the font
  `@font-face` declarations — no external request at runtime. Not deviating from the suggested approach.
- **JetBrains Mono weights loaded: 400 and 700.** §14.2 names JetBrains Mono's *uses* (file sizes,
  dimensions, counters, breadcrumb, stepper) but, unlike Archivo, does not name specific weights for it.
  400 covers the plain data text those uses imply; 700 covers emphasised mono figures — the sample
  design's reduction-percentage figure is rendered in mono/bold/tint, and Functional Design §14.1 lists
  "reduction figure" as one of Tint's explicit uses, so a bold mono weight is needed somewhere for that
  combination to be renderable. Demonstrated in `TokensDemo.vue`'s typography section
  (`.type-sample--mono-strong`).

## Surprises

- `stylelint-use-logical-spec`'s peer dependency range (`stylelint '>=11 <17'`) does not yet cover
  stylelint 17, which is what `pnpm add stylelint` resolves to by default today. Discovered by checking
  peer ranges before installing (not by hitting an install-time error) — pinned both `stylelint` and
  `stylelint-config-recommended` to their latest mutually-compatible 16.x-era versions instead. Worth
  re-checking when a future task touches the CSS toolchain, in case a `stylelint-use-logical-spec` release
  adds stylelint 17 support.
- `@fontsource` packages ship one `@font-face`/file per Unicode subset (latin, latin-ext, cyrillic,
  greek, vietnamese, ...) rather than one file per weight. This is expected/desirable behaviour (the
  browser only fetches the subset it needs for the text actually rendered) but means `dist/assets/`
  after `pnpm build` has several dozen small font files rather than five — not a problem, just worth
  knowing so it doesn't look like a mistake when a later task inspects the build output.

`TokensDemo.vue` use only logical properties as a working example). Functional Design §14.1 (colour

design tokens and demonstrated in `TokensDemo.vue`. Technical Design §11's "logical CSS properties
