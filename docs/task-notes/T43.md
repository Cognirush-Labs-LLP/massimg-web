# T43 — Site shell and navigation

**Status:** complete

## What was built

An outer site shell (`src/app/site/SiteShell.vue`, `SiteHeader.vue`, `SiteFooter.vue`) now
wraps every route, with four new routes registered (`/faq`, `/privacy`, `/terms`, `/desktop`)
pointing at page components T44 fills with content. Chrome is chosen purely by route, not
viewport width: the **tool route gets no outer header at all**, at any screen size — its own
inner header (`ToolPage.vue`'s `Header.vue`) already provides chrome — and a **compact
footer** (tight padding, icon-only GitHub link, but still carrying every site link: For
Desktops, Privacy, Terms, FAQ) stands in for the header entirely there. **Every other route**
(`/faq`, `/privacy`, `/terms`, `/desktop`) gets the **regular header** (icon + wordmark home
link, FAQ/For Desktops nav) and **regular footer** (GitHub gets a visible text label too,
roomier padding). This whole split — including the exact header/footer contents and the "no
header on the app screen, any size" rule — was specified by the user directly, iterated twice
during implementation (see Decisions made for what changed from the first pass). T44 was done
in the same session — see `T44.md` for the content/markdown half.

## Decisions made

- **The shell went through two designs in this session; this note describes the second,
  shipped one.** The first pass built a viewport-breakpoint-driven compact/regular split (both
  header and footer compact only below 900px on the tool route). The user reviewed it running
  and corrected it: no header at all on the tool route regardless of screen size, the footer
  carries every link (including For Desktops and FAQ, not just Privacy/Terms) to compensate,
  and "Desktop"/"Try desktop version" — two different labels for conceptually the same
  thing — both became the single "For Desktops" label. The route-vs-viewport distinction
  this leaves is now purely about which route is active, not how wide the window is.
- **"For Desktops" appears in two places with two different link targets**, both using the
  same `site.nav.desktop` message key: the regular header's nav item (non-app routes) links to
  the in-app `/desktop` page; the footer's "For Desktops" (both chrome variants, every route)
  links straight to the external `https://mic.cognirush.com/download/` URL as a direct funnel.
  Same visible text everywhere per the user's correction, but the two destinations weren't
  explicitly addressed in that correction — flagging in case a single destination is wanted
  instead.
- **`.tool-page` and `.mobile-action-bar` CSS changes were necessary, not optional**, despite
  the task brief's "mounts unchanged" framing. `ToolPage.vue` previously assumed it alone
  filled the browser viewport (`100dvh` sizing, `position: fixed` bottom bar anchored to the
  real viewport edge) — both assumptions become wrong the moment sibling chrome (even just the
  compact footer, now that the header is gone from this route entirely) exists below it.
  "Unchanged" is read here as the tool's composition/behaviour/state machine, not a zero-diff
  constraint on CSS that was only ever correct because nothing else shared the page.
- **`public/manifest.json` built now**, ahead of T46, per the user's explicit answer when
  asked. No service worker, no install/offline testing — that remains entirely T46's job; this
  manifest is unverified for actual installability until then. `theme_color`/
  `background_color` both `#000000` (matches `--color-background`) rather than the tint red,
  to avoid a jarring colour in OS chrome — an easy value to change later if wanted.
- **`edit-ui.spec.ts` given a taller viewport (`720 + 31`), not a weakened assertion.** See
  Surprises for how the regression was found; 31px is the live-measured height of the tool
  route's compact `.site-footer` at the default 1280×720 viewport (the tool route has no
  header at all in the shipped design, so the footer is the only height to compensate for).
  This restores the Edit frame host to exactly its pre-T43 on-screen size rather than guessing
  a number — recomputed once after the header-removal redesign made the first measurement
  (116px, from an earlier design with both a compact header and footer) stale.

## Surprises

- **Running the full existing e2e suite (not just this task's own tests) surfaced two real
  regressions neither the plan nor the user's design review caught**, both fixed (see Decisions
  made): a literal duplicate "Mass Image Compressor" text match (from the first chrome design,
  resolved by the header-removal redesign itself) and `edit-ui.spec.ts`'s pixel-calibrated
  drag-to-corner snap test, which broke because shrinking the tool's available vertical space
  (from adding any outer chrome at all) changes the Edit frame's on-screen size and therefore
  the letterbox-gap geometry that test's fixed 30px mouse offset was tuned against. Caught both
  times by diffing a full `--project=chromium` run against the same run on `git
  stash`-reverted `main` — 8 failures on both sides after each fix, identically named, none
  new. Worth remembering for any future task that adds persistent chrome around the tool, even
  a single compact footer: it can silently invalidate pixel-exact e2e assertions elsewhere that
  were written assuming the tool owned the whole viewport.
- **`tests/e2e/app.spec.ts`'s Tab-cycling test (`mobile: Tab cycling stays inside the open
  drawer`) is already broken on `main`, independent of this task.** Confirmed via the same
  stash diff: it fails identically before and after T43. Root cause (not investigated further,
  out of scope): the test's own comment says "the Hide button is currently the drawer's only
  focusable element... until T35" — but T35 has since shipped real Quality/Size toggle
  buttons into the side panel, so the drawer now has multiple focusable elements and a single
  Tab correctly moves into them rather than wrapping straight back to Hide. The test's
  assumption is stale, not the focus-trap logic (`useFocusTrap.ts` itself looks correct — it
  trusts a document-level keydown handler scoped to the drawer's own `querySelectorAll`,
  unaffected by anything outside it). Left unfixed: this is T35/T37's test assumption going
  stale, not something T43/T44 touched or should own fixing.
- `vite-ssg`'s per-route build output is flat (`dist/faq.html`, not `dist/faq/index.html`) —
  the plan assumed the latter. Caught immediately by running `pnpm build` and looking at the
  actual output; `verify-ssg-html.mjs` was written against the real paths.
