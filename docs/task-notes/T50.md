# T50 — Limits

**Status:** complete with caveats. Every limit has a value and a tag, the guard and the selection-time check are built and tested on three engines, and the Android reference phone is measured. **Open until an iPhone is available:** the mobile values tagged estimated, the 50 MP PNG and AVIF check, and the T39-A Share cases (E4). Those, a Linux CI run, and the desktop 500-file smoke test are listed under "Remaining work".

## What was built

The approach was reframed (assumptions C3): limits are derived from a memory model and a floor device, and each is tagged measured, derived or estimated. Two layers now exist. ImageMagick's resource limits are an always-on guard, delivered to each worker by the pool and proven on Chromium, Firefox and WebKit to turn decompression bombs into catchable per-image failures. A header reader runs at selection and turns away an over-cap still or animation with a named message; a file it cannot read is not rejected. A multi-gigabyte file is no longer read into memory just to be refused.

## Decisions made

1. **`disk = 0` is part of the guard.** The other limits do nothing without it (measured). Alternative rejected: relying on `area`/`memory` alone, which let a 324 MP decode through.
2. **An unparseable header is not rejected** (user's decision). It goes through the normal path and ImageMagick's guard decides.
3. **An unknown device class gets the strict mobile budget.** A budget that is too small fails one image; one that is too large loses the tab.
4. **Provenance lives in Functional Design §5.7, not in code.** Alternative rejected: a provenance tag per field in `limits.ts`, which is more code to keep in step with the table.
5. **Limits are delivered by a `configure` message,** because a worker cannot tell whether it is on a phone. Alternative rejected: a query parameter on the worker URL.

## Surprises

- ImageMagick's defaults allow bombs: a 1.6 gigapixel PNG decoded on Firefox and WebKit (17 to 37 s), and a 3000-frame GIF ended in `exit(1)`, which leaves the instance dead.
- `area` and `memory` alone do not stop a decode, because the cache spills into the same WASM heap.
- The dimension probe (`createImageBitmap` on the whole file) is itself a decode with no guard.
- A worker failure of kind `out-of-memory` halts the whole run (`useProcessingRun.ts`), so a budget breach must not use it.
- ImageMagick's `area` limit is exclusive: an image exactly at it is refused. Found on the phone with an 8192x6400 photo at the 52,428,800 cap; the loader now adds one, and `resource-limits.spec.ts` guards the boundary.
- The encoders' memory is not bounded by ImageMagick's limits (PNG +2.1 GB, AVIF +1.4 GB at 50 MP on the phone).
- Hand-built animated GIFs made of one-pixel frames decode and re-encode as GIF but fail to encode as animated WebP at most sizes (a 590x590 two-frame one worked, a 64x64 six-frame one did not). Not investigated: real files from ImageMagick encode fine, and it is outside this task. If a real-world file ever does this it would be an encoder bug worth chasing.
- Editing a source file while the dev server feeds a phone reloads the phone's page mid-step and invalidates it; leave the tree alone during a device run.

## What the next step should know

Done since the first pass: the header reader, enforcement at selection, the malformed-input tests (every truncation and seeded corruption of real files, plus lengths that point past the data), and moving the stray constants.

Known gaps, none of them blocking:

- **A breach inside the worker is reported as `decode-failed`** ("could not be decoded"), not as a limit. It only happens for a file the header reader cannot size: BMP (its size tracks its pixels, so the file cap already covers it), TIFF, JXL, JPEG 2000, or a header too damaged to parse. A named failure kind would need new copy, report text and tests; decide whether the rarity justifies it.
- **The dimension probe still decodes with `createImageBitmap`**, but now only for those same unreadable-header files. A file the reader cannot size but the browser can decode natively is the one remaining unguarded decode. It runs in a killable worker and a failure is a placeholder.
- **The UPNG APNG decoder is not covered by ImageMagick's limits.** An APNG is always sized by the reader (its IHDR is at a fixed offset), so an over-cap one is refused at selection; no second gate was added in the worker.
- The three `gallery-grid` tests (retained thumbnails, leaving Gallery, removing one tile) fail on a clean `main` too and are unrelated.

The Android confirmation ran (see assumptions C3 for the table): 20 steps on the reference phone, no tab lost, a 50 MP photo works for every output format.

Remaining work:

1. **PNG and AVIF encoder memory at 50 MP.** They sit outside every limit here: 50 MP with alpha to PNG added 2.1 GB and left 722 MB free on a 5.5 GB phone. Nothing is broken on this phone, but a 3 to 4 GB phone is the first place they will fail. If an iPhone or a smaller Android shows it, the options are a lower per-format pixel cap for those two outputs on mobile, or a cheaper path; both change what users see, so that is a decision, not a quiet change.
2. **iPhone**: not available. The first things to run there are a 50 MP photo to PNG and to AVIF, then the T39-A Share cases.
3. **Desktop scale smoke test** for the 500-file batch limit, and a Linux CI run.

## Values still estimated

Mobile budget (800 MiB, chosen to admit 50 MP phone photos; measured on one Android phone, not on an iPhone) and everything derived from it; files per batch (500); single file size (100 MiB); animated frame count (500); Share bytes on iOS. Desktop budget is derived and confirmed on one Apple-silicon Mac only.

## Requirements covered

R-I19, R-I20, R-I21 and R-I22 are covered at selection for JPEG, PNG/APNG, GIF, WebP and AVIF/HEIC, and by the guard for everything else. R-I33, R-X47 and R-X48 are untouched so far.
