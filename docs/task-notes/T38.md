# T38 — Processing view

**Status:** complete

## What was built

The Processing stage mode is real: pressing the primary action now runs every image in the batch
through the actual pipeline worker pool, and the placeholder screen is replaced with a counter,
a decorative donut (every number also written out as text beside it), a running size-reduction
total, live Failed/Skipped lists, Cancel (with honest "Stopping" labeling), and completion actions
(Back to images always, Download when at least one image succeeded).

## Files touched

- `src/ui/processing/useProcessingRun.ts` — new. The run-orchestration composable: builds an
  `intent: 'run'` `Job` per batch image via `resolveSettings`/`getSourceFile`, submits all of them
  to the pool up front (concurrency is bounded by the pool's own size), maps every `JobOutcome` onto
  `useRunStore.recordResult`, and implements Cancel (`stopping` flag, `pool.cancel()`, await
  outstanding, `uiStore.cancelProcessing()`).
- `src/ui/processing/processing-pool.ts` — new. Lazy, never-destroyed singleton `getProcessingPool()`,
  mirroring `preview-pool.ts` exactly, and for the same reason: `pool.ts`'s `supersede()` is blind to
  `intent`, so Processing needs a pool a stray Preview job can never collide with.
- `src/ui/processing/processingText.ts` — new. Translated Failed/Skipped reason text
  (`describeFailureReason`, `describeSkipReason`), independent of `domain/report.ts`'s hardcoded-
  English report formatters.
- `src/ui/processing/ProcessingDonut.vue` — new. Purely decorative inline-SVG donut (`aria-hidden`,
  no text inside it at all — see Decisions).
- `src/ui/processing/Processing.vue` — replaces T31's placeholder in place. Orchestrator: starts the
  run in `onMounted`, renders counter/donut/figures/total/lists/actions, drives the R-K5 aria-live
  region.
- `src/app/ToolPage.vue` — both `PrimaryActionButton` instances now call `uiStore.enterProcessing()`
  on click. No change to `PrimaryActionButton.vue` itself (see Decisions).
- `src/ui/preview/PreviewFrame.vue` / `src/styles/base.css` — promoted `PreviewFrame`'s local
  `.announcement` class to a global `.visually-hidden` utility, per that file's own comment
  anticipating this move for T38.
- `src/i18n/en/messages.json` / `context.json` — all new `processing.*` keys (counter, figures,
  running-total variants, cancel/stopping, completion actions, failure/skip reasons, aria-live
  announcements).
- `src/app/ToolPage.spec.ts` — one new test asserting the primary action enters Processing.
- `src/ui/processing/{useProcessingRun,Processing,ProcessingDonut,processingText}.spec.ts` — new.

## Decisions made

- **Out-of-memory is an ordinary per-image failure here.** ui-design.md §14 describes OOM as halting
  the *whole run* as a terminal state, but that row is explicitly cited under T39's scope (the §10
  error-table wiring), not T38's (R-X1-R-X20/R-X26/R-X27 only). Confirmed with the user before
  building. T39 will need to special-case the `out-of-memory` outcome to call `pool.cancel()` and
  short-circuit the remaining submissions rather than letting `applyOutcome` treat it like any other
  failure.
- **Download's click handler is not wired.** The button renders with correct conditional visibility
  (`progress.succeeded > 0`) and a `data-testid`, but has no `@click` — tasks.md assigns "wire the
  explicit Download button to [`downloadFinishedRun`]" to T42 by name, and `downloadFinishedRun()`
  still unconditionally throws (T40/T41 don't exist yet). Confirmed with the user.
- **Donut colours reuse the four existing design tokens** (`--color-tint`, `--color-primary`,
  `--color-text-muted`, `--color-border-control`) rather than adding new ones — `tokens.css` asks
  that no colour be added without updating the design docs first, and this is a defensible mapping:
  succeeded gets the app's one accent, failed gets the highest-contrast neutral (white), skipped and
  pending step down in contrast. Confirmed with the user.
- **The donut renders no text of any kind**, not even visually-hidden text — every number lives in
  Processing.vue's own sibling `<li>` markup, which doesn't read from or depend on the SVG's DOM at
  all. This makes "every number also present as text" and "fully readable with the chart hidden"
  (the task's own Done-when wording) hold structurally rather than by a runtime visibility toggle.
- **R-K5's announcement interval: every 25% of the batch processed**, plus unconditional
  announcements on run start, Cancel, and completion. No interval value exists anywhere in the design
  documents; a quarter of the batch caps a long run at a handful of announcements (never per-image)
  while still giving a mid-run signal, and guarantees exactly one extra announcement for a batch too
  small to have distinct quartiles.
- **A generation counter plus an unconditional `onScopeDispose` → `pool.cancel()`**, independent of
  the explicit Cancel button's own `cancel()` method. This was not in the original task brief:
  `useBackNavigationGuard.ts`'s `handleProcessingPop()` (already built, not touched by this task)
  calls `uiStore.cancelProcessing()` directly on a back-button press during an in-progress run,
  bypassing `useProcessingRun.cancel()` entirely. Without the unmount guard, a straggling job from a
  bypassed run could resolve after a second run starts and corrupt its freshly-reset counters.
  `onScopeDispose` is the one hook guaranteed to fire on every exit path.
- **Per-image FAILED/SKIPPED statuses recorded before Cancel was pressed are not reverted.**
  `useRunStore.startRun()`'s `clearRunStatuses()` call is what wipes prior statuses, and it only runs
  at the *start of the next run* — consistent with §6.3's explicit rule that only a new run clears
  them. `cancelProcessing()` itself performs no reset.
- **`unimplemented` pipeline failures and the `'terminated'` pool outcome are coerced to
  `encode-failed`** for `runStore`/UI purposes, rather than widening `FailureReason` or giving them
  their own on-screen wording (unlike Preview's own `describeFailure`, which does distinguish
  `unimplemented`). `RunFailureEntry.reason: FailureReason` is domain-typed with no dependency on the
  pipeline layer anywhere else in `stores/*.ts`, and both cases are narrow, currently-unreachable or
  near-unreachable paths (every §4.2 format row now runs; `jobTimeoutMs` is still `null`).
- **Resolution-time caveats are passed into the `Job`** (`caveats: resolution.caveats`), unlike
  `usePreviewEncode.ts`'s own job construction. `executeJob`'s `caveatsForRun` only merges `job.caveats`
  for `intent: 'run'`, so Preview can omit this safely (its caveats are always discarded) but
  Processing cannot — omitting it here would silently drop R-F6's animation-substitution caveat (and
  any future resolution-time caveat) from the report.
- **No change needed to `PrimaryActionButton.vue`.** It has a single root `<div>` with no declared
  emits; a parent `@click` falls through onto that root via Vue's default attribute inheritance, and
  a click on the inner (non-disabled) `<button>` bubbles to it. A disabled native button never
  dispatches `click` at all, so `disabled` already guards this for free.
- **Failed/Skipped lists render live, during the run**, not gated on `finished`. Nothing in §6.3
  restricts this to completion-only, and watching the lists build up is strictly more informative
  than waiting.

## Surprises

None — every prerequisite (`useRunStore`, `useBatchStore`'s mutation methods, the T36-A result
union, the worker pool's cancellation semantics, the back-navigation guard) behaved exactly as its
own handover notes described. The one real gap found during implementation (the back-nav guard
bypassing this composable's own `cancel()`) was anticipated by `useBackNavigationGuard.ts`'s own
code, just not by T38's task brief — see Decisions above.

## What the next task should know

- **T39** needs to special-case `out-of-memory` in `useProcessingRun`'s `applyOutcome` (or wherever
  it ends up) to halt the run rather than continue it, per ui-design.md §14. Today it's treated
  identically to any other failure.
- **T40/T41/T42**: `useProcessingRun` does not retain any output bytes — each job's `Uint8Array`
  result is read only long enough to measure `byteLength` for `recordResult`, then discarded. T40's
  "stream into OPFS as the run proceeds" will need its own hook into this composable's per-image
  success path (most naturally inside `applyResult`'s `result.kind === 'output'` branch) rather than
  assuming bytes are available afterward from `runStore`.
- **T42** wires `processing-download`'s click handler to `downloadFinishedRun()`. The button and its
  visibility condition already exist; only the handler is missing.
- The donut's `pathLength="100"` SVG2 trick means its `stroke-dasharray`/`stroke-dashoffset` values
  are plain percentages — no circumference arithmetic anywhere if a future task needs to adjust its
  visuals.

## Requirements covered

R-X1 to R-X15, R-X17, R-X20, R-X26, R-X27. R-X18/R-X19 were already implemented by the pre-existing
`useBackNavigationGuard`; this task keeps `useRunStore`'s `finished`/`downloaded` state accurate for
it rather than rebuilding it. R-X29's escape hatch is wired defensively (a `'terminated'` outcome is
mapped to an ordinary failure) but stays practically inert, since `jobTimeoutMs` remains `null`.
T36-A's `size-target-unreachable` result is consumed correctly: counted and listed as Skipped, not
Failed, with no output/savings contribution. R-K5 (run progress announced at intervals, not per
image). Not covered: R-X16/R-X30/R-X31's actual download mechanics (T40-T42's scope); the
out-of-memory run-halt behaviour in the §10 error table (T39's scope, see Decisions); the Download
button's click wiring (T42's scope, see Decisions).
