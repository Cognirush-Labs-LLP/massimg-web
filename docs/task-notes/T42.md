# T42 — Download, share and leaving

**Status:** complete

## What was built

Delivery is now real and explicit. The Download button calls T40's `downloadFinishedRun()`, which
was split so §10's "ZIP assembly failure" and "Download blocked by browser" are two distinct,
retryable outcomes rather than one silent path. A new Share action exists end to end:
`platform/share.ts` gained the exact completion-time `canShareExactFiles`/`shareFiles` half it was
always meant to have, `pipeline/run-share.ts` is its component-facing action, and `useProcessingRun`
decides R-X48's availability once at completion. The run store's `downloaded` boolean became a
`pending | downloaded | shared` delivery state plus a shared retryable `deliveryError`, and the
completed Processing view now replaces both delivery actions with R-X54's checked **Download
started** / **Shared** state while keeping the whole summary visible.

Two things that go beyond a literal reading of what T40 left behind, both required by the
requirements rather than by the task prose:

- **Share works for a run that *starts* with exactly one image.** T40's Share plumbing was entirely
  inside `if (multiImage)`, so a one-image run could never offer Share even though R-X47 names "one
  to ten" and R-X49 says "one success shares the same direct output that Download uses".
- **Share's individual copies are now written at the image's grid position and named by a new,
  globally-deduplicated naming function** (`resolveShareNames`), not at completion order with the
  ZIP's directory-scoped basename. Before this, `a/photo.jpg` and `b/photo.jpg` would both have
  been handed to the share sheet as `photo.jpg`, in whatever order the workers finished.

## Decisions made

1. **A run that starts with exactly one image skips the preliminary probe and goes straight to
   R-X48's exact check.** R-X47 makes eligibility conditional on the preliminary probe, and R-X14
   says Share appears "only under R-X47 and R-X48", so the literal alternative was to run
   `probeFileShareForRun` for a one-image run too and gate on it. Rejected because R-X47 governs
   eligibility *to retain share output*, and a one-image run has no retention decision to make:
   R-X51 writes its single direct artifact unconditionally and R-X49 makes that same file the share
   payload. Technical Design §9.1 is explicit that both probes are "optimisations that prevent
   pointless duplicate writes, not the authority to show the action", and for one image there are no
   duplicate writes to prevent. The practical difference is confined to a platform where the generic
   PNG probe fails but the exact real-file check passes — a combination T39-A never observed — and
   the direction of the difference is permissive, never a false promise, because the exact check is
   still the gate.
2. **A Share-eligible run's single surviving copy keeps its *Share* name when Download uses it.**
   For a folder run where two images resolve to the same basename, the lone survivor can be
   `photo-1.jpg` rather than `photo.jpg`. §9.2 ("one physical file may serve both candidate and
   Share roles") and R-X49 ("one success shares the same direct output that Download uses") mean
   there is one file with one name, and R-X53 decides it for the Share role. The same "a suffix can
   be reserved by an image that later failed" property already existed on the ZIP path since T40,
   which resolves every name up front precisely so completion order cannot affect naming.
3. **Both Download failures keep the results and stay retryable**, not just Share's. tasks.md's
   "`AbortError` and other failures stay pending, with only non-cancellation failures shown inline
   and retryable" sits in the delivery-state bullet, and ui-design.md §14 says the blocked-download
   case "offers a retry". So neither Download failure deletes artifacts or moves `delivery`.
4. **`deliveryError` lives in the run store, not in `Processing.vue`.** `downloadFinishedRun()` has
   two call sites — the on-screen button and the back guard's "Download and leave" — and a failure
   from either must surface through the one inline message. A component-local ref could not see the
   guard's failure at all. There is a test for exactly that path.
5. **"Download and leave" stays on Processing when the download fails, and re-arms the back
   guard.** Leaving would unmount `Processing.vue`, whose `onScopeDispose` calls
   `abortAndCleanup()` and would delete the very artifacts the inline retry is offering. The re-arm
   is not optional: the pop that opened the dialog consumed the nested history entry, so without
   `pushNestedEntry()` the next back press would raise the leave-*the-app* dialog instead. (The
   approved plan specified staying put but not the re-arm; found while implementing.)
6. **The R-X18 dialog is now also suppressed for a zero-success or halted run.** Previously (and in
   the approved plan) the only change here was `downloaded` → `delivery !== 'pending'`, which leaves
   an all-failed run raising a three-way dialog whose two non-Stay actions include "Download and
   leave" — for a run §10 says has "no output, Download or Share action", and after a halt that has
   already discarded every partial result and artifact. Read as required by §10 rather than as new
   behaviour; it is the same rule the on-screen view has always applied to the Download button.
7. **The checked delivered state is a `<p>` with a decorative `✓` and the label beside it.**
   `docs/ui-design.md` has no Share section at all — it predates R-X47–R-X53 and names no visual
   treatment for either the Share button or R-X54's checked state. The Share button therefore
   copies Download's treatment, and the delivered state is deliberately not styled as a button
   ("non-interactive"), occupying the slot the two actions vacated. A test asserts it is not a
   `BUTTON`.
8. **The FAQ's two privacy answers were corrected, and no new question was added.** The §10
   "what's still being finished" bullet about the compress-and-download flow is gone and the
   section's opening sentence now names the run, download and share as working. Separately, "Do my
   images ever leave my device? **No.**" and "no image bytes... are sent anywhere" were both
   falsified in substance by a Share button, so each got the smallest qualifier that makes it true
   again (the handoff is the user's own action; nothing is sent to us or to analytics). Per
   AGENTS.md no new Q&A was written — **a Share question is worth adding and needs your approval**;
   suggested: *"What does Share do, and where do my images go?"*
9. **`deleteAllOutputCopies()` asks each backend for its own index set.** The plan's sketch
   iterated `outputMeta`, which is only populated on the OPFS path — in the private-browsing
   fallback the indices live in `fallback.outputs`, so that version would have been a silent no-op
   there. Both branches have an e2e test.
10. **`shareFiles` duck-types `AbortError` on `name`** rather than `instanceof DOMException`. The
    one outcome that must never be misread is cancellation (R-X50: not an error), and nothing
    guarantees the error class across engines.
11. **The `maximumShareBytes` test overrides the limit rather than allocating 40 MB** of real
    output bytes, restored in a `finally`. Allocating the real ceiling twice over (the in-memory
    fallback copies) in a unit suite that runs many files in parallel bought nothing.

## Surprises

**§10's "Download blocked by browser" row is only partly reachable, and this is a genuine
limitation rather than an implementation shortcut.** There is no web API that reports a suppressed
`<a download>` click. What this task can detect is a *throw* from the handoff —
`URL.createObjectURL` or `anchor.click()` raising, e.g. a `SecurityError` — and that path is
implemented, tested and surfaces the §10 message with the Download button still live as the retry.
A browser that silently swallows the download still looks like success to the app, so artifacts are
deleted and the delivered state appears. Both unit tests for this row therefore force a throw; none
of them proves the silent-suppression case, because nothing can.

**The transient-activation question could not be closed here, only bounded.** `shareFinishedRun()`
awaits `readOutputCopies()` before calling `navigator.share()`, because there is no synchronous way
to get `File`s out of OPFS. T39-A measured that Chrome (macOS/Android/Windows) and Safari tolerate
at least 3 seconds between the click and the call, and an OPFS handle read is orders of magnitude
below that — but *that specific sequence* has not been measured on real hardware. If it ever does
lose activation, the failure is a `NotAllowedError`, which this code reports as the retryable inline
error rather than as success, so the failure mode is visible. The alternative — retaining the
`File[]` from the completion-time exact check so the click handler can call `share()` synchronously
— was rejected because the in-memory fallback's `readOutputCopies()` materialises real bytes, and
holding them across an idle period is what R-B1 forbids.

**`ui-design.md` has no Share content whatsoever** — not in §13's "On completion", not in §14. It
documents R-X14/R-X15/R-X16/R-X30/R-X31 and the three-way dialog, all of which predate the Share
requirements. Nothing in it conflicts with what was built; there is simply no visual reference, so
every Share and delivered-state treatment above is a judgment call.

**Technical Design §9.2's "any unused archive is removed before completion actions appear" is still
not implemented** — a Share-eligible or reduced-to-one-success multi-image run leaves its unused
archive in storage until delivery, cancellation or exit cleans the whole set. Pre-existing from
T40, not introduced here, and invisible to the user (`downloadFinishedRun` picks the direct file by
actual success count and never reads that archive). Left alone deliberately rather than quietly
growing this task's scope: fixing it needs a new `deleteArchive` primitive for a storage-hygiene
benefit no requirement names.

## What the next task should know

- **Delivery state is `runStore.delivery` (`'pending' | 'downloaded' | 'shared'`) and
  `runStore.deliveryError`.** `downloaded` no longer exists. Only `downloadFinishedRun()` and
  `shareFinishedRun()` may set them; callers read the return value, and anything that needs to
  render a failure reads `deliveryError` rather than the return value, so both call sites of
  Download agree.
- **`domain/naming.ts` now has two exported collision scopes and they are not interchangeable.**
  `resolveOutputNames` for anything that lands in the ZIP (directory-scoped, R-X22),
  `resolveShareNames` for anything handed to the share sheet (flat and global, R-X53). A
  Share-eligible folder run has both live at once.
- **`writeOutputCopy`'s `index` is now only a sort key.** `readOutputCopies()` returns copies in
  ascending index order and nothing else is promised. A Share-eligible run uses grid positions, so
  the indices are sparse when images fail, and index 0 may not exist at all.
- **T47 (Accessibility):** neither the delivered state nor the three inline delivery errors is
  announced to a screen reader. `Processing.vue` has one existing `role="status"`/`aria-live`
  region, used only for R-K5's progress announcements, and adding delivery copy to it would have
  meant inventing message text no design document specifies. The error paragraphs are plain `<p>`s
  for the same reason. This is a real gap, left to the task that owns the rule.
- **T50 (`maximumShareBytes`):** the ceiling is applied in
  `useProcessingRun.ts`'s `decideShareAvailability` to the sum of `runStore.successes[].outputBytes`,
  before `readOutputCopies()` is called at all. Lowering the constant in `config/limits.ts` is the
  only change needed. The Share-copy quota overhead (4096 bytes/file in `run-archive.ts`) is still
  T40's unmeasured placeholder.
- The one-image Share path writes **no extra OPFS copy**: it shares the same single artifact R-X16's
  direct Download uses. If a future task adds per-role copies, `run-archive.ts`'s `!multiImage`
  branch and `naming.spec.ts`'s "agrees with the ZIP basename for a lone file" test are the two
  places that encode the current assumption.
- `Processing.spec.ts` and `useProcessingRun.spec.ts` now wrap (not replace) `@/platform/share` and
  pin both functions to `false` in `beforeEach`, which is what they really answer in jsdom. A test
  that wants the Share path must opt in with `mockResolvedValue(true)`; a test that leaves a
  `mockResolvedValue` behind would otherwise make a later test's run Share-eligible.
