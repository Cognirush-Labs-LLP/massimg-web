# T21 — Worker protocol and pool

**Status:** complete

## Headline numbers and names for later tasks

- **Pool size is `min(hardwareConcurrency - 1, 3)` on desktop and `1` on mobile**, computed by
  `resolveWorkerPoolSize()` in `config/limits.ts` from three named limits — `maximumWorkers: 3`,
  `mobileWorkers: 1`, `reservedCores: 1`. **T46 changes those three numbers and nothing else.**
  `pool.ts` contains no sizing literal; the browser test proves it by building a pool from a
  different limits object and watching the size move.
- **R-X29's duration threshold is deliberately unset: `runtimeLimits.jobTimeoutMs` is `null`.** §5.3
  says the threshold "is set from measured re-init cost, not guessed" and T21 loads no codec, so it
  measures nothing. It lives in `config/limits.ts` with every other limit rather than only in the
  pool's options, so **T46's sweep of that module will come back and ask for its evidence** instead
  of the number being forgotten. **Whoever measures codec re-init cost (T22 loads them; T38 knows
  when the user is waiting) sets it.** The mechanism it drives is built and proven on all three
  engines; `createWorkerPool({ jobTimeoutMs })` overrides per pool.
- **`run()` returns `{ token, done }`, not a bare promise.** The token has to be available before the
  job finishes, because R-X29's escape hatch identifies its victim by token.

## What was built

`pipeline/protocol.ts`, `pipeline/worker.ts`, `pipeline/execute.ts` and `pipeline/pool.ts` — the
message protocol with a monotonic token per job, the worker that speaks it, the seam where stages
will do the work, and the pool that enforces R-X8's bound and all three of §5.3's cancellation
mechanisms. `config/limits.ts` gained the §5.1 sizing and a pure resolver for it. Eleven Playwright
tests run on Chromium, Firefox and WebKit with no skips; two Vitest files cover the pure sizing
formula and token monotonicity.

The three cancellation mechanisms are three different things and are kept apart in the code, because
conflating them is how the semantics in Functional Design §6.2 get quietly broken:

| Mechanism | Requirement | What the pool does |
| --- | --- | --- |
| Between jobs | R-X26 | `cancel()` stops dispatch and resolves the queue `cancelled`; in-flight jobs finish and deliver |
| Discard on arrival | R-X28 | A newer job for the same image marks the older token stale; its result is dropped when it lands |
| Terminate and respawn | R-X29 | `terminateJob(token)` kills the worker; a replacement spawns on the next dispatch |

## Decisions made

- **The between-jobs flag lives on the main thread, and the worker's copy is a backstop.** §5.3 says
  the flag is "checked by the worker before starting each job". A flag a worker could read *during* a
  WASM call needs a `SharedArrayBuffer`, which needs cross-origin isolation, which `capability.ts`
  already treats as not guaranteed (it is a probed capability, not an assumption). So the pool checks
  `cancelled` before every dispatch — nothing starts after cancel — and the worker independently
  refuses any `run` whose token is at or below the cancel it was told about. With strictly one job in
  flight per worker (§8.1), the worker's check only catches a `run` still unread in its own message
  queue; it is proven directly in the e2e by driving the shipped worker by hand.
- **`cancel` carries a token, not a boolean.** A boolean would poison the worker permanently, so
  `resume()` would have to respawn and pay a full codec re-initialisation — for the *cheap*
  cancellation path, which is backwards. Carrying the highest token issued so far means a resumed
  pool's later jobs are still accepted by the same worker. R-X17's "run again" therefore costs
  nothing, which the e2e asserts (`terminations` stays 0, `workersAlive` stays 1).
- **A refused job still answers, with `skipped`.** A dispatched job that never replies would hold its
  worker slot for the rest of the session. The pool maps `skipped` to a `cancelled` outcome: it never
  ran, so it is cancelled rather than failed.
- **Supersession is automatic, per image.** §5.3 says the main thread "records the latest token per
  image", so submitting a job for an image supersedes the previous live one. This is safe because a
  run encodes each image exactly once; only Preview ever produces two live jobs for one image.
- **A superseded job resolves `superseded` immediately, but its bytes are discarded on arrival.**
  Two separate things: the caller learns at once that its result is not coming (so the UI never waits
  on a doomed encode), while R-X28's actual requirement — the in-flight encode is not interrupted and
  its result is thrown away when it lands — is what the worker and `stats().discarded` do. A
  superseded job that has *not* started yet is dropped from the queue instead, never reaching a
  worker; debouncing (R-P3) is what keeps most superseded previews in that cheaper branch.
- **Every job promise settles; none rejects.** A caller counting a batch to completion needs the
  cancelled, superseded and terminated ones to settle too, or its counter never reaches the end.
  `JobOutcome` is a discriminated union rather than an exception channel.
- **Request bytes are copied; result bytes are transferred.** Transferring the request would detach
  the caller's buffer, and R-X28's shape is precisely "the same image is submitted again a moment
  later" — the second submission would find an empty buffer. The result has no such reuse, so it is
  transferred.
- **Workers spawn lazily, up to `size`.** ImageMagick alone is 14.8 MB (A1, §5.2); spawning three
  workers on construction would pay for three codec initialisations to preview one image.
- **`terminations` counts terminations, not respawns.** The replacement spawns lazily on the next
  dispatch and may never be needed, so a counter called `respawns` would over-report. The e2e asserts
  both halves separately: `workersAlive` drops to 0 at the kill and is back to 1 after the next job.
- **Mobile detection is `matchMedia('(pointer: coarse) and (hover: none)')`, and is injectable.**
  The design documents never define "mobile" operationally — the 900 px in Functional Design §2 is a
  *layout* breakpoint, not a device class. `capability.ts` states the repo rule: feature detection
  only, never user-agent sniffing. A media query honours that; `hover: none` is what separates a
  phone or tablet from a desktop with a touchscreen, which `pointer: coarse` alone misclassifies.
  This is a throughput choice, not user-visible behaviour, so it is recorded here rather than raised
  as a blocker — but it is a heuristic, and `createWorkerPool({ mobile })` overrides it.
- **An unknown `hardwareConcurrency` resolves to one worker, not to the cap.** Memory is the binding
  constraint (§8.1), so guessing high on an unknown device is the failure mode being avoided.
- **`execute.ts` exists as a one-function module and reports `unimplemented`.** The alternative was a
  fabricated `encode-failed`, which would have made the shipped worker lie about why it produced no
  bytes. `unimplemented` is true, it is a distinct `JobFailure` kind so nothing can confuse it with a
  real encode failure, and it disappears when T23–T29 land.
- **The pool takes a `workerFactory`, defaulting to the real worker.** See Surprises — this is what
  made the Done-when clauses provable at all.
- **No watchdog by default, but the mechanism is complete.** `jobTimeoutMs` is configuration, not
  policy: it wires R-X29's named mechanism without inventing its number. It is declared in
  `RuntimeLimits` rather than only as a pool option, so §8.3's one-module rule covers it and a
  deferred number cannot quietly become a permanent one. The option resolves with an explicit
  `!== undefined` test rather than `??`, so a caller passing `null` still means "no watchdog" after
  T46 gives the limit a real value.
- **`messageerror` is handled exactly like `error`.** A response that fails to deserialize would
  otherwise strand its entry in `live`, hold its slot forever and never settle its promise — and with
  `jobTimeoutMs` null there is no watchdog to catch it. Both events discard the worker and settle the
  job as `terminated`/`worker-error`.

## Surprises

- **The Done-when clauses could not be proven against the shipped worker alone, and that is
  structural rather than a shortcut.** Both clauses are about *timing* — what happens to a job that
  is in flight when something else occurs — and `pipeline/worker.ts` has nothing that takes a
  controllable amount of time until T23–T29 build the stages. So `workerFactory` is a real seam (the
  same shape as T20's `fallbackDecoder`), and the e2e injects a probe worker whose job duration is
  read from the job's own source bytes. **Everything the pool is responsible for is real in those
  tests**: the queue, the token arithmetic, the `postMessage` boundary, `Worker.terminate()` and the
  respawn. Only the work inside the worker is substituted. Two further tests drive the shipped
  `pipeline/worker.ts` — one through the pool (it answers on the right token) and one by hand (it
  refuses a job below the cancel token) — so the module that ships is proven to speak the protocol on
  all three engines. A reviewer should read these as two halves of one proof.
- **A fixed per-worker delay in the probe was wrong, and all three engines caught it identically.**
  The first version baked the delay into the worker source, so after the terminate-and-respawn test
  killed a 60-second job, the *replacement* worker also took 60 seconds and the test timed out on
  Chromium, Firefox and WebKit alike. Moving the duration into the job's source bytes fixed it. Worth
  recording because it is the shape of a real bug the pool could have had: anything that must differ
  between the killed job and the job after it belongs to the job, not to the worker.
- **No engine divergence at all**, which is unusual for this repo's platform tasks: module workers,
  classic blob-URL workers, `terminate()`, transferables and structured-cloned `Uint8Array`s behaved
  identically on Chromium, Firefox and WebKit, with no branching and no WebKit special case.
- **`capability.spec.ts:47` did not flake this time.** T20 flagged it; the full suite ran clean here
  (97 passed, 11 skipped, 0 failed), with `pool.spec.ts` adding 33 more WebKit-inclusive tests
  alongside it.

## What the next task should know

- Import `createWorkerPool`, and the `WorkerPool`, `JobHandle`, `JobOutcome`, `PoolStats`,
  `TerminationCause` types from `@/pipeline/pool`; `JobToken`, `JobResult`, `JobFailure` and
  `nextToken` from `@/pipeline/protocol`; `resolveWorkerPoolSize` and `runtimeLimits` from
  `@/config/limits`.
- Usage is `const { token, done } = pool.run(job); const outcome = await done`. Switch on
  `outcome.outcome` — `completed`, `failed`, `superseded`, `cancelled`, `terminated` — and never
  assume a promise rejection.
- **T22 (codec loading) owns `execute.ts`'s body along with T23–T29.** Replace `executeJob` with the
  §4.2 stage dispatch. The protocol and the pool stay unchanged, and the `unimplemented` `JobFailure`
  kind should be deleted once nothing returns it. **Two e2e assertions must change with it, and are
  expected to fail until you do** — they assert the current absence of stages, not a lasting
  property: `tests/e2e/pool.spec.ts` "the shipped pipeline worker speaks the protocol" expects
  `outcome === 'failed'` with `reason.kind === 'unimplemented'` (it becomes `completed`), and "the
  shipped worker checks the between-jobs flag" expects the *second* response to be an `error` (it
  becomes a `result`). The first response in that second test — the `skipped` one — is the real
  assertion and must keep passing. Every other test in the file is independent of what the worker
  does. Note also that the worker is one module per worker instance, so a lazily loaded codec is
  cached per worker, not per app — which is what §5.2's "a worker that needs a module it has not
  loaded loads it and then proceeds" already implies, and is why `terminateJob()` is expensive.
- **The transfer list in `worker.ts` is not exercised by any test**, because every test that reaches
  the shipped worker stops on the error path. The hazard for T23–T29: a stage that returns a
  `Uint8Array` which is a *view* onto the WASM heap — a `subarray()` of codec memory, the natural
  thing to write — will, when its `.buffer` is transferred, detach **the entire codec heap** rather
  than just the output. The first stage to land must either copy into a freshly-owned buffer before
  returning or drop the transfer list. Whichever you choose, add the test that proves it.
- **T36 (Preview) is R-X28's consumer.** Debounce at 300 ms (§5.3) and then just call `run()` again
  for the same `imageId` — the pool supersedes the previous job for you. Render only on a `completed`
  outcome; a `superseded` outcome means throw the request away, not retry.
- **`supersede()` keys on `imageId` alone and ignores `intent`.** Correct for T21, because a run
  encodes each image exactly once and only Preview produces two live jobs for one image — but it
  means a `preview` job submitted while a `run` job is in flight for the same image would silently
  supersede the run's job, and that image would drop out of the batch with **no failure recorded**
  anywhere. **T36 and T38 must never leave both modes concurrently live for one image.** If that ever
  becomes possible, supersession has to key on `intent` too, and this is the note that says why.
- **T38 (Processing view) is R-X26's consumer.** Call `cancel()` on the button, switch the label to
  **Stopping** immediately (R-X27), and keep the button visible until every outstanding `done`
  promise has settled — that is the honest definition of "until the run halts". `stats().active`
  tells you how many images the user is still waiting on. Call `resume()` before running again after
  **Back to images** (R-X17), rather than building a new pool, so the codecs stay loaded.
- **T46 owns every number in `config/limits.ts`** and the mobile heuristic in `pool.ts`. Changing
  `maximumWorkers`/`mobileWorkers`/`reservedCores` needs no change to `pool.ts`; `limits.spec.ts`
  proves that, and the e2e proves it again in a real browser. `jobTimeoutMs` is the one entry with no
  measured value: it is `null` by design and T46's sweep should expect evidence, not a guess.
- The pool holds `Job`s — which carry source bytes — in plain module-scope `Map`s and arrays, never
  in a store (§1.1). Keep it that way when wiring it to Pinia: the store holds ids and counts, the
  pool holds the bytes.
- `destroy()` is one-way; `cancel()`/`resume()` is the reusable pair. Both settle every outstanding
  job.

## Requirements covered

R-X8 (bounded concurrency, proven at pool width 3), R-X26 (between-jobs cancellation), R-X28
(discard on arrival by token), R-X29 (terminate and respawn, mechanism only — its threshold is
explicitly left unset). **R-X27** is not covered: it is the Cancel/Stopping label, which is T38's
view work; the pool provides what that label needs to be honest. Technical Design §5.1 and §5.3 are
implemented in full except for §5.3's debounce interval, which belongs to the Preview caller (R-P3)
rather than to the pool, and §5.2's lazy codec loading, which is T22.
