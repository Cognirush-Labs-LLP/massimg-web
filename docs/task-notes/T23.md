# T23 — Decode, orientation and colour

**Status:** complete

## Headline findings for later tasks

- **ImageMagick does not surface CICP at all, and `image.chromaticity` is a trap.** For a HEIC whose
  colour is signalled only by an `nclx` box, `getColorProfile()` is `null`, `profileNames` has no
  `icc`, no attribute carries the values, and `image.chromaticity` returns BT.709 primaries
  (0.64, 0.33) — **its own default, which it returns for every file including a Display P3 one**. So
  chromaticity cannot be used as colour evidence anywhere in this codebase. A13's open half is
  answered in the worse direction, and `pipeline/stages/colour.ts` now parses the `colr` box out of
  the source bytes instead.
- **D3 is measured and §7.7's animated-PNG contingency is not needed.** The profile survives every
  encoder path byte-identically except one. UPNG writes no `iCCP` (and does write `sRGB`), but an
  `iCCP` spliced into its output reads back identically — **apng-optimizer is what strips it.**
  Attaching the profile *after* the optimiser runs preserves it exactly. **T27 should assemble
  animated PNG as UPNG → apng-optimizer → attach `iCCP`, dropping the `sRGB` chunk**, and should not
  re-derive this. `sRGB` and `iCCP` are mutually exclusive in the PNG specification; leaving both
  produces a file libpng warns about ("iCCP: too many profiles") and whose colour two readers may
  disagree about. That exact mistake was made and caught inside this task's own harness.
- **`autoOrient()` is correct for all eight EXIF values, including all four mirrored ones**, on all
  three engines with no divergence. D4 `OPEN 60%` → `TESTED 95%`. No per-value transform table is
  needed and none was written.
- **`getColorProfile()` returns a live view onto the WASM heap**, not a copy: magick-wasm implements
  it as `HEAPU8.subarray(...)`. A frame holding that reference carries bytes that stop being the
  profile the moment the image is disposed or the heap is resized. `decode.ts` copies it. **Anything
  that reads a profile out of magick-wasm must copy it**, and its `.buffer` must never be
  transferred — it is the whole codec heap. `toByteArray()` is the exception: it is `HEAPU8.slice`,
  already owned.
- **`MagickFormat` is a const object whose keys and values differ** (`MagickFormat.WebP === "WEBP"`).
  Indexing it with the value gives `undefined`, and `image.write(undefined, cb)` **still produces
  bytes**, in the wrong format, with no error. Cost an hour here.
- **HEIF-family write defines live under the `heic:` namespace even for AVIF output.** Setting
  `avif:cicp` is silently ineffective: the encode succeeds and produces a file with no colour
  signalling at all — which looks exactly like a convincing CICP fixture until something reads it.
- **The `heic:` namespace trap bit twice, in two different ways.** `avif:cicp` is ignored (no
  `colr` box is written at all) and so is `avif:chroma` — `avif:chroma=444` produces a file
  byte-identical to passing no define, 506 bytes against 551 for `heic:chroma=444`. Both encode
  successfully. **Every HEIF-family define goes under `heic:`, whatever the output format.**
- **Assumption movements:** A13 `TESTED 95%` → `TESTED 95%` (unchanged figure, entry rewritten and
  split into a settled mechanism half and an unconfirmed frequency half), D3 `OPEN 55%` →
  `TESTED 90%`, D4 `OPEN 60%` → `TESTED 95%`.

## Decisions made

- **T23 does not wire decode into `executeJob`, and `pool.spec.ts` is untouched.** `executeJob` must
  return a `JobResult` carrying *encoded bytes*; a decode stage alone cannot produce one, and
  fabricating an encoder to make the seam look finished would be inventing T26's work. So
  `unimplemented` still stands, and T21's two flagged assertions — `pool.spec.ts`'s
  `outcome === 'failed'` with `reason.kind === 'unimplemented'`, and the second response being an
  `error` — remain correct and still pass. **Whoever lands the first stage that produces bytes
  changes them**, exactly as T21's note says.
- **The stage contract is that stages return owned buffers, and `worker.ts`'s transfer list stays as
  it is.** T21's review flagged that transferring a view onto the WASM heap would detach the entire
  codec heap. `decode.ts` asserts ownership rather than assuming it (`toByteArray` happens to copy
  today, but nothing else in the pipeline would notice if a binding update stopped), and
  `tests/e2e/decode.spec.ts` proves the property end to end: decode, transfer the frame's buffer
  away, then decode again in the same context and check the second result is correct. Dropping the
  transfer list was the alternative; it would have made every result pay a copy to defend against a
  bug that the invariant prevents at no cost.
- **T20's `fallbackDecoder` seam is in T23's scope, and its body now lives in the generation
  worker.** T22 handed it over on the grounds that the body is decode logic, which is right. A seam
  with no body means §10.4 is unimplemented, so shipping the function and leaving the wiring to T30
  would have left the same gap under a different name.
  **It runs in `thumbnail-worker.ts`, not in `thumbnails.ts`.** My first version awaited it on the
  main thread inside `settle()`, which regressed R-G12: `ImageMagick.read` is a synchronous WASM
  call with no abort, so `stop()` could discard the *result* but could not end the *work* — and
  §10.4, `thumbnail-worker.ts`'s own header and a comment in `thumbnails.ts` that I left standing
  ("Deliberately not a main-thread fallback") all say so. It is the case T23 is about that makes it
  bite: on Chromium and Firefox a HEIC batch routes every tile through this path. Moving it into the
  worker satisfies §10.4 literally, makes `stop()`'s existing `terminate()` end the decode, and keeps
  the lazy-import property — the worker imports `thumbnail-fallback.ts` only when a tile actually
  needs it. The service option survives as a way to *replace* the default or switch it off with
  `null`; a decoder passed that way still runs on the main thread, and its caller owns that.
- **The fallback decoder does not apply the stored edit.** `thumbnail-render.ts` owns the edit-op
  walk; reimplementing it here would put the same arithmetic in two places, which §6 warns against.
  A tile whose edit is not shown is still better than a placeholder, and this path is only reached
  when the engine could not decode the source at all.
- **An ICC profile wins over CICP when both are present.** R-I12 names the profile as the thing
  preserved and R-I35 is written for the case where there is no profile. Proven on a real file: the
  AVIF in the local test set associates *both* a `prof` and an `nclx` `colr` box with its primary
  item, and `resolveFrameColour` returns `icc` for it.
- **CICP "unspecified" (2/2/2) is carried verbatim, not collapsed to `untagged`.** A box that says
  nothing is still a box that is present, and collapsing the two is the class of mistake R-I35
  exists to prevent. `isUnspecifiedCicp` is exported so T26 can decide, at encode time, that they
  amount to the same thing — which is a decision about output, not about what the source said.
- **`Frame` carries `sourceOrientation` and has no orientation *tag* field.** The first is an
  internal record of which of the three states the source was in, read by no stage, so that absent /
  present-and-default / present-and-unusual is observable rather than implicit. The second is the
  point: R-I10 holds structurally because there is nowhere to put a tag, not because every later
  stage remembers not to write one.
- **`Frame` deliberately has no `hasAlpha`.** An alpha *channel* is not evidence of transparency
  (D5; the real HEIC in the set reports `hasAlpha: true` and is an ordinary photograph), and R-C13
  requires a pixel-level test. A boolean here would be read as an answer to a question it does not
  answer.
- **The fixtures' EXIF, orientation transforms and ICC profile are all hand-built, not
  ImageMagick's.** ImageMagick is the thing under test; if it generated the fixtures too, a shared
  bug would cancel itself out. It is used only to compress pixels into a container. The ICC profile
  being ours also means no third-party licence attaches to a committed fixture.
- **Fixture bytes are committed, unlike `thumbnails.spec.ts`'s generate-in-the-page convention.** An
  EXIF tag and a `colr` box cannot be produced by a canvas, and for a correctness-critical set a
  reviewer inspecting the exact bytes is worth more than a self-contained page. The generator is
  committed too, and regeneration is byte-identical.
- **`decode.ts` has no unit test, by the same constraint T22 documented.** It imports
  `codecs/loader.ts`, whose dynamic `import()` specifiers Vitest resolves statically, and
  `imagequant`'s bare `.wasm` import fails under Vitest's Node transform. The pure logic therefore
  lives in `frame.ts` and `colour.ts`, which do have unit tests, and `decode.ts` is proven in the
  browser.

## Surprises

- **`getColorProfile()` hands back a live window onto the WASM heap.** magick-wasm implements
  profile access as `HEAPU8.subarray(datum, datum + length)`. The frame outlives the callback, so
  the profile it carried was not the profile that was embedded. Caught by the e2e assertion that
  compares the decoded profile against the fixture's own bytes — which existed only because "carried
  verbatim" seemed worth checking literally rather than by length. A test that had checked
  `profile !== null`, or even `profile.length`, would have passed.
- **The predicted D3 weak point was in the wrong component.** §7.7 named UPNG. UPNG is innocent: it
  simply has no profile to preserve, and one can be attached to its output. apng-optimizer is what
  strips a valid `iCCP`. The difference matters because it turns a forced colour conversion into an
  ordering choice.
- **gifsicle preserves the ICC profile.** It was expected to strip it, which would have made R-I13's
  "convert to sRGB for GIF" a forced move. It is a deliberate choice instead — GIF's ICC application
  extension is not honoured by most viewers, so converting is still right, but it is a choice.
- **`avif:cicp` is silently ineffective; the namespace is `heic:` even for AVIF output.** One coder
  serves the whole HEIF family. The first generated "CICP fixture" had no `colr` box at all and the
  encode reported success — a fixture that looks right and proves nothing.
- **The same trap caught me a second time one line away, and I had already documented it.**
  `avif:chroma=444` is also ignored: it produces a file byte-identical to passing no define at all
  (506 bytes; `heic:chroma=444` gives 551). So the three AVIF fixtures were at default subsampling
  while a comment above them reasoned about the 4:4:4 safety margin they did not have. Found in
  review, not by me. Documenting a trap is not the same as having internalised it.
- **Two `DataView` reads in `colour.ts` were unbounded while every other read in the module was
  careful.** `readBoxes` validates that a box *fits* its parent, which is not the same as it being
  long enough for the fields its type implies — a `pitm` or `ipma` of size 8, last in the buffer,
  reached the version/flags read with nothing there and threw `RangeError`. The consequence was
  worse than the crash: `worker.ts` maps any `RangeError` to `{ kind: 'out-of-memory' }`, so a
  malformed HEIF would have been reported to the user as the machine running out of memory. My own
  malformed-input tests could not catch it — truncation and corruption both produce boxes that fail
  the fits-in-parent check first. It takes a box that fits and is degenerate, which only a
  hand-built tree produces.
- **My own non-blocking test measured nothing, in a way that looked like a pass.** It sampled the
  event loop with `setInterval` and took the maximum gap seen *inside the callback* — but a stall
  long enough to swallow every remaining tick means the callback never fires at all, so the maximum
  stays at its initial 0. A 610 ms main-thread block reported a 10 ms longest gap. Sampling the
  final gap after `clearInterval` fixed it, and the test then separates the two designs cleanly:
  **1217 ms** stall with the fallback on the main thread against **12 ms** in the worker.
- **`heic:cicp` alone is not enough either**; without `heic:preserve-cicp` the box is dropped.
- **`MagickFormat`'s keys are not its values** (`WebP` → `"WEBP"`), and `write(undefined, cb)`
  produces bytes rather than throwing. The thumbnail fallback returned a blob of the wrong format
  and only failed later, at `createImageBitmap`.
- **WebKit refuses a dynamic module import issued from `addInitScript` scope** — "Importing a module
  script failed" — because that scope's base URL is not the page's. Chromium and Firefox resolve it
  either way. The first version of `decode.spec.ts` installed its helper that way and passed 26/26 on
  Chromium while failing 20 on WebKit. The fix is to keep imports inside `page.evaluate`, which is
  what `thumbnails.spec.ts` and `codecs.spec.ts` already do; this is a WebKit-only constraint the
  other two engines will never reveal.
- **My own justification for reading `ipma` was factually wrong, and the harness caught it.** The
  comment claimed the local AVIF's `nclx` belonged to its alpha auxiliary item. Dumping the real
  `ipma` showed the primary item is associated with *both* `colr` boxes and the auxiliary item with
  none. The design (resolve through `ipma` rather than taking the first `nclx`) is still right — the
  format guarantees nothing about the arrangement — but the comment now says what was measured. The
  file turned out to be the both-signals-present precedence fixture I had recorded as impossible to
  obtain.
- AOM reads quality 100 as lossless, and lossless conflicts with this build's default chroma-delta-q
  setting; AVIF fixtures are written at 95.
- No file in the 642-image local set has an EXIF orientation above 1.

## What the next task should know

- Import `decodeFrame` from `@/pipeline/stages/decode`; `Frame`, `FrameColour`, `Cicp`,
  `SourceOrientation`, `isUnspecifiedCicp`, `ownsWholeBuffer` from `@/pipeline/stages/frame`;
  `readCicp`, `resolveFrameColour` from `@/pipeline/stages/colour`.
- **`decodeFrame(source: Uint8Array): Promise<Frame>`.** The frame is upright, RGBA8, and owns its
  buffer. It carries no orientation tag and cannot be made to.
- **T24 (edit stages): the frame you receive is already EXIF-corrected**, so R-I11's "user rotation
  composes on top of the EXIF-corrected image" is satisfied by doing nothing special — apply the ops
  to the frame as given.
- **T26 (encoding) owns the three colour cases.** `icc` → write the profile verbatim where the
  format can carry one (R-I12), convert to sRGB using it for GIF (R-I13). `cicp` → write the values
  back where the format can express them (`heic:cicp` **plus** `heic:preserve-cicp`, under the
  `heic:` namespace even for AVIF), or resolve them into the pixels where it cannot (R-I35).
  `untagged` → treat as sRGB and add no profile (R-I14). Never convert pixels otherwise (R-I15).
  `isUnspecifiedCicp` tells you when a present `cicp` carries no information.
- **`heic:cicp` carries only three values — there is no way to express `full_range_flag` through
  it.** `Cicp.fullRange` is read from the source and carried on the frame, but a re-encode through
  that define cannot write it, and the encoder picks its own. The round-trip test passes because the
  fixture happens to be limited-range; a full-range source would lose the flag silently. If that
  matters for a format T26 supports, the flag has to be set some other way, or the loss recorded as
  a caveat.
- **T26 must also change `pool.spec.ts`'s two `unimplemented` assertions** and delete the
  `unimplemented` `JobFailure` kind once nothing returns it. T23 did not, because T23 produces no
  bytes. `worker.ts`'s transfer list is safe as long as stages keep returning owned buffers.
- **T27 (animated PNG): attach the `iCCP` chunk after apng-optimizer, and drop `sRGB`.** Measured,
  all three engines. See D3. **Scope: the measurement used `UPNG.encode([oneFrame], …)`** — a
  single-frame PNG with no `acTL`, so not literally an APNG. Nothing about chunk handling should
  depend on frame count and the conclusion very likely generalises, but it was not measured on a
  multi-frame file, and this hand-off asks T27 to take the ordering as given.
- **`decodeFrame` handles one still frame.** §4.2's `decode-frames` for animated sources is a
  separate stage and is not built here.
- **`readCicp` returns null when `pitm` is absent**, so a single-item HEIF that omits the primary
  item box degrades silently to `untagged` rather than guessing. That is the conservative direction —
  reporting *some* item's colour as the image's is the failure R-I35 is about — but it is a real
  case the parser gives up on rather than handles.
- **The thumbnail fallback calls `image.strip()`**, so a Display P3 source renders slightly
  oversaturated in the grid. Consistent with the native `createImageBitmap` path, which also drops
  the profile through a canvas, and a tile is not a colour-managed surface — but it is a deliberate
  difference from the pipeline, which preserves the profile.
- **R-I34 (auxiliary images dropped) has no owner yet.** §10.3 says only the primary image is
  processed and the report must record it. Decode reads the primary item and produces no caveat; the
  `auxiliary-images-dropped` caveat in `domain/types.ts` is still unproduced. T23 does not name
  R-I34, so it was not implemented — but decode is where the detection would go, and nothing detects
  it today.
- **R-I16 (Preview renders the encoded output directly) is T36's**, not covered here.
- Re-run the measurements with `pnpm install && pnpm test` from `verification/t23-decode/`
  (`T23_QUICK=1` for Chromium only). D3 needs no `.env`; A13's real-HEIC half reads
  `PHOTO_FIXTURES_DIR` and reports `skipped` with a reason if it is unset. Regenerate fixtures with
  `node scripts/build-test-fixtures.mjs` from the repository root.

## What could not be proven

Stated plainly, because green tests otherwise imply coverage that does not exist:

- **No CICP-only HEIC is committed, and none occurs naturally in the local set.** The build has no
  HEVC encoder (A11), so one cannot be generated; AGENTS.md forbids committing a file from the
  fixtures directory; and a third-party sample would bring a licence obligation. The cross-engine
  committed proof therefore uses a generated **AVIF** — the identical `colr`/`nclx` box in the same
  ISO/IEC 23008-12 container, exercising the identical code path, since `readCicp` never inspects
  the brand and `decode.ts` has no format switch. The real-HEIC proof lives in
  `verification/t23-decode/`, which constructs one in memory from a real file by overwriting its
  `colr` box in place at the same size, and shows identical decoded pixels, no ICC profile, and the
  CICP read back correctly. That is a real HEIC container with a real HEVC bitstream, but it is one
  this task made, not one a camera wrote.
- **That HEIC evidence is a recorded measurement, not a regression guard.** It runs only from
  `verification/t23-decode/`, only when `PHOTO_FIXTURES_DIR` is set, and never in CI. If HEIC
  handling broke tomorrow, nothing committed would fail. The committed AVIF tests are what guard the
  code path day to day.
- **A13's *frequency* clause is not confirmed by anything measured here.** The local set holds
  **three distinct** HEIF-family images (five paths — the directory contains duplicates), and none
  of them signals colour by CICP instead of a profile: one HEIC with a `colr prof`, one `msf1`
  sequence with no `colr` at all, and one AVIF carrying both a `prof` and an `nclx` of 2/2/2. The
  only CICP-only file in evidence is the one this task manufactured. What is settled is the
  *mechanism* — that ImageMagick reports no CICP and that `chromaticity` returns its own BT.709
  default for every file — which is why A13 stays at 95 rather than moving to 100. See its entry.
- **No real camera file with an EXIF orientation above 1 exists locally** (642 images checked), so
  values 2–8 are evidenced only by generated fixtures.
- **A HEIC carrying both `irot`/`imir` and an EXIF orientation tag is untested.** libheif applies the
  transformative properties itself, so such a file could double-rotate. No fixture was obtainable.
  Recorded against D4.
- **D3 used one profile**, 6,668 bytes. A much larger profile could meet a size limit in one of these
  writers that this one does not.
- **R-I13 and R-I16 are not exercised.** Both are encode/Preview behaviour. What D3 measures is that
  the GIF path does not silently *drop* the profile, not that the conversion R-I13 asks for happens.
- **The thumbnail fallback's engine coverage is uneven by nature.** The decoder itself is tested
  directly on all three engines. The service-level test asserts the tile is produced on every engine
  and records which path got there, because WebKit decodes TIFF natively through ImageIO while
  Chromium and Firefox do not — so only two of the three engines actually exercise the fallback
  through the service.

## Requirements covered

**R-I9** (orientation applied to pixels at decode, before anything else), **R-I10** (no orientation
tag on the output — structurally, since `Frame` has no field for one), **R-I12** and **R-I14** and
**R-I15** (profile carried verbatim, absence treated as sRGB with nothing added, no colour
conversion), **R-I35** (CICP read, honoured and carried; never mistaken for untagged sRGB).
Technical Design §7.7 is implemented, and §10.3's "HEIC is ordinary input, no capability probe, no
browser branch" holds — `decode.ts` contains no format switch of any kind.

**R-I11** is satisfied by construction but is T24's to confirm, since no edit stage exists to compose
on top yet. **R-I13** (GIF conversion to sRGB) and **R-I16** (Preview renders the encoded output
directly) are encode- and view-side and are not covered here.
