# T37 — Edit mode

**Status:** complete

## What was built

A real Edit mode: rotation buttons, a zoom slider, a ratio row, a draggable/resizable crop
rectangle with keyboard support, a background row (swatches + native colour picker) shown only on
spill, and Apply/Cancel/Remove edit — replacing T31's placeholder. All of the arithmetic was
already built in T13 (`src/domain/edit.ts`); this task is the UI layer on top of it, plus one new
store to hold the draft editing session.

## Files touched

- `src/stores/edit-draft.ts` (new) — `useEditDraftStore`, the Edit session's draft state
  (rotation, rect, ratio, zoom, background, measured frame/source) and its `apply`/`cancel`/
  `remove` actions. See Decisions made for why this is a store at all.
- `src/ui/edit/Edit.vue` — rewritten from T31's placeholder. Orchestrator: resolves the current
  image, seeds the draft store once a real host size is known, binds the keyboard handler, resets
  the draft store on unmount.
- `src/ui/edit/EditFrame.vue` (new) — the image, the darkened exterior, the checkerboard/fill
  layer, the crop rectangle and its four corner handles, the live `W×H` badge. Owns pointer drag/
  resize and arrow-key nudging, reports drag/resize start and end to the draft store
  (`setDragging`) so the background row never mounts mid-gesture, and snaps the rect's moving
  edge(s) flush with the image edge via `domain/edit.ts`'s `snapMoveToImage`/`snapResizeToImage`
  before every candidate rect reaches the store — see Surprises for both.
- `src/ui/edit/EditRatioRow.vue` (new) — the five ratio chips.
- `src/ui/edit/EditBackgroundRow.vue` (new) — swatches + native colour picker, gated by
  `hasSpill`/effective-format alpha capability.
- `src/ui/edit/EditToolbar.vue` (new) — Rotate left/right, the zoom slider, output W/H fields,
  Remove edit, Cancel, Apply. Registered into `ToolPage.vue`'s `STAGE_TOOLBARS.edit`, mounted
  independently of `Edit.vue` like every other stage's toolbar.
- `src/ui/edit/useEditKeyboard.ts` (new) — the window-level Escape/Enter handler.
- `src/domain/edit.ts` — added `snapMoveToImage`, `snapResizeToImage`, `EDGE_SNAP_THRESHOLD_PX`,
  `ResizeAnchor`. Pure, unit-tested in `edit.spec.ts` alongside T13's own fixtures; nothing
  existing in the file changed.
- `src/domain/format.ts` — added `isAlphaCapable(inputFormat, isAnimated, setting)`, composing the
  existing `resolveFormat`/`supportsAlpha` so there is exactly one place that resolves "does this
  image's effective output format support alpha." Used by the draft store's default fill and by
  `EditBackgroundRow.vue`'s live gating. No existing export changed.
- `src/stores/ui.ts` — added `editRatioPreference` + `setEditRatioPreference`. See Decisions made.
- `src/stores/batch.ts` — `updateImage` now sanitises an incoming `edit` patch (`sanitizedEdit`/
  `sanitizedOp`) before storing it. Not Edit-mode-specific — see Surprises; this is a general fix
  that also covers T36-A's pre-existing `Preview.vue#useDimensionSuggestion` write path.
- `src/app/ToolPage.vue` — one new import and one new `STAGE_TOOLBARS` entry.
- `src/i18n/en/messages.json`, `context.json` — every `edit.*` string.
- Unit tests: `src/stores/edit-draft.spec.ts`, `src/ui/edit/EditFrame.spec.ts`,

## Decisions made

- **A new Pinia store purely for sibling-component plumbing.** `EditToolbar.vue` is mounted by
  `ToolPage.vue` independently of `Edit.vue` (`STAGE_TOOLBARS` vs. `STAGE_COMPONENTS`, the same
  arrangement `PreviewToolbar.vue`/`GalleryToolbar.vue` already use) — a sibling, not a child, so
  neither props/emits nor provide/inject can bridge the toolbar's Rotate/W-H/Apply/Cancel/Remove
  controls to the frame's draft state. `useEditDraftStore` is a store in the "reachable from any
  component" sense only, not in the "survives a mode switch" sense `docs/ui-design.md` §4
  otherwise means by one — `Edit.vue` calls `reset()` in `onBeforeUnmount`, so nothing in it
  outlives one Edit session. Rejected alternative: folding Rotate/W-H/Apply/Cancel/Remove into
  `Edit.vue`'s own template instead of a separate toolbar component — `docs/ui-design.md` §12
  explicitly places the W/H fields "in the toolbar," and departing from the established
  per-mode-toolbar-component pattern (T33–T36 all use it) seemed a larger inconsistency than one
  small new store.
- **Ratio persists across images for the session** (`useUiStore().editRatioPreference`), seeded
  into the draft on every `initFor` and never read from the stored edit. `EditOp['crop']` has no
  ratio field at all — ratio is pure interface state — so R-C11 ("a locked ratio is re-fitted to
  the next image's own dimensions when stepping... and re-entering Edit") only describes real
  behaviour if ratio *can* carry over between images; read literally with nothing persisting it,
  R-C11 would be vacuous. No design document names the storage mechanism, so this is a Decision,
  not a spec fact.
- **No canvas for the frame.** The image is a plain `<img>` on an object URL of the source `File`
  (the same convention `PreviewFrame.vue`'s Original tab uses), and Edit mode performs no encode
  of its own — it only edits `EditRecord`; Preview's existing `editVersion`-watching encode handles
  re-rendering on return. Rotation is simulated with CSS `transform: rotate()` on a box sized at
  the image's *unrotated* dimensions, centred at the same point `imageRectInFrame` always centres
  at regardless of rotation — a quarter turn swaps a box's visual footprint exactly the way
  `rotateSize` swaps width/height, so this reproduces `geometry.imageRect` without a second pixel
  buffer. The crop UI (checkerboard/fill, darken bands, rectangle, handles) is plain layered,
  absolutely-positioned `:style` bindings reading frame-pixel coordinates — the same
  physical-`left`/`top` convention `PreviewFrame.vue` already uses and documents, not CSS written
  in a `<style>` block (which stays logical-properties-only throughout, unaffected).
- **`setFrame` re-anchors the rect by the same normalised fraction, rather than leaving stale
  frame-pixel coordinates when the frame size changes after `initFor`.** See Surprises — this
  started as a bug fix, not a plan.
- Zoom slider range (0.25–4, step 0.05), arrow-key nudge steps (2px plain, 20px with Shift), and
  the darken-overlay opacity (0.55) are undocumented feel-tuned placeholders — no design document
  gives numbers for any of them, the same spirit as Preview's own undocumented
  `MAX_VIEWPORT_SCALE`/wheel-sensitivity constants.
- Cancel's correctness is structural, not implemented restore logic: no store write happens
  anywhere during an Edit session except on Apply/Remove, so "restores every value including
  rotation" (R-C10) falls out of simply never having touched the stored `ImageRecord.edit` in the
  first place. Documented explicitly in `edit-draft.ts` so a future change toward a live-apply- or
  live-preview-while-editing design doesn't reintroduce the exact mistake the spec calls out.

## Surprises

- **`setFrame` originally just overwrote `frame.value`.** This silently corrupted the crop the
  moment the measured host size changed *after* `initFor` had already run on it — which happens on
  every single re-open of an already-edited image: the first entry has no "Remove edit" button, a
  second entry does, and that one extra toolbar button is enough to reflow the toolbar row and
  shrink the available stage-body height by several tens of pixels between the two sessions. The
  stored frame-pixel rect then got silently reinterpreted against the new, different frame — a
  300px-wide crop reopened as 328px wide in testing. Confirmed via live instrumentation in a real
  Playwright session, not a theoretical worry: `tests/e2e/edit-ui.spec.ts`'s "Apply ... re-opening
  Edit restores every value" test caught it immediately. Fixed by having `setFrame` recompute the
  rect from the *previous* resolved geometry's `normalisedRect` reprojected into the new frame,
  which also means a genuine browser-window resize mid-Edit-session now preserves the crop
  correctly, not just the reopen case that surfaced it. One more guard was needed on top: a
  transient zero-size measurement (real in a jsdom test environment before a stubbed
  `clientWidth`/`clientHeight` is set; theoretically possible in a real browser too, e.g. a
  display:none tick) must not be allowed to reproject the rect into a degenerate state that the
  *next*, valid measurement can no longer recover from — `setFrame` now skips reprojection
  entirely when the incoming size isn't positive, only recording it.
- A focused `<button>` (e.g. right after clicking Rotate) initially blocked Escape as well as
  Enter in the keyboard handler — the `<button>` exclusion is only needed for Enter's
  double-activation risk, not Escape, which has no such risk. Caught the same way, by the e2e
  spec's Escape/Enter test actually running against the real app rather than by inline review.
- **A real `DataCloneError` that none of the automated tests caught — found by the user manually
  testing the feature (zoom past 100%, a ratio-locked rectangle dropped past the image edge,
  Apply) and left Preview stuck on "Creating preview..." forever.** Root cause: a Pinia
  `ref<Rgba>`'s `.value` getter returns a reactive Proxy wrapping the object (Vue's `ref()`
  reactifies object values on read), and `apply()` embedded that Proxy straight into the stored
  crop op's `background` field. The next time Preview built a `Job` from that image and
  `postMessage`'d it to the pipeline worker, the Proxy failed structured clone — silently, as an
  unhandled promise rejection in the console, not a thrown error the UI surfaces, which is exactly
  why "stuck on Creating preview" was the only user-visible symptom. Worse: tracing it further
  showed this is not a T37-only bug. T36-A's `Preview.vue#useDimensionSuggestion` reads
  `current.edit` through the same reactive array and passes it into `withTrailingResize`, whose
  `[...ops, newOp]` spread carries forward whatever reactive wrapping was already on each existing
  op — so the identical failure was always reachable from the recovery-action path too, just never
  triggered before, because nothing before T37 could produce a stored crop op with a non-default
  background to poison in the first place. Fixed once, at the actual boundary, rather than at each
  call site that happens to build an edit: `src/stores/batch.ts`'s `updateImage` — the one place
  every `edit` write passes through — now runs a `sanitizedEdit`/`sanitizedOp` pass (`toRaw` on the
  record and on each crop op's `rect`/`background`, since `toRaw` only strips the proxy on the
  value given to it, not on values nested inside) before `Object.assign`. This protects every
  current and future caller, not just `useEditDraftStore#apply`.
  **This should have been caught by the e2e suite, and wasn't**: `tests/e2e/edit-ui.spec.ts`'s
  tests only asserted `preview-root` became visible after Apply, never that the encode actually
  *finished* or that the console stayed clean — unlike `tests/e2e/preview.spec.ts`'s own
  `watchForErrors` convention, which every test in that file uses. The two tests that exercise
  spill + a background colour were extended to wait for `preview-creating` to disappear and
  `preview-image` to actually appear, and to assert zero console errors, matching that existing
  convention — a gap worth watching for in whichever task next adds a new `postMessage`-reachable
  write path.
- **The two complaints the user reported next — "dragging to a corner at 100% zoom shows the
  background panel even for an all-JPEG workflow" and "the panel flickers while I drag" — turned
  out to be the same bug.** `Edit.vue`'s stage is a flex column, and `EditBackgroundRow.vue` has
  real layout height; mounting it the instant `showsBackgroundRow` went reactively true (which it
  did, momentarily, for plenty of in-bounds drag positions, not just the final one) shrank
  `.edit-frame-host`'s measured height *while a drag was still in progress*, firing `setFrame`
  mid-gesture and reprojecting the rect against a frame size the gesture's own delta math wasn't
  using. The resulting distortion is what made corner-dragging look like a boundary-condition bug
  in the spill arithmetic; the arithmetic was fine throughout (confirmed by instrumenting the live
  store: `frame` demonstrably changed mid-drag before the fix, and stayed fixed after it). Fixed
  per the user's own suggested shape — the row now only ever changes after a gesture ends
  (`EditFrame.vue` calls `useEditDraftStore().setDragging(true/false)` around each pointer
  drag/resize) and only after a further 1000ms settle (`visibleBackgroundRow`, debounced off
  `showsBackgroundRow`/`dragging`); `initFor` seeds `visibleBackgroundRow` synchronously on entry
  so a reopened already-spilling edit doesn't wait a second to show it. `Edit.vue`'s template
  mounts on `visibleBackgroundRow`, never `showsBackgroundRow` directly — anything that adds a
  further way to move the rect (a future gesture, a different control) must do the same.
  Fixing the flicker did **not** fully resolve the first complaint on its own, though — see the
  next entry.
- **The flicker fix exposed the real complaint underneath it: a plain in-bounds drag routinely
  landed a few pixels past the image's own edge, into the frame's letterbox margin, triggering
  spill the user had every reason to think was a boundary-condition bug** (JPEG source, JPEG
  output, 100% zoom — nothing about that combination should ever need a fill colour). It wasn't
  arithmetically wrong: `constrainCropRect` has clamped to `frame`, not to `imageRect`, since T13
  (R-C9/R-C12's own words — the rectangle may legitimately range past the image into blank frame
  space, which is exactly what makes deliberate zoom-out spill possible at all). But nothing told
  the user where the image's real edge was relative to the frame's, so a drag aimed at "the
  corner" overshot by whatever the letterbox margin happened to be, every time. Fixed on the
  user's own suggestion — "let's snap at the border when moving the crop rectangle" — with a
  magnetic edge snap: `domain/edit.ts`'s new `snapMoveToImage`/`snapResizeToImage` (threshold
  `EDGE_SNAP_THRESHOLD_PX`, 8 frame px, undocumented by any design doc) pull the rect's moving
  edge(s) flush with the image's corresponding edge once a drag or resize gets within range,
  applied in `EditFrame.vue` to both the pointer-drag and the arrow-key-nudge paths before the
  candidate ever reaches the store. A deliberate drag well past the threshold still reaches spill
  exactly as before — only the accidental few-pixel overshoot is gone. Two existing component
  tests (`EditFrame.spec.ts`'s arrow-key tests) had to move their starting rect away from the
  image's edges first, since the stock zoom-1 identity rect sits exactly flush with every edge and
  a small nudge off it was immediately snapping straight back — correct new behaviour, but it
  changed what those tests needed to set up to isolate the thing they were actually testing.

## What the next task should know

- `domain/viewport.ts` and `job.ts` are unchanged. `domain/format.ts` gained one small additive
  export (`isAlphaCapable`); `domain/edit.ts` gained two more (`snapMoveToImage`/
  `snapResizeToImage`, plus the `EDGE_SNAP_THRESHOLD_PX` constant and `ResizeAnchor` type) — all
  additive, nothing existing moved, changed shape, or changed behaviour.
- The T35 gap ("no real Playwright check that R-D2/R-D3's notes and the Dimension accordion's
  disabled state actually engage from a genuine crop") is closed: `tests/e2e/edit-ui.spec.ts`'s
  last test applies a real crop and asserts `dimension-note-single`/the disabled accordion rows.
- The T36 gap (`domain/viewport.ts`'s crop-aware projection unit-tested on constructed fixtures
  only) is **not** closed here — a real cross-tab (Original/Compressed) zoom/pan regression
  through a genuine crop would need Preview's real encode pipeline warmed up inside the same test,
  which this task's e2e file deliberately avoids needing (Edit mode itself never encodes). Left
  for whichever later task next touches Preview's inspector; `viewportEditGeometry`'s own
  "rotate-after-crop"/"multiple-crops" refusal paths remain unreachable, since `editOpsFor` only
  ever produces rotation-then-at-most-one-crop, confirmed unchanged by this task.
- `useEditDraftStore`'s `apply()` decides "did the crop geometry change" (and therefore whether to
  keep or drop a trailing recovery resize) by comparing the newly built ops against an entry-time
  snapshot with a small epsilon on the crop rect's fractional coordinates — not exact equality.
  This is necessary because the same on-screen crop can round-trip through frame pixels with tiny
  floating-point noise even when the user changed nothing. If a future change needs byte-exact
  reproducibility here, revisit `sameOp`/`CROP_RECT_EPSILON` in `src/stores/edit-draft.ts`.
